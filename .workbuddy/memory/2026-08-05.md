## 账户切换后 "Cookie 异常" 根因排查与修复（xianyu-hunter-dev）

### 排查结论
用户报告：账户切换后导航栏显示 "Cookie 异常"（身份/会话/追踪层 "缺失"）。

1. **切换函数（api_accounts.py:switch_account）的 cookie 逻辑本身无问题**：C-08 修复（失效旧/新用户 CookieStore 缓存 + cookie_rotator.invalidate_all）正确，不会污染新用户 JSON。
2. **真正根因 = Secure cookie 在纯 HTTP（IP 访问 http://127.0.0.1:8001）下被浏览器丢弃**：
   - `xh_token` 是 `HttpOnly` + `Secure` cookie，只在 `make_auth_response` / `app.py:/api/auth/verify` 写入。
   - 浏览器对纯 HTTP 直接丢弃 Secure cookie → 整页刷新后既无 cookie 也无 Bearer → `_resolve_current_user_id` 返回 None → 导航栏读 `cookies_default.json` → 误报 "Cookie 异常"。
   - 这与此前 "IP 登录 Cookie 异常"（bug #2）**同源**：HTTPS（域名）下 Secure cookie 保留，故无问题（用户原话已印证）。
3. **此前 bug #2 的 "Bearer 回退" 修复是无效的死代码**：前端**从未** `setItem('xh_token')`（xh_token 是 HttpOnly，JS 读不到），所以 `localStorage` 永远为空，`client.ts` 的 Bearer 头从不发送，navbar 的 Bearer 回退永不触发。
4. **AccountSwitcher.tsx 的 `storage.remove('xh_token')` 是误导性死代码**：基于"Bearer 携带旧 token 被缓存命中"的假命题；localStorage 本就无该值，删除为 no-op。已修正注释。

### 修复方案（已落地 + 测试通过）
- `auth_helpers.py`：
  - 新增 `_resolve_secure_policy(request)`：HTTPS→`secure=True,samesite="none"`；HTTP→`secure=False,samesite="lax"`（SameSite=None 强制要求 Secure，HTTP 下必须用 lax 否则浏览器拒收）。
  - `make_auth_response` 增加 `request` 参数，按协议决定 Secure/SameSite；无 request 时回退 ContextVar/默认 https（向后兼容）。
  - 新增原始 ASGI 中间件 `RequestSchemeMiddleware`：最外层写入 `scope["scheme"]` 到 ContextVar，端点内（含 BaseHTTPMiddleware 子任务）可靠读取。**已用最小复现验证 http→'http'/https→'https' 透传**。
- `app.py`：`create_app` 末尾注册 `RequestSchemeMiddleware`（最外层）；`/api/auth/verify` 改为按协议设 cookie（加 `request: Request`）。
- `api_accounts.py:switch_account`、`auth_query.py:auth_me`：显式传 `request` 给 `make_auth_response`（确定性 + 可测）。
- `AccountSwitcher.tsx`：修正 `storage.remove('xh_token')` 注释，说明其为 no-op 及真正修复在后端。

### 测试
- 重写 `tests/test_cookie_samesite.py`：覆盖 HTTPS(none+secure) / HTTP(lax+非secure) / X-Forwarded-Proto / 无 request 默认 / make_auth_response 单元。
- 运行：test_cookie_samesite(8)、test_auth_middleware_mu2 + navbar + login_cookie_injection + cookie_sync_scheduler + cookie_store_multi_user(39)、test_unified_login_mu2(13) 全部通过。
- 无其他测试断言 auth cookie 的 secure/samesite（仅 cookie 存在性），无回归。

### 备注
- 这是 xianyu-hunter-dev 系列 bug 的收口：IP 登录(bug2) 与 账户切换(bug3) 的 "Cookie 异常" 现同源同解。
- 后续若要做前端 token 持久化（让 Bearer 路径真正可用），需后端在响应体返回 token 并由前端存入 localStorage —— 当前非必须（cookie 协议自适应已解决）。

## 域名/隧道访问「账户切换跳隧道根 + 404 page not found」排查

### 用户报告
域名（Tailscale funnel / HTTPS）方式访问系统，点击账户切换，页面跳到 `https://desktop-g10o4nl.tailbca47.ts.net/`（隧道裸根）并显示 `404 page not found`。

### 根因结论（已闭合）
**不是源码重定向写错，而是运行实例加载了修复前的旧前端。**
1. 隧道 `path_prefix` 默认 `/xianyu/`（`yaml_config.py:264`），Tailscale funnel 用 `--set-path /xianyu`（`tunnel_providers.py:899`）只转发 `/xianyu/*`，剥离前缀给后端。访问入口固定为 `https://…ts.net/xianyu/`。
2. 落到隧道**裸根 `/`**（不在 `/xianyu` 作用域）→ Tailscale 用自己的默认路由返回 **Go 风格 "404 page not found"**（非后端、非前端白屏）—— 这就是用户看到的 404。
3. 当前源码/产物重定向都是 `/xianyu/`：
   - `AccountSwitcher.tsx:278` = `location.replace(import.meta.env.BASE_URL)` = `/xianyu/`。
   - 已实测部署产物 `static/spa/assets/index-BcT6Xn6a.js`（当前 `index.html` 引用）含 `globalThis.location.replace("/xianyu/")`。
   - `App.tsx:130` 兜底 `<Navigate to="/">` 在 `basename="/xianyu"` 下解析为 `/xianyu/`，**不会**越出作用域。
4. 故跳到裸根 + 404 必是**旧前端**（`location.replace('/')`，即此前 IP 白板 bug 的同一行旧逻辑）在生效 → 运行实例缓存/部署的是修复前构建。
5. ⚠️ **更正（2026-08-05 后续核验）**：先前"残留 46 个历史 `index-*.js`"的判断**有误**。经用 `sw.js` workbox 预缓存清单（117 条 url）作为权威白名单逐一比对：那些 `index-*.js` 全是**当前构建的按需懒加载路由 chunk**（Vite 按路由 code-split），**每一条都在 `sw.js` precache 中**，并非陈旧残留。仓库 `static/spa` 目录与 `sw.js`+`index.html` **完全一致**（total 120 文件，KEEP 119，0 个待删），属干净状态。
   - 真正仍成立的结论：跳裸根 + 404 源于**运行实例加载了修复前的旧前端**（PWA SW 缓存旧 `index.html`+JS，或部署目录 `static/spa` 是旧副本），而非本仓库产物问题。

### 处置（用户侧，非源码改动）
- 源码与仓库 `static/spa` 已正确，**无需改代码、也无需清理陈旧产物**（实测仓库目录干净，0 个待删）。

- 本沙箱 `frontend/node_modules` 缺失，无法可靠 `npm install` 重建；仓库产物已正确，重建仅换 hash，非必须。

## 「LLM 用量指标」页面排查后续三修（Request E 收尾）

在 2026-08-10 定位的路径 bug（ai_usage.py 硬编码 data/ai_usage.json）之上，本回合完成用户确认的三项修复：

1. **时区修正**（`src/xianyu_hunter/infra/ai_usage.py`）
   - 原 `_today_key()` 用 UTC，中国 UTC+8 跨日界会把「今日」偏移一天，导致今日调用/Tokens 与近 7 天趋势整体偏一天。
   - 改为新增 `_date_key_of(ts)` 统一按「本地时区」分桶（`datetime.fromtimestamp(ts)`，不再带 `tz=timezone.utc`），`_today_key()` 复用之。
   - 历史记录存的是原始 epoch，读取时统一本地分桶，无需迁移旧数据。

2. **Embedding token 漏记**（`ai_usage.py` + `embedding_service.py`）
   - 根因：108 条 `chatbot_embedding` 记录 0 token 实为「本地 embedding（BAAI/bge-small-zh-v1.5）」按设计硬写 `usage:{total_tokens:0}`——本地不花钱故成本为 0，但仪表盘 token 趋势因此完全看不到 embedding 负载；远程 embedding 若 provider 只回 `total_tokens` 也会被漏记。
   - `record_usage` 增强：usage 中 `prompt/completion_tokens` 都为 0 时兜底用 `total_tokens` 回填；新增 `input_tokens_override / output_tokens_override / cost_override / billable` 关键字参数。
   - 本地 embedding 调用改为传 `input_tokens_override=按字符数/1.5 估算`、`cost_override=0.0`、`billable=False`。
   - **关键决策**：新增 `UsageRecord.billable` 标志。`check_budget()` 仅统计 billable 记录——本地 embedding 虽记录估算 token 供仪表盘展示，但不占用每日 token/费用预算，避免免费本地调用把真实 LLM 调用饿死。仪表盘汇总（`get_daily_summary`/`get_recent_usage`）仍纳入全部记录以保持可见性。

3. **移动端静默 catch**（`frontend/src/mobile/pages/AIConfig/index.tsx`）
   - 原 `aiApi.getUsage().catch(() => null)` 静默吞错，使「今日用量」卡片凭空消失无诊断。改为 `.catch((e) => { console.warn(...); return null })`，与桌面端 AIConfig 行为一致。

验证：`.venv` 下 `py_compile` 通过；运行时确认时区分桶正确、远程 embedding `total_tokens` 兜底生效、本地 embedding override+cost=0、budget 排除非 billable、仪表盘仍含本地估算 token。测试期间误写入的 record 已按时间戳清理（data/ai_usage.json 回到 454 条）。

注意：data/ai_usage.json 中本次之前的历史 454 条记录无 `billable` 字段（旧格式），仅影响展示聚合，不影响预算（预算只读内存且新记录才带 billable）。
