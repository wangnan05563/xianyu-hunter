# 危险操作文案规范

> 适用范围：所有会产生**不可逆**或**外溢影响**（花钱、断连、掉登录态、删数据、关进程）的前端操作。
> 来源：T02324 逐菜单 UX 评审 §4.15 主线建议 1 / 跨页专题 T3，落地单 T02573。
> 落地组件：`frontend/src/components/DangerSummary.tsx`（`confirmDanger` / `DangerSummary`）。

## 1. 四要素（缺一不可）

确认框必须回答用户真正要判断的四件事，按固定顺序、固定标签渲染：

| 要素 | 标签 | 必须写什么 | 禁止写法 |
| --- | --- | --- | --- |
| ① 动作 | `动作：` | 动词 + 真实对象名（表名、目录名、进程名） | 「此操作」「相关数据」 |
| ② 影响范围 | `影响范围：` | 波及哪些资源，并**显式写「不包含」什么** | 只写会删什么、不写边界 |
| ③ 数量 | `数量：` | 来自接口的真实统计值 | 拍脑袋的固定数字、`全部` |
| ④ 恢复成本 | `恢复成本：` | 怎么撤销 / 用什么备份回滚 / 为什么不可恢复 | 「不可撤销」一句话了事 |

数量拿不到时**必须**显示 `未能预先统计（以预览/执行结果为准）`（组件里的 `COUNT_UNKNOWN`），
不允许省略该行，也不允许退化成 `0` 或「无」——那会把「我不知道」伪装成「没有影响」。

## 2. 真实性高于完整性

文案只能写**已经被代码或接口证实**的后果。写不出依据的句子，就不写。本项目已实测的两条反面教材：

- 系统清理的 `browser_data` 分支删的是 `data/webview_data_*`，而全仓没有任何写入方，浏览器登录态实际在配置
  `browser.user_data_dir` 指向的 `./browser-data`。照原建议写「删除后需重新登录/重新扫码」是**假警告**，
  正确写法是同时说明「不包含 ./browser-data」。
- 反爬「停止会话」停掉的只是 `_m_h5_tk` 的后台续期循环，身份 Cookie 与浏览器数据不受影响。
  照原建议写「X 小时后需重新扫码」同样是**假后果**。

同理：确认框里的「价格」若来自商品标价而非成交价，必须写「标价/预计」，不能写「成交价」。

## 3. 确认强度分三档

| 档位 | 适用 | 实现 |
| --- | --- | --- |
| A. Popconfirm + 四要素描述 | 单人成本可逆（停止任务、重启服务） | `title` 写动作，`description` 用 `DangerSummary` 或等价的「影响范围 + 恢复成本」两句 |
| B. `Modal.confirm` + `DangerSummary` | 不可逆删数据、花钱下单、断开线上连接 | `confirmDanger({title, action, scope, count, recovery})` |
| C. B + 手输确认码 | 批量 / 全表级不可逆删除 | 在 B 的内容里追加 `CONFIRM_DELETE` 输入，`okButtonProps.disabled` 直到输入匹配 |

C 档已在 `DatabaseAdmin.tsx` 使用（`CONFIRM_TOKEN`），保留不动；A/B 档不得再用原生
`globalThis.confirm`——原生框无法承载四要素排版，也无法带 `danger` 语义。

## 4. 已落地改造点位

| 点位 | 文件 | 原问题 | 现文案要点 |
| --- | --- | --- | --- |
| 系统清理 › 缓存/数据库/日志 | `frontend/src/pages/Maintenance/Cleanup.tsx` | 原生 `confirm('确认清理缓存？此操作不可撤销。')` | 真实 `__pycache__` 目录数与 MB、`webview_data_*` 当前值，并声明不含 `./browser-data` 与数据库 |
| 数据库维护 › 单行删除 | `frontend/src/pages/Maintenance/DatabaseAdmin.tsx` | 只显示「主键：xxx」，无业务摘要 | 顶部补 2–3 个业务字段摘要（名称/标题/价格等，按表取真实存在的列） |
| 反爬 › 停止会话 | `frontend/src/pages/AntiCrawl/index.tsx` | 零确认直接停 | 确认框带 Token 已用时长、是否已过期，说明只停续期、不动 Cookie |
| 内网穿透 › 保存配置 | `frontend/src/pages/Maintenance/Tunnel.tsx` | 运行中保存会立刻断线，文案却说「下次启动生效」 | 运行中先确认后保存；成功文案按「是否运行中」分叉 |
| 确认抢单 | `frontend/src/pages/ConfirmBuy/index.tsx` | 花钱动作无二次确认 | 确认框列商品/标价/任务，说明走浏览器自动化真实下单、本页面无法撤销 |
| 移动端 › 系统清理 | `frontend/src/mobile/pages/Cleanup/index.tsx` | Popconfirm 只写「此操作将真实删除数据」 | 同规范补动作对象与恢复成本 |

## 5. 新增危险操作时怎么自检

1. 用 `confirmDanger(...)`（或 A 档 Popconfirm + 等价描述），不要用原生 `confirm`。
2. `count` 只能来自接口：优先复用页面已加载的 status 数据；确实拿不到就留 `null` 走 `COUNT_UNKNOWN`。
3. 文案里出现的每个数字、每个目录名、每个表名，都要能在后端代码里找到对应写入/删除路径。
4. 跑 `npx vitest run src/__tests__/dangerSummary.test.tsx`，并在改动页面上实际点开确认框截图取证。
