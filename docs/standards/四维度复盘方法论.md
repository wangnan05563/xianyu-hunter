> **文档目的**：将历史上多次问题复盘抽象出的方法论与可复用模板沉淀为项目级标准。
>
> **适用范围**：所有"任务执行 → 问题修复 → 经验沉淀"闭环；适用于前后端开发、代码审查、配置变更、文档更新。
>
> **方法论出处**：Sequential Thinking 4 维度复盘法（成功步骤 / 失败点 / 可抽象流程 / 适用边界），与 `mcp_Sequential_Thinking` 工具配套使用。

## 一、复盘方法论：四维度框架

任何「任务执行 → 发现问题 → 修复 → 沉淀」闭环，都应按以下四维度结构化复盘，避免遗漏根因与边界。

### 维度 1：成功执行任务的完整步骤

**目的**：提炼「哪些动作是有效的、应该继续保留」。

**提问模板**：
1. 任务从触发到完成走了哪几步？每步的输入/输出/判断标准是什么？
2. 哪些步骤是"重复 5 次以上都成功"的稳定模式？
3. 哪些工具/脚本/命令显著提升了效率（可固化到 skill 脚本中）？

**典型成功步骤（基于本轮 cookie 自愈系统复盘）**：
1. 用户报告现象 + 错误日志原文
2. AI 阅读相关文件 + 追踪调用链，定位根因类
3. 设计最小修改方案 + 同类问题一并扫描
4. 单测覆盖修复点 + 集成测试验证不回归
5. 沉淀硬约束到 `project_memory.md` + 同步到 `xianyu-hunter-dev` 主题文件
6. 服务重启 + 前端重新部署（必要时）
7. 关闭相关 issue / 文档同步

### 维度 2：任务执行过程中的不确定性与失败点

**目的**：识别「哪些动作容易出错、出错的根因是什么、如何提前预防」。

**提问模板**：
1. 在哪些步骤遇到过"卡住超过 30 分钟"的情况？根因是什么？
2. 哪些 bug 是「修复后又以另一种形式复发」的？
3. 是否有"为了赶进度而妥协"的临时方案尚未清理？

**典型失败模式**（本轮已踩过 6 类）：
1. **相似 bug 重复出现**：datetime 混用 bug 出现在 `repo_chatbot.py`、`api_orders.py` 多处 → 修复未全仓库扫描
2. **配置一致性盲区**：HF_ENDPOINT 镜像地址未注入到生产 `.env` → 文档未明确必填项
3. **跨语言契约模糊**：前端按 `msg.includes('expired')` 判断错误 → 后端换文案前端失效
4. **熔断/重试副作用**：BatchRefresh 熔断后未持久化剩余商品 → 断点续传失效
5. **资源生命周期泄漏**：JS 侧 `new Proxy()` 局部变量被 GC → 代理失效
6. **空 except 吞异常**：迁移/启动关键路径用 `logger.warning(f"...{e}")` 丢失堆栈

### 维度 3：可抽象的固定流程与判断逻辑

**目的**：从具体 case 提取可复用模板，让下次遇到类似问题"按模板走"即可。

**提问模板**：
1. 这个问题可以归纳为哪类通用流程？（错误处理/状态机/配置/资源管理…）
2. 流程的「输入 → 判断分支 → 输出 → 异常兜底」是否可以画出流程图？
3. 流程中的「魔数 / 字符串 / 决策表」是否可以配置化？

**本轮提炼的 7 个工作流模板**（详见 `meta-rules.md` 第 21-24 条 + 本文档第二章）：
- A. 错误处理决策树（启动/迁移路径 vs 业务路径）
- B. 跨时区/跨格式数据契约（datetime 字段传递）
- C. 批处理熔断模板（长任务断点续传）
- D. 资源生命周期管理（浏览器/订阅/连接）
- E. 配置驱动参数管理（阈值/域名/关键字）
- F. 跨组件状态同步（Zustand store 跨页同步）
- G. 配置 vs 凭证分离（密钥管理）

### 维度 4：该流程和判断逻辑的适用场景与不适用场景

**目的**：避免「为了 1 个 case 把通用流程复杂化」的过度设计陷阱。

**提问模板**：
1. 这个模板在什么场景下**不适用**？（性能 hot path / 一次性脚本 / 测试代码）
2. 如果硬套模板会出现什么副作用？（复杂度上升 / 性能下降 / 调试困难）
3. 有没有更简单的方案在「适用场景的 80%」已足够？

**典型边界判定**（本轮经验）：
- 错误处理决策树 → 启动/迁移路径**必须** `logger.exception()`；性能 hot path 用结构化异常而非全捕获
- 跨时区契约 → 跨进程/跨服务传递**必须**遵守；同一进程内的纯 Python 对象传递保留类型
- 批处理熔断 → 长任务 + 多步进度**适用**；单次请求 / 用户主动取消**不适用**（走"停止"分支）
- 资源生命周期 → 长连接 / 订阅 / 浏览器实例**适用**；一次性 useEffect / 短生命周期计算**不适用**
- 配置驱动 → 阈值 / 域名 / 业务开关**适用**；业务常量（订单状态枚举值）**不适用**（枚举值就是业务语义）
- 跨组件状态同步 → 复杂前端应用（多组件共享数据）**适用**；1-2 层 props drilling**不适用**
- 配置 vs 凭证分离 → 任何需要密钥场景**适用**；本地一次性脚本 / 测试 fixture（mock 凭证）**不适用**

## 二、可抽象的 7 个工作流模板（核心沉淀）

> **配置驱动**：所有模板的参数（阈值、域名、关键字、白名单）均在 `config.yaml` 的对应节点管理，不在代码中硬编码。

### 模板 A：错误处理决策树

**适用场景**：所有 `try/except`、`async try/except`、前端 `.catch()` 块。

**决策流程**：
```
捕获异常
├─ 询问 1：是否为启动/迁移/关键路径？
│   ├─ 是 → logger.exception() 输出完整 traceback + 阻断启动
│   └─ 否 → 进入询问 2
├─ 询问 2：是否需要向用户展示？
│   ├─ 是 → reason_code + user_message + 内部 detail 三层
│   └─ 否 → logger.warning + 计数累计
└─ 询问 3：是否需要重试？
    ├─ 是 → 指数退避 + 熔断 + 持久化重试状态
    └─ 否 → 直接记录 + 上报
```

**配置节点**（`config.yaml` 的 `error_handling_decision_tree`）：
```yaml
error_handling_decision_tree:
  critical_path_patterns:  # 启动/迁移/初始化的函数名 regex
    - "^(startup|migrate|init)_"
  exception_log_level: "logger.exception"  # 关键路径默认级别
  user_facing_reason_codes:  # 文案枚举值（与后端 failure_reason_propagation.reason_enum 对齐）
    - "cookie_expired"
    - "rate_limited"
    - "service_unavailable"
  retry_strategy: "exponential_backoff"  # fixed / exponential / fibonacci
  max_retry_count: 3  # 默认 3，从 config 读取
```

**判断信号**：`grep "except" <file>` → 关键路径缺 `logger.exception()` → 违规。

**不适用**：性能 hot path（用结构化异常而非全捕获）/ 测试代码（`pytest.raises` 期望异常）。

**历史教训**：迁移函数 `_migrate_add_column` 用 `logger.warning(f"...{e}")` 吞掉异常 → 后续迁移块全部跳过 → 启动时缺列触发 `OperationalError`。

### 模板 B：跨时区/跨格式数据契约

**适用场景**：所有 datetime 字段在前后端、DB、跨服务间传递。

**契约表**：

| 传递方向 | 输入格式 | 输出格式 | 转换函数 |
|---|---|---|---|
| 后端 → DB | `datetime.now(timezone.utc).replace(tzinfo=None)` | naive UTC | `_utcnow()` helper |
| DB → 后端 → API | naive UTC（SQLite） | ISO 8601 字符串（带时区 `+00:00`） | `isoformat()` |
| API → 前端 | ISO 8601 字符串 | 解析为 `Date` 对象 | `new Date(isoStr)` |
| 前端 → API → DB | `Date` 对象 | ISO 8601 字符串 | `.toISOString()`（保留 UTC） |
| 前端展示 | `Date` 对象 | 本地时区字符串 | `.toLocaleString()` |

**配置节点**（`config.yaml` 的 `datetime_contract`）：
```yaml
datetime_contract:
  backend_default_timezone: "UTC"  # DB 存储时区
  api_response_format: "iso8601_with_tz"  # iso8601_with_tz / unix_timestamp / naive_iso
  frontend_input_format: "iso8601"  # 禁止 toString()
  display_format: "locale_string"  # 前端展示格式
  backend_datetime_field_suffixes:  # 受契约约束的字段后缀白名单
    - "_at"
    - "_seen"
    - "_time"
    - "_active"
    - "_expiry"
```

**判断信号**：
- 后端：`grep "datetime.utcnow()"` → 已弃用 API → 违规
- 后端：`grep "\\.toString()"` 用于 datetime 字段 → 违规
- 前端：`grep "(at|seen|time|active)\\.replace\\("` → 字符串拼接 datetime → 违规

**不适用**：纯前端日期库组件（AntD DatePicker）的输入；同一进程内的纯 Python 对象传递。

**历史教训**：`repo_chatbot.py` 用 `datetime.now() - row.created_at` 触发 `TypeError: can't subtract offset-naive and offset-aware datetimes`，根因是后端 `_utcnow()` 返回 aware 而 `row.created_at` 存的是 naive。修复用 `_utcnow().replace(tzinfo=None) - row.created_at` 统一为 naive。

### 模板 C：批处理熔断模板

**适用场景**：长任务（>30 秒）+ 多步进度 + 需要断点续传。

**状态机**：
```
running → paused（可恢复）→ running（续传）
running → stopped（用户主动停止，终态）
running → failed（异常退出，终态）
running → completed（成功结束，终态）
```

**强制约束**：
1. **每完成一项就 `save_progress()`**（**关键**：本轮 BatchRefresh bug 的根因就是熔断时漏持久化）
2. **熔断时**：剩余项标记 `pending`，保存当前 cursor
3. **续传**：从持久化的 cursor 恢复，跳过已完成项
4. **日志区分**：「暂停（可恢复）」 vs 「终止（不可恢复）」

**配置节点**（`config.yaml` 的 `batch_process_circuit_breaker`）：
```yaml
batch_process_circuit_breaker:
  failure_threshold: 3  # 连续失败 N 次触发熔断（默认 3）
  save_progress_on_circuit_break: true  # 必须 true，禁止 false
  mark_remaining_as: "pending"  # pending / skipped
  persist_keys:  # 持久化的关键字段
    - "batch_id"
    - "cursor"
    - "completed_ids"
    - "remaining_ids"
  log_phrasing:
    paused: "批次熔断暂停（可恢复），剩余 X 项标记为 pending"
    stopped: "批次终止（用户主动），剩余 X 项不处理"
    failed: "批次失败（异常退出），剩余 X 项标记为 skipped"
```

**判断信号**：
- `grep "consecutive failure" <file>` 但代码无 `save_progress()` 调用 → 视为违规
- `break` 与 `paused` 混用（`break` 终止循环不保留状态）→ 视为违规
- 日志文案"暂停"但实际 `break` 跳出循环 → 视为违规（语义不一致）

**不适用**：
- 实时单次请求
- 幂等的小批量（≤3 个）操作
- 用户主动取消（走"停止"分支而非"熔断"分支）

**历史教训**：`batch_refresh_scheduler.py` 的 `BatchRefresh#95` 连续失败 3 次后用 `break` 跳出循环并标记剩余商品为 `skipped`，但**没有调用 `_save_progress()`** 持久化剩余项。导致"断点续传失效 + 剩余项被永久跳过"双重问题。修复后：熔断分支调用 `_save_progress()` + 修正日志措辞。

### 模板 D：资源生命周期管理

**适用场景**：浏览器自动化、订阅、长连接、Proxy/Observer。

**强制约束**：
1. **持有**：实例属性 / ref，命名以 `_` 开头表示私有（`self._page`、`this._proxy`）
2. **清理**：在 `stop()` / `useEffect cleanup` 中调用 `close()` / `dispose()`
3. **检测**：硬约束禁止 `const x = new Proxy()` 局部变量（被 GC 回收导致代理失效）
4. **监控**：建立资源使用计数 dashboard

**配置节点**（`config.yaml` 的 `resource_lifecycle`）：
```yaml
resource_lifecycle:
  required_holder_patterns:  # 必须持有的资源类型
    - "Playwright Page/Browser"
    - "EventSource/SSE"
    - "WebSocket"
    - "Proxy/Observer"
    - "asyncio.Task"
  cleanup_hook_method: "cleanup"  # 清理方法名
  forbid_local_var_creation:  # 禁止局部变量创建的资源
    - "Proxy"
    - "MutationObserver"
    - "IntersectionObserver"
    - "ResizeObserver"
  lifecycle_audit_interval_seconds: 3600  # 资源使用审计周期
```

**判断信号**：
- `grep "(const|let)\\s+\\w+\\s*=\\s*new (Proxy|MutationObserver|IntersectionObserver|ResizeObserver)" <file>` → 视为违规
- `asyncio.create_task(coro)` 未赋值给实例属性 → 视为违规（GC 风险）
- 长连接组件无 `useEffect(() => { return () => es.close() }, [])` cleanup → 视为违规

**不适用**：短生命周期的局部计算（一次性数组 map）/ 一次性 useEffect（无需 cleanup）。

**历史教训**：前端反爬模块中 `const observer = new MutationObserver(...)` 后未保存到实例属性，被 GC 回收后 DOM 变化不再触发回调，表面上"代码正常执行"但实际"功能失效"，难以察觉。

### 模板 E：配置驱动参数管理

**适用场景**：阈值、域名、白名单、错误文案模板、关键字正则。

**强制约束**：
1. 所有"魔数"必须提取到 `config.yaml` 对应节点
2. 技能通过 `load_config()` 读取，禁止 `import` 常量到代码中
3. 配置文件支持热更新（可选，但推荐）

**配置节点命名规范**：
- 节点名 `snake_case`
- 层级结构清晰，避免扁平化
- 每个节点含 `enabled` 开关 + 详细参数字段

**配置节点**（`config.yaml` 的 `config_driven_rules`）：
```yaml
config_driven_rules:
  enforced_node_naming: "snake_case"
  required_structure:  # 每个配置节点的强制字段
    - "enabled"
    - "fields"
  forbidden_in_code:  # 禁止在代码中硬编码的常量类型
    - "magic_numbers"
    - "url_patterns"
    - "regex_patterns"
    - "keyword_lists"
    - "domain_lists"
  exception_types:  # 例外：允许硬编码
    - "http_status_codes"  # HTTP 200/401/500
    - "protocol_fixed_values"  # path: "/"
    - "security_required_constants"  # hmac.compare_digest
```

**判断信号**：
- `grep "[0-9]{3,}" <file>` → 出现 ≥3 位数字且非端口号 → 视为可疑魔数
- `grep "https?://[a-z]" <file>` → URL 字面量出现在代码中 → 视为违规

**不适用**：
- 业务常量（订单状态枚举值 = 业务语义本身）
- 数学/算法常数（`math.pi`、排序阈值）
- 协议/标准固定值（HTTP 200、`/` 路径）

### 模板 F：跨组件状态同步

**适用场景**：复杂前端应用（多组件共享同一份数据）+ 多 Tab / 多路由 + 配置变更实时生效。

**强制约束**：
1. **单一可信源**：后端 `GET /api/xxx` 是前端唯一数据源，**禁止**前端 `usePersistentState` 重复持久化
2. **统一入口**：所有写入路径必须通过 `useXxxStore().setXxx(newData)` 集中入口，**禁止**各组件独立 `setState`
3. **统一 refetch**：API 调用后必须 `refetch()` 而非推断新状态（避免乐观更新与后端实际不一致）
4. **跨进程同步**：子进程状态变更必须 SSE 推送，**禁止**前端用 30 秒 TTL 缓存兜底

**配置节点**（`config.yaml` 的 `cross_component_state_sync`）：
```yaml
cross_component_state_sync:
  single_source_of_truth:  # 必须以哪个 API 为唯一可信源
    - "GET /api/cookies/layers"
    - "GET /api/auth/me"
    - "GET /api/batch-refresh/config"
  forbid_persistent_state_for:  # 禁止前端重复持久化的字段
    - "task.status"
    - "cookie_layer.validity"
    - "config.values"
  required_unified_hooks:  # 统一状态管理 Hook 列表
    - "useCookieLayersStore"
    - "useAuthStore"
    - "useBatchRefreshConfigStore"
  sse_push_required_for:  # 跨进程状态变更必须 SSE 推送的字段
    - "cookie_layer"
    - "scheduler_status"
    - "health_check"
  ttl_grace_seconds: 0  # 跨进程同步的 TTL 兜底秒数（0 即不依赖 TTL）
```

**判断信号**：
- `grep "usePersistentState" <file>` 但该字段在后端有 `GET /api/xxx` → 视为违规（重复持久化）
- 多个组件独立 `useEffect(() => fetch(...), [])` 拉取同一份数据 → 视为违规
- `setTimeout(refresh, 30000)` 作为跨进程状态同步方案 → 视为违规

**不适用**：
- 简单组件树（1-2 层 props drilling 即可）
- 服务端渲染场景（无客户端状态）
- 纯 UI 偏好（如主题色、视图模式）→ 这些应该用 `usePersistentState`（参考模板 G）

**历史教训**：用户反馈"功能正常但状态显示失效"（30 秒才恢复），根因：子进程登录后只更新自己的内存缓存，主进程读时取到 TTL 内的旧"失效"状态，前端 `LayerStatusBadge` 仅依据 `valid: boolean` 显示（无"未检测"区分），三层叠加导致用户体感"明明能跑却一直报错"。

### 模板 G：配置 vs 凭证分离

**适用场景**：任何需要密钥/凭证的配置文件。

**强制约束**：
1. **凭证必须从环境变量/密钥管理服务读取**（不入版本库）
2. **配置 `.yaml` 只放路径、白名单、阈值**（如 `cookie_db_path`、`hf_endpoint` 而非 `hf_token`）
3. **检测**：`grep "(token|password|secret|api_key)\\s*[:=]\\s*['\"]" <file>` → 字面量出现 → 视为违规

**配置节点**（`config.yaml` 的 `secret_management`）：
```yaml
secret_management:
  required_env_vars:  # 必须从环境变量读取的密钥清单
    - "HF_TOKEN"
    - "COOKIE_ENCRYPTION_KEY"
    - "DINGTALK_WEBHOOK_SECRET"
  forbidden_in_yaml:  # 禁止在 yaml 中出现的字段名
    - "token"
    - "password"
    - "secret"
    - "api_key"
  default_storage: "keyring"  # Windows DPAPI / macOS Keychain / Linux Secret Service
  rotation_reminder_days: 90  # 密钥轮换提醒周期
```

**判断信号**：
- `grep "(token|password|secret)\\s*[:=]\\s*['\"][^'\"]{8,}"` 在 `config.yaml` 中 → 违规
- `import os; os.environ["XXX_TOKEN"]` → 视为可疑（应通过 `_load_secrets_from_keyring()` 封装）

**不适用**：
- 本地一次性脚本（无协作，无 .env 共享需求）
- 测试 fixture（mock 凭证，明确标识）
