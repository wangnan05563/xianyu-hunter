# 编码规范提炼过程四维度复盘

> **复盘对象**：从"反复修复同类 bug"到"沉淀 24 条元规范 + 128 step 编码规范 + 7 个工作流模板"的完整过程
> **复盘方法论**：四维度框架（成功步骤 / 不确定性与失败点 / 可抽象流程 / 适用与不适用边界），见 [`四维度复盘方法论.md`](./四维度复盘方法论.md)
> **本文不重复**：方法论本体、7 个工作流模板 A-G 详细定义（见上述方法论）、128 step 编码规范完整内容（见 `xianyu-hunter-dev/assets/guides/coding-rules/`）、`编码规范.md` 铁律清单

## 一、背景与适用范围

### 1.1 为什么需要这份复盘

`xianyu-hunter` 项目在过去 4 个月内遇到 30+ 个反复出现的 bug 模式：datetime 混用、YAML 浅合并、熔断漏持久化、catch 笼统提示、统计查询与写入端不对齐……每次修复完都"以为根除了"，但 2-3 周后又在另一个文件复发。

**本文不记录"有哪些规范"（已在 24 条元规范、128 step、7 个模板中沉淀），只回答：**
1. 哪些沉淀动作是"重复 5 次以上都成功"的稳定模式？
2. 哪些"以为根除"的 bug 又复发了，根因是什么？
3. 编码规范沉淀是否可以抽象为 SOP？
4. 这套 SOP 在什么场景下不适用？

### 1.2 适用读者

| 角色 | 关心什么 |
|---|---|
| 未来要维护 `xianyu-hunter-dev` 的人 | 哪些 step 模板可复用、哪些沉淀路径有效 |
| 团队要建立类似编码规范体系的 | 通用化 SOP：现象归类→根因抽象→元规范+配置节点→code-review 审查要点→防回归 |
| 临时遇到 bug 想"沉淀为规范"的人 | 直接看「维度 3」的 5 步 SOP 流程图 |
| 项目维护者 | 24 条元规范如何支撑 128 step，未来扩展路径 |

## 二、维度 1：成功执行任务的完整步骤

### 2.1 成功路径：5 阶段沉淀法，10 步动作

| 阶段 | 步骤 | 关键产出 | 复用建议 |
|---|---|---|---|
| **0. 现象归类** | 1. 收集 ≥3 个相似 bug 报告 | bug 现象清单（症状 + 上下文） | **固化**：1 个 bug 不算"模式"，≥3 个才提规范 |
| | 2. 区分"偶发 bug"和"系统性缺陷" | 分类标记：真 bug / 误报 / 配置盲区 | **固化**：系统性缺陷才值得沉淀 |
| **1. 根因抽象** | 3. 用 5 Why / 根因追溯找根因类 | 根因描述（不是"哪里出错"而是"为什么"） | **固化**：根因必须能复现到 ≥3 个 case |
| | 4. 抽象为元规范（meta-rule） | 写入 `meta-rules.md`，配判断信号 | **固化**：每条元规范都要有 grep 判断信号 |
| **2. 模板沉淀** | 5. 提炼为"工作流模板" | 写入四维度方法论，含配置节点 YAML | **固化**：模板必须含适用/不适用边界 |
| | 6. 写 step 编码规范（若有特定语言细节） | 写入 `coding-rules/<topic>.md` | **固化**：step 引用元规范，不重复定义 |
| **3. code-review 映射** | 7. 提炼为 code-review 审查要点 | 写入 `xianyu-{frontend,backend}-code-review/config.example.yaml` | **固化**：每条元规范都要对应 1-2 条审查要点 |
| | 8. 编写报告模板扩展 | `templates/report-template.md` 加"四维度复盘"章节 | **固化**：审查结果可追溯到方法论 |
| **4. 防回归** | 9. 写回归测试 | `tests/` 下补单测覆盖修复点 | **固化**：规范必须配测试，否则只是"建议" |
| | 10. 沉淀硬约束到 `project_memory.md` | 跨会话保留的硬约束清单 | **固化**：跨会话的硬约束要进项目记忆 |

### 2.2 重复 5+ 次都成功的稳定模式

1. **"现象归类"先于"根因抽象"**：先收集 ≥3 个相似 bug，再写规范（避免"为 1 个 bug 立 1 个规范"的过度抽象）
2. **"元规范 + step 编码规范"双层结构**：meta-rule 是通用规则（24 条），step 是特定细节（128 条），避免重复
3. **"判断信号优先 grep"**：所有元规范都用 `grep "pattern" file` 表达判断逻辑，避免"语义判断"模糊描述
4. **"配置驱动"原则**：每条规范都对应 `config.yaml` 节点（`config_driven_rules` / `error_handling_decision_tree` / `batch_process_circuit_breaker` 等），禁止硬编码
5. **"code-review 技能同步"**：每条元规范都映射到 1-2 条 `xianyu-frontend/backend-code-review` 审查要点，形成"开发规范-审查规范"双向闭环
6. **"硬约束进项目记忆"**：高频复发的硬约束（HMAC 校验、KBManager 白名单、datetime naive/aware）写入 `project_memory.md`，跨会话保留

### 2.3 显著提升效率的工具/脚本

| 工具 | 提升效率 | 建议固化位置 |
|---|---|---|
| `meta-rules.md` 元规范索引 | 1 处看 24 条通用规则 | 任何规范体系都该有 |
| `coding-rules/_step-index.md` | 按主题 / step 编号双索引 128 条 | 避免"找不到规范"问题 |
| `xianyu-frontend-code-review` / `xianyu-backend-code-review` | 自动扫描 + 报告生成 | 任何编码规范都该有"自动验证"工具 |
| `project_memory.md` | 跨会话保留硬约束，避免重复踩坑 | 任何长期项目都该有 |
| `version-history.md` | 按版本组织历史教训，便于追溯 | 避免"教训散落各文档" |

## 三、维度 2：任务执行过程中的不确定性与失败点

### 3.1 不确定性（卡住超过 30 分钟的情况）

| 现象 | 根因 | 解决方式 | 启示 |
|---|---|---|---|
| 修复 datetime bug 后 2 周又在 `api_orders.py` 复发 | 修复未全仓库扫描相似用法 | 用 `grep "datetime.now() - row\."` 全仓搜 | 任何"根因类 bug"必须全仓扫 |
| 元规范 #21（错误处理决策树）被多个 step 重复定义 | 元规范和 step 边界未划清 | 明确"元规范定义通用规则，step 只写特有细节" | 元规范和 step 必须有引用关系 |
| code-review 审查要点与元规范不对齐 | 两者由不同人维护，缺少映射表 | 在 `四维度复盘方法论` 第三章加映射表 | 规范体系必须有"总-分"映射 |
| `project_memory.md` 写得太长导致"读不完" | 硬约束未按主题分组 | 按主题分（WebView2 / HMAC / KBManager / datetime / cookie） | 硬约束必须分类，重要项置顶 |
| step 规范越来越多（128 条）但利用率 < 30% | "为 1 个 bug 立 1 个 step" | step 必须被 ≥2 个文件使用，否则合并 | step 必须用"被引用次数"衡量价值 |
| 配置节点和代码不同步（配置加字段但代码不读） | "配置全链路生效"检查缺失 | 加 meta-rule #16：grep 每个配置项的字段名 | 配置驱动必须有"全链路验证" |

### 3.2 反复出现的同类失败（6 类"以为根除但复发"）

#### 失败模式 1：相似 bug 重复出现

- **症状**：`repo_chatbot.py:478` 用 `datetime.now() - row.created_at` 触发 `TypeError: can't subtract offset-naive and offset-aware datetimes`，修复后 2 周又出现在 `api_orders.py:57`
- **根因**：单点修复未全仓扫描相似用法（`_utcnow().replace(tzinfo=None)` vs `datetime.now()`）
- **修复**：用 `grep "datetime.now() - row\." src/ api/ services/ -r` 全仓搜，统一改用 `_utcnow().replace(tzinfo=None)` 模式
- **预防**：meta-rule #22 明确"跨时区契约"+ grep 判断信号
- **教训**：根因类 bug 必须全仓扫，单点修复是"治标不治本"

#### 失败模式 2：配置一致性盲区

- **症状**：`local_embedding.py` 写 `os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")` 但只在开发环境生效，生产环境没设
- **根因**：配置盲区 - `.env.example` 没列必填项，部署文档未注明
- **修复**：补 `.env` 必填项 + 部署文档加 "HF_ENDPOINT 必须设置" 红字警告
- **预防**：meta-rule #16（配置全链路生效验证）+ meta-rule #1（配置驱动原则）
- **教训**：配置项必须有"开发→生产→部署文档"全链路同步

#### 失败模式 3：跨语言契约模糊

- **症状**：前端按 `msg.includes('expired')` 判断错误，后端把 `expired` 改成 `expired_or_invalidated`，前端失效
- **根因**：前后端错误码契约散落在代码各处，无单一可信源
- **修复**：建 `failure_reason_propagation.reason_enum` 枚举，前后端共用
- **预防**：meta-rule #8（错误粒度区分）+ step 23/123（错误码契约）
- **教训**：跨语言契约必须有"枚举层"，禁止字符串拼接

#### 失败模式 4：熔断/重试副作用

- **症状**：`BatchRefresh#95` 连续失败 3 次后用 `break` 跳出循环，标记剩余商品为 `skipped`，但**没有调用 `_save_progress()`** 持久化
- **根因**：熔断分支和"用户主动停止"分支共用代码，但熔断需要持久化而停止不需要
- **修复**：熔断分支显式调用 `_save_progress()` + 修正日志措辞为"批次熔断暂停（可恢复）"
- **预防**：meta-rule #22（批处理熔断模板）+ step 88-90
- **教训**：熔断/重试是"长任务断点续传"高发 bug 区，必须独立模板

#### 失败模式 5：资源生命周期泄漏

- **症状**：前端反爬模块 `const observer = new MutationObserver(...)` 后未保存到实例属性，被 GC 回收后 DOM 变化不再触发回调
- **根因**：JS 侧局部变量被 GC，导致 Proxy/Observer 失效
- **修复**：硬约束禁止 `const x = new Proxy()` 局部变量，必须用 `this._proxy` 实例属性持有
- **预防**：meta-rule #23（资源生命周期管理）+ step 41-50
- **教训**：资源生命周期是"难以察觉"类 bug，必须有硬约束 + 监控

#### 失败模式 6：空 except 吞异常

- **症状**：`run_migrations()` 用外层 `try/except Exception as e: logger.warning(f"迁移失败: {e}")` 吞掉异常，后续迁移块全部跳过
- **根因**：关键路径（启动/迁移/初始化）的异常必须**阻断启动 + 完整 traceback**，不能用 warning 替代
- **修复**：每个迁移块独立 try/except + 关键路径用 `logger.exception()` 输出 traceback
- **预防**：meta-rule #21（错误处理决策树）+ 7 个模板中的模板 A
- **教训**：关键路径异常必须可见，warning 级别不够

### 3.3 临时方案（未清理的妥协）

| 妥协 | 状态 | 清理计划 |
|---|---|---|
| 128 step 中有 5-8 条 step 利用率 < 3 次引用 | 未清理 | 下版本合并到主题文件 |
| `编码规范.md` 铁律与 `meta-rules.md` 元规范有重叠 | 未清理 | 明确"铁律是总入口，元规范是详细规则" |
| 部分 step 的判断信号不精确（`grep` 命中后还需语义判断） | 未清理 | 提炼为 AST 级检查 |
| `version-history.md` 仅记录重大事件，未按 bug 分类 | 未清理 | 下一版本按"现象-根因-修复-预防"组织 |
| `project_memory.md` 硬约束 30+ 条但未按主题分组 | 部分按主题分组（WebView2/HMAC/KBManager/datetime/cookie） | 持续完善 |

## 四、维度 3：可抽象的固定流程与判断逻辑（SOP）

### 4.1 SOP：编码规范沉淀 5 步法

> **适用范围**：任何团队想把"反复出现的 bug"沉淀为"可执行规范"
> **不适用**：1 次性 bug、纯样式问题、性能优化（这些不需要规范，需要 PR review）

```
阶段 0：现象归类（沉淀的门槛）
├─ 问 1：这个 bug 是"1 次偶发"还是"≥3 次反复出现"？
│   ├─ 1 次 → 走 PR review 修复即可，不立规范
│   └─ ≥3 次 → 进入问 2
├─ 问 2：是"真 bug"还是"误报"？
│   ├─ 误报 → 加入"豁免清单"（如 xianyu-rule-overrides.md）
│   └─ 真 bug → 进入问 3
└─ 输出：≥3 个相似 bug 报告 + 分类标记

阶段 1：根因抽象（从"哪里错"到"为什么"）
├─ 1.1 用 5 Why / 根因追溯找根因类
├─ 1.2 检查是否"系统性缺陷"（非局部偶然）
│   ├─ 系统性 → 继续
│   └─ 局部 → 走 PR review
├─ 1.3 抽象为元规范（meta-rule）格式：
│   - 核心规则（一句话）
│   - 适用/不适用场景
│   - 判断信号（grep 优先）
│   - 历史教训（简短引用）
└─ 输出：1 条 meta-rule，4 个标准字段齐全

阶段 2：模板沉淀（从元规范到模板）
├─ 2.1 若是"高频工作流"（错误处理/熔断/资源/状态同步/配置/凭证/契约）
│   └─ 抽象为"工作流模板"（写入四维度方法论第二章）
├─ 2.2 若是"特定语言细节"（async/await、SQLAlchemy、AntD）
│   └─ 抽象为"step 编码规范"（写入 coding-rules/<topic>.md）
├─ 2.3 配套配置节点（写入 config.yaml 对应节点）
└─ 输出：模板 + step + 配置节点，三件套

阶段 3：code-review 映射（规范到审查）
├─ 3.1 每条元规范映射 1-2 条审查要点
│   - 前端 → xianyu-frontend-code-review/config.example.yaml
│   - 后端 → xianyu-backend-code-review/config.example.yaml
├─ 3.2 报告模板扩展"四维度复盘"章节
├─ 3.3 在 code-review 技能中加"指向本文档"的反向链接
└─ 输出：双向闭环（开发规范 ↔ 审查规范）

阶段 4：防回归（从规范到代码）
├─ 4.1 写回归测试
│   - 单元测试覆盖修复点
│   - 集成测试覆盖"该 bug 触发条件"
├─ 4.2 沉淀硬约束到 project_memory.md
│   - 跨会话保留的硬约束（HMAC/KBManager/WebView2/datetime/cookie）
├─ 4.3 加入 CI 门禁（如 hard_constraints 扫描）
└─ 输出：测试 + 硬约束 + CI 门禁，三道防线
```

### 4.2 关键判断信号（grep 优先）

| 信号 | 含义 |
|---|---|
| `grep "datetime.now() - row\." src/ api/ -r` | 跨时区 bug 未全仓扫 |
| `grep "dict.update(yaml" src/ -r` | YAML 浅合并（应 `_deep_merge_yaml`） |
| `grep "except.*pass\|except.*logger.warning(f" api/ services/ -r` | 关键路径异常被吞 |
| `grep "const.*= new Proxy\|let.*= new Proxy" frontend/src -r` | Proxy 局部变量被 GC |
| `grep "asyncio.create_task" api/ -r` 但无 `self._task` 赋值 | Task 引用未保留，GC 风险 |
| `grep "msg.includes('expired')" frontend/src -r` | 跨语言错误码契约模糊 |
| `grep "break" scheduler/` 上下文含"consecutive failure" | 熔断未持久化 |

### 4.3 决策表：现象分类 → 沉淀路径

| 现象分类 | 沉淀路径 | 写入位置 |
|---|---|---|
| 单次偶发 bug | PR review 修复 | git commit 即可 |
| 相似 bug 出现 ≥3 次 | 元规范 | `meta-rules.md` |
| 反复出现的高频工作流（错误/熔断/资源/状态） | 工作流模板 | `四维度复盘方法论` 第二章 |
| 特定语言/框架细节（async/await/SQLAlchemy/AntD） | step 编码规范 | `coding-rules/<topic>.md` |
| 框架/库已知误报 | 豁免清单 | `xianyu-rule-overrides.md` |
| 跨会话必记的硬约束 | 项目记忆 | `project_memory.md` |
| 重大 bug 教训 | 版本历史 | `version-history.md` |

### 4.4 关键模板（与四维度方法论对应）

本文产出的元规范 #21-24 直接对应四维度方法论的 4 个工作流模板：

| 元规范 | 工作流模板 | 提炼自 |
|---|---|---|
| #21 错误处理决策树 | 模板 A | `run_migrations()` 关键路径吞异常 bug |
| #22 批处理熔断模板 | 模板 C | `BatchRefresh#95` 熔断漏持久化 bug |
| #23 资源生命周期管理 | 模板 D | 前端反爬模块 Proxy 被 GC bug |
| #24 跨组件状态同步 | 模板 F | "30 秒才恢复"状态同步 bug |

模板 B（跨时区契约）/E（配置驱动）/G（凭证分离）已对应到现有 meta-rule + step，不重复新增。

## 五、维度 4：适用场景与不适用场景

### 5.1 适用场景

| 场景 | 适用程度 | 关键产出 |
|---|---|---|
| **多人协作的长期项目**（> 6 个月，> 3 人） | ✅ 完全适用 | 元规范 + step + code-review + 测试，四件套 |
| **跨会话复发的硬约束**（HMAC/KBManager/WebView2） | ✅ 完全适用 | project_memory.md 硬约束清单 |
| **多模块多语言项目**（Python 后端 + TypeScript 前端） | ✅ 完全适用 | xianyu-frontend/backend-code-review 双技能 |
| **有 CI/CD 的项目** | ✅ 完全适用 | hard_constraints CI 门禁 |
| **需要新人快速上手** | ✅ 完全适用 | meta-rules 24 条 + 铁律清单 + step 索引 |
| **外部团队协作**（银行适配器/供应商） | ✅ 完全适用 | xianyu-adapter-developer 等专用 skill |

### 5.2 不适用场景

| 场景 | 不适用原因 | 替代方案 |
|---|---|---|
| **< 1000 LOC 脚本** | 规范体系是过度设计 | 写 README + 几条关键约定即可 |
| **原型/MVP** | 6 个月后大概率重写，规范无价值 | 不立规范，跑通业务为主 |
| **单文件 CLI 工具** | 没有"多人多模块"问题 | 写 docstring + 类型注解 |
| **生成代码（OpenAPI 生成的 controller）** | 规范无法控制生成器 | sonar.exclusions 排除 generated/ |
| **临时 fork 的外部项目** | 不会长期维护 | 不立规范，跟随上游即可 |
| **强类型语言 + 严格 linter（Rust/Go + clippy/golangci-lint）** | 编译器和 linter 已是规范 | 启用 strict 模式即可 |
| **教学/演示项目** | 教学价值 > 工程规范 | 写注释解释为什么 |

### 5.3 边界判定的反模式

> **不要做**：
> 1. **"为 1 个 bug 立 1 个规范"**：单次偶发不沉淀，避免"规范膨胀"导致利用率 < 30%
> 2. **"规范没有 grep 判断信号"**：所有规范必须能用 grep 验证，禁止"语义判断"
> 3. **"元规范和 step 重复定义"**：元规范是通用规则，step 是特定细节，必须有引用关系而非重复
> 4. **"规范没配 code-review 审查要点"**：规范和审查脱节，规范形同虚设
> 5. **"规范没写回归测试"**：没有测试的规范只是"建议"，无法强制
> 6. **"硬约束不进项目记忆"**：跨会话的硬约束必须写进 `project_memory.md`，否则下次又踩

### 5.4 适用边界的动态调整

| 项目阶段 | 规范粒度建议 |
|---|---|
| **0-3 个月（早期）** | 铁律 5-8 条 + 元规范 ≤ 10 条 + step ≤ 30 条 |
| **3-12 个月（成长期）** | 铁律 10-15 条 + 元规范 10-20 条 + step 30-80 条 |
| **12+ 个月（成熟期）** | 铁律 15-20 条 + 元规范 20-30 条 + step 80-150 条（本项目当前阶段） |
| **退化期** | 持续合并 step 利用率 < 3 的项，避免规范膨胀 |

## 七、风险与未解决项

### 7.1 已识别风险

1. **规范膨胀风险**：128 step 中可能有 5-8 条利用率 < 3，需定期合并
2. **元规范和 step 边界模糊**：偶尔有重复定义，需明确"元规范定义通用规则，step 只写特有细节"
3. **code-review 审查要点与元规范同步**：两者由不同人维护，缺少自动化校验
4. **`project_memory.md` 持续增长**：当前 ~30 条硬约束，6 个月后可能 50+ 条，需按主题分组
5. **新场景未被覆盖**：AI 代码（70% 以上由 AI 生成的代码）模式库未建立
6. **跨项目复用**：当前规范主要针对 `xianyu-hunter`，其他项目复用时需重新分类硬约束

### 7.2 未解决项

| # | 事项 | 优先级 | 计划 |
|---|---|---|---|
| 1 | step 利用率 < 3 的项合并 | 中 | 下一迭代 |
| 2 | code-review 审查要点与元规范自动化映射校验 | 中 | 待研究 AST 级工具 |
| 3 | `project_memory.md` 按主题分组优化 | 中 | 持续完善 |
| 4 | AI 代码模式库建立 | 低 | 社区需求驱动 |
| 5 | 跨项目复用规范抽取 | 低 | 长期 |

### 7.3 反馈循环

- **下次发现 bug 时必查**：本文「维度 3 SOP 阶段 0」问 1-2，确认是否值得立规范
- **下次立规范时必查**：本文「维度 3 SOP 阶段 1-4」，按 5 步走完，避免遗漏环节
- **下次扩展规范时必查**：本文「维度 4 适用边界」，避免"为不适用场景立规范"
- **下次发现"以为根除但复发"时必查**：本文「维度 2 失败模式 6 类」，确认是否新类型
