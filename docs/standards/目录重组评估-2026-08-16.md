# 目录重组评估（2026-08-16）

> 触发：用户要求按"前端→frontend / 后端→backend / 脚本→script / 构建产物→dist / 日志→log / 文档→docs"六分类重组项目，并评估是否合理。
> 结论先行：**不建议按字面执行"全部文件迁移到 6 个目录"的重组**。当前结构已实现功能分类目标，且比扁平 6 目录更贴合本项目的构建/运行耦合。

## 一、目标六分类 ↔ 现状映射

| 目标分类 | 现状目录 | 匹配度 | 说明 |
|---|---|---|---|
| 前端代码 → `frontend` | `frontend/`（React18+TS+Vite+antd） | ✅ 已就位 | `index.html`/`vite.config.ts`/`src`/`package.json` 齐全，且 `目录结构.md` 标记为"不可移动" |
| 后端代码 → `backend` | `backend/xianyu_hunter/`（Python 主包） | ⚠️ 已就位但名为 `src/` | 改名 `backend/` 会破坏构建与运行（见第三节） |
| 自动化/工具脚本 → `script` | `scripts/` | ⚠️ 已就位但名为 `scripts/`（复数） | 已被 PyInstaller spec、build-exe.ps1 强引用；复数 `scripts/` 是社区标准 |
| 构建产物与打包输出 → `release` | `release/`（PyInstaller onedir 输出 + 中间产物 `release/.work`） | ✅ 已就位 | 含 exe 与已部署 SPA 副本；`cleanup-config.yaml` 列入 `preserve_roots` |
| 运行日志 → `log` | `logs/`（+ 散落 `run.stdout.log`） | ⚠️ 名为 `logs/`（复数） | 复数 `logs/` 通用约定；`run.stdout.log` 在根是**有意设计**（服务标准输出，见 `目录结构.md` §6.5） |
| 项目文档 → `docs` | `docs/` | ✅ 已就位 | `目录结构.md` 等规范已落位 |

**结论**：六分类中 4 项（`frontend`/`release`/`docs`/`logs`）命名与意图已完全吻合；2 项（`src`→`backend`、`scripts`→`script`）仅命名不同，但这两个命名是构建耦合的硬性约定。

## 二、六分类模型未覆盖的关键目录

目标模型只给了 6 个桶，无法容纳本项目的专职目录。这些目录均为有意为之、不可随意归并：

| 目录 | 职责 | 是否可归入六分类 |
|---|---|---|
| `config/` | YAML 配置，代码硬编码引用 `paths.get_config_dir()` | ❌ 不能并入 docs/或 backend/，否则破坏配置加载 |
| `data/` | 运行时 SQLite/向量库/Prompt（gitignore） | ❌ 运行时数据，独立桶 |
| `browser-data/` | Playwright 登录态/Cookie | ❌ 运行时数据，独立桶 |
| `tests/` | 测试源码，`pyproject.toml` `testpaths=["tests"]` | ❌ 不能并入 backend/，否则 pytest 失效 |
| `release/.work/` | PyInstaller 中间产物（可重生成，位于 `release/.work`） | 属"构建产物"，但是**中间**品，应清理而非并入 `release/` 出货目录 |
| `assets/` | 应用图标（spec 引用 `assets/xianyu-hunter.ico`） | 静态资源，独立桶 |
| `plugins/` / `_skill_optim/` | 插件与技能优化文档 | 独立桶 |

## 三、为什么"字面迁移"不合理（风险点）

### 3.1 `src/` → `backend/` 会破坏构建与运行
`src/` 在以下位置被硬编码引用（已逐一核实）：
- `pyproject.toml`：`[tool.setuptools.packages.find] where = ["src"]`、`pythonpath = ["src"]`、`--cov=backend/xianyu_hunter`、`[tool.coverage.run] source = ["backend/xianyu_hunter"]`
- `xianyu-hunter.spec`：`pathex=[..., os.path.join(repo_root, 'src')]`（PyInstaller 入口分析路径）
- `backend/xianyu_hunter.egg-info/`：editable 安装元数据
- 运行时 SPA 伺服根：`backend/xianyu_hunter/web/static/spa/`（部署副本 `release/xianyu-hunter/static/spa/`）

改名需要：改 pyproject（4 处）+ spec pathex + 重建 egg-info + 修正任何 `sys.path`/相对解析 + **重装 + 全量 `vite build` + `pytest` 验证**。这是独立重构任务，不是"移动文件"。

### 3.2 `scripts/` → `script/` 会破坏引用
- `xianyu-hunter.spec` 入口：`scripts/launcher.py`
- `build-exe.ps1`：将 `scripts/` 复制到 `release/xianyu-hunter/`
- 多处 `.ps1`/`.bat`/`.py` 引用 `scripts/`
- `scripts/`（复数）是社区与工具链通用命名；`cleanup-config.yaml` 的 `workspace.script_dir` 也是 `"scripts"`

### 3.3 命名约定：复数 `scripts/`/`logs/` 优于单数
- `logs/`（复数）是日志目录的通用约定，且已被构建脚本与 `cleanup-config.yaml` 引用。
- `run.stdout.log` 位于根目录是 `目录结构.md` §6.5 明文规定的"服务标准输出"位置，**不是散落垃圾**，不应挪动（挪动需同步改启动器写路径）。

## 四、可安全执行的改进（不破坏构建）

1. **维持物理结构不变**，仅在点上澄清：在 `目录结构.md` 增加一段"为何不使用 `backend/`/`script/` 命名"的注释（纯文档，零风险）。
2. 常规清理（按需、独立进行）：`release/.work/`（PyInstaller 中间产物，可重生成）、各类缓存（`__pycache__/`/`.pytest_cache/`/`.scannerwork/`），属 `cleanup-config.yaml` 的 `garbage_patterns`，与"重组"是两件事。
3. 若确有"统一命名"诉求：仅做**文档层别名说明**，不动任何物理路径，避免触发构建回归。

## 五、若坚持 `src` → `backend` 重构（高风险 · 独立任务 · 需明确授权）

改造清单（任一遗漏即构建/运行失败）：
1. `pyproject.toml`：`where=["backend"]`、`pythonpath=["backend"]`、`--cov=backend/xianyu_hunter`、`source=["backend/xianyu_hunter"]`
2. `xianyu-hunter.spec`：`pathex` 第二个元素改为 `backend`
3. 移动 `backend/xianyu_hunter` → `backend/xianyu_hunter`，删除旧 `backend/xianyu_hunter.egg-info`，重跑 `pip install -e .`
4. `web/app.py` 及 SPA 伺服逻辑：`backend/xianyu_hunter/web/static/spa/` 路径协议需同步（现有记忆已记录此路径为运行期契约）
5. 全量验证：`vite build` → `python -m pytest tests/ -v` → `pyinstaller xianyu-hunter.spec` → 启动 exe 冒烟
6. 同步更新 `目录结构.md`、`cleanup-config.yaml`、`README.md`

## 六、最终建议

- **现状结构合理，符合"功能分类、职责清晰"的目标，且更贴合本项目构建耦合**——不建议字面迁移。
- 唯一"不达标"的是两个命名差异（`src`/`scripts`），但它们是构建契约，改名弊大于利。
- 如需推进，请明确选择：① 维持现状（推荐）；② 仅补文档说明；③ 授权执行高风险的 `src→backend` 重构（按第五节清单 + 全量验证）。
