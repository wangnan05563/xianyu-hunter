# XianyuHunter 用户体验评估与功能审查报告

> 报告版本：v1.0
> 报告日期：2026-06-06
> 评估范围：Web UI 全量页面 + 关键交互流程 + 已有 v1/v2 优化项落地追踪
> 评估方法：界面走查 + 流程推演 + 行业最佳实践对照 + HEART 框架打分
> 受众：产品 / 前端 / 后端 / 用户本人

---

## 摘要：5 个核心判断

1. **系统已从"可看"升级为"可运营"，但"高密度监控"场景仍是最大短板**。Dashboard、通知中心、接管 Modal、移动端响应式 v1/v2 已落地，但高频用户的"异常巡检"和"批量管理"操作路径仍然偏长。
2. **数据可视化停留在"静态分布"层级，缺乏时间趋势与对比基线**。直方图只展示分布，没有"过去 7 天趋势 / 同关键词价格中位数 / 任务成功率折线"等真正能驱动决策的视图。
3. **键盘 / Command Palette 缺失，高频用户每天损失分钟级时间**。运营每天要操作"暂停 / 恢复 / 接管 / 切 Tab / 查日志"几十次，每次 1-2 秒鼠标移动累计可观。
4. **任务管理是真正的"主战场"，但缺少批量操作、模板、导入导出与协作分享**。这与 requirements.md 中"团队协作 / 备份"非目标存在张力——单用户同样需要"换电脑时一键导入"。
5. **可观测性目前仅在"事件流 + 日志"两层，缺乏"评估命中率 / 误报率 / 配置变更影响"等业务指标**。用户改了阈值后，无法量化"改对了还是改错了"。

## 3. 目标用户与使用场景

### 3.1 核心用户画像

> 来源：requirements.md §3.1 + design.md §6.1

- **唯一画像**：懂技术、有研究、对二手商品有追求的中文个人买家
- **技术能力**：能在 Windows 跑 Python / Node、能配推送 Key、能理解"职业卖家 / 黑名单"
- **使用时段**：白天 9-22 + 晚上 22-2 + 周末高频
- **使用设备**：PC（主）+ 手机（监控/接收通知）+ 偶尔平板
- **痛点锚点**：
  - 抢到低价优质商品的窗口期 < 60s
  - 一天 1-2 单成功属于正常水平
  - 配置错 1 次 = 系统失灵 1 周

### 3.2 关键使用场景

| 场景 | 频率 | 关键诉求 |
|---|---|---|
| 加新任务 | 1-2 次/天 | 快、模板可复用、避免误操作 |
| 巡检 Dashboard | 5-20 次/天 | 一眼看出异常、点击直达处理 |
| 处理接管 | 1-3 次/天 | Modal + 倒计时 + 状态联动 |
| 调整评估权重 | 1 次/周 | diff 预览、可回滚、效果可验证 |
| 排查失败订单 | 1-2 次/天 | 时间线聚合、跨数据过滤、payload 详情 |
| 配置通知通道 | 首次/换设备 | 测试按钮、状态可见 |
| 移动端查看 | 2-5 次/天 | 异常数、抢单状态可见、关键操作 |

### 3.3 隐含但未明示的需求

| # | 隐含需求 | 推论依据 |
|---|---|---|
| H-1 | 换电脑/重装系统时数据可迁移 | requirements.md 提到"个人使用 7×24"，意味着用户必然遇到硬件迭代 |
| H-2 | 多人分享配置（如朋友也想监控同样关键词） | requirements.md "团队协作"被列为非目标，但实际中同好会交流 |
| H-3 | 知道"哪个任务最近没效果"（沉默任务） | requirements.md §10.1 提到 `discover_rate`，但 UI 无对应视图 |
| H-4 | AI 帮判断"这单要不要抢" | requirements.md §4.9 F9.1 已纳入 v1.0 候选 |
| H-5 | 凌晨被推送吵醒 → 需要"免打扰时段" | Notifier 文档提到 3 渠道，但无时段控制 |

## 4. 优化需求清单（按 P0/P1/P2 排序）

### 4.1 P0（1-2 周内必做）：解决"高密度监控 + 误操作预防"

#### UX-01 顶栏状态 chip 可下钻
- **现状**：`base.html:43-50` 顶栏 `status-chip` 不可点击
- **需求**：点击 → 跳到 `/tasks?status=running`（运行中数 > 0）/ `/tasks`（无运行中）
- **实施要点**：chip 加 `@click` + `cursor: pointer` + 鼠标 hover 反馈
- **预期效果**：用户从"看"到"管"少 2 步点击

#### UX-02 抢单记录"商品标题"列
- **现状**：`orders.html:49-52` 只有 item_id 链接
- **需求**：增加"商品"列，调用 `/api/items/{item_id}` 异步拉取标题（带缓存）
- **实施要点**：表头加列 + `<td x-text="itemCache[o.item_id] || '加载中…'">` + 后端加 `GET /api/items/{id}/summary` 轻量接口
- **预期效果**：接管决策时不再需要先点开链接看是不是想要的

#### UX-03 价格直方图叠加分位数 + 时间对比
- **现状**：`dashboard.html:212-247` 只有静态分布
- **需求**：在 SVG 上叠加 P25/P50/P75 三条虚线 + 鼠标 hover 显示"今日均价 / 7 日均价 / 偏差 %"
- **实施要点**：复用 `renderHistogram()` 框架，加 3 个 `<line class="quantile">` + tooltip
- **预期效果**：用户能"看图决策"——是不是整体在涨价

#### UX-04 任务复制后给出明确"副本"标识
- **现状**：`tasks/list.html:402-414` 复制后 name 清空、keyword 不改
- **需求**：复制时把 keyword 末尾加" 副本"（如"iPhone 13 副本"），name 留空；保存时强制要求 name 非空
- **实施要点**：`clone()` 改 keyword 拼接 + 提交时 `if (!form.name.trim()) toast('请填写任务名')`
- **预期效果**：避免"我以为复制了，提交后原任务被覆盖"的误操作

#### UX-05 关键错误信息持久化到通知中心
- **现状**：`base.html:312` Toast 3.5s 自动消失
- **需求**：err 级别的 toast 自动"升级"为通知中心的一条记录（"二维码加载失败 [立即重试] 按钮"）
- **实施要点**：`pushBanner()` 中 err 级调用 `createNotification()` API（已有 `/api/notifications`）
- **预期效果**：关键告警不丢失、可追溯、可一键重试

#### UX-06 任务控制按钮用 Modal 替代 confirm
- **现状**：`tasks/list.html:525/532` 用 `confirm()`
- **需求**：危险操作（删除 / 停止）弹 inline 确认条（替代 Modal），非危险操作（暂停 / 恢复）直接生效 + toast 反馈
- **实施要点**：行尾加"二次确认"展开/收起（无新 Modal），复用 `toast()`
- **预期效果**：减少打断感、保留可逆性

### 4.2 P1（1 个月内做）：解决"批量管理 + 决策支持"

#### UX-07 Dashboard 时间趋势小图
- **需求**：在 4 张统计卡下方加 3 个 sparkline（今日新增订单 / 评估分中位数 / 事件密度）
- **实施要点**：SVG 自绘（与现有直方图同栈），`/api/stats/trend?metric=...&range=24h` 接口
- **预期效果**：5 秒看到"今天是不是异常"

#### UX-08 任务列表批量操作
- **需求**：行首 checkbox + 顶部"批量 [暂停 / 恢复 / 删除] [N] 项"工具条
- **实施要点**：复用 htmx 批量 POST `/api/tasks/batch-control`
- **预期效果**：从 5 个任务一个一个点 = 5 次操作 → 1 次勾选 + 1 次按钮

#### UX-09 接管 Modal 自动关闭 done 阶段
- **现状**：`orders.html:212` 用户需手动点"完成"
- **需求**：done 阶段 3s 后自动关闭（用 `setTimeout`）
- **实施要点**：加 `autoCloseAt` + `setTimeout(() => closeTakeover(), 3000)` + 鼠标移入时清除
- **预期效果**：少 1 次点击 + 不打扰（鼠标在 Modal 内时不会自动关）

#### UX-10 评估分布直方图
- **需求**：在评估明细页加 "分数分布" 图：横轴 0-100 分 5 档、纵轴命中数
- **实施要点**：复用 `renderHistogram()` 框架 + 后端加 `GET /api/evaluations/distribution`
- **预期效果**：用户能看出"是不是阈值定太严了"

#### UX-11 任务详情页"运行历史"Tab
- **现状**：`tasks/detail.html` 只有"基本信息 / 评估"
- **需求**：增加"运行历史"Tab：每次 cron 触发的（开始时间 / 命中数 / 错误 / 耗时）
- **实施要点**：后端加 `/api/tasks/{id}/runs`（基于 events 表聚合），前端用 htmx 懒加载
- **预期效果**：能看到"这任务今天跑了几次 / 失败几次"

#### UX-12 时间线"严重度"过滤
- **需求**：在时间线过滤区加"严重度"多选（info / warn / err）
- **实施要点**：`timeline.html` 过滤区加一组 pill + 后端 query 加 `levels=` 参数
- **预期效果**：排查故障时少 50% 噪声

#### UX-13 配置保存后内联"已保存 v123"提示
- **现状**：`config/base.html:359` 保存成功只 toast
- **需求**：在配置页头部加"📌 已保存 v2026-06-06-12-30 · [↺ 立即回滚]"链接
- **实施要点**：保存成功后 `inlineSaveBadge` 显示 + 点击直接打开回滚 Modal
- **预期效果**：误改后可 1 步回滚

### 4.3 P2（迭代中）：解决"长期能力建设 + 体验升级"

#### UX-14 全局键盘快捷键
- **需求**：

## 5. 新增功能建议

### 5.1 智能运营类

#### F-AI1 沉默任务检测 + 推送
- **价值**：自动发现"配置后从未触发 / 触发但无命中"的任务，提醒用户清理
- **实现**：每日 cron 扫 `tasks LEFT JOIN events ON task_id AND created_at > 7d` → 推 1 条"以下任务 7 天无活动：xxx [停用 / 调整]"
- **预期效果**：用户对"哪些任务还活着"一目了然

#### F-AI2 任务模板市场
- **价值**：内置 10+ 常见品类模板（iPhone / 球鞋 / 演出票 / 显卡 / 相机），用户一键克隆
- **实现**：`/api/task-templates` 静态 JSON + "使用此模板"按钮复制为新任务
- **预期效果**：新用户从"无从下手"到"5 分钟开始监控"

#### F-AI3 评估分变化追踪
- **价值**：同一卖家评分随时间变化（账号被风控 / 涨粉 / 改标题），用 sparkline 显示
- **实现**：`/api/sellers/{id}/eval-trend` + 任务详情页加"该卖家历史评分"小图
- **预期效果**：避免"上次 80 分的卖家，这次 30 分"的黑天鹅

### 5.2 协作与可观测类

#### F-CO1 团队共享 Dashboard（可选）
- **价值**：硬核用户邀请 1-2 个朋友共用一个 Dashboard（"看今天又捡了什么"）
- **实现**：后端加 `share_token` + read-only 路由；前端不实现
- **预期效果**：增加"晒战绩"动力，间接促活

#### F-CO2 操作审计日志
- **价值**：记录"谁 / 何时 / 改了什么配置 / 启停了什么任务"
- **实现**：后端在 `tasks`、`config` 表加 `updated_by` + `audit_log` 表
- **预期效果**：误操作可追溯、解决"我刚才是不是改了什么"的疑惑

#### F-OB1 业务指标看板
- **价值**：在 Dashboard 加"过去 30 天"小卡片：发现商品数 / 通过率 / 抢单成功率 / 推送失败率
- **实现**：`/api/stats/business-kpi?range=30d` 聚合接口 + 4 张小卡
- **预期效果**：把"系统跑得怎么样"量化

#### F-OB2 配置变更影响追踪
- **价值**：调高 pass_score 后，对比"调整前 7 天 vs 调整后 7 天"的通过率
- **实现**：每次配置保存记录"变更前 7 天均值"，30 天后展示对比
- **预期效果**：避免"改了反而更差"的情况

### 5.3 体验升级类

#### F-EX1 引导式新手训练营
- **价值**：当前引导是 4 步点完即止，缺少"任务运行后该怎么观察"
- **实现**：在 `onboarding.html` 加 step 5："观察 Dashboard 5 分钟，看事件流变化"
- **预期效果**：新用户首次成功率 ↑

#### F-EX2 智能通知聚合
- **价值**：连续 10 条"评估通过"推送时，合并为 1 条摘要
- **实现**：Notifier 加 `aggregation_window_min` 配置 + 摘要模板
- **预期效果**：通知渠道不被刷屏

#### F-EX3 个人战绩卡（分享图）
- **价值**：月底生成"本月捡漏报告"（成功 N 单 / 节省 ¥X / 最高评分 Y）
- **实现**：每月 1 日 cron 生成 HTML 截图，前端可下载或分享
- **预期效果**：增加用户成就感与社交传播

#### F-EX4 多窗口/多任务 Workspace
- **价值**：用户可同时开 2 个 Dashboard（一个看总览、一个看特定任务）
- **实现**：URL 支持 `?workspace=xxx` 保存布局，存到 localStorage
- **预期效果**：复杂场景可定制

## 8. 风险与依赖

### 8.1 实施风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Alpine 3.x 在 SVG 内的 `<template x-for>` 失败（已遇到） | 高 | 中 | 沿用 vanilla DOM API（已有先例） |
| SSE 重连风暴（标签页频繁切回） | 中 | 中 | 加 5s debounce |
| 移动端"批量操作"按钮太小易误触 | 中 | 中 | 加二次确认 |
| 快捷键与系统快捷键冲突（如 Ctrl+K 与浏览器地址栏） | 中 | 中 | 注册前 `e.metaKey || e.ctrlKey` 检测 + Escape 退出 |
| Command Palette 索引数据量增长后变慢 | 低 | 中 | 用 lunr.js 增量索引 |

### 8.2 业务约束

- 保持 Alpine.js + htmx 技术栈（不引入 React/Vue）
- 不引入图表库（用 SVG 自绘）
- 移动端优先解决"查看"场景，"操作"继续降级
- 换电脑迁移在 v3 仍属 P2（用户群体小）
