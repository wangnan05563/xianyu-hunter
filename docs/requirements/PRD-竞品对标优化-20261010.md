## 1. 背景

### 1.1 竞品结论（T01719 摘要）

- 头部竞品均为单点产品：ai-goofish-monitor（监控+AI 筛选，~13k⭐）、XianyuAutoAgent（AI 客服/议价，~7.3k⭐）、xianyu-auto-reply（卖家店铺管理）、xianyu-monitor-extension（Chrome 扩展监控）。
- 「监控 + 评估 + 自动抢单 + 客服 + 运维面板」**一体化桌面端目前只有 XianyuHunter**，差异化成立；不照抄竞品的 Docker/Web 优先架构。

### 1.2 问题驱动（为什么是这四个 P0）

| 问题 | 证据 |
|---|---|
| **登录态可信度危机**：Cookie 面板、实时搜索、反爬管理三处数据源不一致，用户看到自相矛盾的状态 | T01717（面板正常/搜索不可用）、T01675（dev 与打包版显示不一致）、T01714（auth_helper 静默失败）系列任务，近 5 天 4 单 |
| **缺「监控」核心心智**：监控类产品的价值锚是「降价/新货第一时间知道」，当前只有采集快照、无价格历史与降价提醒 | 竞品 ai-goofish-monitor 已内建价格历史库（SQLite） |
| **自动抢单无安全阀**：全链路只有真实下单一种模式，任何改动都无法安全验证 | 用户每次修复后只能真枪实弹验证；竞品有测试模式 |
| **登录依赖单一扫码通道**：扫码有风控门槛，且打包版/dev 数据隔离放大了使用摩擦 | T01675 排查中「dev 登录态不共享打包版」造成用户误解 |

## 2. 目标与成功指标

### 2.1 产品目标

1. **可信**：任何界面展示的登录态结论一致、可解释、可一键自愈；
2. **敏感**：商品价格变动 5 分钟内触达用户（推送 + 站内）；
3. **安全**：抢单全链路可演练、可回放，不产生真实订单；
4. **低门槛**：新用户 3 分钟内完成登录态配置（扫码之外多一条通道）。

### 2.2 成功指标（发布后 30 天）

| 指标 | 目标 |
|---|---|
| 登录态相关工单/任务数（T01xxx 系列） | ≤ 1 个 / 月（基线：5 个 / 周） |
| 实时搜索「登录态不可用」误报率 | < 1%（基线：100% 复现于档案污染场景） |
| 降价提醒推送延迟（从价格变化到推送） | P95 ≤ 5 分钟 |
| 演练模式使用率（改动后先演练的用户占比） | ≥ 60% |
| 新用户登录态配置耗时 | P50 ≤ 3 分钟 |

## 5. 需求详述（P0）

### 5.1 C1 登录态健康度统一诊断与自愈

**优先级**：P0 ｜ **规模**：L ｜ **涉及**：后端 CookieStore / 前端 Cookie 面板 / 实时搜索前置检查

#### 问题

登录态结论分散在三处、数据源各异（T01717 根因）：

| 展示处 | 数据源 | 失败模式 |
|---|---|---|
| Cookie 状态面板（/cookie/health） | `cookies_default.json` | 与 per-user 档案不一致时误报「正常」 |
| 实时搜索前置检查 | `cookies_{uid}.json` + Worker 浏览器内存 | 档案污染 → 503 死循环 |
| 反爬登录管理 | `cookies_{uid}.json` | 同上 |

#### 用户故事

- 作为用户，我想在**一处**看到唯一可信的登录态结论（健康/降级/失效 + 原因 + 哪个 Cookie、哪个数据源出了问题），而不是两个面板互相矛盾。
- 当档案数据源不一致或含过期身份 Cookie 时，我希望系统**自动修复**（从最新鲜的数据源合并），修复不了时明确告诉我「需要扫码/导入」，一键直达。

#### 功能需求

- **FR-C1-1 健康度统一模型**：新增 `/api/auth/health/unified`，聚合三处数据源输出单一结论：`status ∈ {healthy, degraded, invalid}`、`reasons[]`（逐条：哪个 Cookie / 哪个档案 / 过期还是缺失）、`self_healed: bool`。
- **FR-C1-2 诊断优先级**：身份 Cookie（cookie2/sgcookie/unb）有效以「最新鲜数据源」为准（exported_at 最新且含有效未过期身份 Cookie 的档案）；各展示处一律消费该端点，禁止再各自读档案下结论。
- **FR-C1-3 自动自愈**：检测到档案间身份 Cookie 不一致/过期时，按「登录导出 > last_login > default > per-user」新鲜度顺序自动合并修复（复用 T01717 已落地的 merge + 过期过滤逻辑），修复动作写入事件时间线。
- **FR-C1-4 不可自愈的引导**：`invalid` 时返回可执行的修复动作（`relogin` / `import_json` / `restart_worker`），前端一键触发。
- **FR-C1-5 面板改造**：Cookie 状态面板展示统一结论 + 「诊断详情」抽屉（逐 Cookie：名称/过期时间/来源档案/状态徽标）。

#### 验收标准

- [ ] 构造「default 新鲜 + per-user 过期」场景（T01717 复现脚本）：面板与实时搜索结论一致，且 60s 内自动修复，事件时间线有记录；
- [ ] 构造「全部档案身份 Cookie 过期」场景：结论 `invalid`，面板给出「重新登录 / 导入 JSON」按钮且可用；
- [ ] 全仓 grep 确认无第二处直接读档案下登录态结论的代码路径（测试锁住）；
- [ ] 单测覆盖：新鲜度排序、合并自愈、结论聚合 ≥ 12 例。

#### 依赖与风险

- 依赖 T01717 修复（已合入：`is_expired_cookie` + merge 回写）。
- 风险：自动合并误把旧数据当新鲜 → 以 exported_at + 身份 Cookie 过期时间双重判据，单测覆盖。

### 5.2 F1 商品价格历史曲线 + 降价即时提醒

**优先级**：P0 ｜ **规模**：M ｜ **涉及**：采集链路 / SQLite / 通知引擎 / 商品中心前端

#### 用户故事

- 作为捡漏用户，我给关注商品设一个心理价，**跌破时手机 5 分钟内收到推送**，点开能看到价格走势再决定是否抢单。

#### 功能需求

- **FR-F1-1 价格快照落库**：新增 `price_history` 表（item_id、price、captured_at、source ∈ {collect, live_search, detail}）；采集/实时搜索/详情采集三条链路在商品落库时同步写快照（同值去重：与最新快照相同价不重复写）。
- **FR-F1-2 走势图**：商品中心行展开/详情抽屉展示近 30 天价格走势（ECharts 折线，标注每次降价点）；无历史时展示「暂无价格记录」。
- **FR-F1-3 降价检测**：新快照价 < 该商品此前最低价 × (1 - 阈值)（任务级可配，默认 0%）即触发降价事件；事件进通知引擎（复用现有 8 渠道 + 免打扰时段）与事件时间线。
- **FR-F1-4 通知内容**：推送文案含商品标题、现价、历史最低、降幅、深链（移动端 /m/ 商品详情）。
- **FR-F1-5 降级保护**：批量采集首轮全量建快照时**不**触发降价通知（避免冷启动轰炸）；单轮通知合并（同一任务一次推送汇总多条降价）。

#### 验收标准

- [ ] 模拟价格 100 → 80：推送触发、文案与深链正确、时间线有降价事件；
- [ ] 首轮建快照不触发推送；同值不重复落快照；
- [ ] 1000 商品 × 30 天快照（3 万行）走势图加载 P95 < 500ms（含索引）；
- [ ] 免打扰时段内降价只进站内不外推。

#### 依赖与风险

- 依赖采集与实时搜索链路的落库 hook 点（均已存在 display.price 字段，改动集中在写入侧）。
- 风险：快照写入放大采集耗时 → 批量写 + 异步队列。

### 5.3 C3 抢单演练（测试模式）

**优先级**：P0 ｜ **规模**：M ｜ **涉及**：Buyer 模块 / 任务配置 / 前端

#### 用户故事

- 作为自动抢单用户，我改完价格容差/评估规则后，想**跑一次完整演练**（搜索→评估→命中→模拟点击→下单前中止），拿到演练报告确认链路健康，而不产生真实订单。

#### 功能需求

- **FR-C3-1 演练开关**：任务级 `dry_run` 模式；全局「演练中」横幅常驻（所有相关页面可见），防止误以为在真实抢单。
- **FR-C3-2 中止点**：演练在 Buyer 下单动作前（支付页打开前）硬中止；中止点之后的所有步骤（下单、支付跳转）标记为 `skipped`。
- **FR-C3-3 演练报告**：每次演练产出结构化报告：命中的商品、四维评估得分、价格策略判定、模拟下单耗时（从命中到中止点的各段耗时）、中止原因；报告落抢单记录（type=dry_run，红色徽标与真实记录区分）。
- **FR-C3-4 防泄漏**：演练模式代码路径与真实下单共用 Buyer 前置逻辑，但下单调用点由 `dry_run` 守卫；守卫缺失时单元测试失败（CI 强制）。
- **FR-C3-5 入口**：任务详情「演练一次」按钮 + 仪表盘快捷入口；演练频率限制（同任务 ≥ 60s 间隔）防风控。

#### 验收标准

- [ ] 演练全程 0 真实订单（订单接口调用断言）；报告各段数据完整；
- [ ] 真实记录与演练记录在抢单记录页视觉可区分；
- [ ] 移除 dry_run 守卫的变异测试被 CI 捕获；
- [ ] 演练触发频率限制生效。

#### 风险

- 演练与真实抢购共用浏览器会话，演练中的风控指纹与真实一致（这是特性不是缺陷，文档注明）。

### 5.4 C2+F2 登录态多通道导入

**优先级**：P0 ｜ **规模**：S ｜ **涉及**：登录路由 / 前端登录面板 / CookieStore

#### 用户故事

- 作为被扫码风控卡住的用户，我想从日常浏览器导出登录态（安装小扩展一键导出，或粘贴 Cookie JSON），**粘贴进来即可用**；过期/残缺的导入要被明确拒绝并说明原因。

#### 功能需求

- **FR-F2-1 导入端点**：`POST /api/auth/cookies/import`，body 为 Cookie JSON 数组或整档 JSON；服务端校验：必需身份 Cookie（cookie2/sgcookie/unb）齐全、**过滤/拒绝已过期条目**（复用 `is_expired_cookie`）、测试 Cookie 过滤（复用 `is_test_cookie`）。
- **FR-F2-2 校验反馈**：逐 Cookie 返回校验结果（接受 / 过期跳过 / 残缺拒绝）；身份 Cookie 全缺失时 400 + 明确文案。
- **FR-F2-3 多用户归档**：导入成功后按 unb 识别用户写入 per-user + default 档案（复用 export_cookies + invalidate_cache），并触发 Worker 注入（复用 `inject_cookie_store_to_worker_browser`）。
- **FR-C2-4 前端入口**：登录面板新增「导入登录态」Tab：粘贴框 + 文件上传 + （P1）配套 Chrome 扩展下载链接；导入后显示逐 Cookie 校验回执。
- **FR-C2-5 帮助文案**：内嵌「如何从浏览器 DevTools 导出 Cookie」图文步骤（扩展未安装时的兜底路径）。

#### 验收标准

- [ ] 粘贴含过期 unb 的 JSON：过期条目被跳过并在回执中说明；身份 Cookie 全过期时 400；
- [ ] 导入成功后 30s 内 /cookie/health（统一端点）变 healthy、实时搜索可搜；
- [ ] 导入的档案写入 per-user + default 双档案（多用户隔离测试）；
- [ ] 注入 Worker 失败时（浏览器未启动）给出「重启服务」引导而非静默。

## 8. 开放问题

1. **C1 自愈的自动合并边界**：当两个档案「互有新鲜项」时（A 的 unb 新、B 的 sgcookie 新），逐 Cookie 取新鲜 or 整档取最新？（建议：身份 Cookie 逐项取未过期者，整档 method 记录 `self_heal`）
2. **F1 快照来源口径**：实时搜索（闲鱼搜索列表价）与详情页价可能不同，是否区分 source 展示两条曲线？（建议：单曲线取详情页价优先，列表价兜底，source 入 tooltip）
3. **C3 演练是否记录截图**：与真实抢购一致的截图能力是否在演练中启用？（建议：启用，但脱敏价格字段）
4. **Chrome 扩展**：自研导出扩展（竞品同款方案）M4 内做还是延后？（建议：先 DevTools 手动导出兜底，扩展排 P1）
