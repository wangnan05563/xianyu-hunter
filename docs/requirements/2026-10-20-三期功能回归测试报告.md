## 3. 五条指标逐条

### 指标 1 · 可见菜单点击后落到实现页（目标 31/31）

断言（`test_all_visible_menu_paths_have_implementation` / `test_menu_paths_are_unique`）：从 [config/menu_registry.yaml](file:///D:/code/otherProjects/17_xianyu/config/menu_registry.yaml) 取全部可见路径，与 [frontend/src/App.tsx](file:///D:/code/otherProjects/17_xianyu/frontend/src/App.tsx) 里 `<Route path="…">` 集合做差，要求差集为空、路径无重复、且 `len(paths) >= 29`；单独点名 `/price-dashboard`、`/export`（评审当日的两条死路由）。

实测：注册表当前 29 条、无 `hidden` 项；真机侧 `GET /api/menu` 下发同一批 29 条，29/29 全部命中实现页，`/price-dashboard` 与 `/export` 已不再被送回首页（见 §6.2 真机报告）。PRD 表里的分母 31 是评审当日口径，M1「2.1 导航元数据单一事实源治理」后重复项已收敛，实际分母为 29 —— 达成率 100%。

### 指标 2 · 「待处理」卡数值 = 真实 `pending_pay` 行数（原现状：恒 0）

断言（`test_pending_card_equals_real_pending_pay_rows`、`test_takeover_pending_is_not_counted_as_pending`）：往临时库灌 `pending_pay`×3 与 `takeover_pending/succeeded/failed/cancelled/dry_run` 各 1，要求 `GET /api/orders` 的 `stats.pending` 既 > 0 又逐字等于 `SELECT count(*) … status='pending_pay'`，同时等于 `status=pending_pay` 筛选的 `total`；翻到第 2 页数值不漂。关键反向断言：`takeover_pending`（抢单待处理）不得混进「待处理」分母——这正是原「恒 0」的同源病灶。

实测：三条等式全部成立（3 = 3 = 3），`takeover_pending` 单独计数不进分母。

### 指标 3 · 导出行数 = 筛选预期行数（原现状：不可判定）

断言（`test_export_row_count_matches_filter`、`test_export_zero_rows_returns_header_only_and_reports_zero`、`test_export_unknown_dataset_is_400_not_silent_success`）：`X-Export-Rows` 响应头 = SQL 行数 = CSV 数据行数；0 行时只回表头且报 0（不静默成功）；未知 dataset 必须 400 而非「导出成功」。

实测：2 = 2 = 2 通过；0 行用例返回 `x-export-rows: 0`；未知 dataset 返回 400。前端侧由 `exportFeedback.test.ts` 补齐文案层断言：0 行 → `message.warning` 含「0 行 / 只有表头」且不调 `success`；37 行 → 成功文案带「37 行」；行数未知（blob 无头）→ 只说「已保存」，不编造数字。

### 指标 4 · UI 展示但后端无实现的能力项（目标 0，grep + 契约锁）

断言（`test_daily_grab_limit_is_backed_by_schema_and_guard`、`test_guide_claims_are_backed_by_implementation`、`test_menu_admin_and_logs_copy_state_what_actually_happens`）：
- 「单日抢单数量上限」——配置字段、`BuyerStrategy` 读取点、前端控件三层都要有；且 UI 文案必须是真实口径（出现「待 UI 化」这类假承诺字样即失败，JSX 注释先剥掉再扫可见文案）。
- 引导文案里每条能力宣称要能反查到实现（「拖拽排序」→ MenuAdmin 的实际交互、「自动滚动」→ Logs 的实际行为）。

实测：护栏链三层齐备（该条已在 T02589 落地）。回归过程中**新查出 2 条假承诺**并当场修文案：
- [frontend/src/guides/menuGuides.ts](file:///D:/code/otherProjects/17_xianyu/frontend/src/guides/menuGuides.ts) `/menu-admin` 原写「拖拽排序」，页面实际是编辑 `sort_order` 数值 → 改为「排序通过编辑数值完成，页面不提供鼠标拖动」；

### 指标 5 · 前端请求体与后端 schema 不匹配的端点（目标 0）

断言（`test_menu_put_body_matches_schema`、`test_config_save_dry_run_is_a_real_field`、`test_export_and_orders_query_params_match_backend`）：以 `create_app().openapi()` 为后端事实源，比对请求体属性集合与 query 参数集合，并检查前端源码里的**字面量**（`client.put('/api/menu', { menus: items })`、`{ payload, dry_run: dryRun }`）与 schema 同形。

实测：`PUT /api/menu` 体属性恰为 `{menus}`（原必 422 的病灶已闭）；`POST /api/config/save` 体含 `payload` + `dry_run`，且当场发一次 `dry_run=True` 请求，断言状态码非 422 **且** `config/config.yaml` 的 sha256 前后一致（空跑真不落盘）；导出与订单查询参数覆盖前端使用到的全部名字。
