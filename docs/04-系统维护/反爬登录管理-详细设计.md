## 2. 功能概述

**一句话说明**：暴露 LoginOrchestrator 能力给前端，提供登录策略评估、会话管理、健康检查、Cookie 分层管理、指纹信息、频率伪装统计六大模块。

**核心价值**：
- 所有端点通过 `LoginOrchestrator` 单例（`get_orchestrator()`）操作，保证状态一致；
- 写操作（initialize/start/stop/update）用 POST，读操作用 GET，异步操作（start/stop/health）使用 async 路由；
- Cookie 三层管理（identity/session/tracking），原子更新 + 依赖校验，identity 失效级联导致 session 失效；
- 健康检查权重：Cookie 检查器（40）+ WAF 状态提供器（10），score 0-100；api/page 维度未配置时默认通过；
- WAF 状态：`fail_rate > 0.5` → BLOCKED，`> 0.2` → WARNING，否则 CLEAR；
- launch 模式生成随机 FingerprintProfile + stealth 脚本注入；CDP 模式连接真实浏览器无需指纹；
- TokenRenewer 后台续期，过期前通过浏览器导航触发刷新（导航是用户自然行为，风控压力低于直接调用 API）；
- Cookie 三重兜底同步：JSON 同步 → 浏览器内存兜底 → 功能可用性兜底；
- 浏览器 Cookie 导入支持 DPAPI / AES-256-GCM / 明文三种格式解密；
- LoginOrchestrator 自愈机制：续期失败 → 标记 session 失效 → JSON 同步恢复 → 自动重登（连续失败 2 次 + 10 分钟冷却）；
- 续期回调导航成功后会读取浏览器完整 Cookie 回写 CookieStore，保证 JSON 与浏览器内存一致。

## 3. 用户场景

**场景 1：首次登录配置**
用户首次部署系统，进入「反爬登录管理」页面。先在「登录策略评估」卡片看到推荐策略（如 `cdp_connect`），点击「初始化协调器」按钮选择 launch 或 CDP 模式。初始化后点击「启动会话」开启 TokenRenewer 后台续期，10 秒间隔自动刷新会话状态。

**场景 2：Cookie 失效恢复**
系统运行一段时间后，`/cookies/layers` 显示 session 层失效。用户点击「更新 Cookie」按钮，弹窗自动预填当前 CookieStore 中的 cookie 明文（调用 `/cookies/current`）。用户修改 `_m_h5_tk` 等字段后提交，后端分层合并写入并同步所有层状态。

**场景 3：从系统浏览器导入 Cookie**
用户已在 Edge 浏览器登录闲鱼，希望在系统中复用登录态。点击「从浏览器导入」按钮选择 `edge`，后端通过 `import-from-browser/preview` 接口解密浏览器 Cookie 数据库（DPAPI/AES-256-GCM），仅返回预览不写入。用户确认后调 `/cookies/update` 才会真正分层写入。

## 5. 接口定义

所有接口前缀：`/api/anticrawl`，路由文件：`backend/xianyu_hunter/web/routes/api_anticrawl.py`。

### 5.1 策略评估

#### GET /strategy
评估当前环境并推荐最优登录策略。

**响应**：`ok` / `recommended` / `reason` / `available_strategies[]` / `details`。

#### POST /strategy/set
设置当前使用的登录策略。

**请求体**：`{"strategy": "cdp_connect"}`

**响应**：`ok` / `strategy` / `message`。
**错误响应**：`ok=false` / `error="无效的策略名: {strategy_name}"` / `valid_strategies=["cdp_connect","reuse_userdata","browser_import","qr_scan","cookie_inject"]`。

### 5.2 协调器初始化

#### POST /initialize
初始化 LoginOrchestrator。

**请求体**：`{"use_cdp": false}`

**响应**：`ok` / `mode`（`launch`/`cdp`）/ `fingerprint_profile` / `user_agent` / `stealth_scripts_count` / `message`。

launch 模式生成随机 FingerprintProfile，BrowserManager 启动时自动读取该 profile 注入一致的 stealth 脚本和 UA；CDP 模式连接真实浏览器，无需指纹注入。

### 5.3 会话管理

#### GET /session/status
获取会话状态摘要（SessionStatus）。

**响应字段**：

| 字段                  | 类型    | 说明                                          |
| --------------------- | ------- | --------------------------------------------- |
| `active`              | bool    | 会话是否活跃                                  |
| `strategy`            | string  | 当前登录策略                                  |
| `fingerprint_profile` | string  | 指纹 profile 名称                             |
| `token_age_sec`       | float   | Token 年龄（秒）                              |
| `token_expired`       | bool    | Token 是否过期                                |
| `health_score`        | int     | 健康分（0-100）                               |
| `health_action`       | string  | 建议动作（none/renew_token/relogin/pause）    |
| `waf_status`          | string  | 风控状态（clear/warning/blocked）             |
| `cookie_layers`       | object  | 各 Cookie 层有效性                            |
| `freq_stats`          | object  | 频率伪装统计                                  |
| `captcha_stats`       | object  | 验证码统计                                    |
| `started_at`          | float   | 会话启动时间戳（Unix 秒）                     |
| `uptime_sec`          | float   | 会话已运行时间（秒，active=false 时为 0）     |

#### POST /session/start
启动会话管理（TokenRenewer 后台续期）。

**请求体**（可选）：`{"cookie_provider_name": "_m_h5_tk"}`

启动后 TokenRenewer 定期检查 token 年龄，过期前自动续期。续期失败触发 session 层 Cookie 失效。

**幂等行为**：会话已活跃时返回 `{"ok": true, "already_active": true, "message": "会话已处于活跃状态，无需重复启动"}`，不视为失败。

> 为什么不返回 `ok:False`：登录流程通过 `trigger_session_start()` 在登录成功后自动启动会话（fire-and-forget），用户进入反爬登录管理页面手动点击"启动会话"按钮往往会话已是活跃状态。若标记为 `ok:False`，前端会显示"启动会话失败"提示，但定时器 10 秒后又会把状态同步为"已启动"，造成 UX 矛盾。改为幂等成功后前端根据 `already_active` 字段显示 `info` 提示"会话已是活跃状态"，与实际状态保持一致。

**响应**：`ok` / `message` / `already_active`（仅幂等返回时为 `true`，首次启动时不带此字段）。
**失败响应**：`ok=false` / `error="启动会话失败: {e}"`。

#### POST /session/stop
停止会话管理。

**响应**：`ok=true` / `message="会话管理已停止"`。
**未启动响应**：`ok=false` / `error="会话未启动"`。
**失败响应**：`ok=false` / `error="停止会话失败: {e}"`。

### 5.4 健康检查

#### GET /health
执行健康检查，返回 HealthReport。

**响应**：`ok` / `score`（0-100） / `cookie_valid` / `api_reachable` / `page_accessible` / `waf_status` / `action` / `details` / `is_healthy` / `needs_attention`。

**未配置检查器响应**：`ok=false` / `error="未配置健康检查器，请先调用 POST /api/anticrawl/initialize"` / `hint="initialize 会自动配置默认的 cookie 和 waf 检查器"`。前端 `handleHealthCheck` 检测到 `error` 包含 `initialize` 时会自动调用 `/initialize` 后重试。

### 5.5 指纹与频率

#### GET /fingerprint
获取当前指纹 profile 信息（不返回 canvas_noise_seed 等敏感种子）。CDP 模式返回空 profile。

**响应**：`ok` / `mode`（`launch`/`cdp`）/ `profile`（name/ua/platform/vendor/hardware_concurrency/device_memory/gpu_vendor/gpu_renderer/screen_width/screen_height/color_depth/pixel_ratio/languages）/ `stealth_scripts_count` / `message`（CDP 模式下「CDP 模式，无需指纹注入」）。

#### GET /freq/stats
获取频率伪装统计。

**响应**：`ok` / `total_requests` / `noise_requests` / `noise_ratio` / `mean_interval` / `median_interval` / `std_interval` / `history_size`。无历史数据时间隔字段返回 `0.0`。

#### GET /freq/delay
获取指定操作的请求延迟（秒）。

**Query 参数**：`action=browse|search|scroll|detail|login`

**响应**：`ok` / `action` / `delay_sec`。

**错误响应**：`ok=false` / `error="无效的操作类型: {action}"` / `valid_actions=["browse","search","scroll","detail","login"]`。

### 5.6 Cookie 分层管理

#### GET /cookies/current
读取当前 CookieStore JSON 中的全部 Cookie（供更新弹窗自动预填）。

**响应**：`ok` / `cookies`（`{name: value}` 字典）/ `count`。

#### POST /cookies/import-from-browser/preview
从系统已登录浏览器（Edge/Chrome）读取 Cookie，仅返回不写入。

**请求体**：`{"browser": "edge", "auto_close": false}`

**响应**：`ok` / `cookies`（`{name: value}` 字典）/ `imported_count` / `dry_run=true` / `message`。
**失败响应**：`ok=false` / `error` / `hint` / `error_detail`（控制台调试用）/ `errors[]`（单条 cookie 解密失败列表）。

与 `/api/auth/import-from-browser` 的区别：那个端点读取后立即 `export_cookies` 写入 CookieStore 覆盖现有登录态；本接口仅返回 cookie 字典供前端预填文本框，由用户确认后调 `/cookies/update` 才会真正分层写入。

#### POST /cookies/update
分层更新 Cookie（合并写入，不丢失已有 Cookie）。

**请求体**：`{"cookies": {"unb": "123", "_m_h5_tk": "tk_123", ...}}`

**响应**：`ok` / `written`（实际写入 JSON 的 cookie 数量，可能因测试数据过滤少于传入）/ `worker_injected`（是否同步注入到 Worker 浏览器）/ `message`。

#### GET /cookies/layers
获取 Cookie 各层状态，含三重兜底同步逻辑。

**响应**：`ok` / `layers`（identity/session/tracking，每层 valid/updated_at/cookie_count）。

#### POST /cookies/invalidate
使指定 Cookie 层失效。identity 层失效会级联导致 session 层失效。

**请求体**：`{"layer": "session"}`

**响应**：`ok` / `message` / `cascaded`（仅当 layer=identity 时为 `true`，标记触发了 session 级联失效）。
**错误响应**：`ok=false` / `error="无效的层名: {layer_name}"` / `valid_layers=["identity","session","tracking"]`。

## 6. 数据结构

### 6.1 Cookie 三层定义（LAYER_DEFINITIONS）

| 层        | 中文名   | 包含 Cookie                                  | TTL        | 依赖        |
| --------- | -------- | -------------------------------------------- | ---------- | ----------- |
| `identity`| 身份层   | `unb`/`cookie2`/`sgcookie`/`t`/`_tb_token_`/`lg2` | session    | 无          |
| `session` | 会话层   | `_m_h5_tk`/`_m_h5_tk_enc`                    | 15-22min   | identity    |
| `tracking`| 追踪层   | `cna`/`tfstk`/`xlly_s`/`ali_aplus_v3`/`utdid` | dynamic    | 无          |

**原子更新规则**：
1. 同一层的 Cookie 必须同时写入，不允许中间状态；
2. 更新 session 层时必须验证 identity 层是否有效；
3. identity 层失效时，session 层自动失效。

### 6.2 LayerState（层状态）

```python
@dataclass
class LayerState:
    valid: bool = False
    updated_at: float = 0.0
    cookie_count: int = 0
    manual_invalidate: bool = False  # 用户主动失效，自动同步应跳过此层
```

`manual_invalidate` 字段语义：
- `True`：用户通过 `/cookies/invalidate` 主动失效，自动同步应跳过此层；
- `False`：系统失效（RGV587/续期失败等）或从未失效，自动同步可恢复。

### 6.3 SessionStatus（会话状态摘要）

```python

class SessionStatus:
    active: bool = False
    strategy: str = ""
    fingerprint_profile: str = ""

    health_action: str = ""
    waf_status: str = ""
    cookie_layers: dict[str, bool] = field(default_factory=dict)
    freq_stats: dict[str, Any] = field(default_factory=dict)
    captcha_stats: dict[str, int] = field(default_factory=dict)
```

## 7. 业务逻辑

### 7.1 CookieRotator 分层管理

`CookieRotator` 类（`modules/cookie_rotator.py`）核心方法：

| 方法                          | 说明                                                          |
| ----------------------------- | ------------------------------------------------------------- |
| `atomic_update(cookies)`      | 原子更新某层 Cookie，自动识别层并校验依赖                     |
| `invalidate_layer(layer, manual)` | 失效指定层，identity 失效级联 session                     |
| `invalidate_all()`            | 失效所有层                                                    |
| `sync_state_from_cookies(map)`| 根据 cookie 字典同步所有层状态                                |
| `is_layer_valid(layer)`       | 检查层是否有效                                                |
| `force_restore_layers(layers, reason)` | 强制恢复指定层（功能可用性兜底用）                  |
| `get_layer_state(layer)`      | 获取单层状态                                                  |
| `get_all_states()`            | 获取所有层状态                                                |

### 7.2 健康检查权重

`SessionHealthChecker` 各维度权重（总和=100）：cookie=40 / api=30 / page=20 / waf=10。`/api/anticrawl/initialize` 默认仅配置 `cookie_checker` 与 `waf_provider`，未配置的 api/page 维度默认通过（即默认满分为 40+20+10=70，cookie 失效时直接掉到 30 以下触发 RELOGIN/PAUSE）。

| 检查器           | 权重 | 检查内容                                                     |
| ---------------- | ---- | ------------------------------------------------------------ |
| `cookie_checker` | 40   | _m_h5_tk 存在/有值/未过期 + identity 层至少一个 + 关键 cookie expires 未过期 + 自动同步层状态 + collector.last_session_invalid 粘性标志处理 |
| `waf_provider`   | 10   | 验证码处理统计：`fail_rate > 0.5` → BLOCKED；`> 0.2` → WARNING；否则 CLEAR |

**Cookie 检查器逻辑**（在 `_configure_default_health_checkers` 中定义，主流程拆分为 5 个辅助函数）：
1. **`_load_and_check_session_layer`**：`invalidate_cache` 后读 JSON；若无数据转 `_browser_cookies_fallback`。检查 `_m_h5_tk` 存在、有值、未过期（`is_m5tk_expired` 检查内嵌 timestamp）。JSON 中过期/缺失时调用 `_try_refresh_m5tk_from_browser` 从浏览器内存读取并回写 JSON 后重试；仍不可信则转浏览器内存兜底。
2. **`_check_identity_layer`**：identity 层至少一个 Cookie 存在（不同登录方式返回的 Cookie 集合不同，强制要求全部会导致误判）。JSON 缺失时同样转 `_browser_cookies_fallback`。
3. **`_check_key_cookies_expiry`**：仅检查 identity + session 层关键 cookie 的 `expires` 字段。为什么不再检查所有 cookie：tracking 层 cookie（cna/tfstk 等）过期不影响实时搜索，但会导致健康检查误判。无 expires 字段视为 session cookie。
4. **`_sync_layer_states_if_needed`**：identity 层 `valid=False 且 manual_invalidate=False` 时，重新构造 cookie_map 调用 `sync_state_from_cookies` 同步层状态。被系统失效的层（RGV587/续期失败）`updated_at>0` 但 `valid=False`，需能被自动同步恢复。
5. **`_check_collector_session`**：检查 `collector.last_session_invalid` 标志（RGV587_ERROR 表示服务端已注销会话）。
   - 标志为 True 且 `_m_h5_tk` 存在有值（不检查 timestamp 过期，语义与 session 层不同）：清除粘性标志，避免反复触发 invalidate；
   - 标志为 True 且 token 不存在：主动失效 identity 层（`manual=False`，可被自动同步恢复），返回 False。

**`_browser_cookies_fallback` 浏览器内存兜底复核**：JSON 判定无效时从浏览器内存读取 cookie 复核，判定标准与实时搜索 `_ensure_live_search_cookies` 对齐：`_m_h5_tk` 有效 + identity 层至少一个 + 关键 cookie expires 未过期 + 粘性标志清理。

### 7.3 WAF 状态推断

```python
def waf_provider() -> WAFStatus:
    stats = orch.captcha_handler.get_stats()
    failed = stats.get("failed", 0)
    total = stats.get("total_detected", 0)
    if total == 0:
        return WAFStatus.CLEAR
    fail_rate = failed / total
    if fail_rate > 0.5:
        return WAFStatus.BLOCKED
    if fail_rate > 0.2:
        return WAFStatus.WARNING
    return WAFStatus.CLEAR
```

### 7.4 LoginOrchestrator 单例

`get_orchestrator()` 返回单例，串联所有反爬模块：

```python
class LoginOrchestrator:
    def __init__(self):
        self._strategy_selector = LoginStrategySelector()
        self._fingerprint_profile: FingerprintProfile | None = None
        self._cookie_rotator = CookieRotator()
        self._token_renewer = TokenRenewer()
        self._health_checker = SessionHealthChecker()
        self._freq_disguiser = FreqDisguise()
        self._captcha_handler = CaptchaHandler()
        # 自愈状态
        self._renew_fail_count = 0
        self._auto_relogin_callback: Callable[[], Awaitable[bool]] | None = None
        self._auto_relogin_cooldown_until = 0.0

    # 阈值常量
    _RENEW_FAIL_THRESHOLD = 2          # 连续失败 2 次触发自动重登
    _AUTO_RELOGIN_COOLDOWN_SEC = 600   # 重登冷却 10 分钟
```

**launch 模式**：生成随机 FingerprintProfile + `build_stealth_script()` 注入；BrowserManager 启动时自动读取该 profile 注入一致的 stealth 脚本和 UA。`get_stealth_scripts()` 在 launch 模式下返回 `[fingerprint_stealth, awsc_spoof]` 两条脚本（`is_awsc_spoof_needed` 判定后追加），CDP 模式返回空列表。

**CDP 模式**：连接真实浏览器，无需指纹注入。

**start_session(cookie_provider, renew_callback)**：
- `cookie_provider`：闭包，每次调用读取最新 token 值（token 会随续期更新）；
- `renew_callback`：通过浏览器导航到 `https://h5.m.taobao.com/` 触发 token 刷新（导航是用户自然行为，风控压力低于直接调用 getTimestamp API）；
- 启动后 TokenRenewer 定期检查 token 年龄，过期前自动续期；
- 同时注册 `_on_renew_fail` 作为续期失败回调，触发自愈流程。

**默认会话启动（登录后自动调用）**：
- `start_session_default()`：使用 `_default_cookie_provider` + `_default_renew_callback` 启动会话；
- `_default_cookie_provider`：从 CookieStore 读取 `_m_h5_tk`，跳过已过期的 token（`is_m5tk_expired`）；
- `_default_renew_callback`：导航到 `https://h5.m.taobao.com/`，成功后读取浏览器 `goofish.com`/`taobao.com` 域完整 Cookie 回写 CookieStore，保证 JSON 与浏览器内存一致；
- 失败仅记录日志，不抛异常（避免影响登录成功的返回路径）。

**续期失败自愈机制（`_on_renew_fail`）**：

```
1. _invalidate_session_layer_after_renew_fail
   - 调用 cookie_rotator.invalidate_layer(SESSION, manual=False)
     （manual=False 让 /cookies/layers 自动同步可恢复该层）
   - _renew_fail_count += 1

2. _try_recover_session_from_json
   - 调用 sync_cookie_layers_from_json() 重新读取 JSON 同步层状态
   - 成功则 _renew_fail_count = 0，不再触发自动重登
   - 为什么先尝试同步：浏览器登录子进程可能已刷新 cookie 但主进程缓存未更新，
     重新读 JSON 有机会恢复，成本远低于重新登录

3. _maybe_trigger_auto_relogin（连续失败 ≥ 2 次 + 冷却期已过）
   - 设置 _auto_relogin_cooldown_until = now + 600s
   - 通过 asyncio.get_event_loop().create_task 调度 _do_auto_relogin
   - _do_auto_relogin 调用 _auto_relogin_callback（外部注入的 browser_login 等异步重登流程）
   - 成功则 _renew_fail_count = 0；失败则等待下次重试
   - 无事件循环或未配置回调时降级为日志告警
```

**`sync_cookie_layers_from_json()`**：在所有登录路径成功写入 JSON 后调用的统一补救入口，替代 `on_login_success` 的职责。重新读 JSON 构造 cookie_map（过滤 expires 过期 + `_m_h5_tk` 内嵌 timestamp 过期），调用 `cookie_rotator.sync_state_from_cookies` 同步层状态。

### 7.5 /cookies/update 分层更新逻辑

```
1. 读取现有 JSON 全量 Cookie
   - 必须先 invalidate_cache：浏览器登录子进程写入 JSON 后只更新子进程自己的缓存，
     主进程 30 秒 TTL 缓存仍是旧数据
2. 合并传入值（覆盖同名 value，新增的用默认元信息：domain=.goofish.com / path=/ / expires=-1）
3. 一次性写入合并后的完整列表（export_cookies 内部会过滤测试数据）
4. 重新读 JSON 同步层状态
   - 为什么不用 merged_list：export_cookies 内部会过滤测试数据，
     用 merged_list 构造 cookie_map 会包含被过滤的测试数据
5. sync_state_from_cookies(cookie_map) 同步所有层状态
6. inject_cookie_store_to_worker_browser("Cookie 分层更新") 注入 Worker 浏览器
   - 失败仅 debug 日志，不影响主流程（已写入 JSON + 同步层状态）
   - 返回 worker_injected 字段告知前端是否同步成功
```

### 7.6 /cookies/layers 三重兜底同步

```
第一步：_sync_layers_from_json（对所有非用户主动失效的层）
   - 排除 manual_invalidate=True 的层（用户主动失效不应被自动同步覆盖）
   - store.invalidate_cache() 后读取 JSON
   - _filter_valid_cookies_for_sync 过滤：
     * 必须有 name 和 value
     * name 必须在该层 needed_names 中
     * expires 未过期（session cookie 不过滤）
     * _m_h5_tk 检查内嵌 timestamp 是否过期（is_m5tk_expired，TTL=1200s）
   - sync_state_from_cookies(cookie_map)

第二步：_sync_layers_from_browser（前一步后仍有非 manual 失效层时）
   - 从浏览器内存读取 goofish.com / taobao.com 域 cookie
   - 用同一份 _filter_valid_cookies_for_sync 过滤规则构造 cookie_map
   - sync_state_from_cookies 同步层状态
   - _write_browser_cookies_to_json 回写浏览器内存中的关键 cookie 到 JSON
     （用 upsert_cookie_values，含 value/domain/path/expires）
   - 为什么需要：JSON 可能缺少 MTOP token（_m_h5_tk）或部分 identity cookie，
     但浏览器内存中有（功能正常）

第三步：_functional_fallback_restore（前两步后仍有非 manual 失效层时）
   - 收集功能可用信号（任一为真即认为功能正常）：
     * 信号1 _collect_collector_signal：collector._last_m5tk_refresh>0
       且 last_session_invalid=False（实际搜索成功，可恢复所有层）
     * 信号2 _collect_json_m5tk_signal：JSON 中存在未过期的 _m_h5_tk
       （只能证明 session 有效，且需 IDENTITY 已有效）
   - _compute_layers_to_restore 根据信号组合计算可恢复的层集合：
     * collector 信号：恢复所有 still_invalid 层
     * m5tk 信号 + IDENTITY 已有效：仅恢复 SESSION 层
     * m5tk 信号 + IDENTITY 无效：返回空集（依赖关系不允许恢复）
   - cookie_rotator.force_restore_layers 执行恢复
     （force_restore_layers 内部会再次校验依赖层有效性，避免无效恢复）
```

| ----------------------------------- | ----------------------------------------------------- |
| `has_valid_cookies()`               | 验证 Cookie 是否存在                                  |

1. 黑名单匹配：拦截测试用例的已知默认值（`unb=123456` 等）；
2. 格式校验：对有关键格式特征的 Cookie 名称校验值是否符合真实格式（如 `_m_h5_tk` 必须是 `32位hex_13位时间戳` 格式）。

### 7.9 安全机制

1. **测试数据过滤**：`is_test_cookie` 拦截测试用例默认值与不符合格式的值，防止污染 JSON 存储；
2. **invalidate_cache 必须先调用**：浏览器登录子进程写入 JSON 后只更新子进程自己的缓存，主进程 30 秒 TTL 缓存仍是旧数据；
3. **manual_invalidate 字段保护**：用户主动失效的层不被自动同步覆盖；
4. **层依赖校验**：更新 session 层时必须验证 identity 层是否有效；
5. **续期回调用导航而非 API**：导航是用户自然行为，风控压力低于直接调用 getTimestamp API；
6. **浏览器 Cookie 解密在本地完成**：DPAPI/AES-GCM 解密不传输到外部；
7. **敏感种子不返回**：`/fingerprint` 接口不返回 `canvas_noise_seed` 等敏感种子；
8. **续期回调 Cookie 回写闭环**：`_default_renew_callback` 导航成功后读取浏览器 `goofish.com`/`taobao.com` 域完整 Cookie 回写 CookieStore，避免 JSON 落后于浏览器内存导致健康检查误判；
9. **续期失败自愈分级降级**：先标记 session 失效 → JSON 同步恢复（低成本）→ 自动重登（高成本，10 分钟冷却），避免一失败就重登；
10. **m5tk 过期双重判定**：`cookie.expires` 字段（session cookie 为 -1）+ `is_m5tk_expired` 检查 token 内嵌 timestamp（TTL=1200s），二者任一过期都视为失效。

## 9. 常见问题 FAQ

**Q1：launch 模式和 CDP 模式有什么区别？**
A：
- **launch 模式**：系统启动独立的 Playwright 浏览器，生成随机 FingerprintProfile（UA/平台/GPU/屏幕等），通过 stealth 脚本注入伪装指纹。适合无真实浏览器的服务器环境。
- **CDP 模式**：通过 Chrome DevTools Protocol 连接用户已打开的真实浏览器，复用真实指纹，无需注入。适合开发调试或本机已登录闲鱼的场景。

**Q2：Cookie 三层（identity/session/tracking）有什么区别？**
A：
- **identity（身份层）**：最稳定，仅登录时变化。包含 `unb`/`cookie2`/`sgcookie` 等，标识用户身份。
- **session（会话层）**：中等频率更新（15-22 分钟）。包含 `_m_h5_tk`/`_m_h5_tk_enc`，是 API 调用的 token。依赖 identity 层。
- **tracking（追踪层）**：每次请求可能变化。包含 `cna`/`tfstk` 等，用于行为追踪。

**Q3：identity 层失效会怎样？**
A：identity 层失效会级联导致 session 层失效（因为 session 依赖 identity）。可通过 `/cookies/invalidate` 主动失效，或由系统自动失效（RGV587_ERROR）。失效后需重新登录或调用 `/cookies/update` 恢复。

**Q4：为什么 /cookies/update 不直接调用 on_login_success？**
A：`on_login_success` 分 3 次调用 `atomic_update`，每次触发 `export_cookies` 覆盖写 JSON，导致只有最后一层的 Cookie 被保留，且 session 层因 identity 层未更新而抛 `SessionExpiredError`。`/cookies/update` 改为：先读取现有 JSON 全量 Cookie，合并传入值后一次性写入，再用 `sync_state_from_cookies` 同步所有层状态。

**Q5：为什么 /cookies/layers 需要三重兜底同步？**
A：
1. **JSON 同步**：服务重启或协调器初始化后，内存层状态默认全 False，需从 JSON 同步；
2. **浏览器内存兜底**：JSON 可能缺少某些 cookie（如 MTOP token 未回写），但浏览器内存中有（功能正常）；
3. **功能可用性兜底**：JSON 和浏览器都可能未初始化，但实际功能正常（搜索/采集都能用），此时应反映真实可用性而非机械依赖 cookie 检测。

**Q6：从浏览器导入 Cookie 支持哪些加密格式？**
A：支持三种格式：
- **DPAPI**（旧版浏览器，v10 前缀）：Windows 数据保护 API 解密；
- **AES-256-GCM**（Chrome v80+，v10 前缀）：从 Local State 获取 AES 密钥解密；
- **明文**：无加密的 cookie 值直接返回。

**Q7：浏览器 Cookie 数据库被锁定怎么处理？**
A：4 级降级策略：
1. SQLite `immutable=1` + backup（完全绕过文件锁）；
2. SQLite `mode=ro&nolock=1` + backup（兼容旧版 SQLite）；
3. `copy_file_with_share`（robocopy + CreateFileW 共享模式 + WAL/SHM）；
4. 检测到锁定时自动关闭浏览器进程并重试。

**Q8：TokenRenewer 是如何续期的？**
A：通过浏览器导航到 `https://h5.m.taobao.com/` 触发 token 刷新。为什么用导航而非 API：导航是用户自然行为，风控压力低于直接调用 getTimestamp API。续期失败会触发 session 层 Cookie 失效。

**Q9：健康检查的 WAF 状态如何推断？**
A：基于验证码处理统计：`fail_rate = failed / total_detected`。
- `fail_rate > 0.5` → `BLOCKED`（已熔断）；
- `fail_rate > 0.2` → `WARNING`（警告）；
- 否则 → `CLEAR`（正常）。

无验证码检测记录时返回 `CLEAR`。

**Q10：manual_invalidate 字段有什么作用？**
A：标识层是否由用户主动失效（通过 `/cookies/invalidate`）。
- `True`：用户主动失效，自动同步应跳过此层（避免被 /cookies/layers 自动同步覆盖）；
- `False`：系统失效（RGV587/续期失败等）或从未失效，自动同步可恢复。

用户主动失效后通常需重新登录或调用 `/cookies/update` 才能恢复层状态。

**Q11：cookie_checker 为什么检查 collector.last_session_invalid 标志？**
A：cookie 存在不代表服务端仍认可。`RGV587_ERROR` 表示服务端已注销会话，此时 cookie 虽在本地但已失效。检查此标志可识别服务端失效场景。粘性标志清理：`_m_h5_tk` 实际有效时清除 `last_session_invalid` 标志，避免反复触发 invalidate。

**Q12：从浏览器导入和 /cookies/update 的关系是什么？**
A：
- `/cookies/import-from-browser/preview`：仅解密读取浏览器 Cookie，返回字典供前端预填文本框，**不写入** CookieStore；
- 用户在弹窗中确认或修改后调 `/cookies/update`：**才真正分层写入** CookieStore，触发 `sync_state_from_cookies` 同步层状态。

这种分离设计避免导入预览阶段就覆盖现有登录态。

**Q13：为什么 /cookies/current 不直接读 /cookies/layers？**
A：`/cookies/layers` 只返回每层是否有效与数量，不包含 cookie 明文。前端「更新 Cookie」弹窗需要 `name=>value` 字典来预填文本框，所以需要专门的 `/cookies/current` 接口读取明文。

**Q14：会话活跃时为什么每 10 秒刷新状态？**
A：自动更新 token 年龄、健康分、WAF 状态等动态信息。10 秒间隔平衡实时性与服务器压力。非活跃状态下不刷新，减少无效请求。前端还有两个独立定时器：频率统计每 10 秒刷新（业务模块持续调用 apply_freq_delay/record_freq_request），Cookie 层状态每 30 秒轮询（后端会基于 JSON/浏览器内存/功能信号同步层状态）。

**Q15：LoginOrchestrator 的自愈机制如何工作？**
A：TokenRenewer 续期失败时触发 `_on_renew_fail` 三步策略：
1. **标记 session 层失效**：调用 `invalidate_layer(SESSION, manual=False)`，`manual=False` 让 `/cookies/layers` 自动同步可恢复该层；
2. **尝试 JSON 同步恢复**：调用 `sync_cookie_layers_from_json()` 重新读 JSON 同步层状态。成功则重置失败计数。为什么先尝试同步：浏览器登录子进程可能已刷新 cookie 但主进程缓存未更新，成本远低于重新登录；
3. **自动重登**：连续失败 ≥ 2 次（`_RENEW_FAIL_THRESHOLD`）且冷却期已过（`_AUTO_RELOGIN_COOLDOWN_SEC=600s`）时，通过事件循环调度 `_do_auto_relogin` 调用外部注入的 `_auto_relogin_callback`（如 browser_login）。无事件循环或未配置回调时降级为日志告警。

**Q16：默认 cookie_provider 和 renew_callback 是什么？**
A：登录成功后通过 `start_session_default()` 自动启动会话，使用协调器内置的默认实现：
- `_default_cookie_provider`：从 CookieStore 读取 `_m_h5_tk`，跳过已过期的 token（`is_m5tk_expired` 检查内嵌 timestamp）；
- `_default_renew_callback`：导航到 `https://h5.m.taobao.com/` 触发 token 续期。导航成功后读取浏览器 `goofish.com`/`taobao.com` 域完整 Cookie 回写 CookieStore（`export_cookies(method="renew")`），保证 JSON 与浏览器内存一致。回写失败不影响续期成功状态（token 已在浏览器内存中刷新）。

**Q17：健康检查未配置检查器时会发生什么？**
A：`/api/anticrawl/health` 返回 `ok=false` + `error="未配置健康检查器，请先调用 POST /api/anticrawl/initialize"` + `hint`。前端 `handleHealthCheck` 检测到 `error` 包含 `initialize` 时会自动调用 `/initialize`（按当前 useCdp 模式）后重新执行健康检查。`initialize` 端点会调用 `_configure_default_health_checkers` 自动配置 cookie + waf 两个检查器，无需前端额外调用 configure 端点。

**Q18：/cookies/layers 三重兜底同步中 _filter_valid_cookies_for_sync 起什么作用？**
A：JSON 同步（第一步）和浏览器内存兜底（第二步）共用此过滤函数，避免规则漂移。过滤规则：
- 必须有 name 和 value；
- name 必须在该层 `needed_names` 中；
- `expires` 未过期（`expires>0 且 <now` 视为过期，session cookie 不过滤）；
- `_m_h5_tk` 检查内嵌 timestamp 是否过期（`is_m5tk_expired`，TTL=1200s）。`_m_h5_tk` 的 cookie.expires 通常是 -1 无法判断真实过期，但 token 内嵌 timestamp + 服务端 TTL 决定真实有效期。
