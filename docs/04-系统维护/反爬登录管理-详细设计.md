## 2. 功能概述

**一句话说明**：暴露 LoginOrchestrator 能力给前端，提供登录策略评估、会话管理、健康检查、Cookie 分层管理、指纹信息、频率伪装统计六大模块。

**核心价值**：
- 所有端点通过 `LoginOrchestrator` 单例（`get_orchestrator()`）操作，保证状态一致；
- 写操作（initialize/start/stop/update）用 POST，读操作用 GET，异步操作（start/stop/health）使用 async 路由；
- Cookie 三层管理（identity/session/tracking），原子更新 + 依赖校验，identity 失效级联导致 session 失效；
- 健康检查权重：Cookie 检查器（40）+ WAF 状态提供器（10），score 0-100；
- WAF 状态：`fail_rate > 0.5` → BLOCKED，`> 0.2` → WARNING，否则 CLEAR；
- launch 模式生成随机 FingerprintProfile + stealth 脚本注入；CDP 模式连接真实浏览器无需指纹；
- TokenRenewer 后台续期，过期前通过浏览器导航触发刷新（导航是用户自然行为，风控压力低于直接调用 API）；
- Cookie 三重兜底同步：JSON 同步 → 浏览器内存兜底 → 功能可用性兜底；
- 浏览器 Cookie 导入支持 DPAPI / AES-256-GCM / 明文三种格式解密。

## 3. 用户场景

**场景 1：首次登录配置**
用户首次部署系统，进入「反爬登录管理」页面。先在「登录策略评估」卡片看到推荐策略（如 `cdp_connect`），点击「初始化协调器」按钮选择 launch 或 CDP 模式。初始化后点击「启动会话」开启 TokenRenewer 后台续期，10 秒间隔自动刷新会话状态。

**场景 2：Cookie 失效恢复**
系统运行一段时间后，`/cookies/layers` 显示 session 层失效。用户点击「更新 Cookie」按钮，弹窗自动预填当前 CookieStore 中的 cookie 明文（调用 `/cookies/current`）。用户修改 `_m_h5_tk` 等字段后提交，后端分层合并写入并同步所有层状态。

**场景 3：从系统浏览器导入 Cookie**
用户已在 Edge 浏览器登录闲鱼，希望在系统中复用登录态。点击「从浏览器导入」按钮选择 `edge`，后端通过 `import-from-browser/preview` 接口解密浏览器 Cookie 数据库（DPAPI/AES-256-GCM），仅返回预览不写入。用户确认后调 `/cookies/update` 才会真正分层写入。

## 5. 接口定义

所有接口前缀：`/api/anticrawl`，路由文件：`src/xianyu_hunter/web/routes/api_anticrawl.py`。

### 5.1 策略评估

#### GET /strategy
评估当前环境并推荐最优登录策略。

**响应**：`ok` / `recommended` / `reason` / `available_strategies[]` / `details`。

#### POST /strategy/set
设置当前使用的登录策略。

**请求体**：`{"strategy": "cdp_connect"}`

### 5.2 协调器初始化

#### POST /initialize
初始化 LoginOrchestrator。

**请求体**：`{"use_cdp": false}`

**响应**：`ok` / `mode`（`launch`/`cdp`）/ `fingerprint_profile` / `user_agent` / `stealth_scripts_count` / `message`。

launch 模式生成随机 FingerprintProfile，BrowserManager 启动时自动读取该 profile 注入一致的 stealth 脚本和 UA；CDP 模式连接真实浏览器，无需指纹注入。

### 5.3 会话管理

#### GET /session/status
获取会话状态摘要（SessionStatus）。

**响应字段**：

| 字段                  | 类型    | 说明                                          |
| --------------------- | ------- | --------------------------------------------- |
| `active`              | bool    | 会话是否活跃                                  |
| `strategy`            | string  | 当前登录策略                                  |
| `fingerprint_profile` | string  | 指纹 profile 名称                             |
| `token_age_sec`       | float   | Token 年龄（秒）                              |
| `token_expired`       | bool    | Token 是否过期                                |
| `health_score`        | int     | 健康分（0-100）                               |
| `health_action`       | string  | 建议动作（none/renew_token/relogin/pause）    |
| `waf_status`          | string  | 风控状态（clear/warning/blocked）             |
| `cookie_layers`       | object  | 各 Cookie 层有效性                            |
| `freq_stats`          | object  | 频率伪装统计                                  |
| `captcha_stats`       | object  | 验证码统计                                    |
| `uptime_sec`          | float   | 会话已运行时间（秒）                          |

#### POST /session/start
启动会话管理（TokenRenewer 后台续期）。

**请求体**（可选）：`{"cookie_provider_name": "_m_h5_tk"}`

启动后 TokenRenewer 定期检查 token 年龄，过期前自动续期。续期失败触发 session 层 Cookie 失效。

#### POST /session/stop
停止会话管理。

### 5.4 健康检查

#### GET /health
执行健康检查，返回 HealthReport。

**响应**：`ok` / `score`（0-100） / `cookie_valid` / `api_reachable` / `page_accessible` / `waf_status` / `action` / `details` / `is_healthy` / `needs_attention`。

### 5.5 指纹与频率

#### GET /fingerprint
获取当前指纹 profile 信息（不返回 canvas_noise_seed 等敏感种子）。CDP 模式返回空 profile。

**响应**：`ok` / `mode` / `profile`（name/ua/platform/vendor/hardware_concurrency/device_memory/gpu_vendor/gpu_renderer/screen_width/screen_height/color_depth/pixel_ratio/languages）/ `stealth_scripts_count`。

#### GET /freq/stats
获取频率伪装统计。

**响应**：`ok` / `total_requests` / `noise_requests` / `noise_ratio` / `mean_interval` / `median_interval` / `std_interval`。

#### GET /freq/delay
获取指定操作的请求延迟（秒）。

**Query 参数**：`action=browse|search|scroll|detail|login`

**响应**：`ok` / `action` / `delay_sec`。

### 5.6 Cookie 分层管理

#### GET /cookies/current
读取当前 CookieStore JSON 中的全部 Cookie（供更新弹窗自动预填）。

**响应**：`ok` / `cookies`（`{name: value}` 字典）/ `count`。

#### POST /cookies/import-from-browser/preview
从系统已登录浏览器（Edge/Chrome）读取 Cookie，仅返回不写入。

**请求体**：`{"browser": "edge", "auto_close": false}`

与 `/api/auth/import-from-browser` 的区别：那个端点读取后立即 `export_cookies` 写入 CookieStore 覆盖现有登录态；本接口仅返回 cookie 字典供前端预填文本框，由用户确认后调 `/cookies/update` 才会真正分层写入。

#### POST /cookies/update
分层更新 Cookie（合并写入，不丢失已有 Cookie）。

**请求体**：`{"cookies": {"unb": "123", "_m_h5_tk": "tk_123", ...}}`

**响应**：`ok` / `written` / `worker_injected` / `message`。

#### GET /cookies/layers
获取 Cookie 各层状态，含三重兜底同步逻辑。

**响应**：`ok` / `layers`（identity/session/tracking，每层 valid/updated_at/cookie_count）。

#### POST /cookies/invalidate
使指定 Cookie 层失效。identity 层失效会级联导致 session 层失效。

**请求体**：`{"layer": "session"}`

## 6. 数据结构

### 6.1 Cookie 三层定义（LAYER_DEFINITIONS）

| 层        | 中文名   | 包含 Cookie                                  | TTL        | 依赖        |
| --------- | -------- | -------------------------------------------- | ---------- | ----------- |
| `identity`| 身份层   | `unb`/`cookie2`/`sgcookie`/`t`/`_tb_token_`/`lg2` | session    | 无          |
| `session` | 会话层   | `_m_h5_tk`/`_m_h5_tk_enc`                    | 15-22min   | identity    |
| `tracking`| 追踪层   | `cna`/`tfstk`/`xlly_s`/`ali_aplus_v3`/`utdid` | dynamic    | 无          |

**原子更新规则**：
1. 同一层的 Cookie 必须同时写入，不允许中间状态；
2. 更新 session 层时必须验证 identity 层是否有效；
3. identity 层失效时，session 层自动失效。

### 6.2 LayerState（层状态）

```python
@dataclass
class LayerState:
    valid: bool = False
    updated_at: float = 0.0
    cookie_count: int = 0
    manual_invalidate: bool = False  # 用户主动失效，自动同步应跳过此层
```

`manual_invalidate` 字段语义：
- `True`：用户通过 `/cookies/invalidate` 主动失效，自动同步应跳过此层；
- `False`：系统失效（RGV587/续期失败等）或从未失效，自动同步可恢复。

### 6.3 SessionStatus（会话状态摘要）

```python
@dataclass
class SessionStatus:

    captcha_stats: dict[str, int] = field(default_factory=dict)
    started_at: float = 0.0
```

## 7. 业务逻辑

### 7.1 CookieRotator 分层管理

`CookieRotator` 类（`modules/cookie_rotator.py`）核心方法：

| 方法                          | 说明                                                          |
| ----------------------------- | ------------------------------------------------------------- |
| `atomic_update(cookies)`      | 原子更新某层 Cookie，自动识别层并校验依赖                     |
| `invalidate_layer(layer, manual)` | 失效指定层，identity 失效级联 session                     |
| `invalidate_all()`            | 失效所有层                                                    |
| `sync_state_from_cookies(map)`| 根据 cookie 字典同步所有层状态                                |
| `is_layer_valid(layer)`       | 检查层是否有效                                                |
| `force_restore_layers(layers, reason)` | 强制恢复指定层（功能可用性兜底用）                  |
| `get_layer_state(layer)`      | 获取单层状态                                                  |
| `get_all_states()`            | 获取所有层状态                                                |
| `classify_cookie(name)`       | 分类 cookie 到对应层                                          |

### 7.2 健康检查权重

`SessionHealthChecker` 配置两个检查器：

| 检查器           | 权重 | 检查内容                                                     |
| ---------------- | ---- | ------------------------------------------------------------ |
| `cookie_checker` | 40   | _m_h5_tk 存在 + identity 层至少一个 + 过期检查 + 自动同步层状态 + collector.last_session_invalid 标志 |
| `waf_provider`   | 10   | 验证码处理统计：`fail_rate > 0.5` → BLOCKED；`> 0.2` → WARNING；否则 CLEAR |

**Cookie 检查器逻辑**（在 `_configure_default_health_checkers` 中定义）：
1. 读取 CookieStore JSON（必须 `invalidate_cache` 清缓存）；
2. 检查 `_m_h5_tk` 存在且有值；
3. 检查 identity 层至少一个 Cookie 存在（不同登录方式返回的 Cookie 集合不同，强制要求全部会导致误判）；
4. 过期检查（无 expires 字段视为 session cookie）；
5. 自动同步层状态（对所有非用户主动失效的层）；
6. 检查 `collector.last_session_invalid` 标志（RGV587_ERROR 表示服务端已注销会话）；
7. 粘性标志清理：`_m_h5_tk` 实际有效时清除 `last_session_invalid` 标志，避免反复触发 invalidate。

### 7.3 WAF 状态推断

```python
def waf_provider() -> WAFStatus:
    stats = orch.captcha_handler.get_stats()
    failed = stats.get("failed", 0)
    total = stats.get("total_detected", 0)
    if total == 0:
        return WAFStatus.CLEAR
    fail_rate = failed / total
    if fail_rate > 0.5:
        return WAFStatus.BLOCKED
    if fail_rate > 0.2:
        return WAFStatus.WARNING
    return WAFStatus.CLEAR
```

### 7.4 LoginOrchestrator 单例

`get_orchestrator()` 返回单例，串联所有反爬模块：

```python
class LoginOrchestrator:
    def __init__(self):
        self._strategy_selector = LoginStrategySelector()
        self._fingerprint_profile: FingerprintProfile | None = None
        self._cookie_rotator = CookieRotator()
        self._token_renewer = TokenRenewer()
        self._health_checker = SessionHealthChecker()
        self._freq_disguiser = FreqDisguise()
        self._captcha_handler = CaptchaHandler()
```

**launch 模式**：生成随机 FingerprintProfile + `build_stealth_script()` 注入；BrowserManager 启动时自动读取该 profile 注入一致的 stealth 脚本和 UA。

**CDP 模式**：连接真实浏览器，无需指纹注入。

**start_session(cookie_provider, renew_callback)**：
- `cookie_provider`：闭包，每次调用读取最新 token 值（token 会随续期更新）；
- `renew_callback`：通过浏览器导航到 `https://h5.m.taobao.com/` 触发 token 刷新（导航是用户自然行为，风控压力低于直接调用 getTimestamp API）；
- 启动后 TokenRenewer 定期检查 token 年龄，过期前自动续期。

### 7.5 /cookies/update 分层更新逻辑

```
1. 读取现有 JSON 全量 Cookie
   - 必须先 invalidate_cache：浏览器登录子进程写入 JSON 后只更新子进程自己的缓存，
     主进程 30 秒 TTL 缓存仍是旧数据
2. 合并传入值（覆盖同名 value，新增的用默认元信息）
3. 一次性写入合并后的完整列表（export_cookies 内部会过滤测试数据）
4. 重新读 JSON 同步层状态
   - 为什么不用 merged_list：export_cookies 内部会过滤测试数据，
     用 merged_list 构造 cookie_map 会包含被过滤的测试数据
5. sync_state_from_cookies(cookie_map) 同步所有层状态
6. inject_cookie_store_to_worker_browser 注入 Worker 浏览器
```

### 7.6 /cookies/layers 三重兜底同步

```
第一步：JSON 同步（对所有非用户主动失效的层）
   - 排除 manual_invalidate=True 的层（用户主动失效不应被自动同步覆盖）
   - 读取 JSON，过滤过期 cookie，构造 cookie_map
   - sync_state_from_cookies(cookie_map)

第二步：浏览器内存兜底同步
   - 前一步同步后仍有层失效时，从浏览器内存读取 cookie 作为兜底同步源
   - 为什么需要：JSON 可能缺少 MTOP token（_m_h5_tk）或部分 identity cookie，
     但浏览器内存中有（功能正常）
   - 回写浏览器内存中的关键 cookie 到 JSON，避免下次再兜底

第三步：功能可用性兜底
   - 前两步同步后仍有层失效时，基于实际功能状态恢复
   - 信号1：collector.last_session_invalid=False（实际搜索成功，可恢复所有层）
   - 信号2：json_has_valid_m5tk（_m_h5_tk 属于 SESSION 层，只能证明 session 有效，
     且需 IDENTITY 已有效）
   - 不同信号能恢复的层范围不同（避免用 session 信号恢复 identity 层）
```

### 7.7 浏览器 Cookie 导入解密

`browser_import.py` 中 `_do_import_from_browser(browser, auto_close, dry_run)` 支持 Edge/Chrome 三种加密格式：

| 函数                    | 说明                                                  |
| ----------------------- | ----------------------------------------------------- |
| `decrypt_dpapi(bytes)`  | Windows DPAPI 解密（旧版浏览器，v10 前缀）            |
| `_get_browser_aes_key(user_data_dir)` | 从 Local State 获取 AES 密钥（Chrome v80+）|
| `_decrypt_aes_gcm(key, bytes)` | AES-256-GCM 解密（v10 前缀，Chrome v80+）      |
| `decrypt_cookie_value(enc_val, plain_val, aes_key)` | 根据 prefix 路由到 DPAPI 或 AES-GCM 解密 |

**文件复制策略（4 级降级）**：
1. SQLite `immutable=1` + backup（完全绕过文件锁，最优先尝试）；
2. SQLite `mode=ro&nolock=1` + backup（兼容旧版 SQLite）；
3. `copy_file_with_share`（robocopy + CreateFileW 共享模式 + WAL/SHM）；
4. 检测到锁定时自动关闭浏览器并重试（即使 `auto_close=False` 也尝试一次）。

**目标域名**：`%goofish%` / `%taobao%` / `%alipay%`。

**目标 Cookie 名称**：`_m_h5_tk` / `_m_h5_tk_enc` / `cookie2` / `sgcookie` / `unb` / `lg2` / `tracknick`。

### 7.8 CookieStore 单例

`get_cookie_store()` 返回单例（`web/services/cookie_store.py`），核心方法：

| 方法                                | 说明                                                  |
| ----------------------------------- | ----------------------------------------------------- |
| `has_valid_cookies()`               | 验证 Cookie 是否存在                                  |
| `validate_cookies_with_expiry()`    | 验证 Cookie 有效性 + 过期检查                         |
| `export_cookies(cookies, method)`   | 写入 JSON + 同步 SQLite（过滤测试数据）              |
| `sync_to_sqlite(cookies)`           | 同步到 browser-data SQLite                           |
| `update_cookie_values(updates)`     | 按 name 更新 value（保留其他元信息）                 |
| `upsert_cookie_values(upserts)`     | 按 name upsert（含 value/domain/path/expires）       |
| `invalidate_cache()`                | 清除 30 秒 TTL 缓存                                   |

**测试数据过滤**：`is_test_cookie(name, value)` 两层过滤：
1. 黑名单匹配：拦截测试用例的已知默认值（`unb=123456` 等）；
2. 格式校验：对有关键格式特征的 Cookie 名称校验值是否符合真实格式（如 `_m_h5_tk` 必须是 `32位hex_13位时间戳` 格式）。

### 7.9 安全机制

1. **测试数据过滤**：`is_test_cookie` 拦截测试用例默认值与不符合格式的值，防止污染 JSON 存储；
2. **invalidate_cache 必须先调用**：浏览器登录子进程写入 JSON 后只更新子进程自己的缓存，主进程 30 秒 TTL 缓存仍是旧数据；
3. **manual_invalidate 字段保护**：用户主动失效的层不被自动同步覆盖；
4. **层依赖校验**：更新 session 层时必须验证 identity 层是否有效；
5. **续期回调用导航而非 API**：导航是用户自然行为，风控压力低于直接调用 getTimestamp API；
6. **浏览器 Cookie 解密在本地完成**：DPAPI/AES-GCM 解密不传输到外部；
7. **敏感种子不返回**：`/fingerprint` 接口不返回 `canvas_noise_seed` 等敏感种子。

## 9. 常见问题 FAQ

**Q1：launch 模式和 CDP 模式有什么区别？**
A：
- **launch 模式**：系统启动独立的 Playwright 浏览器，生成随机 FingerprintProfile（UA/平台/GPU/屏幕等），通过 stealth 脚本注入伪装指纹。适合无真实浏览器的服务器环境。
- **CDP 模式**：通过 Chrome DevTools Protocol 连接用户已打开的真实浏览器，复用真实指纹，无需注入。适合开发调试或本机已登录闲鱼的场景。

**Q2：Cookie 三层（identity/session/tracking）有什么区别？**
A：
- **identity（身份层）**：最稳定，仅登录时变化。包含 `unb`/`cookie2`/`sgcookie` 等，标识用户身份。
- **session（会话层）**：中等频率更新（15-22 分钟）。包含 `_m_h5_tk`/`_m_h5_tk_enc`，是 API 调用的 token。依赖 identity 层。
- **tracking（追踪层）**：每次请求可能变化。包含 `cna`/`tfstk` 等，用于行为追踪。

**Q3：identity 层失效会怎样？**
A：identity 层失效会级联导致 session 层失效（因为 session 依赖 identity）。可通过 `/cookies/invalidate` 主动失效，或由系统自动失效（RGV587_ERROR）。失效后需重新登录或调用 `/cookies/update` 恢复。

**Q4：为什么 /cookies/update 不直接调用 on_login_success？**
A：`on_login_success` 分 3 次调用 `atomic_update`，每次触发 `export_cookies` 覆盖写 JSON，导致只有最后一层的 Cookie 被保留，且 session 层因 identity 层未更新而抛 `SessionExpiredError`。`/cookies/update` 改为：先读取现有 JSON 全量 Cookie，合并传入值后一次性写入，再用 `sync_state_from_cookies` 同步所有层状态。

**Q5：为什么 /cookies/layers 需要三重兜底同步？**
A：
1. **JSON 同步**：服务重启或协调器初始化后，内存层状态默认全 False，需从 JSON 同步；
2. **浏览器内存兜底**：JSON 可能缺少某些 cookie（如 MTOP token 未回写），但浏览器内存中有（功能正常）；
3. **功能可用性兜底**：JSON 和浏览器都可能未初始化，但实际功能正常（搜索/采集都能用），此时应反映真实可用性而非机械依赖 cookie 检测。

**Q6：从浏览器导入 Cookie 支持哪些加密格式？**
A：支持三种格式：
- **DPAPI**（旧版浏览器，v10 前缀）：Windows 数据保护 API 解密；
- **AES-256-GCM**（Chrome v80+，v10 前缀）：从 Local State 获取 AES 密钥解密；
- **明文**：无加密的 cookie 值直接返回。

**Q7：浏览器 Cookie 数据库被锁定怎么处理？**
A：4 级降级策略：
1. SQLite `immutable=1` + backup（完全绕过文件锁）；
2. SQLite `mode=ro&nolock=1` + backup（兼容旧版 SQLite）；
3. `copy_file_with_share`（robocopy + CreateFileW 共享模式 + WAL/SHM）；
4. 检测到锁定时自动关闭浏览器进程并重试。

**Q8：TokenRenewer 是如何续期的？**
A：通过浏览器导航到 `https://h5.m.taobao.com/` 触发 token 刷新。为什么用导航而非 API：导航是用户自然行为，风控压力低于直接调用 getTimestamp API。续期失败会触发 session 层 Cookie 失效。

**Q9：健康检查的 WAF 状态如何推断？**
A：基于验证码处理统计：`fail_rate = failed / total_detected`。
- `fail_rate > 0.5` → `BLOCKED`（已熔断）；
- `fail_rate > 0.2` → `WARNING`（警告）；
- 否则 → `CLEAR`（正常）。

无验证码检测记录时返回 `CLEAR`。

**Q10：manual_invalidate 字段有什么作用？**
A：标识层是否由用户主动失效（通过 `/cookies/invalidate`）。
- `True`：用户主动失效，自动同步应跳过此层（避免被 /cookies/layers 自动同步覆盖）；
- `False`：系统失效（RGV587/续期失败等）或从未失效，自动同步可恢复。

用户主动失效后通常需重新登录或调用 `/cookies/update` 才能恢复层状态。

**Q11：cookie_checker 为什么检查 collector.last_session_invalid 标志？**
A：cookie 存在不代表服务端仍认可。`RGV587_ERROR` 表示服务端已注销会话，此时 cookie 虽在本地但已失效。检查此标志可识别服务端失效场景。粘性标志清理：`_m_h5_tk` 实际有效时清除 `last_session_invalid` 标志，避免反复触发 invalidate。

**Q12：从浏览器导入和 /cookies/update 的关系是什么？**
A：
- `/cookies/import-from-browser/preview`：仅解密读取浏览器 Cookie，返回字典供前端预填文本框，**不写入** CookieStore；
- 用户在弹窗中确认或修改后调 `/cookies/update`：**才真正分层写入** CookieStore，触发 `sync_state_from_cookies` 同步层状态。

这种分离设计避免导入预览阶段就覆盖现有登录态。

**Q13：为什么 /cookies/current 不直接读 /cookies/layers？**
A：`/cookies/layers` 只返回每层是否有效与数量，不包含 cookie 明文。前端「更新 Cookie」弹窗需要 `name=>value` 字典来预填文本框，所以需要专门的 `/cookies/current` 接口读取明文。

**Q14：会话活跃时为什么每 10 秒刷新状态？**
A：自动更新 token 年龄、健康分、WAF 状态等动态信息。10 秒间隔平衡实时性与服务器压力。非活跃状态下不刷新，减少无效请求。
