## 1. 概述

「向量数据库维护」是闲鱼猎人系统维护菜单下的运维工具页面，专门用于管理智能客服的"记忆库"。

### 1.1 什么是向量数据库

闲鱼猎人的智能客服使用 RAG（检索增强生成）技术回答用户问题，其工作流程是：

1. 把知识库文档切分成小段（称为"片段"）
2. 把每一段文字转换成数字向量（称为"嵌入"，让 AI 能理解语义）
3. 把这些向量存到一个特殊的数据库里（即向量数据库，本系统使用 ChromaDB）
4. 用户提问时，把问题也转成向量，在数据库里找最相似的片段，再交给大模型组织回答

简单理解：**向量数据库 = 智能客服的记忆库**。它存着智能客服"读过的所有文档"。

### 1.2 本菜单的用途

智能客服运行过程中，记忆库会随着知识库更新而不断变化。本菜单提供以下能力：

- **查看记忆库状态**：当前有多少片段、占用多少磁盘、有多少存档点
- **创建存档点（快照）**：在重要操作前给记忆库"存档"，万一出问题可以回滚
- **从存档点恢复**：把记忆库恢复到某个存档点的状态
- **清理数据**：清空整个记忆库（全量重建前使用）或只删除某个文档对应的片段
- **查看操作日志**：所有维护操作都有审计记录，便于追溯

### 1.3 谁应该使用

| 角色 | 使用场景 |
|------|----------|
| 系统管理员 | 知识库大版本更新前备份、磁盘空间清理、故障排查 |
| 知识库运营人员 | 误导入文档后按来源删除、过期文档清理 |
| 客服运维人员 | 监控记忆库健康度、检查审计日志 |

> ⚠️ 普通客服人员无需访问此页面。本页面所有操作均会影响智能客服的回答质量，请谨慎使用。

## 2. 核心特性

- **可视化运维**：所有操作通过浏览器完成，无需登录服务器执行命令
- **状态实时总览**：顶部 4 张状态卡片显示片段数、数据大小、快照数、集合名
- **一键快照备份**：点击按钮即可给当前记忆库创建"存档点"，支持添加备注标签
- **精准回滚**：从任意存档点恢复，覆盖当前数据
- **多种清理方式**：支持清空整库（重建前使用）或按来源文件精准删除（误导入场景）
- **双重确认机制**：所有危险操作必须输入 `CONFIRM_DELETE` 才能执行，防止误操作
- **完整审计追溯**：所有维护操作自动记录到审计日志，可随时查看
- **未启用保护**：智能客服未启用时自动拒绝访问，避免暴露内部细节

## 5. 向量库状态详解

### 5.1 状态卡片含义

页面顶部并排展示 4 张状态卡片，进入页面时自动加载：

| 卡片 | 含义 | 说明 |
|------|------|------|
| **片段数** | 当前集合的片段总数 | 片段是文档切分后的最小检索单元。每个文档会被切成多个片段，每片段单独向量化。数量越多表示知识库覆盖越广 |
| **数据大小** | 主数据目录占用磁盘 | 显示如 `12.3 MB`。**已自动排除快照目录**，反映的是当前记忆库本身的实际大小，不会因为快照积累而虚高 |
| **快照数** | 已存档点数量 | 后缀括号显示最近一次快照时间（如「（最近 07-05 12:00）」），无快照时后缀为空 |
| **集合名** | ChromaDB 集合名称 | 默认 `xianyu_hunter_docs`。下方小字显示持久化目录路径（如 `data/chromadb`），用于排查问题时定位磁盘位置 |

`[截图：4 张状态卡片]`

#### 卡片字段对照

| 卡片 | 后端字段 | 示例值 |
|------|----------|--------|
| 片段数 | `chunk_count` | `1523` |
| 数据大小 | `data_size_display` | `12.0 MB` |
| 快照数 | `snapshot_count` + `last_snapshot_at` | `5`（最近 07-05 12:00） |
| 集合名 | `collection_name` + `persist_path` | `xianyu_hunter_docs` / `data/chromadb` |

> 📌 数据大小自动排除 `snapshots/` 子目录。若不排除，快照积累会让用户误以为记忆库本身在膨胀，影响判断。

### 5.2 何时需要维护

下列场景建议进入本页面检查或维护：

| 场景信号 | 建议操作 |
|----------|----------|
| 知识库即将进行大版本更新 | 更新前创建快照（详见 6.2） |
| 知识库更新失败，需要回滚 | 从快照恢复（详见 6.4） |
| 误导入过期或错误文档 | 按来源文件删除（详见 7.2） |
| 准备全量重建知识库 | 先创建快照 → 清空集合 → 重建（详见 7.1） |
| 智能客服回答质量明显下降 | 查看片段数是否异常，必要时排查并重建 |
| 磁盘空间紧张 | 查看快照数，删除早期无用快照（详见 6.5） |
| 需要审计某次维护操作 | 打开审计日志抽屉查询（详见第 9 章） |

## 6. 快照管理

### 6.1 什么是快照

**快照 = 记忆库的"存档点"**。

类比玩游戏时的"存档"功能：在重要节点存一次档，万一后续操作出错，可以读档回到当时的状态。

本系统的快照是**文件级副本**：把当前向量数据库目录（含主数据库、集合数据）完整复制一份，存到 `snapshots/` 子目录下。每个快照独立存在，互不影响。

快照的两个核心用途：

1. **回滚保险**：知识库大版本更新、清空集合等破坏性操作前先存档
2. **状态对比**：保留历史节点，必要时可对比不同时点的知识库状态

#### 快照与 KB 版本快照的区别

系统里其实有两类快照，共享同一个 `snapshots/` 目录但通过命名前缀区分：

| 类型 | 前缀 | 创建者 | 创建时机 |
|------|------|--------|----------|
| 手动快照 | `manual_` | 本页面用户 | 用户主动点击「创建快照」 |
| KB 版本快照 | `kb_version_` | KBManager（系统自动） | 知识库构建时自动创建 |

两者都可以在本页面快照列表中看到，但只有手动快照是用户主动创建的。KB 版本快照由智能客服模块管理，建议不要在本页面删除（除非明确知道在做什么）。

### 6.2 创建快照

#### 操作步骤

1. 切换到「备份与恢复」Tab
2. 点击「创建快照」按钮（蓝色主操作按钮，带相机图标）
3. 在弹出的「创建快照」对话框中：
   - **可选**：在输入框中填写备注标签（label），如 `pre-rebuild`、`更新前备份_20260705`
   - 不填也可以创建，系统会自动用时间戳命名
4. 点击「创建」按钮提交
5. 等待系统完成文件复制（数据量越大耗时越长，100MB 数据约 30 秒内完成）
6. 创建成功后顶部弹出绿色提示「快照已创建: manual_xxx」，快照列表自动刷新

`[截图：创建快照对话框]`

#### label 命名建议

label 会拼入快照目录名，建议使用简短英文或下划线分隔的中文：

| ✅ 推荐 | ❌ 不推荐 | 原因 |
|--------|----------|------|
| `pre-rebuild` | `重建前备份!!!` | 避免特殊字符 |
| `更新前备份_20260705` | `2026/07/05 备份` | 斜杠会影响路径 |
| `v2-release` | `very long label with spaces` | 避免过长空格 |
| （留空） | `..` 或 `../etc` | 后端会拒绝路径穿越字符 |

#### 快照 ID 命名规则

```
manual_{YYYYMMDD}_{HHMMSS}[_{label}]
```

示例：

- 无 label：`manual_20260705_120000`
- 有 label `pre-rebuild`：`manual_20260705_120000_pre-rebuild`
- 有 label `更新前备份`：`manual_20260705_120000_更新前备份`

> 💡 创建快照是**非破坏性操作**，不会影响当前数据，因此**无需**输入 `CONFIRM_DELETE`。

### 6.3 快照目录结构

所有快照统一存放在向量库持久化目录下的 `snapshots/` 子目录：

```
data/chromadb/                            ← 持久化根目录
├── chroma.sqlite3                        ← ChromaDB 主数据库
├── collections/                          ← 集合数据
│   └── xianyu_hunter_docs/
└── snapshots/                            ← 快照根目录
    ├── manual_20260629_120000_label1/    ← 手动快照（用户创建）
    ├── manual_20260705_120000_pre-rebuild/
    └── kb_version_a1b2c3d4/              ← KB 版本快照（系统自动）
```

每个快照目录内是完整的一份向量库副本，包括 `chroma.sqlite3` 与 `collections/`。

**重要**：

- 快照创建后**不再修改**，目录的修改时间近似等于创建时间
- 快照目录会占用与主数据相当的磁盘空间，请定期清理无用快照
- 状态卡片的「数据大小」**不包含** `snapshots/` 目录，避免与快照大小混淆

### 6.4 恢复快照

⚠️ **这是危险操作，会覆盖当前集合数据，不可撤销！**

#### 操作步骤

1. 在「备份与恢复」Tab 的快照列表中找到目标快照
2. 点击该行「操作」列的「恢复」按钮（蓝色链接样式，带回退图标）
3. 弹出二次确认对话框，内容包含：
   - 快照 ID（如 `manual_20260705_120000_pre-rebuild`）
   - 快照大小（如 `12.0 MB`）
   - 创建时间（如 `2026-07-05 12:00:00`）
   - 警示语：「将用快照内容覆盖当前集合，当前数据将丢失」
4. 在输入框中**精确**输入 `CONFIRM_DELETE`（区分大小写）
5. 输入正确后，「确认」按钮从灰色变为可点击的红色
6. 点击「确认」提交
7. 等待恢复完成（清空当前数据 + 复制快照内容 + 重建集合引用）
8. 成功后弹出绿色提示「恢复成功」，状态卡片与快照列表自动刷新

`[截图：恢复快照二次确认弹窗]`

#### 恢复过程说明

恢复操作底层会执行三步：

1. **清空当前持久化目录**（保留 `snapshots/` 子目录，避免其他快照丢失）
2. **复制快照内容到持久化目录**（覆盖式复制）
3. **重建集合引用**（旧集合对象绑定的数据已被替换，需要重新绑定）

> ⚠️ 恢复期间智能客服的对话功能会**短暂不可用**（通常几秒到几十秒，取决于数据量）。请选择业务低峰期操作。

#### 恢复前建议

强烈建议在恢复前**先创建一个新快照**备份当前状态，万一恢复效果不如预期，还可以回到当前状态。弹窗中也会提示此建议，但**不强制**自动创建（避免双重操作让用户困惑）。

### 6.5 删除快照

⚠️ **这是危险操作，会删除快照文件，不可恢复！**

#### 操作步骤

1. 在「备份与恢复」Tab 的快照列表中找到要删除的快照
2. 点击该行「操作」列的「删除」按钮（红色链接样式，带删除图标）
3. 弹出二次确认对话框，内容包含：
   - 快照 ID
   - 快照大小
   - 警示语：「此操作不可恢复」
4. 在输入框中**精确**输入 `CONFIRM_DELETE`（区分大小写）
5. 点击「确认」提交
6. 成功后弹出绿色提示「已删除」，快照列表自动刷新

`[截图：删除快照二次确认弹窗]`

#### 删除影响范围

- ✅ **仅删除快照文件**：`shutil.rmtree(snapshot_path)` 删除快照目录
- ✅ **不影响当前集合数据**：当前向量库内容保持不变
- ✅ **不影响其他快照**：只删除指定的那一个

#### 何时应该删除快照

| 场景 | 建议 |
|------|------|
| 磁盘空间紧张 | 删除早期已无回滚价值的手动快照 |
| 恢复成功后 | 可保留最近 1-2 个快照，删除更早的 |
| KB 版本快照过多 | 谨慎删除，最好与开发团队确认 |
| 测试性快照 | 创建后立即删除，避免遗留 |

> 📌 删除 KB 版本快照（前缀 `kb_version_`）可能影响智能客服模块的版本管理能力，非必要不删除。

## 7. 数据清理

### 7.1 清空集合

⚠️ **这是危险操作，会删除集合中所有片段，不可撤销！**

#### 用途

清空集合 = 把整个记忆库"格式化"。通常在**知识库全量重建前**使用：

- 知识库结构发生重大调整，需要从头重建
- 知识库被严重污染，需要彻底清理后重新导入
- 切换嵌入模型等底层配置变更，需要重新向量化所有文档

#### 操作步骤

1. 切换到「数据清理」Tab
2. 在「清空集合」Card 中查看提示信息：
   - 「删除集合中的所有片段。通常在知识库全量重建前调用。」
3. 点击红色的「清空集合」按钮
4. 弹出二次确认对话框，内容包含：
   - 集合名（如 `xianyu_hunter_docs`）
   - 当前片段数（如 `1523 条`）
   - 警示语：「操作不可恢复。建议先创建快照备份。」
5. 在输入框中**精确**输入 `CONFIRM_DELETE`
6. 点击「确认」提交
7. 等待清空完成（删除集合并重建空集合，通常 1 秒内完成）
8. 成功后弹出绿色提示「已清空 N 条片段」，状态卡片刷新

`[截图：清空集合二次确认弹窗]`

#### 清空后的状态

- 集合对象被删除并重新创建（保持同名 `xianyu_hunter_docs`）
- 片段数归零
- 数据大小显著减小
- **快照不受影响**（快照独立存放在 `snapshots/` 目录）
- 智能客服在重新导入知识库前**无法回答任何业务问题**

> ⚠️ 清空后必须尽快执行知识库重建（由智能客服模块的 KBManager 负责，参考 [智能客服-使用说明.md](../06-智能客服/智能客服-使用说明.md)）。清空期间智能客服将无法正常工作。

### 7.2 按来源文件删除

⚠️ **这是危险操作，会删除指定文档的所有片段，不可撤销！**

#### 用途

按来源文件删除 = 只删除某个文档对应的片段，保留其他文档的内容。适用于：

- 误导入过期文档
- 文档内容错误需要清理后重新导入
- 单个文档被废弃，需要从知识库移除

#### source_file 是什么

每个片段在写入向量库时都会记录其来源文件路径（`source_file` 字段），通常是文档的相对路径。例如：

- `docs/06-智能客服/chatbot-rag-agent-requirements.md`
- `docs/04-系统维护/向量数据库维护-需求规格.md`

按来源删除时，需要填写**与片段 metadata 中完全一致**的 `source_file` 字符串。

#### 操作步骤

1. 切换到「数据清理」Tab
2. 在「按来源文件删除」Card 的输入框中：
   - 输入要删除的 `source_file` 路径
   - 输入框带文件搜索图标，宽度 360px
3. 点击红色的「删除」按钮
4. **若输入为空**：弹出黄色警告「请输入 source_file」，不进入二次确认
5. **若输入非空**：弹出二次确认对话框，内容包含：
   - 要删除的 `source_file` 值
   - 警示语：「将删除该 source_file 的所有片段，操作不可恢复」
6. 在输入框中**精确**输入 `CONFIRM_DELETE`
7. 点击「确认」提交
8. 等待删除完成（先查询匹配片段，再批量删除，10000 片段约 2 秒）
9. 成功后弹出绿色提示「已删除 N 条片段」，输入框清空，状态卡片刷新

`[截图：按来源删除输入与确认弹窗]`

#### 删除结果说明

- **匹配到片段**：返回删除数量，如「已删除 12 条片段」
- **未匹配到片段**：返回 0，提示「已删除 0 条片段」（**不视为错误**，可能是 source_file 拼写错误或该文档已删除）

> 💡 若返回 0 但你确信文档存在，请检查 `source_file` 拼写是否完全一致（包括大小写、路径分隔符、文件扩展名）。可联系开发团队协助查询片段 metadata 确认准确值。

### 7.3 何时选择哪种清理方式

| 场景 | 推荐方式 | 原因 |
|------|----------|------|
| 知识库结构大调整，需要全量重建 | 清空集合 | 彻底清理，避免残留旧数据干扰 |
| 仅误导入 1-2 个文档 | 按来源删除 | 精准清理，不影响其他正常文档 |
| 文档内容更新需要重新导入 | 按来源删除 | 先删旧片段，再重新导入新内容 |
| 嵌入模型变更，所有片段需要重新向量化 | 清空集合 | 维度变化导致旧片段无法复用 |
| 测试性导入后清理 | 按来源删除 | 仅清理测试文档，保留生产数据 |
| 知识库被严重污染，无法定位具体文档 | 清空集合 | 兜底方案，配合快照恢复使用 |

**决策原则**：

- 能用「按来源删除」解决的，就不要用「清空集合」
- 「清空集合」是最后手段，使用前**务必先创建快照**
- 两种清理方式都是**危险操作**，必须输入 `CONFIRM_DELETE` 二次确认

## 8. 双重确认机制

### 8.1 为什么需要双重确认

向量库维护涉及多种破坏性操作，一旦误执行无法撤销。为防止用户误点，系统对危险操作设置了"双重确认"机制：

1. **第一重**：用户主动点击危险操作按钮
2. **第二重**：弹窗中要求用户**手动输入**确认令牌 `CONFIRM_DELETE`，输入正确后「确认」按钮才会启用

这种设计借鉴了 GitHub 删除仓库、AWS 注销账号等高危场景的确认模式，通过强制用户输入特定字符串来确保用户充分意识到操作后果。

### 8.2 危险操作列表

以下 4 个操作必须输入 `CONFIRM_DELETE` 才能执行：

| 序号 | 操作 | 入口 | 后果 |
|------|------|------|------|
| 1 | 从快照恢复 | 快照列表「恢复」按钮 | 当前集合数据被快照覆盖，丢失 |
| 2 | 删除快照 | 快照列表「删除」按钮 | 快照文件被永久删除 |
| 3 | 清空集合 | 「数据清理」Tab「清空集合」按钮 | 集合中所有片段被删除 |
| 4 | 按来源文件删除 | 「数据清理」Tab「删除」按钮 | 指定文档的所有片段被删除 |

### 8.3 确认令牌说明

| 项 | 值 |
|----|----|
| 令牌字符串 | `CONFIRM_DELETE` |
| 大小写 | **区分大小写**（必须全大写） |
| 输入位置 | 二次确认弹窗中的密码输入框 |
| 启用条件 | 输入内容**精确等于** `CONFIRM_DELETE` 时，「确认」按钮才可点击 |
| 失败处理 | 输入错误时按钮保持灰色禁用状态，可重新输入 |

### 8.4 确认弹窗交互流程

```
[用户点击危险操作按钮]
        ↓
[弹出 Modal.confirm 二次确认弹窗]
        ↓
[弹窗内容：操作描述 + 危险提示]
        ↓
[密码输入框：请输入 CONFIRM_DELETE 以确认（区分大小写）]
        ↓
┌─── 输入错误 ───┐    ┌─── 输入正确 ────┐
│                │    │                  │
│ 确认按钮禁用    │    │ 确认按钮启用      │
│ 用户可重新输入  │    │ 用户点击「确认」  │
│ 或点击「取消」  │    │       ↓          │
│                │    │ 调用后端 API     │
└────────────────┘    │ （携带          │
                      │  confirm_token） │
                      │       ↓          │
                      │ 后端校验 token   │
                      │       ↓          │
                      │ 执行操作 +       │
                      │ 写审计日志       │
                      │       ↓          │
                      │ 前端刷新状态     │
                      └──────────────────┘
```

### 8.5 非破坏性操作免确认

以下操作**无需**输入 `CONFIRM_DELETE`：

| 操作 | 原因 |
|------|------|
| 创建快照 | 文件级复制，不破坏现有数据 |
| 查看状态 | 只读操作 |
| 查看快照列表 | 只读操作 |
| 查看审计日志 | 只读操作 |
| 刷新页面 | 只读操作 |

> 💡 后端也会再次校验 `confirm_token`，即使前端被绕过，后端缺失或不匹配的 token 会返回 400 错误「需要 confirm_token=CONFIRM_DELETE」。

## 9. 审计日志

### 9.1 审计日志的作用

审计日志记录所有向量库维护操作，便于：

- **故障复盘**：出问题时追溯是哪个操作导致的
- **权责追溯**：记录每次操作的来源与目标
- **合规审计**：满足运维操作可追溯的要求

### 9.2 查看审计日志

#### 操作步骤

1. 点击页面右上角的「审计日志」按钮（带文件图标）
2. 从右侧滑出「向量库维护审计日志」抽屉（宽度 720px）
3. 抽屉内展示最近 200 条 `vector_admin.*` 操作记录
4. 表格列：时间 / 操作（蓝色 Tag）/ 目标（超长省略）/ 来源

`[截图：审计日志抽屉]`

#### 表格列说明

| 列 | 字段 | 示例 |
|----|------|------|
| 时间 | `created_at` | `2026-07-05T12:00:00Z` |
| 操作 | `action` | `vector_admin.snapshot_create`（蓝色 Tag） |
| 目标 | `target` | `manual_20260705_120000_pre-rebuild` |
| 来源 | `source` | `web` |

### 9.3 审计日志存储

审计日志存储在 `chatbot_audit_logs` 表中（与智能客服模块共享），通过 `action` 字段前缀 `vector_admin.` 区分向量库维护操作。

#### action 类型对照

| action | 触发时机 | target 示例 |
|--------|----------|-------------|
| `vector_admin.snapshot_create` | 创建快照 | `manual_20260705_120000_pre-rebuild` |
| `vector_admin.snapshot_restore` | 恢复快照 | `manual_20260705_120000_pre-rebuild` |
| `vector_admin.snapshot_delete` | 删除快照 | `manual_20260705_120000_pre-rebuild` |
| `vector_admin.cleanup_all` | 清空集合 | `cleared 1523 chunks` |
| `vector_admin.cleanup_by_source` | 按来源删除 | `docs/foo.md (12 chunks)` |

### 9.4 审计日志的特性

- **共享表**：与智能客服的审计记录同表，通过 action 前缀过滤
- **前缀过滤**：本页面只显示 `vector_admin.` 前缀的记录，不混入其他操作
- **来源固定**：所有记录的 `source` 字段为 `web`（来自 Web 操作）
- **不阻塞主流程**：审计日志写入失败时仅记录后端错误日志，**不影响主操作结果**
- **无值哈希**：本模块不记录 `old_value_hash` / `new_value_hash`（与数据库维护模块不同）
- **加载策略**：后端取 `limit × 3` 条记录后内存过滤前缀，确保返回足够的 `vector_admin.*` 记录

> 💡 审计日志不阻塞主流程意味着：即使审计日志写入失败（如数据库异常），你的实际维护操作（如创建快照）依然会成功完成。这是为了保障运维操作的可用性，代价是极少数情况下可能丢失审计记录。

## 10. 常见场景

### 场景 1：知识库大版本更新前创建快照

**背景**：知识库即将进行重大版本更新，新增多个文档并调整现有内容，担心更新失败无法回滚。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. 查看状态卡片，记录当前片段数（如 1523）
3. 切换到「备份与恢复」Tab
4. 点击「创建快照」
5. 在 label 输入框填写：`v2-pre-rebuild`
6. 点击「创建」，等待完成
7. 确认快照列表中出现 `manual_20260705_120000_v2-pre-rebuild`
8. 通知开发团队可以开始更新知识库

**回滚预案**：若更新失败，回到本页面找到该快照，点击「恢复」，输入 `CONFIRM_DELETE` 即可回到更新前的状态。

### 场景 2：知识库更新失败后回滚

**背景**：知识库更新后智能客服回答质量明显下降，需要快速回滚到更新前的状态。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. 切换到「备份与恢复」Tab
3. 在快照列表中找到更新前创建的快照（如 `manual_20260705_120000_v2-pre-rebuild`）
4. **强烈建议**：先点击「创建快照」备份当前（虽然有问题但可分析的）状态，label 填 `failed-update-backup`
5. 在原快照行点击「恢复」
6. 在弹窗中输入 `CONFIRM_DELETE`
7. 点击「确认」
8. 等待恢复完成，状态卡片刷新
9. 验证智能客服回答是否恢复正常

**注意事项**：恢复期间智能客服对话功能会短暂不可用，建议在业务低峰期操作。

### 场景 3：删除某个过时的来源文件

**背景**：发现 `docs/06-智能客服/old-requirements.md` 内容已过时被错误导入到知识库，需要清理。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. 切换到「数据清理」Tab
3. 在「按来源文件删除」Card 的输入框中输入：`docs/06-智能客服/old-requirements.md`
4. 点击「删除」
5. 在弹窗中确认 source_file 值正确
6. 输入 `CONFIRM_DELETE`
7. 点击「确认」
8. 等待删除完成，查看提示「已删除 N 条片段」
9. **建议**：到智能客服页面测试相关问题，确认过时内容不再被引用

**注意事项**：

- source_file 必须与片段 metadata 中的值**完全一致**（区分大小写、路径分隔符）
- 若返回「已删除 0 条片段」，说明 source_file 拼写可能有误，请核对
- 删除后该文档对应的内容将不再被智能客服引用

### 场景 4：全量重建知识库

**背景**：知识库结构发生重大调整，需要彻底清空后重新导入所有文档。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. **第一步：创建备份快照**
   - 切换到「备份与恢复」Tab
   - 点击「创建快照」，label 填 `pre-full-rebuild`
   - 等待完成
3. **第二步：清空集合**
   - 切换到「数据清理」Tab
   - 点击「清空集合」
   - 输入 `CONFIRM_DELETE` 确认
   - 等待清空完成，确认片段数归零
4. **第三步：重建知识库**
   - 由开发团队通过智能客服模块的 KBManager 触发重建
   - 重建完成后回到本页面确认片段数恢复正常
5. **第四步：验证与清理**
   - 测试智能客服回答质量
   - 若一切正常，可保留 `pre-full-rebuild` 快照作为短期回滚保险
   - 一周后确认稳定，可删除该快照释放磁盘

**注意事项**：清空集合后到重建完成期间，智能客服**无法回答任何业务问题**。请提前通知业务团队，并选择业务低峰期操作。

### 场景 5：排查向量库异常

**背景**：智能客服回答异常，怀疑向量库数据有问题。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. 查看状态卡片：
   - 片段数是否与预期相符？（异常减少可能意味着数据丢失）
   - 数据大小是否合理？（异常增大可能意味着重复导入）
   - 快照数是否正常？
3. 点击「审计日志」查看最近操作：
   - 是否有人误执行了清空或删除操作？
   - 是否有失败的恢复操作？
4. 根据排查结果决定后续操作：
   - 若发现误删除 → 从最近的快照恢复
   - 若数据异常 → 清空后重建
   - 若无法定位 → 联系开发团队查看后端日志

### 场景 6：清理磁盘空间

**背景**：服务器磁盘空间紧张，需要清理无用快照。

**操作步骤**：

1. 进入「向量数据库维护」页面
2. 查看状态卡片的「快照数」（如 15 个）
3. 切换到「备份与恢复」Tab
4. 查看快照列表，按创建时间排序（默认倒序，最早创建的在底部）
5. 识别可删除的快照：
   - 早期测试性快照（label 含 test、tmp 等）
   - 已成功恢复且验证无问题后的旧快照
   - 超过 1 个月的手动快照（业务已稳定）
6. 对每个待删除快照：
   - 点击「删除」
   - 输入 `CONFIRM_DELETE` 确认
7. 定期检查磁盘空间释放情况

**注意事项**：

- **谨慎删除** `kb_version_` 前缀的快照（系统自动创建，可能影响 KB 版本管理）
- 删除前确认该快照不再需要回滚
- 建议保留最近 2-3 个快照作为短期保险

### 场景 7：访问被拒绝（智能客服未启用）

**背景**：访问「向量数据库维护」页面时提示「智能客服未启用，向量库不可用」。

**原因**：系统检测到 chatbot 子容器未初始化（`container.chatbot is None`），可能是：

- `config.yaml` 中 `chatbot.enabled` 设置为 `false`
- `chromadb` 包未安装
- chatbot 配置错误导致初始化失败

**处理步骤**：

1. 联系开发团队检查 `config.yaml` 中 `chatbot.enabled` 是否为 `true`
2. 确认 `chromadb` 已通过 `pip install chromadb>=1.0.0` 安装
3. 检查后端启动日志中是否有 chatbot 初始化失败的错误
4. 修复后重启后端服务
5. 重新访问页面

**详细信息**：参考 [智能客服-详细设计.md](../06-智能客服/智能客服-详细设计.md) 中的 chatbot 子容器初始化逻辑。

## 11. 常见问题 FAQ

### Q1：访问页面提示「智能客服未启用，向量库不可用」怎么办？

**A**：这是 403 `CHATBOT_DISABLED` 错误。原因及处理：

- **原因 1**：`config.yaml` 中 `chatbot.enabled` 未设置为 `true` → 修改配置后重启服务
- **原因 2**：`chromadb` 包未安装 → 执行 `pip install chromadb>=1.0.0`
- **原因 3**：chatbot 初始化失败 → 查看后端日志排查

修复后重启后端服务即可恢复访问。详见场景 7。

### Q2：快照能跨版本恢复吗？

**A**：**不建议**。快照是文件级副本，包含当时的 ChromaDB 数据结构与嵌入向量。若系统升级后 ChromaDB 版本或嵌入模型（`BAAI/bge-small-zh-v1.5`，dim=512）发生变化，旧快照恢复后可能不兼容。建议：

- 升级前咨询开发团队
- 升级后创建新快照作为基线
- 旧快照仅用于短期回滚（如同一天内）

### Q3：恢复快照会覆盖现有数据吗？

**A**：**会**。恢复操作会用快照内容完全替换当前集合数据，当前数据将丢失。这就是为什么恢复是危险操作、需要输入 `CONFIRM_DELETE` 的原因。**强烈建议在恢复前先创建一个新快照**备份当前状态，万一恢复效果不理想还可以回到当前状态。

### Q4：清空集合和按来源删除的区别？

**A**：

| 维度 | 清空集合 | 按来源删除 |
|------|----------|------------|
| 影响范围 | 删除集合中**所有**片段 | 仅删除指定 `source_file` 对应的片段 |
| 实现方式 | 删除集合并重建空集合 | 查询匹配片段后批量删除 |
| 典型场景 | 知识库全量重建前 | 误导入文档清理 |
| 后续操作 | 必须重新导入所有文档 | 其他文档不受影响 |
| 风险等级 | 高（影响全部数据） | 中（影响单个文档） |

决策原则：能用按来源删除解决的，就不要用清空集合。

### Q5：快照占用磁盘空间吗？

**A**：**占用**，且与主数据大小相当。每个快照是向量库的完整文件级副本，存放在 `{persist_path}/snapshots/{snapshot_id}` 目录下。例如主数据 12MB，每个快照也约占 12MB。

**注意**：状态卡片的「数据大小」**不包含**快照目录，避免与快照大小混淆。若需查看快照占用，可在「备份与恢复」Tab 的快照列表中查看每个快照的 `size_display`。

建议定期清理无用快照（详见 6.5）。

### Q6：为什么必须输入 `CONFIRM_DELETE`，不能直接点击确认？

**A**：这是**双重确认机制**，专门为防止误操作设计。手动输入特定字符串可以确保：

1. 用户充分意识到操作的后果
2. 不会因为鼠标误点导致数据丢失
3. 即使前端被绕过，后端也会再次校验

`CONFIRM_DELETE` 是固定的确认令牌，**区分大小写**（必须全大写）。这种设计借鉴了 GitHub 删除仓库、AWS 注销账号等高危场景的最佳实践。

### Q7：创建快照为什么不需要输入 `CONFIRM_DELETE`？

**A**：因为创建快照是**非破坏性操作**——只是文件复制，不会修改或删除任何现有数据。即使误点也只是多创建一个快照文件，删除即可。所以为了简化操作流程，创建快照无需二次确认。

### Q8：审计日志写入失败会影响我的操作吗？

**A**：**不会**。审计日志采用"不阻塞主流程"策略：

- 写入失败时仅在后端记录错误日志（`logger.exception`）
- **不会**抛出异常或返回错误
- 你的实际维护操作（如创建快照、清空集合）依然会成功完成

这是为了保障运维操作的可用性。代价是极少数情况下（如数据库异常）可能丢失审计记录。若发现审计日志缺失，请联系开发团队查看后端错误日志。

### Q9：按来源删除时 source_file 应该填什么？

**A**：填写文档导入时使用的 `source_file` 路径，通常是文档的**相对路径**。例如：

- `docs/06-智能客服/chatbot-rag-agent-requirements.md`
- `docs/04-系统维护/向量数据库维护-需求规格.md`

该值必须与片段 metadata 中的 `source_file` 字段**完全一致**（区分大小写、路径分隔符）。若不确定准确值，可联系开发团队通过向量库查询接口查看片段的 metadata。

**注意**：若返回「已删除 0 条片段」，可能是 source_file 拼写错误，请仔细核对。

### Q10：快照列表里的「手动」和「自动」标签什么意思？

**A**：

| 标签 | 含义 | 创建者 |
|------|------|--------|
| 手动（橙色 Tag） | 用户主动在本页面创建的快照，前缀 `manual_` | 系统管理员/运营人员 |
| 自动（蓝色 Tag） | 系统在知识库构建时自动创建的 KB 版本快照，前缀 `kb_version_` | KBManager（系统自动） |

两类快照共享同一个 `snapshots/` 目录，但通过命名前缀和 Tag 颜色区分。

**注意**：删除「自动」快照可能影响智能客服模块的版本管理能力，非必要不删除。

### Q11：恢复快照期间智能客服还能用吗？

**A**：**短暂不可用**。恢复操作底层会清空持久化目录并复制快照内容，期间 ChromaDB 集合引用被替换，对外 API 会报错。恢复时长取决于数据量：

- 100MB 数据约 30 秒内完成
- 恢复期间对话功能不可用

建议在业务低峰期执行恢复操作，并提前通知业务团队。

### Q12：本菜单为什么不在侧栏菜单中显示？

**A**：本菜单作为「系统维护」侧栏下的子页面，未在 `menu_registry.yaml` 中独立注册。入口方式：

1. 通过 `/maintenance` 系统清理页面的 Sheet 多 tab 入口跳转
2. 直接访问浏览器路径 `/maintenance/vector`

这种设计与数据库维护、批量采集等同级子页面保持一致。若需独立菜单 key，需在 `config/menu_registry.yaml` 的 maintenance 分类下新增配置（详见 [详细设计](./向量数据库维护-详细设计.md)）。

## 12. 最佳实践

### 实践 1：重要操作前必先创建快照

任何会影响数据的操作（清空集合、按来源删除、知识库重建）之前，**务必先创建快照**。快照是回滚的最后保障，创建成本极低（文件复制），但能避免灾难性损失。

**推荐 label 命名**：`pre-{操作类型}-{日期}`，如 `pre-rebuild-20260705`、`pre-cleanup-source-20260705`。

### 实践 2：恢复前再创建一个"当前状态"快照

恢复快照会覆盖当前数据。若恢复后发现恢复的快照也不是想要的状态，还可以从"恢复前创建的当前状态快照"回到恢复前。这种"双保险"策略在重要回滚场景非常有效。

### 实践 3：定期清理无用快照

每个快照占用与主数据相当的磁盘空间。建议：

- **每周**：检查快照数量，超过 10 个时考虑清理
- **每月**：删除 1 个月以上的手动快照（业务已稳定）
- **保留**：最近 2-3 个快照作为短期保险
- **谨慎**：不删除 `kb_version_` 前缀的自动快照（除非明确知道在做什么）

### 实践 4：优先使用按来源删除而非清空集合

清空集合是"核武器"级别的操作，影响范围太大。能用按来源删除解决的，就绝不用清空集合。清空集合仅用于：

- 知识库全量重建前
- 嵌入模型变更需要重新向量化所有文档
- 知识库被严重污染且无法定位具体文档

### 实践 5：业务低峰期执行危险操作

恢复快照、清空集合等操作会导致智能客服短暂不可用。建议：

- 选择业务低峰期（如深夜或周末）执行
- 提前通知业务团队维护时间窗口
- 操作完成后立即验证智能客服功能正常

### 实践 6：操作后立即验证效果

每次维护操作完成后，建议立即验证：

- **状态卡片**：片段数、数据大小是否符合预期
- **智能客服**：测试几个典型问题，确认回答质量
- **审计日志**：确认操作已被记录

发现问题及时处理，避免问题累积。

### 实践 7：准确记录 source_file

按来源删除时，source_file 拼写错误会导致"删除 0 条片段"。建议：

- 从知识库管理界面复制准确的文件路径
- 删除前先用查询接口确认 source_file 存在
- 若不确定，联系开发团队协助查询片段 metadata

### 实践 8：定期查看审计日志

即使没有问题，也建议每周查看一次审计日志，了解：

- 近期有哪些维护操作
- 是否有人误操作
- 操作频率是否合理

这有助于及时发现潜在问题，培养良好的运维习惯。
