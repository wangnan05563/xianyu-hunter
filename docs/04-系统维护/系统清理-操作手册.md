## 1. 概述

「系统清理」是闲鱼猎人「系统维护」分类下的二级菜单，提供缓存、数据库、日志三类系统资源的统一清理入口。系统长期运行后，浏览器缓存、Python 字节码、事件表、日志文件会持续占用磁盘空间，甚至拖慢查询速度；本菜单通过一个页面完成"查看现状 → 预览影响 → 执行清理 → 自动留痕"的全流程，让普通运维和管理员也能安全地完成日常维护工作。

本菜单的核心设计理念是「先预览、再执行、可追溯」：所有清理操作均支持预览模式（dry_run），关闭预览前必须通过浏览器原生弹窗二次确认，每次清理都会自动写入审计日志，便于事后回溯。

## 2. 核心特性

- **三类清理目标统一入口**：缓存 / 数据库 / 日志 三列卡片并排展示，互不干扰，各自独立配置清理范围与保留天数
- **预览模式（dry_run）**：所有清理操作默认开启预览，先列出"将处理哪些条目"再决定是否真正执行，避免误删
- **二次确认机制**：关闭预览模式后，点击清理按钮会弹出浏览器原生确认框，必须主动点击"确认"才会执行
- **数据库空间回收（VACUUM）**：在事务外独立执行 VACUUM，重建数据库文件、回收已删除数据占用的空间，类似磁盘碎片整理
- **关键目录排除保护**：自动跳过 `.venv` / `node_modules` / `.git` / `data` / `dist` / `build` / `target` / `.cache` / `__pycache__` 等 9 个目录，避免误删第三方依赖与构建产物
- **审计日志全程留痕**：每次清理操作（含预览）都写入系统事件表，记录清理类型、目标、数量与时间，可在「实时日志」页查询
- **存储状态实时总览**：进入页面自动加载当前数据库大小、日志占用、缓存占用的统计卡片，执行清理后自动刷新
- **参数化查询防注入**：所有数据库清理使用参数化绑定，杜绝 SQL 注入风险

## 4. 基本操作

| 序号 | 操作 | 触发方式 | 说明 |
|------|------|----------|------|
| 1 | 查看存储状态 | 进入页面自动加载 | 页面打开时自动拉取数据库 / 日志 / 缓存三组统计，无需手动操作 |
| 2 | 刷新存储状态 | 点击右上角「刷新状态」按钮 | 重新拉取最新统计；建议清理前、清理后各点一次对比 |
| 3 | 选择清理范围 | 在卡片内「清理范围」下拉框中选择 | 三张卡片各自独立选择目标类型，互不影响 |

| 5 | 开启预览模式 | 默认开启；可点击「仅预览」开关切换 | 开启时仅列出将处理条目，不实际删除；关闭时显示红色"将执行真实删除"标签 |
| 6 | 缓存预览 | 缓存卡片：开关保持开启 → 点击「清理缓存」 | 返回 `[预览]` 前缀的待删除目录列表，不修改任何文件 |
| 7 | 缓存清理执行 | 缓存卡片：关闭预览开关 → 点击「清理缓存」→ 在弹窗中点击「确认」 | 浏览器原生弹窗二次确认后执行真实删除 |
| 8 | 数据库预览 | 数据库卡片：开关保持开启 → 点击「清理数据库」 | 返回将删除的行数统计，不修改任何数据 |
| 9 | 数据库清理执行 | 数据库卡片：关闭预览开关 → 点击「清理数据库」→ 在弹窗中点击「确认」 | 弹窗提示"建议先备份数据"，确认后执行 DELETE 与 VACUUM |
| 10 | 日志预览 | 日志卡片：开关保持开启 → 点击「清理日志」 | 返回将删除的日志文件列表（含大小、日期），右上角同时弹出 toast 提示数量 |
| 11 | 日志清理执行 | 日志卡片：关闭预览开关 → 点击「清理日志」→ 在弹窗中点击「确认」 | 弹窗确认后删除符合条件的日志文件，并显示释放的磁盘空间 |

## 5. 三类清理目标详解

### 5.1 缓存清理

#### 清理范围

| 目标 | 说明 | 影响 |
|------|------|------|
| 浏览器数据目录 | `data/webview_data_*` 下的所有子目录 | 包含闲鱼登录 Cookie 与浏览器指纹，清理后需重新登录闲鱼 |
| Python 字节码缓存 | 项目源码下所有 `__pycache__` 目录 | 删除后首次 Python 导入会重新编译 `.pyc`，无业务影响 |
| 临时文件 | 系统临时目录下的 `xianyu_*` 文件（Windows 上不存在则跳过） | 无业务影响 |

#### 清理范围选项

| 选项 | 行为 |
|------|------|
| 全部缓存（默认） | 同时清理浏览器数据 + Python 缓存 |
| 浏览器数据 | 仅清理 `webview_data_*` 目录 |
| 临时文件 | 仅清理 `__pycache__` 目录（受历史命名影响，选项名"临时文件"实际指 Python 缓存） |

#### 排除目录（关键保护）

为避免误删第三方依赖与构建产物，扫描 `__pycache__` 时自动跳过以下 9 个目录：

| 序号 | 目录 | 排除原因 |
|----|------|----------|
| 1 | `.venv` | Python 第三方依赖缓存，清理后首次导入变慢且无意义 |
| 2 | `node_modules` | 前端 npm 依赖 |
| 3 | `.git` | 版本控制元数据 |
| 4 | `data` | 运行时数据（含向量库等） |
| 5 | `dist` | 前端构建产物 |
| 6 | `build` | 通用构建产物 |
| 7 | `target` | Java/Rust 等其他语言构建产物 |
| 8 | `.cache` | 通用缓存目录 |
| 9 | `__pycache__` | 避免递归进入已命中的 `__pycache__` 内部 |

> **为什么不能清理 .venv 下的 __pycache__？**
> `.venv` 目录包含数千个第三方依赖子目录，每个包内部都有自己的 `__pycache__`。如果扫描进入 `.venv`，单次清理耗时将从 0.1 秒飙升至 30 秒以上；同时清理这些缓存仅会让下次导入变慢，没有任何收益。系统通过 `os.walk` 原地剪枝技术跳过这些目录，将扫描时间稳定在 0.1 秒以内。

#### 重要提示

- 清理浏览器数据后**必须重新登录闲鱼**，建议在低峰期或确认无活跃采集任务时执行
- 缓存清理与"保留天数"无关，因此卡片中**不显示**保留天数输入框

### 5.2 数据库清理

#### 清理范围

| 目标 | 说明 | 关联数据表 |
|------|------|------------|
| 旧事件记录 | 删除创建时间早于"保留天数"前的事件 | `events` 表 |
| 旧未关联商品 | 删除首次发现时间早于"保留天数"前、且**未被任何任务监控**的商品 | `items` 表 |
| 已售商品关联 | 删除已售出商品的关联记录（`display` 字段中 `is_sold` 为 true） | `task_links` 表 |
| VACUUM 压缩 | 重建数据库文件、回收已删除数据占用的空间 | 整个 `xianyu.db` 文件 |
| 全部清理（默认） | 依次执行：旧事件 → 旧未关联商品 → 已售商品关联 → VACUUM | 以上四项 |

#### 保留天数（days）

- 取值范围：1-365 天（前端输入框强约束）
- 后端额外保护：若传入 0 或负值，自动钳制为 1，防止误删全表
- 计算方式：以"当前时间 - 保留天数"为截止时间，删除该时间之前的数据
- 推荐值：日常维护 30 天；高频采集系统 7-14 天；审计需求高 90 天

#### VACUUM（数据库空间回收）

**通俗解释**：VACUUM 类似磁盘碎片整理。SQLite 删除数据后，文件大小不会立即缩小，而是留下"空洞"；VACUUM 会重建整个数据库文件，把空洞真正释放给操作系统。

**特点**：
- 在事务外独立执行，不会长时间锁表
- 100MB 数据库约需 1-3 秒，期间数据库不可读写
- dry_run 预览模式下仅显示"将执行 VACUUM"，不实际执行
- 与 DELETE 操作配合使用效果最佳（先删除冗余数据，再 VACUUM 回收空间）

**适用场景**：
- 数据库文件明显大于实际数据量
- 执行大量 DELETE 后想真正释放磁盘空间
- 数据库查询变慢、备份耗时增加

#### 安全保护

- **关联保护**：清理旧商品时，自动排除仍在监控任务中的商品（即被 `task_links` 引用的商品不会被删）
- **参数化查询**：所有 DELETE 使用参数绑定，杜绝 SQL 注入
- **事务原子性**：所有 DELETE 在同一事务中执行，任一步失败整体回滚

### 5.3 日志清理

#### 清理范围

- 清理目标：`data/logs/*.log*` 目录下的日志文件（含 rotation 切分后的 `.log.1` / `.log.2` 等后缀）
- 不会清理其他目录的日志文件

#### 清理规则选项

| 选项 | 行为 | 是否需要保留天数 |
|------|------|------------------|
| 按天数清理（默认） | 删除最后修改时间早于"保留天数"前的日志文件 | 是（默认 7 天） |
| 大文件清理 | 删除大小超过 10MB 的日志文件（与天数无关） | 否 |
| 全部清理 | 同时按天数与大文件两个条件清理，满足任一即删除 | 是（默认 7 天） |

#### 大文件阈值

- 当前固定为 10MB（不可在前端调整）
- 如需调整阈值，需联系开发人员修改源码并重新部署

#### 日志目录不存在的处理

- 若 `data/logs/` 目录不存在，清理操作不会报错，结果区域显示"日志目录不存在"
- 此情况通常发生在系统首次部署尚未产生日志时

## 6. 预览模式（dry_run）

### 为什么需要预览

清理操作不可撤销，直接执行可能带来以下风险：
- 误删正在使用的浏览器会话（导致采集任务中断）
- 删除仍在监控的商品数据（导致任务找不到商品）
- 清理后才发现影响范围超出预期

预览模式让你在执行前先看到"将要处理哪些条目"，相当于"试运行"。

### 预览与执行的差异

| 维度 | 预览模式（dry_run=ON） | 实际执行（dry_run=OFF） |
|------|------------------------|-------------------------|
| 是否真正删除 | 否，仅列出条目 | 是，物理删除 |
| 结果列表前缀 | `[预览] 将删除 xxx` | `已删除 xxx` |
| 是否弹二次确认 | 否 | 是，浏览器原生弹窗 |
| 是否刷新状态卡片 | 否（便于对比） | 是，自动刷新 |
| 是否写入审计日志 | 是 | 是 |
| 按钮颜色 | 默认主题色 | 红色（警示） |
| 视觉标识 | 无特殊标识 | 显示红色"将执行真实删除"标签 |

### 推荐工作流（先预览再执行）

1. **配置参数**：选择清理范围、设置保留天数
2. **保持预览开关开启**（默认即为开启）
3. **点击清理按钮**：查看结果区域列出的待处理条目
4. **评估影响**：
   - 待处理条目数量是否符合预期？
   - 待删除的目录 / 文件 / 数据是否真的可以删除？
5. **关闭预览开关**：卡片显示红色"将执行真实删除"标签，按钮变红
6. **点击清理按钮**：浏览器弹出原生确认框
7. **点击"确认"**：执行真实删除
8. **查看结果**：状态卡片自动刷新，结果区域显示已删除条目

> 提示：日志预览时右上角会额外弹出 toast 提示"预览完成：将处理 N 项日志"或"预览完成：无需要清理的日志文件"，方便快速判断。

## 7. 二次确认机制

### 弹窗形式

关闭预览模式后点击清理按钮，会弹出**浏览器原生确认框**（不是页面内的弹窗）。这种设计的好处是：原生弹窗无法被前端代码绕过，必须由用户主动点击"确认"或"取消"。

### 不同清理类型的话术差异

| 清理类型 | 弹窗话术 | 设计意图 |
|----------|----------|----------|
| 缓存清理 | 确认清理缓存？此操作不可撤销。 | 标准警示 |
| 数据库清理 | 确认清理数据库？**建议先备份数据**。此操作不可撤销。 | 额外提示备份，因为数据库清理影响最大 |
| 日志清理 | 确认清理日志文件？此操作不可撤销。 | 标准警示 |

### 为什么需要双重确认

清理操作本质上是"高风险且不可逆"的：

1. **第一重确认**：关闭预览开关 — 用户主动选择"我要真删"
2. **第二重确认**：浏览器原生弹窗 — 用户再次确认"我确实要真删"

两层确认的设计目的：
- 防止误触（点击按钮不等于确认删除）
- 防止匆忙操作（弹窗强制用户停顿思考）
- 留出反悔机会（弹窗的"取消"按钮可立即中止）

> 弹窗点击"取消"后不会发起任何请求，结果区域保持不变，可重新调整参数后再次尝试。

## 8. 审计与可追溯

### 审计日志记录内容

每次清理操作（**包括预览模式**）都会自动写入系统事件表（`events`），记录以下信息：

| 字段 | 内容 |
|------|------|
| 类型（type） | `maintenance.cache` / `maintenance.database` / `maintenance.logs`（按清理类别区分） |
| 阶段（stage） | 固定为 `cleanup` |
| 等级（level） | `info`（正常）或 `err`（出现错误时） |
| 消息（message） | 例如：`清理cache(all): 5 项完成` 或 `清理database(old_events): 12345 项完成, 1 错误` |
| 详情（payload） | 类别、目标、清理条数、错误条数、前 20 条已清理项、前 5 条错误信息 |
| 时间（created_at） | 操作发生的时间戳 |

### 审计日志的容错

审计写入失败**不会阻塞**主清理流程。即使审计记录失败，清理操作仍会正常完成并返回结果。这是为了避免"清理成功了但用户看不到结果"的尴尬情况。

### 如何查询审计日志

1. 进入侧栏 → **实时日志** 页面
2. 在过滤条件中按 `type` 字段筛选：
   - `maintenance.cache` — 查看所有缓存清理记录
   - `maintenance.database` — 查看所有数据库清理记录
   - `maintenance.logs` — 查看所有日志清理记录
3. 点击具体事件可查看 `payload` 中的完整详情（清理类别、目标、数量、错误等）

### 审计内容限制

为防止审计日志自身膨胀：
- 已清理条目列表仅保留前 20 条
- 错误信息列表仅保留前 5 条
- 不记录任何用户凭据、Cookie、Token（符合安全规范）

## 9. 常见场景

### 场景 1：日常磁盘清理（缓存 + 日志）

**适用情况**：系统运行 1-2 个月后，C 盘 / 安装目录空间紧张，但数据库查询正常。

**操作步骤**：

1. 进入「系统维护 → 系统清理」页面，查看存储状态卡片
2. **缓存清理**：
   - 清理范围选择「全部缓存」
   - 保持预览开关开启
   - 点击「清理缓存」 → 查看预览结果（应显示若干 `webview_data_*` 与 `__pycache__` 目录）
   - 关闭预览开关 → 点击「清理缓存」 → 弹窗点击「确认」
   - 等待执行完成，状态卡片自动刷新
3. **日志清理**：
   - 清理规则选择「按天数清理」
   - 保留天数设置为 7
   - 保持预览开关开启
   - 点击「清理日志」 → 查看预览结果（应显示若干天前的日志文件）
   - 关闭预览开关 → 点击「清理日志」 → 弹窗点击「确认」
4. 点击右上角「刷新状态」按钮，对比清理前后的存储占用

> 提示：清理浏览器数据后需重新登录闲鱼，建议在无活跃采集任务时执行。

### 场景 2：数据库空间回收（旧事件 + VACUUM）

**适用情况**：`events` 表累积到几十万行，数据库文件明显偏大，查询变慢。

**操作步骤**：

1. 进入页面，查看存储状态卡片中的"数据库"列
2. 关注 `events` 数量（在副信息中显示）
3. **数据库清理**：
   - 清理范围选择「旧事件记录」
   - 保留天数设置为 30（保留近 30 天事件）
   - 保持预览开关开启
   - 点击「清理数据库」 → 查看预览结果（应显示"将删除 N 条 30 天前的事件"）
   - 评估 N 是否合理（通常为总量的 50%-90%）
   - 关闭预览开关 → 点击「清理数据库」 → 弹窗点击「确认」（**建议先备份数据**）
4. **VACUUM 压缩**：
   - 清理范围选择「VACUUM 压缩」
   - 保持预览开关开启
   - 点击「清理数据库」 → 应显示"将执行 VACUUM 压缩数据库"
   - 关闭预览开关 → 点击「清理数据库」 → 弹窗点击「确认」
   - 等待 1-3 秒（视数据库大小），观察数据库文件大小变化

> 提示：也可以直接选「全部清理」，一次性完成"删旧事件 + 删旧商品 + 删已售关联 + VACUUM"全流程。

### 场景 3：清理 30 天前的旧数据

**适用情况**：希望统一清理 30 天前的所有冗余数据，简化操作。

**操作步骤**：

1. 进入页面，查看存储状态卡片
2. **数据库清理**：
   - 清理范围选择「全部清理」
   - 保留天数设置为 30
   - 保持预览开关开启
   - 点击「清理数据库」 → 查看预览结果，应依次显示：
     - 将删除 N 条 30 天前的事件
     - 将删除 M 条 30 天前未关联的商品
     - 将删除 K 条已售商品关联
     - 将执行 VACUUM 压缩数据库
   - 评估各项数量是否合理
   - 关闭预览开关 → 点击「清理数据库」 → 弹窗点击「确认」
3. 等待执行完成（数据库较大时可能需要 2-5 秒）
4. 状态卡片自动刷新，观察数据库大小变化

### 场景 4：清理失败任务的关联数据

**适用情况**：部分任务已失效，但其关联的商品记录仍占用空间。

**操作步骤**：

1. 进入页面，查看存储状态卡片中的"商品"数量
2. **数据库清理**：
   - 清理范围选择「旧未关联商品」
   - 保留天数设置为 30（或按实际需求调整）
   - 保持预览开关开启
   - 点击「清理数据库」 → 查看预览结果
   - 系统会自动排除仍在监控任务中的商品（关联保护机制）
   - 关闭预览开关 → 点击「清理数据库」 → 弹窗点击「确认」
3. 若希望同时清理已售商品的关联记录：
   - 清理范围改为「已售商品关联」
   - 重复上述预览 → 执行流程

> 提示：被任务监控的商品不会被清理，可放心执行。

### 场景 5：清理过大的日志文件

**适用情况**：某次异常导致单个日志文件膨胀到几十 MB 甚至更大，影响磁盘空间。

**操作步骤**：

1. 进入页面，查看存储状态卡片中的"日志文件"列
2. 关注文件数量与总大小，若总大小异常偏高（如 >50MB），可能存在大文件
3. **日志清理**：
   - 清理规则选择「大文件清理 (>10MB)」
   - 此时**不显示**保留天数输入框（与天数无关）
   - 保持预览开关开启
   - 点击「清理日志」 → 查看预览结果，应列出所有 >10MB 的日志文件及其大小
   - 关闭预览开关 → 点击「清理日志」 → 弹窗点击「确认」
4. 结果区域显示释放的磁盘空间（MB）

### 场景 6：系统迁移前完整清理

**适用情况**：系统准备迁移到新服务器，希望精简数据库与文件，减小迁移体积。

**操作步骤**：

1. **强烈建议先备份数据库**：复制 `data/xianyu.db` 到安全位置
2. 进入「系统清理」页面，记录清理前的存储状态
3. **缓存清理**：选「全部缓存」 → 预览 → 执行
4. **日志清理**：选「全部清理」、保留天数 7 → 预览 → 执行
5. **数据库清理**：选「全部清理」、保留天数 30 → 预览 → 执行
6. 点击「刷新状态」对比清理前后
7. 关闭系统，复制精简后的 `data/` 目录到新服务器

### 场景 7：审计回溯某次误删

**适用情况**：怀疑某次清理操作删除了不该删的数据，希望查证。

**操作步骤**：

1. 进入侧栏 → **实时日志** 页面
2. 在过滤条件中按 `type` 筛选：
   - `maintenance.cache` / `maintenance.database` / `maintenance.logs`
3. 按时间倒序查看最近的清理记录
4. 点击具体事件，查看 `payload` 详情：
   - `target` — 当时清理的目标
   - `cleaned_count` — 清理了多少条
   - `cleaned_items` — 前 20 条已清理项的名称
   - `errors` — 前 5 条错误信息（如有）
5. 根据审计记录判断是否需要恢复（从备份还原数据库）

> 提示：审计日志仅记录元数据，不含完整文件路径或数据内容，无法直接"撤销"清理，需依赖数据库备份恢复。

## 10. 常见问题 FAQ

**Q1：清理后磁盘空间没变化？**

A：可能的原因：
- **缓存清理**：浏览器数据目录可能被 WebView2 进程占用，未完全释放。关闭闲鱼猎人后重新启动，空间会释放。
- **数据库清理**：DELETE 不会缩小数据库文件，只是标记为可复用。需要再执行一次「VACUUM 压缩」才能真正释放空间。
- **日志清理**：日志文件可能正在被进程写入，已删除但仍占用空间。重启 Web 服务后释放。

**Q2：误删了怎么办？**

A：清理操作**不可撤销**，所有删除均为物理删除。恢复途径：
- **数据库**：从最近的备份还原 `data/xianyu.db` 文件
- **日志**：无法恢复（日志不备份）
- **缓存**：无需恢复，重新运行系统会自动重建
- **审计回溯**：进入「实时日志」页按 `type=maintenance.*` 过滤，查看误删操作的详情

> 强烈建议：执行数据库清理前，先备份 `data/xianyu.db` 文件。

**Q3：为什么 .venv 下的 __pycache__ 不清理？**

A：`.venv` 是 Python 第三方依赖目录，包含数千个子目录。如果扫描进入 `.venv`：
- 单次扫描耗时从 0.1 秒飙升至 30 秒以上
- 清理这些缓存仅让下次导入变慢，没有任何收益
- 可能误删依赖包的关键文件

系统通过 `os.walk` 原地剪枝技术跳过 `.venv` 及其他 8 个目录（共 9 个），将扫描时间稳定在 0.1 秒以内。

**Q4：VACUUM 会锁表吗？**

A：VACUUM 会持有数据库的**排他锁**，期间数据库不可读写。但本系统的 VACUUM 设计有两层保护：
- **在事务外独立执行**：通过独立的 AUTOCOMMIT 连接，不会与其他操作冲突
- **执行时间短**：100MB 数据库约 1-3 秒，不会长时间阻塞

建议在低峰期执行 VACUUM，或先暂停采集任务。

**Q5：dry_run 显示的数量和实际删除不一致？**

A：这通常是 Bug，应立即反馈给开发人员。可能原因：
- 状态卡片的统计范围与实际清理范围不一致
- 预览期间有新数据产生（如采集任务正在写入）
- 并发清理导致数据变化

排查方法：进入「实时日志」页查看该次清理的审计记录，对比 `cleaned_count` 与预览数量。

**Q6：清理过程中能关闭页面吗？**

A：不建议。清理请求已发送到后端，即使关闭页面，后端仍会继续执行；但你将无法看到结果与错误提示。如果必须离开，建议：
- 等待结果区域出现"完成"提示后再关闭
- 或先切换到预览模式确认无误，再关闭预览执行后离开

**Q7：清理浏览器数据后为什么闲鱼掉线了？**

A：浏览器数据目录（`webview_data_*`）包含闲鱼的登录 Cookie 与浏览器指纹。清理后 Cookie 失效，需重新登录闲鱼。建议：
- 在无活跃采集任务时执行
- 清理后立即重新登录闲鱼，避免任务调度失败

**Q8：为什么数据库清理建议先备份数据？**

A：数据库清理涉及 DELETE 操作，**不可撤销**。虽然系统有关联保护（不删除监控中的商品）和参数化查询（防注入），但仍可能因以下原因误删：
- 保留天数设置过小（如设为 1，会删除昨天之前的数据）
- 选择了错误的清理范围
- 数据本身有问题（如时间戳异常）

备份方法：复制 `data/xianyu.db` 文件到其他位置即可。

**Q9：可以同时清理多个类别吗？**

A：可以，但需要分别点击三张卡片的清理按钮。三张卡片相互独立，可以并行配置参数，但建议**串行执行**（一次只点一个清理按钮），避免：
- 数据库清理与日志清理同时争抢磁盘 IO
- 缓存清理与数据库清理同时影响采集任务

**Q10：清理日志的"大文件清理"阈值能调整吗？**

A：当前固定为 10MB，**无法在前端调整**。如需调整阈值，需联系开发人员修改源码并重新部署。变通方案：
- 选「按天数清理」并设置较小的保留天数（如 3 天），间接控制日志总量
- 或选「全部清理」一次性清理所有符合条件的日志

**Q11：为什么 days 输入框允许的最大值是 365？**

A：防止用户输入过大值导致计算溢出或误删全部数据。如果确实需要保留更长时间的数据，建议**不清理**而非设置超大天数。后端另有 `days = max(1, req.days)` 保下限，防止 0 或负值导致删除全表。

**Q12：清理操作可撤销吗？**

A：**不可撤销**。所有清理操作（除 VACUUM）均为物理删除：
- 缓存清理：`shutil.rmtree` 物理删除目录
- 数据库清理：SQL `DELETE` 物理删除行
- 日志清理：`unlink` 物理删除文件

唯一可恢复的途径是从备份还原。强烈建议执行前先预览、先备份。

## 11. 最佳实践

1. **先预览再执行**
   - 任何清理操作前，先保持预览开关开启查看影响范围
   - 评估预览结果符合预期后，再关闭预览执行真实删除
   - 这是避免误删的最有效手段

2. **定期清理频率**
   - 缓存清理：每月 1 次（或磁盘占用超过 200MB 时）
   - 日志清理：每周 1 次（保留 7 天）
   - 数据库清理：每月 1 次（保留 30 天）
   - VACUUM 压缩：每次大规模 DELETE 后执行一次

3. **保留天数推荐值**
   - 日常维护：30 天（兼顾历史查询与空间占用）
   - 高频采集系统：7-14 天（数据量大，需频繁清理）
   - 审计需求高：90 天（保留更长时间便于回溯）
   - 不建议 >90 天，否则失去清理意义

4. **备份建议**
   - **执行数据库清理前**：必须备份 `data/xianyu.db` 文件
   - **每周全量备份**：复制整个 `data/` 目录到备份位置
   - **保留至少 2 份历史备份**：避免最近备份损坏

5. **低峰期执行**
   - 缓存清理：会中断闲鱼登录，建议在无采集任务时执行
   - 数据库清理：会持有数据库锁，建议在查询低谷期执行
   - VACUUM：会持有排他锁，建议在系统空闲时执行

6. **关注审计日志**
   - 定期进入「实时日志」页查看 `maintenance.*` 类型事件
   - 核对清理记录是否符合预期
   - 异常清理记录（如 `level=err`）需立即排查

7. **避免并发清理**
   - 一次只点击一个清理按钮，等待完成后再点下一个
   - 不要同时打开多个浏览器标签执行清理
   - SQLite 单写入特性决定了并发清理会触发锁错误

8. **关注统计与清理范围一致性**
   - 若发现"状态卡片显示 0MB，但清理时列出 271 项"，说明统计与清理范围不一致
   - 此为 Bug，应立即反馈给开发人员修复
