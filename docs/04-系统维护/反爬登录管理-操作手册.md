## 1. 概述

「反爬登录管理」是闲鱼猎人系统「系统维护」分组下的二级菜单，**用于集中管理闲鱼登录会话、Cookie 凭证、浏览器指纹和请求频率伪装，保障系统的商品采集与自动下单能力不被闲鱼风控拦截**。

闲鱼（淘宝系）通过持续监控登录态、浏览器指纹、请求节奏来判断是否为自动化工具。一旦判定异常，会触发验证码、限流甚至封号。本菜单把这些原本散落在系统内部的反爬能力统一暴露给运维人员，让用户在一个页面里完成：

- 选择合适的登录策略
- 启动 / 停止会话后台续期
- 实时查看会话健康分
- 手动管理或恢复 Cookie
- 查看当前浏览器指纹
- 调整请求频率伪装

### 1.1 谁适合使用本菜单

| 角色 | 使用场景 |
|------|---------|
| 运营人员 | 日常巡检健康分、观察 WAF 状态、确认会话活跃 |
| 系统管理员 | 排查登录失效问题、从浏览器同步 Cookie、切换登录模式 |
| 新部署用户 | 首次启动系统时初始化协调器、选择登录策略 |
| 高级调试 | 查看指纹 profile、频率统计判断请求节奏是否自然 |

> **不需要技术背景**，但需要理解"会话过期"、"健康分下降"等运维信号的处置流程。

### 1.2 术语速查

| 术语 | 通俗解释 |
|------|---------|
| Cookie | 网站的登录凭证，相当于"通行证" |
| 指纹 | 浏览器的身份证，让网站认不出是自动化工具 |
| WAF | 网站的反爬防火墙 |
| 熔断 | 连续失败太多自动停一停，避免被风控封号 |
| CDP 模式 | 直接连接你正在用的浏览器 |
| launch 模式 | 自动开一个隐藏浏览器 |
| Token | API 调用的令牌，会过期需要续期 |
| 续期 | Token 快过期前自动刷新令牌有效期 |
| 自愈 | 系统自动尝试恢复会话，无需用户干预 |
| 健康分 | 综合评估当前登录态的得分（0-100） |
| 主动失效 | 用户主动让某层 Cookie 失效 |
| 兜底同步 | 多重备份机制，确保状态准确 |

## 2. 核心特性

- **六大功能模块集中展示**：登录策略 / 会话管理 / 健康检查 / Cookie 三层管理 / 指纹信息 / 频率伪装，全部一屏可见
- **两种登录模式可选**：launch 模式（系统自动开一个隐藏浏览器）与 CDP 模式（直接连接你正在用的真实浏览器），刷新页面后会记住上次选择
- **会话状态实时刷新**：会话状态与频率统计每 10 秒自动刷新，Cookie 层状态每 30 秒自动同步
- **健康分等级着色**：健康分 ≥ 80 显示绿色（健康），≥ 60 显示黄色（注意），< 60 显示红色（异常）
- **Cookie 三层结构化展示**：身份层（identity）/ 会话层（session）/ 追踪层（tracking）独立显示有效性，支持单独失效
- **从浏览器导入 Cookie 预览**：可读取 Edge / Chrome 浏览器中已登录的闲鱼 Cookie，预览无误后再确认写入，避免误覆盖现有登录态
- **自愈机制自动恢复**：续期失败时系统先尝试 JSON 同步恢复（低成本），连续失败 2 次后才触发自动重登（10 分钟冷却，避免频繁重登）
- **频率伪装统计透明化**：实时显示总请求数、噪声请求占比、平均间隔等指标，便于判断当前请求节奏是否自然

## 5. 六大模块详解

### 5.1 登录策略

**用途**：根据当前环境（是否检测到本机已运行的 Edge/Chrome、是否已有持久化 Cookie 等）推荐最合适的登录方式。

**支持的 5 种策略**：

| 策略标识 | 中文名称 | 适用场景 |
|---------|---------|---------|
| `cdp_connect` | CDP 连接系统浏览器 | 本机已打开并登录闲鱼的真实浏览器 |
| `reuse_userdata` | 复用 browser-data Cookie | 系统已持久化过登录态 |
| `browser_import` | 从系统浏览器导入 | Edge/Chrome 已登录闲鱼，希望复用 |
| `qr_scan` | 扫码登录 | 用闲鱼 App 扫码 |
| `cookie_inject` | 手动 Cookie 注入 | 用户从其他渠道拿到 Cookie 文本 |

**两种模式（CDP 开关）**：

| 模式 | 通俗解释 | 优点 | 缺点 |
|------|---------|------|------|
| launch（默认） | 系统自动开一个隐藏浏览器 | 不依赖用户已开的浏览器；自动注入指纹 | 占用独立资源；指纹是随机的 |
| CDP | 直接连接你正在用的浏览器 | 复用真实指纹与登录态；风控压力低 | 需要保持浏览器开启；本机调试更适合 |

**初始化按钮**：点击「初始化协调器（CDP/Launch 模式）」会按当前 CDP 开关状态初始化协调器单例。

> **CDP 开关会持久化**：刷新页面后保持上次的选择（保存在浏览器 localStorage 的 `xh.anticrawl.useCdp` key 中）。

### 5.2 会话管理

**用途**：管理 TokenRenewer 后台续期。会话活跃时系统会定期检查 Token 是否过期，过期前自动通过浏览器导航刷新 Token。

**显示字段**：

| 字段 | 含义 |
|------|------|
| 会话状态 | 活跃 / 未启动 |
| 运行时间 | 会话已运行的秒数（仅活跃时显示） |
| Token 年龄 | 当前 Token 距上次刷新的秒数；过期时显示为红色 |

**警告提示**：当检测到有效 Cookie 但会话未启动时，Card 顶部会显示黄色警告 Alert，提示「正常情况下登录/导入/注入完成后会自动启动 TokenRenewer 后台续期」。

**按钮互斥逻辑**：
- 会话未启动 → 「启动会话」可点 / 「停止会话」置灰
- 会话已启动 → 「启动会话」置灰 / 「停止会话」可点

**幂等说明**：如果会话已被登录流程自动启动，再次点击「启动会话」会返回「会话已是活跃状态」提示，**不算失败**。

### 5.3 健康检查

**用途**：综合评估当前登录态是否健康，给出 0-100 分的量化得分和处置建议。

**4 个维度权重**：

| 维度 | 权重 | 检查内容 |
|------|------|---------|
| Cookie | 40 | `_m_h5_tk` 是否存在/有效；identity 层是否至少有一个 Cookie；关键 cookie 是否过期 |
| API | 30 | 默认未配置，**视为通过** |
| 页面 | 20 | 默认未配置，**视为通过** |
| WAF | 10 | 验证码处理失败率 |

**健康分等级**：

| 得分 | 颜色 | 状态 | 含义 |
|------|------|------|------|
| ≥ 80 | 绿色 | 健康 | 一切正常，可放心使用 |
| ≥ 60 | 黄色 | 注意 | 有风险信号，建议观察或处置 |
| < 60 | 红色 | 异常 | 立即处理 |

**WAF 状态判定**（基于验证码处理统计）：

| 失败率 | 状态 | 含义 |
|--------|------|------|
| > 50% | 已熔断 | 风控火力全开，应立即暂停采集 |
| > 20% | 警告 | 有失败但未熔断，建议降频观察 |
| ≤ 20% | 正常 | 风控平稳 |

**建议动作**：健康检查后会给出 4 种建议之一：
- 无需操作
- 续期 Token
- 重新登录
- 暂停 + 通知

> **自动初始化**：第一次点击「检查」时若提示「未配置健康检查器」，系统会自动调用初始化接口配置默认检查器并重试，无需手动处理。

### 5.4 Cookie 三层管理

**用途**：把闲鱼 Cookie 按职责分成 3 层独立管理，方便精准失效与恢复。

| 层 | 中文名 | 包含的 Cookie | 更新频率 | 依赖 |
|----|--------|--------------|---------|------|
| identity | 身份层 | `unb` / `cookie2` / `sgcookie` / `t` / `_tb_token_` / `lg2` | 仅登录时变化 | 无 |
| session | 会话层 | `_m_h5_tk` / `_m_h5_tk_enc` | 15-22 分钟 | identity |
| tracking | 追踪层 | `cna` / `tfstk` / `xlly_s` / `ali_aplus_v3` / `utdid` | 每次请求可能变化 | 无 |

**显示规则**：

| 状态 | 显示文本 |
|------|---------|
| 有效且 Cookie 数量 > 0 | 「N 个 Cookie」 |
| 有效但 Cookie 数量 = 0 | 「已恢复（无 Cookie）」 |
| 无效 | 「未初始化」 |

**主动失效**：每层 Card 下方有「主动失效」按钮，点击后弹出确认框。失效 identity 会**级联导致 session 失效**（因为 session 依赖 identity）。

> **主动失效的特点**：通过按钮主动失效的层不会被自动同步覆盖，必须用户手动更新 Cookie 或重新登录才能恢复。

### 5.5 指纹信息

**用途**：展示当前浏览器指纹 profile，便于调试时确认指纹是否合理。

**显示字段**：

| 字段 | 含义 |
|------|------|
| Profile | 指纹名称（如 `fp_a3f8b2c1`） |
| UA | User-Agent 用户代理字符串 |
| 平台 | 如 `Win32` |
| 厂商 | 如 `Google Inc.` |
| CPU 核心 | 如 `8` |
| 内存 | 如 `8 GB` |
| GPU | 厂商 + 渲染器 |
| 屏幕 | 宽 × 高（如 `1920 × 1080`） |
| 色深 | 如 `24 bit` |
| Stealth 脚本数 | launch 模式为 2（指纹 + AWSC 伪装），CDP 模式为 0 |

**两种模式提示**：

| 模式 | 显示 |
|------|------|
| launch 模式 | 完整指纹字段表格 |
| CDP 模式或未初始化 | 显示提示 Alert：「CDP 模式使用真实浏览器，无需指纹注入。点击上方「初始化协调器」生成 launch 模式指纹」 |

> **安全提示**：本 Card 不会展示 `canvas_noise_seed` 等敏感种子字段。

### 5.6 频率伪装

**用途**：展示请求频率伪装的统计数据，判断当前请求节奏是否自然。

**显示字段**：

| 字段 | 含义 | 健康范围 |
|------|------|---------|
| 总请求数 | 累计发起的请求总数 | 持续增长 |
| 噪声请求 | 其中用于打乱规律的噪声请求数 | 与总请求数保持比例 |
| 噪声占比 | 噪声请求 / 总请求数（百分比） | 10%-20% 较自然 |
| 平均间隔 | 请求之间的平均秒数 | 应略大于中位间隔 |
| 中位间隔 | 排序后位于中间的间隔秒数 | 反映典型请求节奏 |
| 标准差 | 间隔的离散程度 | 越大越像人类 |

**策略说明**：系统使用对数正态分布模拟人类请求间隔的右偏特征（平均间隔 > 中位间隔），并插入噪声请求打乱请求规律，让闲鱼风控难以从节奏上识别出是机器人。

**操作类型与延迟**：系统针对不同操作类型设置不同的请求延迟：

| 操作类型 | 说明 |
|---------|------|
| browse | 浏览商品列表 |
| search | 搜索商品 |
| scroll | 滚动加载更多 |
| detail | 查看商品详情 |
| login | 登录操作 |

> **自动刷新**：每 10 秒自动刷新一次，也可点击 Card 右上角刷新按钮立即刷新。

## 6. 健康检查解读

### 6.1 健康分计算

健康分满分 100 分，按 4 个维度加权累计：

| 维度 | 权重 | 默认是否配置 | 默认通过得多少分 |
|------|------|-------------|-----------------|
| Cookie | 40 | ✅ 已配置 | 0 或 40（看是否有效） |
| API | 30 | ❌ 未配置 | 30（默认通过） |
| 页面 | 20 | ❌ 未配置 | 20（默认通过） |
| WAF | 10 | ✅ 已配置 | 0 或 10（看是否触发风控） |

**默认满分为 70 分**（Cookie 40 + WAF 10 + API 默认通过 30 - 但需注意：实际默认配置下未配置维度视为 100% 通过，最终满分为 40 + 30 + 20 + 10 = 100，但默认仅 cookie + waf 两个维度真正参与判定，故常见的"满分"现象为 70 分）。

> **简化理解**：日常看到健康分 70 分是正常的（Cookie 有效 + WAF 正常）；低于 70 分需要关注；低于 60 分需要立即处理。

### 6.2 WAF 状态判定

WAF（网站的反爬防火墙）状态基于验证码处理统计推断：

| 失败率 | WAF 状态 | 应对建议 |
|--------|---------|---------|
| > 50% | 已熔断 | 立即停止采集，等待 30 分钟以上再观察 |
| 20%-50% | 警告 | 降低请求频率，密切关注健康分 |
| ≤ 20% | 正常 | 无需处理 |

> **没有验证码检测记录时**：WAF 状态自动判为「正常」。

### 6.3 健康分等级着色

| 健康分 | 颜色 | 含义 | 处置 |
|--------|------|------|------|
| ≥ 80 | 绿色 | 健康 | 无需操作 |
| 60-79 | 黄色 | 注意 | 观察 WAF 状态、Token 年龄，必要时手动续期 |
| < 60 | 红色 | 异常 | 立即按建议动作处置（重新登录 / 暂停） |

`[截图：健康检查 Card 三种着色状态对比]`

### 6.4 健康分下降时怎么办

按以下顺序排查：

1. **查看 Cookie 维度**：如果 Cookie 无效 → 检查 identity 层是否有效 → 失效则更新 Cookie 或重新登录
2. **查看 WAF 维度**：如果 WAF 为「警告」或「已熔断」→ 暂停采集，等待 10-30 分钟让风控冷却
3. **查看 Token 年龄**：如果 Token 已过期（红色）→ 检查会话是否活跃，必要时启动会话让 TokenRenewer 自动续期
4. **查看建议动作**：Card 底部的建议动作 Alert 会给出明确处置建议（续期 Token / 重新登录 / 暂停 + 通知）

### 6.5 健康检查 5 步内部流程（参考）

健康检查内部按 5 步顺序执行，了解此流程有助于理解为什么有时健康分会"突然变化"：

| 步骤 | 名称 | 通俗解释 |
|------|------|---------|
| 1 | 加载并检查 session 层 | 读取本地存储，确认 `_m_h5_tk` 是否存在且未过期；过期会尝试从浏览器内存刷新 |
| 2 | 检查 identity 层 | 确认身份层至少有一个 Cookie（不要求全部，因为不同登录方式返回的 Cookie 集合不同） |
| 3 | 检查关键 cookie 过期 | 仅检查 identity + session 层关键 cookie 的过期时间（tracking 层过期不影响） |
| 4 | 同步层状态 | 如果发现 identity 层失效但不是用户主动失效的，重新同步层状态 |
| 5 | 检查采集器会话标志 | 检查服务端是否返回过 RGV587_ERROR（会话已被注销）；如有则清理粘性标志 |

> **用户感知**：这 5 步对用户透明。用户只看到最终的健康分与 4 维状态。如果健康分"突然变化"，通常是某一步判定结果变了（如服务端注销会话导致第 5 步失败）。

### 6.6 m5tk 过期双重判定

`_m_h5_tk` 是闲鱼 API 调用的核心 Token，系统对其过期判定采用**双重机制**，任一过期都视为失效：

| 判定方式 | 说明 |
|---------|------|
| cookie.expires 字段 | 标准 Cookie 过期时间；session cookie 为 -1 时不参与判定 |
| is_m5tk_expired | 检查 Token 内嵌的时间戳是否过期（TTL=1200 秒，约 20 分钟） |

> **为什么需要双重**：`_m_h5_tk` 的 cookie.expires 通常是 -1（session cookie）无法判断真实过期，但 Token 内嵌的时间戳 + 服务端 TTL 决定了真实有效期。

## 7. Cookie 管理详解

### 7.1 三层 Cookie 的作用

| 层 | 通俗解释 | 失效影响 |
|----|---------|---------|
| identity（身份层） | 网站的登录凭证，相当于"身份证" | 失效后系统完全无法识别用户，必须重新登录 |
| session（会话层） | 网站的会话令牌，相当于"通行证" | 失效后 API 调用失败，但身份仍在，可通过续期恢复 |
| tracking（追踪层） | 网站的追踪 Cookie，相当于"脚印" | 失效后不影响核心功能，但风控可能加强监控 |

### 7.2 主动失效某层（影响范围）

| 失效层 | 直接影响 | 级联影响 | 恢复方式 |
|--------|---------|---------|---------|
| identity | identity 标记为失效 | session 自动失效（依赖关系） | 必须重新登录或更新 Cookie |
| session | session 标记为失效 | 无 | 续期或更新 Cookie 即可恢复 |
| tracking | tracking 标记为失效 | 无 | 后续请求会自动重新生成 |

**重要约束**：用户主动失效的层**不会被自动同步覆盖**，必须用户手动恢复。

### 7.3 从浏览器导入（三种解密方式）

系统支持从 Edge / Chrome 浏览器的本地数据库读取已加密的 Cookie 并解密：

| 加密格式 | 适用版本 | 解密方式 |
|---------|---------|---------|
| DPAPI | 旧版浏览器（v10 前缀） | Windows 数据保护 API |
| AES-256-GCM | Chrome v80+（v10 前缀） | 从 Local State 获取 AES 密钥解密 |
| 明文 | 无加密的 Cookie 值 | 直接返回 |

**目标域名**：仅读取 `goofish.com` / `taobao.com` / `alipay.com` 域名下的 Cookie。

**目标 Cookie 名称**：`_m_h5_tk` / `_m_h5_tk_enc` / `cookie2` / `sgcookie` / `unb` / `lg2` / `tracknick`。

**安全保证**：所有解密在本地完成，**不传输到外部**。

### 7.4 导入预览 vs 确认导入

为避免误覆盖现有登录态，导入分为两步：

| 步骤 | 操作 | 是否写入 |
|------|------|---------|
| 1. 预览 | 在 Cookie 更新弹窗点击「从浏览器导入」 | ❌ 不写入，仅覆盖文本框 |
| 2. 确认 | 在文本框中确认或修改后点击「更新」 | ✅ 真正分层写入 |

> **设计原因**：直接写入会覆盖现有登录态。如果浏览器中的 Cookie 比当前系统中的旧，会反而让登录态变差。预览步骤让用户有机会检查后再决定是否提交。

### 7.5 三重兜底同步

为了让 Cookie 层状态尽可能准确反映真实情况，系统在每次查询层状态时执行三步兜底同步：

| 步骤 | 名称 | 通俗解释 |
|------|------|---------|
| 1 | JSON 同步 | 从本地存储读取 Cookie，同步层状态 |
| 2 | 浏览器内存兜底 | 如果 JSON 中没有但浏览器内存中有，从浏览器读取并回写 JSON |
| 3 | 功能可用性兜底 | 如果 JSON 和浏览器都没有，但实际功能能用（搜索能成功），强制恢复层状态 |

**为什么需要三重**：

- 第一步解决"服务重启后内存状态丢失"
- 第二步解决"JSON 落后于浏览器内存"
- 第三步解决"JSON 和浏览器都没初始化但功能实际可用"

> **用户感知**：这三步对用户透明，用户只看到每 30 秒刷新一次的层状态结果。理解原理有助于在状态突然变化时不困惑。

### 7.6 浏览器 Cookie 数据库锁定处理

从浏览器导入 Cookie 时，如果浏览器正在运行，Cookie 数据库可能被锁定。系统采用 4 级降级策略自动处理：

| 级别 | 策略 | 说明 |
|------|------|------|
| 1 | SQLite immutable 模式 + backup | 完全绕过文件锁，最优先尝试 |
| 2 | SQLite mode=ro + nolock | 兼容旧版 SQLite |
| 3 | robocopy + 共享模式复制 | 通过 Windows 共享模式复制文件 |
| 4 | 自动关闭浏览器重试 | 检测到锁定时自动关闭浏览器进程（即使 `auto_close=false`） |

如果 4 级降级都失败，会提示用户**手动关闭浏览器后重试**。

> **关闭浏览器前**：请保存好浏览器中的工作内容，避免数据丢失。

## 8. LoginOrchestrator 自愈机制

### 8.1 什么是自愈

**自愈**：系统检测到续期失败后，自动尝试恢复会话，无需用户干预。

**触发条件**：TokenRenewer 后台续期失败（如浏览器导航失败、网络异常等）。

**自愈目标**：尽可能用低成本方式恢复，避免一失败就重新登录（重新登录对风控压力较大）。

### 8.2 10 分钟冷却期

**冷却期**：自动重登触发后，10 分钟内不会再次触发自动重登。

**为什么需要冷却**：
- 防止频繁重登被风控识别为异常行为
- 给系统时间完成上一轮重登流程
- 避免在环境本身就异常时反复失败

### 8.3 三步策略

自愈按以下顺序尝试恢复：

| 步骤 | 操作 | 通俗解释 |
|------|------|---------|
| 1 | 标记 session 层失效 | 把当前会话令牌标为"不可用"，让后续操作不再使用过期令牌 |
| 2 | 从 JSON 同步恢复 | 重新读取本地存储的 Cookie，看是否子进程已刷新但主进程缓存没更新（低成本恢复） |
| 3 | 自动重登 | 连续失败 ≥ 2 次且冷却期已过才触发；调用外部注入的重登流程（高成本恢复） |

**阈值说明**：

| 参数 | 值 | 含义 |
|------|------|------|
| 连续失败次数阈值 | 2 次 | 累计 2 次失败才触发自动重登 |
| 冷却时间 | 10 分钟（600 秒） | 距上次重登不足 10 分钟时不重复触发 |

### 8.4 何时需要手动干预

自愈失败的常见信号：
- 健康检查 Card 显示「重新登录」建议
- WAF 状态变为「已熔断」
- Cookie 层 identity 失效且 30 秒后仍未恢复

**手动干预方式**：
1. 进入 Cookie 分层管理 → 点击「更新 Cookie」→ 从浏览器导入 → 确认更新
2. 或者重新走登录流程（扫码登录 / 浏览器登录）
3. 如果 WAF 已熔断，建议先暂停采集 30 分钟以上再操作

### 8.5 续期为什么用浏览器导航而非 API

TokenRenewer 续期时通过浏览器导航到 `https://h5.m.taobao.com/` 触发 Token 刷新，而不是直接调用 getTimestamp API。原因如下：

| 方式 | 风控压力 | 说明 |
|------|---------|------|
| 浏览器导航 | 低 | 模拟用户自然行为，符合正常用户浏览模式 |
| 直接调用 API | 高 | 容易被识别为机器行为，触发风控 |

> **续期回写闭环**：导航成功后，系统会读取浏览器 `goofish.com` / `taobao.com` 域的完整 Cookie 回写到本地存储，确保 JSON 与浏览器内存一致。回写失败不影响续期成功状态（Token 已在浏览器内存中刷新）。

### 场景 2：会话失效后自动恢复

**背景**：系统运行中，Token 过期且续期失败。

**预期行为**：

1. TokenRenewer 检测到续期失败
2. 自动标记 session 层失效
3. 尝试从 JSON 同步恢复（如果浏览器子进程已刷新 Cookie）
4. 如果同步成功 → 失败计数清零，继续运行

- Cookie 层 session 短暂显示「未初始化」
- 30 秒内通常能自动恢复

**用户操作**：通常无需干预。如长时间未恢复，参考场景 4 排查。

### 场景 3：手动从浏览器同步 Cookie

**背景**：用户在 Edge 浏览器中重新登录了闲鱼，希望把新 Cookie 同步到系统。

**操作步骤**：

1. 进入「反爬登录管理」页面
2. 在「Cookie 分层管理」Card 点击「更新 Cookie」按钮，弹出更新弹窗
3. 弹窗会自动预填当前 CookieStore 中的 Cookie
4. 在弹窗中选择浏览器（Edge / Chrome）
5. 点击「从浏览器导入（覆盖文本框）」按钮
6. 等待几秒，文本框被新 Cookie 覆盖，下方提示「从 Edge 导入 N 个 Cookie」
7. 检查文本框内容无误后，点击「更新」按钮
8. 系统提示「已更新 N 个 Cookie」，关闭弹窗
9. Cookie 层状态自动刷新

> **如果导入失败**：通常是浏览器 Cookie 数据库被锁定，按提示关闭浏览器后重试。

### 场景 4：健康分下降排查

**背景**：日常巡检发现健康分从 80 降到 40。

**排查步骤**：

1. 进入「健康检查」Card，点击「检查」按钮重新获取健康分
2. 查看 4 个维度的状态：
   - Cookie 维度是否「无效」→ 检查 Cookie 层状态
   - WAF 维度是否「警告」或「已熔断」→ 暂停采集
   - API 维度是否「不可达」→ 检查网络
3. 查看建议动作 Alert，按建议处置：
   - 「续期 Token」→ 启动会话让 TokenRenewer 续期
   - 「重新登录」→ 走登录流程或从浏览器导入
   - 「暂停 + 通知」→ 立即暂停采集

### 场景 5：WAF 状态变 WARNING / BLOCKED 应对

**背景**：健康检查发现 WAF 维度从「正常」变成「警告」。

**应对策略**：

| WAF 状态 | 应对 |
|---------|------|
| 警告 | 降低采集频率，观察 30 分钟；如果继续恶化则暂停 |
| 已熔断 | 立即停止所有采集任务，等待 30 分钟以上；确认风控冷却后再恢复 |

**注意事项**：
- 不要在已熔断状态下继续采集，会加重封号风险
- 恢复后建议先用低频率小批量测试，确认 WAF 状态稳定在「正常」再逐步恢复正常节奏

### 场景 6：切换 launch ↔ CDP 模式

**背景**：原本用 launch 模式，希望切换到 CDP 模式连接本机已开的浏览器。

**操作步骤**：

1. 在「登录策略评估」Card 右上角，打开 CDP 模式开关
2. 点击「初始化协调器（CDP 模式）」按钮
3. 系统提示「协调器已初始化（cdp 模式）」
4. 「指纹信息」Card 切换为提示 Alert「CDP 模式使用真实浏览器，无需指纹注入」
5. 切换完成后建议重新启动会话

> **持久化**：CDP 开关状态会保存在浏览器 localStorage，刷新页面后保持。

### 场景 7：identity 层意外失效

**背景**：发现 identity 层显示「未初始化」，但用户没有主动失效过。

**可能原因**：
- 服务端返回 RGV587_ERROR（会话已被注销）
- 续期失败后系统自动失效

**应对步骤**：

1. 查看会话状态 Card 的 Token 年龄是否过期
2. 点击「健康检查」按钮获取建议动作
3. 如果建议「重新登录」→ 走登录流程或从浏览器导入 Cookie
4. 如果建议「续期 Token」→ 启动会话让 TokenRenewer 自动续期

### 场景 8：刷新页面后状态丢失

**背景**：刷新浏览器后，所有 Card 显示「未初始化」。

**原因**：刷新会重新加载页面状态，但后端协调器是单例不会重置。

**预期行为**：
- 进入页面后并行加载所有数据，几秒内恢复显示
- Cookie 层状态会通过三重兜底同步恢复
- 如果长时间停留在「未初始化」，点击顶部「刷新」按钮重新加载

## 10. 常见问题 FAQ

### Q1：健康分为什么不是 100？

**A**：默认配置下，系统仅配置了 Cookie 和 WAF 两个检查器（共 50 分），另外两个维度（API 和页面）虽默认视为通过，但实际"满分"通常表现为 70 分。这是正常现象，只要 ≥ 60 就属于健康范围。

### Q2：自愈失败怎么办？

**A**：
1. 检查健康检查 Card 的建议动作
2. 如果建议「重新登录」→ 走登录流程或从浏览器导入 Cookie
3. 如果建议「暂停 + 通知」→ 立即停止采集，等待 30 分钟
4. 如果 10 分钟内多次重登失败，参考 Q3

### Q3：launch 和 CDP 哪个更好？

**A**：
- **本机调试 / 已开浏览器** → 推荐 CDP，复用真实指纹，风控压力低
- **服务器部署 / 无真实浏览器** → 推荐 launch，系统自动起隐藏浏览器并注入指纹
- **首次使用** → 看「登录策略评估」Card 的推荐策略

### Q4：导入 Cookie 后为什么还要确认？

**A**：导入按钮仅"预览"——把浏览器中的 Cookie 读到文本框，**不会写入** CookieStore。这样设计是为了避免误覆盖现有登录态（如果浏览器中的 Cookie 比当前系统中的旧，直接写入反而让登录态变差）。需要用户检查无误后点击「更新」才会真正分层写入。

### Q5：主动失效 identity 会怎样？

**A**：identity 失效会**级联导致 session 失效**（因为 session 依赖 identity）。失效后：
- identity 层标记为「未初始化」
- session 层自动标记为「未初始化」
- tracking 层不受影响
- 主动失效的层**不会被自动同步覆盖**，必须重新登录或更新 Cookie 才能恢复

### Q6：频率统计为什么 10 秒才刷新？

**A**：业务模块持续在调用频率伪装模块，前端需要定时拉取才能反映最新请求节奏。10 秒间隔是实时性与服务器压力的平衡点。需要立即查看可点击 Card 右上角刷新按钮。

### Q7：Cookie 层状态为什么 30 秒才刷新？

**A**：后端在每次查询层状态时会执行三重兜底同步（JSON 同步 → 浏览器内存兜底 → 功能可用性兜底），相对耗时。30 秒间隔既能反映最新状态，又不会给后端造成过大压力。

### Q8：Token 年龄为什么显示红色？

**A**：Token 已过期。可能原因：
- TokenRenewer 后台续期未启动（会话未启动）
- 续期失败（参考场景 4 排查）
- 网络异常导致导航失败

**处置**：先确认会话是否活跃；如活跃但 Token 长期红色，建议从浏览器导入最新 Cookie。

### Q9：CDP 模式为什么指纹信息 Card 是空的？

**A**：CDP 模式直接连接你正在用的真实浏览器，复用真实指纹，**无需指纹注入**。Card 会显示提示 Alert「CDP 模式使用真实浏览器，无需指纹注入」。如需查看指纹字段，请切换到 launch 模式并重新初始化协调器。

### Q10：「启动会话」提示「会话已是活跃状态」是失败吗？

**A**：**不是失败**。这是正常的幂等行为——登录流程通常会在登录成功后自动启动会话，再次点击「启动会话」按钮时后端返回「会话已处于活跃状态」，前端以 info 提示形式告知用户。系统提示颜色为蓝色（info），不是红色（error）。

### Q11：浏览器导入失败提示「数据库被锁定」怎么办？

**A**：Edge / Chrome 浏览器正在运行时会锁定 Cookie 数据库。系统会自动尝试 4 级降级策略：
1. SQLite immutable 模式 + backup
2. SQLite mode=ro + nolock
3. robocopy + 共享模式复制
4. 检测到锁定时自动关闭浏览器重试

如果仍然失败，请按提示**手动关闭浏览器**后重试。注意：关闭浏览器前请保存好浏览器中的工作内容。

### Q12：健康检查提示「未配置健康检查器」怎么办？

**A**：系统会自动调用初始化接口配置默认检查器（cookie + waf）并重试健康检查，**用户无需手动处理**。如果仍然失败，请手动点击「初始化协调器」按钮，再点击「检查」。

## 11. 最佳实践

### 11.1 健康分监控阈值

| 阈值 | 行动 |
|------|------|
| ≥ 80 | 健康运行，无需操作 |
| 60-79 | 关注 WAF 状态与 Token 年龄，必要时手动续期 |
| < 60 | 立即处置，按建议动作操作 |

**建议巡检频率**：日常每 1-2 小时查看一次；高峰期每 30 分钟查看一次。

### 11.2 何时切换策略

| 场景 | 推荐策略 |
|------|---------|
| 本机已开浏览器并登录闲鱼 | CDP 模式 |
| 服务器无真实浏览器 | launch 模式 |
| Edge/Chrome 已登录但不想保持浏览器开启 | browser_import（导入后可关闭浏览器） |
| 系统已持久化过登录态 | reuse_userdata |

### 11.3 Cookie 同步频率

- **日常**：依赖系统的自动同步（30 秒一次），无需手动操作
- **手动同步时机**：
  - 在浏览器中重新登录闲鱼后
  - 健康分下降到 60 以下
  - identity 层失效

### 11.4 WAF 状态应对

| 状态 | 应对 |
|------|------|
| 正常 | 正常运行 |
| 警告 | 降低采集频率，观察 30 分钟 |
| 已熔断 | 立即暂停 30 分钟以上 |

### 11.5 CDP 模式使用建议

- 保持浏览器持续运行（关闭浏览器后 CDP 模式失效）
- 浏览器中保持闲鱼已登录状态
- 不要在浏览器中同时打开多个闲鱼标签页（避免干扰）

### 11.6 launch 模式使用建议

- 定期查看指纹信息 Card，确认指纹合理（UA、屏幕分辨率等与目标用户群体匹配）
- 健康分异常时优先检查指纹是否过于"独特"（如 GPU 渲染器包含 NVIDIA 但屏幕分辨率是 800×600）

### 11.7 Cookie 主动失效使用场景

仅在以下场景使用主动失效：
- 怀疑当前 Cookie 已被风控标记，希望强制失效后重新登录
- 测试系统的自愈机制
- 排查 Cookie 层依赖问题

**不要在正常状态下随意失效 identity 层**，会导致 session 也失效，影响采集与下单。

### 11.8 频率伪装观察

- **噪声占比建议**：10%-20% 比较自然；过低容易被识别规律，过高浪费资源
- **平均间隔 vs 中位间隔**：平均间隔应略大于中位间隔（对数正态分布的右偏特征）；如果两者接近，可能请求节奏过于均匀
- **标准差**：越大说明请求节奏越不规则，越难被识别为机器人
