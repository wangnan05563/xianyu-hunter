## 2. 功能概述

**一句话说明**：ChromaDB 运维操作台，提供快照备份与恢复、按来源清理片段、状态监控、审计日志。

**核心价值**：
- 复用 chatbot 子容器的 VectorStore 与 ChatbotRepository，与 `api_chatbot` 保持一致；
- chatbot 未启用时统一返回 403 `CHATBOT_DISABLED`，避免暴露内部细节；
- 危险操作（恢复/删除快照/清空/按来源删除）需 `confirm_token=CONFIRM_DELETE`，前端弹窗需用户输入此 token 才能继续；
- 快照目录与 KBManager 共享：`{persist_path}/snapshots/{snapshot_id}`，手动快照用 `manual_{timestamp}` 前缀与 KB 版本快照区分；
- 路径穿越防护：`snapshot_id` 不允许含 `/`、`\`、`..`；
- 审计日志写入 `chatbot_audit_logs` 表，`action` 前缀 `vector_admin.`，失败不阻塞主流程；
- 状态查询排除 `snapshots` 子目录，避免快照膨胀导致主数据大小统计失真。

## 3. 用户场景

**场景 1：知识库全量重建前备份**
用户准备对智能客服知识库做大规模更新，担心更新失败无法回滚。进入「向量数据库维护」页面，点击「创建快照」按钮输入备注 label（如「重建前备份_20260629」），系统在 `{persist_path}/snapshots/manual_20260629_120000_重建前备份_20260629` 目录创建文件级快照。重建完成后若效果不佳，可从快照恢复。

**场景 2：删除错误导入的文档**
用户发现某份文档内容过期被错误导入到知识库，需要清理。进入「数据清理」Tab，在「按来源文件删除」Card 的输入框填入 source_file 路径并点击「删除」按钮，弹窗提示「将删除 source_file=xxx 的所有片段，操作不可恢复」，输入 `CONFIRM_DELETE` 后系统调用 `vector_store.delete_by_source(source_file)` 删除该文档对应的所有片段，删除完成后 toast 显示已删除的片段数。

**场景 3：监控向量库健康度**
用户希望了解向量库的存储占用与增长趋势。进入页面后顶部 4 列状态卡片显示片段数、数据大小、快照数、集合名。发现快照数过多时，可在「备份与恢复」Tab 中删除旧快照释放磁盘空间。

## 5. 接口定义

所有接口前缀：`/api/vector-admin`，路由文件：`backend/xianyu_hunter/web/routes/api_vector_admin.py`。

### 5.1 状态监控

#### GET /status

向量库状态总览。

**响应字段**：

| 字段                 | 类型    | 说明                                                       |
| -------------------- | ------- | ---------------------------------------------------------- |
| `collection_name`    | string  | ChromaDB 集合名                                            |
| `persist_path`       | string  | 持久化目录路径                                             |
| `chunk_count`        | int     | 当前集合片段数（`await vector_store.count()`）             |
| `data_size_bytes`    | int     | 主数据目录大小（字节，排除 `snapshots` 子目录）            |
| `data_size_display`  | string  | 人类可读大小（如 `12.3 MB`）                               |
| `snapshot_count`     | int     | 快照数量                                                   |
| `last_snapshot_at`   | string  | 最近一次快照时间，无快照时为 `null`                        |

### 5.2 快照管理

#### GET /snapshots
列出所有快照，按创建时间 DESC 排序。

**响应**：`items[]` / `total`。

**item 字段**：

| 字段            | 类型    | 说明                                                |
| --------------- | ------- | --------------------------------------------------- |
| `id`            | string  | 快照目录名（如 `manual_20260629_120000_label`）     |
| `size_bytes`    | int     | 快照目录大小（字节）                                |
| `size_display`  | string  | 人类可读大小                                        |
| `created_at`    | string  | 创建时间（取目录 mtime，格式 `YYYY-MM-DD HH:MM:SS`） |
| `is_manual`     | bool    | 是否手动创建（前缀 `manual_`）                      |

#### POST /snapshots
手动创建快照（无 confirm_token 要求，是非破坏性操作）。

**请求体**：

| 字段    | 类型   | 必填 | 说明                                             |
| ------- | ------ | ---- | ------------------------------------------------ |
| `label` | string | 否   | 可选备注，拼入快照目录名 `manual_{ts}_{label}`   |

**响应**：`ok` / `snapshot_id`。

#### POST /snapshots/{snapshot_id}/restore
从快照恢复（覆盖当前集合，需 confirm_token）。

**请求体**：`{"confirm_token": "CONFIRM_DELETE"}`

**响应**：`ok` / `restored_from`。

#### DELETE /snapshots/{snapshot_id}
删除快照文件（不影响当前集合数据，需 confirm_token）。

**Query 参数**：`confirm_token=CONFIRM_DELETE`（必须）

**响应**：`ok` / `deleted`。

### 5.3 数据清理

#### POST /cleanup/all
清空集合（删除并重建 collection，需 confirm_token）。

**请求体**：`{"confirm_token": "CONFIRM_DELETE"}`

**响应**：`ok` / `cleared`（清空前的片段数）。

#### POST /cleanup/by-source
按来源文件删除片段（需 confirm_token）。

**请求体**：

| 字段            | 类型   | 必填 | 说明                              |
| --------------- | ------ | ---- | --------------------------------- |
| `source_file`   | string | 是   | 来源文件路径（非空）              |
| `confirm_token` | string | 是   | 必须为 `CONFIRM_DELETE`           |

**响应**：`ok` / `deleted`（删除的片段数）。

### 5.4 审计日志

#### GET /audit-log
向量库维护审计日志（action 前缀 `vector_admin.`）。

**Query 参数**：`limit=100`（1-500）

**响应**：`items[]` / `total`。

## 7. 业务逻辑

### 7.1 chatbot 未启用保护

`_get_chatbot_or_403()` 检查 `container.chatbot is None`，抛出 403：

```python
HTTPException(
    status_code=403,
    detail={"code": "CHATBOT_DISABLED", "message": "智能客服未启用，向量库不可用"},
)
```

VectorStore 是 chatbot 子容器的可选依赖（chromadb 未装时整个 chatbot 为 None），复用 `api_chatbot` 的 403 策略保持一致。

### 7.2 路径穿越防护

恢复/删除快照接口校验 `snapshot_id` 不允许含路径分隔符：

```python
if "/" in snapshot_id or "\\" in snapshot_id or ".." in snapshot_id:
    raise HTTPException(status_code=400, detail="非法快照 ID")
```

防止恶意请求通过 `../../../etc/passwd` 等路径访问快照目录外的文件。

### 7.3 快照创建流程

```
1. 用户点击「创建快照」→ 输入可选 label
2. 后端生成 snapshot_id = f"manual_{ts}{label_part}"
   ts = datetime.now().strftime("%Y%m%d_%H%M%S")
   label_part = f"_{label}" if label else ""
3. snapshot_path = _snapshot_dir(vector_store) / snapshot_id
4. await vector_store.export_snapshot(snapshot_path)
   - 文件级复制（跳过 snapshots 子目录，避免递归复制自身）
5. _log_audit(repo, "vector_admin.snapshot_create", snapshot_id)
6. 返回 {"ok": True, "snapshot_id": snapshot_id}
```

### 7.4 危险操作状态机

```
[用户点击危险操作按钮]
        ↓
[openDangerConfirm 弹窗]
        ↓
[用户输入 CONFIRM_TOKEN]
        ↓
┌─── 输入错误 ───┐    ┌─── 输入正确 ───┐
│                │    │                │
│ 确认按钮禁用    │    │ 确认按钮启用    │
│ 用户可重新输入  │    │ 用户点击确认    │
│                │    │       ↓        │
└────────────────┘    │ 调用后端 API    │
                      │ (含 confirm_   │
                      │  token)        │
                      │       ↓        │
                      │ _require_      │
                      │ confirm 校验   │
                      │       ↓        │
                      │ 执行操作 + 写  │
                      │ 审计日志        │
                      │       ↓        │
                      │ 前端 loadAll   │
                      │ 刷新状态        │
                      └────────────────┘
```

### 7.5 安全机制

1. **chatbot 未启用保护**：所有接口首行调用 `_get_chatbot_or_403()`，未启用时返回 403。
2. **路径穿越防护**：`snapshot_id` 不允许含 `/`、`\`、`..`。
3. **CONFIRM_TOKEN 双重确认**：恢复/删除快照/清空/按来源删除必须传 `confirm_token=CONFIRM_DELETE`。
4. **非破坏性操作免 token**：创建快照是文件复制，不破坏现有数据，无需 confirm_token。
5. **审计日志不阻塞**：`_log_audit` 失败时仅 `logger.exception` 记录，不抛异常阻塞主流程。
6. **source_file 非空校验**：按来源删除时 `body.source_file.strip()` 不能为空。

### 7.6 大小统计排除 snapshots

`GET /status` 计算主数据大小时显式排除 `snapshots` 子目录：

```python
for item in persist_path.iterdir():
    if item.name == "snapshots":
        continue  # 避免快照膨胀统计
    if item.is_dir():
        main_size += _dir_size(item)
    else:
        main_size += item.stat().st_size
```

否则快照数量增长会导致 `data_size_display` 失真，无法反映集合实际大小。

### 7.7 审计日志查询策略

`list_audit_log` 接口调用 `repo.list_audit_logs(action=None, limit=limit*3)` 取较多记录后内存过滤：

```python
all_logs = repo.list_audit_logs(action=None, limit=limit * 3)
items = [log for log in all_logs if log.get("action", "").startswith("vector_admin.")]
return {"items": items[:limit], "total": len(items)}
```

因为 `list_audit_logs` 不支持前缀过滤，需取 3 倍记录后内存过滤，确保返回足够的 `vector_admin.*` 记录。

## 9. 常见问题 FAQ

**Q1：访问向量数据库维护页面提示「智能客服未启用，向量库不可用」怎么办？**
A：这是 403 `CHATBOT_DISABLED` 错误。原因：chromadb 未安装或 chatbot 配置未启用。需在后端配置中启用 chatbot（参考 `docs/05-智能客服/智能客服-详细设计.md`），并确保 `chromadb` 已 pip 安装。重启服务后生效。

**Q2：创建快照和 KB 版本快照有什么区别？**
A：手动快照目录名前缀为 `manual_`（如 `manual_20260629_120000_label`），由本页面用户主动创建；KB 版本快照由 KBManager 在知识库构建时自动创建，前缀为 `kb_version_`。两者共享 `{persist_path}/snapshots/` 目录但通过命名前缀区分。

**Q3：从快照恢复会覆盖当前数据吗？**
A：会。`vector_store.restore_from_snapshot(snapshot_path)` 会用快照内容替换当前集合数据，当前数据将丢失。建议在恢复前先创建一个新快照备份当前状态。该操作需输入 `CONFIRM_DELETE` 二次确认。

**Q4：清空集合和按来源删除有什么区别？**
A：
- `cleanup/all`：调用 `vector_store.clear_collection()`，删除并重建 collection，所有片段被清除。通常在 KB 全量重建前调用。
- `cleanup/by-source`：调用 `vector_store.delete_by_source(source_file)`，只删除指定 source_file 对应的片段。用于删除某个文档（文档过期/错误导入场景）。

**Q5：快照 ID 含特殊字符会导致什么问题？**
A：快照 ID 用于构造文件系统路径。若含 `/`、`\`、`..` 会导致路径穿越攻击（访问快照目录外的文件）。后端在恢复/删除快照接口中校验 `snapshot_id` 不允许含这些字符，校验失败返回 400「非法快照 ID」。

**Q6：状态卡片显示的「数据大小」为什么不包括快照目录？**
A：`GET /status` 计算主数据大小时显式跳过 `snapshots` 子目录，避免快照膨胀导致主数据大小统计失真。否则快照数量增长会让用户误以为集合数据本身在膨胀。快照大小可在「备份与恢复」Tab 中按单条快照查看。

**Q7：审计日志在哪里查看？**
A：调用 `GET /api/vector-admin/audit-log`，或在「向量数据库维护」页面点击右上角「审计日志」按钮打开抽屉。日志来自 `chatbot_audit_logs` 表，`action` 字段以 `vector_admin.` 前缀过滤。

**Q8：审计日志写入失败会影响主操作吗？**
A：不会。`_log_audit` 用 try/except 包裹，失败时仅 `logger.exception` 记录日志，不抛异常。审计日志不应阻塞主流程，这是与 `api_db_admin._log_audit` 一致的策略。

**Q9：按来源删除时 source_file 应该填什么？**
A：填写文档导入时使用的 source_file 路径（通常是文档的相对路径或绝对路径）。该值与片段的 metadata 中的 `source_file` 字段匹配。可通过 `vector_store` 的查询接口查看片段的 metadata 确认正确的 source_file 值。

**Q10：快照大小是如何计算的？**
A：`_dir_size(path)` 递归遍历快照目录下所有文件，累加 `f.stat().st_size`。`_format_size(n)` 把字节数转为人类可读（B/KB/MB/GB/TB）。快照创建后不再修改，目录 mtime 作为创建时间近似值。

**Q11：为什么审计日志查询要取 limit*3 倍的记录？**
A：`repo.list_audit_logs(action=None, limit=limit*3)` 取较多记录后内存过滤 `vector_admin.*` 前缀。因为 `list_audit_logs` 不支持前缀过滤，若只取 `limit` 条可能因为夹杂其他 action 的记录导致 `vector_admin.*` 数量不足。取 3 倍是经验值，确保返回足够的 `vector_admin.*` 记录。
