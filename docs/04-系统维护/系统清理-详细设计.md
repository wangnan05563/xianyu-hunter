## 2. 功能概述

**一句话说明**：提供缓存、数据库、日志三类资源的统一清理入口，支持预览模式与审计追踪。

**核心价值**：
- 三列卡片布局对应三类清理对象，每列独立配置 dry_run / target / days，互不干扰；
- 所有删除操作均提供 `dry_run=True` 预览模式，先列出将处理的条目再决定是否执行；
- 非预览模式前端必须 `globalThis.confirm` 二次确认（等价于 `window.confirm`），避免误删；
- 每次清理操作通过 `_log_cleanup_action` 写入 `events` 表（`type=maintenance.*`），可在「实时日志」页回溯；
- VACUUM 通过 `execution_options(isolation_level="AUTOCOMMIT")` 显式关闭事务，符合 SQLite 要求；
- 数据库清理使用 SQLAlchemy `text()` + `:param` 绑定参数，防止 SQL 注入。

## 3. 用户场景

**场景 1：磁盘空间告急**
用户登录后发现系统运行缓慢，进入「系统维护」页面，发现缓存占用 500MB、日志占用 200MB。先开启 dry_run 预览浏览器数据清理范围，确认无误后关闭预览开关并执行清理，系统自动刷新存储状态卡片。

**场景 2：数据库膨胀**
长期运行后 `events` 表达到 50 万行，用户在数据库清理卡片选择 `old_events`，保留天数设为 30，先用预览模式确认将删除的行数，再实际执行；最后选中 `vacuum` 压缩数据库文件，回收磁盘空间。

**场景 3：日志归档**
用户希望保留最近 7 天的日志，选择 `old_logs` 并设保留 7 天，预览看到将删除的旧日志列表及大小，确认后释放磁盘空间。

## 5. 接口定义

所有接口前缀：`/api/maintenance`，路由文件：`backend/xianyu_hunter/web/routes/api_maintenance.py`。

### 5.1 GET /status

获取系统当前存储状态，供清理前评估。统计范围必须与实际清理范围保持一致，避免「显示 0MB 但清理 271 项」的不一致。

**响应字段**：

| 路径                       | 类型    | 说明                                                            |
| -------------------------- | ------- | --------------------------------------------------------------- |
| `db.tasks`                 | int     | tasks 表行数                                                    |
| `db.items`                 | int     | items 表行数                                                    |
| `db.task_links`            | int     | task_links 表行数                                               |
| `db.events`                | int     | events 表行数                                                   |
| `db.orders`                | int     | orders 表行数                                                   |
| `db.notifications`         | int     | notifications 表行数                                            |
| `db.db_size_mb`            | float   | `data/xianyu.db` 文件大小（MB）                                 |
| `logs.file_count`          | int     | `data/logs/*.log*` 文件数                                       |
| `logs.total_size_mb`       | float   | 日志文件总大小（MB）                                            |
| `logs.oldest`              | string  | 最早日志日期 `YYYY-MM-DD`，无日志时为 `null`                    |
| `cache.browser_data_mb`    | float   | `data/webview_data_*/` 总大小（MB）                             |
| `cache.pycache_mb`         | float   | `__pycache__` 总大小（MB）                                      |
| `cache.pycache_count`      | int     | `__pycache__` 目录数                                            |
| `cache.temp_files`         | int     | `/tmp/xianyu_*` 文件数（Windows 上 `/tmp` 不存在时返回 0）       |

### 5.2 POST /cache

清理缓存数据。

**请求体**（`CleanupRequest`）：

| 字段       | 类型    | 必填 | 默认    | 说明                                             |
| ---------- | ------- | ---- | ------- | ------------------------------------------------ |
| `target`   | string  | 否   | `all`   | `browser_data` / `temp` / `all`                  |
| `days`     | int     | 否   | 30      | 缓存清理不使用此字段                             |
| `dry_run`  | bool    | 否   | `False` | `True` 时只列出将删除项，不实际执行               |

**响应字段**：`target` / `dry_run` / `cleaned[]` / `errors[]` / `count`。

### 5.3 POST /database

清理数据库冗余数据。

**target 取值**：

| target        | 行为                                                                              |
| ------------- | --------------------------------------------------------------------------------- |
| `old_events`  | `DELETE FROM events WHERE created_at < :cutoff`                                  |
| `old_items`   | `DELETE FROM items WHERE first_seen < :cutoff AND id NOT IN (SELECT link_key FROM task_links WHERE link_type='item')` |
| `sold_items`  | `DELETE FROM task_links WHERE link_type='item' AND display LIKE :pattern`，`pattern = '%"is_sold":true%'` |
| `vacuum`      | 在 AUTOCOMMIT 隔离级别下执行 `VACUUM`，压缩数据库文件                             |
| `all`         | 依次执行上述四项                                                                  |

**响应字段**：`target` / `days` / `dry_run` / `cleaned[]` / `errors[]` / `total_deleted`。

### 5.4 POST /logs

清理日志文件。

**target 取值**：

| target        | 行为                                                                  |
| ------------- | --------------------------------------------------------------------- |
| `old_logs`    | 删除 mtime 早于 `now - days` 的 `*.log*` 文件                          |
| `large_logs`  | 删除大小 > 10MB 的 `*.log*` 文件                                       |
| `all`         | 同时按天数与大小阈值清理                                               |

**响应字段**：`target` / `days` / `dry_run` / `cleaned[]` / `errors[]` / `total_freed_mb`。

## 7. 业务逻辑

### 7.1 清理流程状态机

```
[用户进入页面] → loadStatus() → 渲染三列卡片
                          ↓
       [用户配置 target/days/dry_run]
                          ↓
             [点击清理按钮]
                          ↓
       ┌─── dry_run=True ───┐
       │                    │
       │  直接调用 POST      │
       │  返回预览列表       │
       │                    │
       └────────────────────┘
                          ↓
       ┌─── dry_run=False ──┐
       │                    │
       │  globalThis.confirm│
       │  二次确认           │
       │       ↓            │
       │  用户取消 → 中止    │
       │  用户确认 → 调用    │
       │                    │
       └────────────────────┘
                          ↓
       POST /api/maintenance/{cache|database|logs}
                          ↓
       后端执行清理 + _log_cleanup_action 写审计
                          ↓
       前端 loadStatus() 刷新存储状态卡片
```

### 7.2 安全机制

1. **dry_run 预览模式**：所有清理接口均接受 `dry_run=True`，仅返回将处理的条目列表，不实际删除。
2. **前端 `globalThis.confirm` 二次确认**：非预览模式下，浏览器原生弹窗需用户主动点击「确认」（代码使用 `globalThis.confirm`，等价于 `window.confirm`）。
3. **审计日志**：每次清理调用 `_log_cleanup_action` 写入 `events` 表，记录 category / target / cleaned_count / error_count / cleaned_items 前 20 条 / errors 前 5 条。
4. **参数化查询防注入**：数据库清理使用 `text("DELETE FROM ... WHERE created_at < :cutoff")` + `{"cutoff": cutoff}` 绑定参数。
5. **LIKE 模式特殊处理**：`sold_items` 清理使用 `LIKE :pattern` 而非字符串拼接，因为模式中的冒号会被 SQLAlchemy 误判为绑定参数。
6. **天数下限保护**：`days = max(1, req.days)` 防止用户传 0 或负值导致删除全表。

### 7.3 VACUUM 特殊处理

VACUUM 不能在事务中执行，SQLAlchemy 2.0 的 `engine.connect()` 默认开启隐式事务。代码将 VACUUM 逻辑封装在 `_vacuum_database` 函数中，通过 `execution_options(isolation_level="AUTOCOMMIT")` 显式关闭事务：

```python
def _vacuum_database(engine, dry_run, cleaned, errors):
    if dry_run:
        cleaned.append("[预览] 将执行 VACUUM 压缩数据库")
        return
    try:
        with engine.connect().execution_options(
            isolation_level="AUTOCOMMIT"
        ) as conn:
            conn.execute(text("VACUUM"))
            cleaned.append("已执行 VACUUM 压缩数据库")
    except Exception as e:
        errors.append(f"VACUUM 失败: {e}")
```

`POST /database` 主流程在 `engine.begin()` 事务块结束后才调用 `_vacuum_database`，避免在事务中执行 VACUUM；dry_run 模式下仅打印 `[预览] 将执行 VACUUM 压缩数据库`，不实际执行。

### 7.4 统计与清理范围一致性

`GET /status` 的缓存统计范围必须与 `POST /cache` 实际清理范围保持一致：
- 浏览器数据：`_data_dir().glob("webview_data_*")`
- Python 缓存：`_iter_pycache_dirs(Path("."))`，使用 `os.walk` 遍历并通过 `_EXCLUDE_SCAN_DIRS` 原地剪枝，排除 `.venv` / `node_modules` / `.git` / `data` / `dist` / `build` / `target` / `.cache` / `__pycache__` 等第三方依赖与构建产物目录（避免 `.venv` 内数千子目录的无效遍历，将扫描时间从 30s+ 降至 <0.1s）
- 临时文件：`Path("/tmp").glob("xianyu_*")`（Windows 上 `/tmp` 不存在时返回 0）

否则会出现「显示 0MB 但清理 271 项」的不一致问题。

## 9. 常见问题 FAQ

**Q1：为什么点击「清理缓存」后状态卡片没有更新？**
A：仅在 `dry_run=False`（实际执行）模式下才会调用 `loadStatus()` 刷新状态。预览模式不会刷新，便于用户对比清理前后的预览结果。

**Q2：dry_run 预览显示「将删除 0 条」，但实际执行后删除了多条，是怎么回事？**
A：这通常意味着 `GET /status` 的统计范围与 `POST /cache` 的清理范围不一致。代码注释明确要求两者必须保持一致，如发现此类问题应作为 Bug 修复，检查 `_data_dir().glob("webview_data_*")` 与 `_iter_pycache_dirs()` 的扫描路径是否对齐。

**Q3：VACUUM 报错「cannot VACUUM from within a transaction」怎么办？**
A：VACUUM 不能在事务中执行。代码已通过 `execution_options(isolation_level="AUTOCOMMIT")` 显式关闭事务。如果仍报错，检查 SQLAlchemy 版本是否 ≥ 2.0，以及 `engine.connect()` 是否被外层 `begin()` 包裹。

**Q4：数据库清理的 sold_items 为什么用 LIKE 而不是 JSON 函数？**
A：`task_links.display` 字段是 JSON 字符串，SQLite 的 JSON1 扩展虽然支持 `json_extract`，但本系统兼容性考虑使用 `LIKE '%"is_sold":true%'`。注意必须用参数化查询 `LIKE :pattern`，因为模式中的冒号会被 SQLAlchemy 误判为绑定参数。

**Q5：清理操作有审计日志吗？在哪里查看？**
A：有。每次清理调用 `_log_cleanup_action` 写入 `events` 表，`type` 字段为 `maintenance.cache` / `maintenance.database` / `maintenance.logs`，可在「实时日志」页面过滤查看。`payload` 字段包含完整的 category / target / cleaned_count / error_count / cleaned_items 前 20 条 / errors 前 5 条。

**Q6：日志清理的「大文件清理」阈值是多少？能调整吗？**
A：当前硬编码为 10MB（`size_mb > 10`），见 `api_maintenance.py` 第 406 行 `should_delete` 计算逻辑。如需调整需修改源码并重新部署。

**Q7：清理浏览器数据会影响已登录的闲鱼会话吗？**
A：会。`webview_data_*` 目录包含浏览器 Cookie 和缓存，清理后需要重新登录。建议在低峰期执行，或先确认无活跃采集任务。

**Q8：为什么 days 输入框允许的最大值是 365？**
A：前端 `InputNumber max={365}` 限制，防止用户输入过大值导致 `cutoff = now - timedelta(days=N)` 计算溢出或误删全部数据。后端另有 `days = max(1, req.days)` 保证下限。

**Q9：清理过程中报错「数据库被锁定」怎么处理？**
A：SQLite 单写入特性导致并发写入会触发锁。建议：
1. 暂停所有采集任务后再清理；
2. 重试清理操作（短时间锁通常自动释放）；
3. 若持续锁定，重启 Web 服务后立即清理。

**Q10：可以一次清理多个 target 吗？**
A：可以。选择 `all` 即可执行该类别下的全部清理操作。例如数据库清理选 `all` 会依次执行 old_events → old_items → sold_items → vacuum。
