## 2. 功能概述

**一句话说明**：定时（默认每 30 分钟）刷新在售商品的详情，检测已售状态、补全字段变更，支持暂停/继续/停止与断点续传，并提供完整的执行历史查询与清理能力。

**核心价值**：
- 基于 APScheduler `BackgroundScheduler` 实现定时调度，通过 `run_coroutine_threadsafe` 提交到主事件循环执行 async 采集逻辑（因 `collector.detail()` 依赖 Playwright，绑定主事件循环）；
- 状态机：`idle/running/paused/stopping/unavailable`，通过 `asyncio.Event` 实现暂停/继续，通过 `_stop_flag` 实现停止；
- 任务控制端点立即返回（<500ms），实际暂停/停止在当前 item 处理完成后生效，保证当前 item 的数据库写入完整；
- 进度持久化到 `batch_refresh_progress` 表（`BatchRefreshProgressRow`），停止时保存未处理 item_id 列表，下次触发从断点续传；
- 变更检测：`_refresh_one` 通过 `ItemCollectionService.collect()` 统一采集逻辑，返回 `result.changed_fields`；`_record_change()` 记录变更字段到内存 `_change_log`（上限 1000 条，避免 OOM）；
- 失败重试：单商品失败记录原因并跳过，连续失败超过阈值（默认 3 次）时熔断当前批次（剩余记为 skipped，历史 `status=failed`）；
- 资源调度优化：每个 item 处理后 `await asyncio.sleep(0.3)` 让出事件循环，确保主业务请求优先处理；
- 配置热更新：`PATCH /config` 修改 `interval_minutes` 后立即 `reschedule_job`，`enabled` 仅修改标志位（下次启动按此标志决定）；
- 执行历史持久化：批次开始时插入 `batch_refresh_history` 表（`status=running`），结束时更新为终态（`completed`/`cancelled`/`failed`），支持分页查询、详情、清理；
- `task_id` 全局自增：调度器启动时从 `MAX(task_id)` 初始化计数器，跨进程重启不重置；
- 错误消息累积：单批次错误聚合到 `error_messages` JSON 字段（上限 50 条，FIFO 丢弃最旧），便于事后排查。

## 3. 用户场景

**场景 1：手动触发批量采集**
用户希望立即刷新所有在售商品的详情，进入「批量采集」页面点击「立即触发」按钮。系统返回 `task_id`，状态变为 `running`，前端自动开启高频轮询（3 秒间隔）观察进度。处理过程中可看到当前处理的 item_id、进度百分比、已耗时。

**场景 2：暂停与断点续传**
批量采集进行到一半时，用户希望临时暂停以释放浏览器资源给主业务。点击「暂停」按钮，状态变为 `paused`，实际暂停在当前 item 处理完成后生效（保证写入完整）。停止时才调用 `_save_progress()` 持久化未处理 item_id 列表。稍后点击「继续」从断点恢复。

**场景 3：停止与未处理项持久化**
用户希望彻底停止当前批次，点击「停止」按钮。状态变为 `stopping`，循环检查 `_stop_flag` 后 break，未处理的 items 持久化到 `batch_refresh_progress` 表（status=`stopped`）。下次触发时 `_load_resumable_progress()` 读取并过滤已售商品后从断点续传。

**场景 4：执行历史查询与清理**
用户希望排查过往批次的执行情况，切换到「执行历史」Tab。可按 `task_id` / 状态（执行中/已完成/已取消/已失败）/ 来源（手动/定时）/ 时间范围筛选，支持分页与多字段排序。点击「详情」查看抽屉，包含基本信息、采集统计、错误消息列表。可一键清理 30 天前的历史，或清空全部历史。

**场景 5：连续失败熔断**
浏览器实例异常时，连续多个商品采集失败。当连续失败次数达到阈值（默认 3 次）时，调度器标记 `circuit_broken=True`，剩余未处理商品记为 `skipped`，批次结束。历史记录 `status=failed`，`consecutive_failures` 字段记录触发熔断时的连续失败次数，便于排查。

| 交互                                | 实现位置                            | 说明                                                                |
| ----------------------------------- | ----------------------------------- | ------------------------------------------------------------------- |
| 进入页面加载状态                     | `useEffect(() => loadStatus(), [])` | 调用 `GET /api/batch-refresh/status`                                |
| Tab 切换持久化                       | `usePersistentState('xh.batchRefresh.activeTab')` | 切换 Tab 后刷新页面仍保持上次选择                          |
| 自动刷新智能间隔                     | `useEffect([autoRefresh, status?.status, forceFastPoll])` | running/paused/stopping 或 forceFastPoll 时 3s 高频；其他 10s 低频 |
| 自动刷新开关持久化                   | `usePersistentState('xh.batchRefresh.autoRefresh')` | 避免每次进入页面都需重新开启                                  |

| 表单 dirty 标记                      | `formDirtyRef.current`              | 用户编辑配置后标记 dirty，避免轮询拉取的状态覆盖未保存的编辑值     |

## 5. 接口定义

所有接口前缀：`/api/batch-refresh`，路由文件：`src/xianyu_hunter/web/routes/api_batch_refresh.py`。
认证：由 `BearerAuthMiddleware` 统一处理（`/api/batch-refresh/*` 不在 `PUBLIC_PREFIXES` 中），路由内部不再做 token 校验。

接口分两组：
- **当前批次**（status/trigger/config/pause/resume/stop）：操作调度器内存中「正在运行」的批次；
- **执行历史**（history/stats/detail/delete/cleanup）：查询与清理 `batch_refresh_history` 表中「已持久化」的批次记录。

### 5.1 GET /status

返回调度器当前状态、上次执行结果和最近变更日志。

**响应字段**：

| 字段                | 类型     | 说明                                                                 |
| ------------------- | -------- | -------------------------------------------------------------------- |
| `status`            | string   | `idle` / `running` / `paused` / `stopping` / `unavailable`           |
| `last_run_at`       | string   | 上次执行开始时间 ISO 字符串，无执行时为 `null`                       |
| `last_result`       | object   | `{success, failed, skipped, stopped}`，无结果时为 `null`             |
| `change_log`        | array    | 最近 50 条变更日志（item_id / changed_fields / timestamp）           |
| `enabled`           | bool     | 定时调度是否启用                                                     |
| `interval_minutes`  | int      | 调度间隔（分钟）                                                     |
| `progress`          | object   | 进度信息（task_id/current/total/current_item_id/started_at/elapsed_ms），无批次时为 `null` |
| `control_available` | bool     | 是否允许 pause/resume/stop 操作（`status in (running, paused)`）     |

调度器未启动时返回 `status=unavailable`，但 `enabled`/`interval_minutes` 仍从全局 config 读取并返回，便于前端展示配置值。

### 5.2 POST /trigger

手动触发一次批量采集，返回任务 ID。

**响应**：`{"ok": true, "task_id": 1}`

**错误码**：
- 503：调度器未启动（需 `XH_WITH_SCHEDULER=1` 且 `batch_refresh.enabled=true`）
- 409：已有批次在运行（`trigger_now()` 返回 -1）

### 5.3 PATCH /config

运行时热更新配置。

**请求体**（`BatchRefreshConfigPatch`）：

| 字段               | 类型    | 必填 | 范围      | 说明                                              |
| ------------------ | ------- | ---- | --------- | ------------------------------------------------- |
| `interval_minutes` | int     | 否   | 1-1440    | 修改后立即 `reschedule_job`                       |
| `enabled`          | bool    | 否   | -         | 仅修改标志位（不影响已注册的 job，下次启动按此标志决定） |

**响应**：`ok` / `enabled` / `interval_minutes` / `batch_size` / `max_items_per_run`。

调度器未启动时仍允许更新全局 config 单例（下次启动时生效）。

### 5.4 POST /pause

暂停当前批次。立即更新状态为 `paused` 并 `clear event`，但实际暂停在当前 item 处理完成后生效（`await event.wait()` 阻塞）。

**响应**：`{"ok": true, "status": "paused"}`

**错误码**：
- 503：调度器未启动
- 409：当前状态不允许暂停（仅 `running` 态可暂停）

### 5.5 POST /resume

继续执行已暂停的批次。`set event` 解除阻塞。

**响应**：`{"ok": true, "status": "running"}`

**错误码**：
- 503：调度器未启动
- 409：当前状态不允许继续（仅 `paused` 态可继续）

### 5.6 POST /stop

停止当前批次。立即更新状态为 `stopping` 并 `set event`（解除暂停阻塞），未处理的 items 持久化以便下次续传。

**响应**：`{"ok": true, "status": "stopping"}`

**错误码**：
- 503：调度器未启动
- 409：当前状态不允许停止（仅 `running/paused` 态可停止）

### 5.7 GET /history

分页查询批量采集执行历史，支持多维度筛选与排序。

**查询参数**：

| 参数             | 类型    | 必填 | 默认值     | 说明                                              |
| ---------------- | ------- | ---- | ---------- | ------------------------------------------------- |
| `task_id`        | int     | 否   | -          | 按 task_id 精确过滤                               |
| `status`         | string  | 否   | -          | `running` / `completed` / `cancelled` / `failed`  |
| `trigger_source` | string  | 否   | -          | `manual` / `scheduler`                            |
| `start`          | string  | 否   | -          | 起始时间 ISO8601（按 `started_at` 过滤）          |
| `end`            | string  | 否   | -          | 结束时间 ISO8601                                  |
| `order_by`       | string  | 否   | `started_at` | `started_at` / `task_id` / `status` / `duration_ms` |
| `order_dir`      | string  | 否   | `desc`     | `asc` / `desc`                                    |
| `limit`          | int     | 否   | 20         | 1-200                                             |
| `offset`         | int     | 否   | 0          | ≥0                                                |

**响应**：`{items: BatchRefreshHistoryItem[], total, limit, offset, status_counts}`。

`status_counts` 为按状态聚合的字典（如 `{"completed": 12, "failed": 1}`），供前端概览卡片展示。

### 5.8 GET /history/stats

按 `task_id` 聚合统计执行次数与最近执行时间。

**响应**：`{items: [{task_id, run_count, last_run_at, total_success, total_failed}], count}`。

### 5.9 GET /history/{history_id}

查询单条历史记录详情（含完整错误消息列表）。

**响应**：`BatchRefreshHistoryItem`（`error_messages` JSON 字符串已解析为 list[dict]）。

**错误码**：404：历史记录不存在。

### 5.10 DELETE /history/{history_id}

删除单条历史记录。

**响应**：`{"ok": true}`

**错误码**：404：历史记录不存在。

### 5.11 DELETE /history?days=N

按天数清理过期历史记录。

**查询参数**：

| 参数   | 类型 | 必填 | 范围   | 说明                                            |
| ------ | ---- | ---- | ------ | ----------------------------------------------- |
| `days` | int  | 是   | 0-3650 | 0=清空全部（直接 `DELETE FROM`），>0=清理 N 天前 |

**响应**：`{"ok": true, "deleted": <int>}`

`days=0` 与 `days>0` 走不同分支：`days=0` 直接删除表内所有记录（前端「清空全部」按钮使用）；`days>0` 复用 `cleanup_old_batch_refresh_history()`，与启动时自动清理逻辑一致。

## 6. 数据结构

### 6.1 BatchRefreshConfig（YAML 配置）

定义在 `src/xianyu_hunter/infra/yaml_config.py`，配置文件 `config/config.example.yaml` 的 `batch_refresh` 段。

| 字段                     | 类型    | 默认值 | 范围     | 说明                                                |
| ------------------------ | ------- | ------ | -------- | --------------------------------------------------- |
| `enabled`                | bool    | true   | -        | 总开关                                              |
| `interval_minutes`       | int     | 30     | -        | 定时触发间隔（分钟）                                |
| `batch_size`             | int     | 50     | -        | 每批从 DB 拉取的最大商品数（分页控制）              |
| `max_items_per_run`      | int     | 100    | -        | 单次运行最多采集的商品数（防止长时间占用浏览器）    |
| `history_retention_days` | int     | 90     | 0-3650   | 执行历史保留天数，启动时清理超过此天数的记录（0=永不清理） |

### 6.2 BatchRefreshConfigPatch（Pydantic 模型）

```python
class BatchRefreshConfigPatch(BaseModel):
    interval_minutes: int | None = Field(default=None, ge=1, le=1440)
    enabled: bool | None = None
```

### 6.3 batch_refresh_progress 表（BatchRefreshProgressRow）

定义在 `src/xianyu_hunter/infra/db_models.py` §5.20。同一时刻最多只有一条记录（单批次运行），批次结束即清理。

| 字段                | 类型     | 说明                                                    |
| ------------------- | -------- | ------------------------------------------------------- |
| `id`                | int      | 自增主键                                                |
| `task_id`           | int      | 批次任务 ID（自增，每次 trigger 或定时触发 +1）         |
| `pending_item_ids`  | Text     | 未处理 item_id 列表（JSON 数组字符串）                  |
| `total`             | int      | 批次总商品数                                            |
| `processed`         | int      | 已处理数量（默认 0）                                    |
| `status`            | string   | `paused` / `stopped` / `running`（进程异常退出残留）/ `done`（仅声明未使用） |
| `created_at`        | datetime | 记录创建时间                                            |
| `updated_at`        | datetime | 记录更新时间（onupdate 自动更新）                       |

索引：`ix_batch_refresh_progress_task_id`。

### 6.4 batch_refresh_history 表（BatchRefreshHistoryRow）

定义在 `src/xianyu_hunter/infra/db_models.py` §5.21。持久化每次执行的完整记录。

| 字段                  | 类型     | 说明                                                                |
| --------------------- | -------- | ------------------------------------------------------------------- |
| `id`                  | int      | 自增主键                                                            |
| `task_id`             | int      | 全局自增任务 ID（从 DB MAX(task_id) 初始化，跨进程重启不重置）      |
| `trigger_source`      | string   | `manual`=用户手动 / `scheduler`=APScheduler 定时                    |
| `started_at`          | datetime | 开始时间                                                            |
| `completed_at`        | datetime | 完成时间（running 状态时为 NULL）                                   |
| `total`               | int      | 总商品数                                                            |
| `success`             | int      | 成功数                                                              |
| `failed`              | int      | 失败数                                                              |

## 7. 业务逻辑

### 7.1 状态机

```
                trigger
  idle ─────────────────> running
   ↑                        │
   │                        │ pause
   │                        ↓
   │                     paused
   │                        │
   │           ┌─ resume ───┘
   │           ↓
   │        running
   │                        │
   │           ┌────────────┼────────────┐
   │           │ stop       │ 熔断       │ 全部完成
   │           ↓            ↓            ↓
   │       stopping      (break)     (break)
   │                        │
   │       (current item done)
   │                        │
   └────────────────────────┴────────────┘
   (all done / stop_flag / circuit_broken)

unavailable：调度器未启动（XH_WITH_SCHEDULER≠1 或 batch_refresh.enabled≠true）
```

**状态转换规则**：
- `idle → running`：`trigger_now()` 或定时调度触发
- `running → paused`：`pause()` 设置 `_status="paused"` 并 `clear event`
- `paused → running`：`resume()` 设置 `_status="running"` 并 `set event`
- `running/paused → stopping`：`stop_current()` 设置 `_stop_flag=True` 和 `_status="stopping"` 并 `set event`
- `* → idle`：批次结束（`finally: _status = "idle"`），三种退出路径：
  - 正常完成（无熔断、无 stop_flag）→ 历史 `status=completed`
  - 用户停止（`_stop_flag=True`）→ 历史 `status=cancelled`
  - 连续失败熔断（`circuit_broken=True`）→ 历史 `status=failed`

注意：`_status` 是调度器内存状态（仅 5 种值），与 `batch_refresh_history.status`（4 种终态值）是两套独立的状态字段，前者表示运行时调度器状态，后者表示历史记录的批次终态。

### 7.2 断点续传机制

**暂停时状态变更**：
```
pause() 调用
    ↓
_status = "paused"
_pause_event.clear()  # 阻塞 await event.wait()
    ↓
当前 item 处理完成
    ↓
循环进入下一次迭代前 await event.wait() 阻塞
    ↓
（用户 resume 或 stop）
```

注意：暂停本身不写 `_save_progress`，仅在停止时持久化未处理 item_id 列表。如果进程异常退出，残留的 `running` 状态记录会被 `_load_resumable_progress` 视为可续传。

**停止时持久化**：
```
stop_current() 调用
    ↓
_stop_flag = True
_status = "stopping"
_pause_event.set()  # 解除暂停阻塞
    ↓
循环检查 _stop_flag 后 break
    ↓
remaining = items[idx:]  # 含当前 item
_save_progress(task_id, remaining, processed, total, "stopped")
    ↓
finally: _status = "idle"
```

**续传加载**（`_prepare_batch_items` 启动时调用 `_load_resumable_progress`）：
```
_run_batch_async 启动时
    ↓
_load_resumable_progress()
    ↓
SELECT * FROM batch_refresh_progress
WHERE status IN ('paused', 'running')
ORDER BY created_at DESC LIMIT 1
    ↓
┌─── 有记录 ───┐    ┌─── 无记录 ───┐
│              │    │              │
│ pending_ids  │    │ 新批次：     │
│ = json.loads │    │ list_unsold_ │
│ (pending_    │    │ items(       │
│  item_ids)   │    │   limit=     │
│              │    │   max_items_ │
│ items =      │    │   per_run)   │
│  list_items_ │    │              │
│  by_ids(...) │    │ Cookie 同步  │
│              │    │ inject_      │
│ 过滤已售     │    │ cookie_store │
│ (暂停期间    │    │ _to_worker   │
│  可能已售)   │    │ _browser     │
│              │    │              │
│ _clear_      │    │              │
│  progress()  │    │              │
└──────────────┘    └──────────────┘
```

### 7.3 变更检测

`_refresh_one(item_id, existing_item)` 通过统一的 `ItemCollectionService.collect()` 采集单个商品详情并合并写库：

```python
result = await asyncio.wait_for(
    ItemCollectionService(self._container).collect(
        item_id,
        task_id=str(existing_item.get("task_id") or ""),
        mode=CollectionMode.OFFICIAL_FULL,
        existing_item=existing_item,
        source="official",
    ),
    timeout=_DETAIL_TIMEOUT,  # 60 秒，与 refresh_item 端点一致
)
```

`ItemCollectionService.collect()` 内部已统一处理：调用 `collector.detail()` 获取详情 → 构造 `new_row` → `upsert_item` 写入 items 表 → `is_sold` 时 `mark_sold()` 补写 `sold_detected_at` 与 `task_links.display` → `sync_item_display_from_detail()` 合并 `task_links.display` → 计算变更字段。

返回值约定：
- `result.ok=False` 或抛 `CollectionError(status_code=410)`：返回 `None`（采集失败或商品已下架，记为 skipped）
- 正常返回：`result.changed_fields`（可能为空列表，表示无字段变化）

调度器侧 `_record_change(item_id, changed_fields)` 仅在 `changed_fields` 非空时记录到 `_change_log`。
`_change_log` 内存上限 1000 条（`_MAX_CHANGE_LOG`），FIFO 丢弃最旧，避免无限增长导致 OOM。`get_status()` 仅返回最近 50 条。

### 7.4 失败重试与熔断机制

主循环 `_process_items_loop` 将单个 item 处理委托给 `_process_single_item`，失败时由 `_handle_item_failure` 处理：

```python
async def _process_single_item(self, item_id, item, task_id, started_at, counters, total_items) -> bool:
    try:
        changed_fields = await self._refresh_one(item_id, item)
        if changed_fields is None:
            counters.skipped += 1
        else:
            counters.success += 1
            if changed_fields:
                self._record_change(item_id, changed_fields)
        counters.consecutive_failures = 0  # 成功时重置
        return False
    except Exception as e:
        return self._handle_item_failure(e, task_id, item_id, started_at, counters, total_items)

def _handle_item_failure(self, e, task_id, item_id, started_at, counters, total_items) -> bool:
    counters.failed += 1
    counters.consecutive_failures += 1
    self._append_error(item_id, str(e), datetime.now(timezone.utc))  # 累积到历史 error_messages
    if counters.consecutive_failures < self._fail_pause_threshold:
        return False  # 未达阈值，继续下一轮
    # 熔断：剩余未处理商品记为 skipped
    counters.circuit_broken = True
    processed_count = counters.success + counters.failed + counters.skipped
    remaining_count = total_items - processed_count
    counters.skipped += remaining_count
    return True  # 跳出主循环
```

`_fail_pause_threshold` 默认 3 次（构造函数注入）。熔断后历史记录 `status=failed`，`consecutive_failures` 字段记录触发熔断时的连续失败次数。

### 7.5 资源调度优化

每个 item 处理后 `await asyncio.sleep(_YIELD_INTERVAL)`（0.3 秒）让出事件循环：

```python
# 资源调度优化：让出事件循环给主业务请求
# 不在 finally 中，避免暂停阻塞时也 sleep
await asyncio.sleep(_YIELD_INTERVAL)
```

为什么需要：批量采集是低优先级后台任务，sleep 让出控制权给主业务请求，避免在大量商品采集时阻塞 API 响应。

### 7.6 任务控制立即返回

三个控制端点（pause/resume/stop）均立即返回（<500ms），实际暂停/停止在当前 item 处理完成后生效：

```python
@router.post("/pause")
def pause_batch() -> dict[str, Any]:
    scheduler = _get_scheduler()
    if not scheduler.pause():  # 立即更新状态 + clear event，不等待
        raise HTTPException(status_code=409, ...)
    return {"ok": True, "status": "paused"}  # 立即返回
```

这样保证当前 item 的数据库写入完整，避免数据不一致。

### 7.7 自动刷新轮询策略

前端根据状态动态调整轮询间隔，并由 `forceFastPoll` 在用户操作后强制短期高频：

```typescript
const fast = forceFastPoll
  || (status != null && ['running', 'paused', 'stopping'].includes(status.status))
const interval = fast ? 3000 : 10000
timerRef.current = setInterval(() => loadStatus(true), interval)
```

`loadStatus(true)` 静默刷新（不显示 loading），避免 UI 闪烁。
`forceFastPoll` 由 `startForceFastPoll()` 触发，30 秒兜底超时：trigger/pause/resume/stop 后立即开启 3s 高频轮询，status 进入运行/暂停/停止态后解除；若 30 秒内仍未变化则自动恢复低频，避免后端异常时持续无意义请求。

### 7.8 执行历史持久化机制

批次开始时 `_create_history()` 插入一条 `status=running` 的历史记录，返回主键 ID 存到 `_current_history_id`。批次结束时根据 `_compute_final_status()` 计算终态，由 `_finalize_history()` 更新为终态：

| 终态         | 触发条件                       | `consecutive_failures` |
| ------------ | ------------------------------ | ---------------------- |
| `completed`  | 正常完成（无熔断、无 stop_flag）| 0                      |
| `cancelled`  | 用户停止（`_stop_flag=True`）  | 0                      |
| `failed`     | 连续失败熔断（`circuit_broken`）| 触发熔断时的连续失败次数 |

异常兜底：`_run_batch_job` 中 `future.result(timeout=_BATCH_TIMEOUT)` 抛 TimeoutError 时，协程可能仍在运行，历史记录可能停留在 `running`。此时 `_finalize_history_on_exception()` 兜底更新为 `failed`，并追加 `_batch_timeout` 错误消息。

错误消息累积：`_append_error()` 在每次失败时调用，单批次上限 `_MAX_ERROR_MESSAGES=50` 条，FIFO 丢弃最旧；单条错误截断为 500 字符，避免超长堆栈。结束时序列化为 JSON 写入 `error_messages` 字段（无错误时为 NULL）。

`task_id` 全局自增：调度器启动时 `get_max_batch_refresh_task_id()` 读取历史表 MAX(task_id) 初始化 `_current_task_id`，跨进程重启不重置。`trigger_now()` 与 `_run_batch_job` 均先 `+=1` 再使用，保证手动触发与定时触发的 task_id 单调递增。

启动时自动清理：`startup.py` 中 `cleanup_batch_refresh_history_on_startup()` 根据 `history_retention_days` 配置清理超过此天数的记录（`days=0` 时不清理）。

### 7.9 配置热更新

`PATCH /config` 调用 `scheduler.update_config()`：

- `interval_minutes` 修改后立即 `reschedule_job("batch_refresh", trigger="interval", minutes=...)`，已注册的 job 重新调度；
- `enabled` 仅修改 `_config.enabled` 标志位，不影响已注册的 job（下次启动时按此标志决定是否注册）；
- 调度器未启动时仍允许更新全局 config 单例，下次启动时生效。

## 9. 常见问题 FAQ

**Q1：状态显示 `unavailable` 是什么意思？**
A：调度器未启动。需同时满足两个条件：1) 启动 Web 服务时设置环境变量 `XH_WITH_SCHEDULER=1`；2) 配置文件中 `batch_refresh.enabled=true`。检查启动命令是否包含 `--with-scheduler` 参数。

**Q2：触发批量采集返回 409「已有批次在运行」怎么办？**
A：说明上一个批次尚未完成。可通过 `GET /status` 查看当前状态：若为 `running`/`paused`/`stopping`，需先停止当前批次（`POST /stop`）才能触发新批次；若为 `idle`/`unavailable` 可直接触发。

**Q3：暂停后能立即看到状态变化吗？**
A：能。`pause()` 立即更新 `_status="paused"` 并返回，前端 3 秒内会通过轮询看到状态变化。但实际暂停在当前 item 处理完成后生效（`await event.wait()` 阻塞），可能需要几秒到几十秒，取决于当前 item 的采集耗时。

**Q4：停止后未处理的商品会丢失吗？**
A：不会。停止时 `_save_progress()` 将未处理 item_id 列表持久化到 `batch_refresh_progress` 表（status=`stopped`）。下次触发时 `_load_resumable_progress()` 读取并过滤已售商品后从断点续传。

**Q5：变更日志最多保留多少条？**
A：内存上限 1000 条（`_MAX_CHANGE_LOG`），避免无限增长导致 OOM。`GET /status` 仅返回最近 50 条，避免响应体过大。变更日志不持久化，进程重启后清空。

**Q6：连续失败几次会熔断当前批次？**
A：默认 3 次（`_fail_pause_threshold=3`）。连续失败达到阈值时，剩余未处理商品记为 skipped，批次结束，历史记录 `status=failed`，`consecutive_failures` 字段记录触发熔断时的连续失败次数。这是为了在浏览器实例异常时避免持续无效请求。

**Q7：每个商品处理间隔多久？**
A：0.3 秒（`_YIELD_INTERVAL`）。这是资源调度优化，让出事件循环给主业务请求，避免批量采集独占事件循环导致 API 响应延迟。

**Q8：单次批次最长执行多久？**
A：1 小时（`_BATCH_TIMEOUT=3600`）。BackgroundScheduler 线程通过 `future.result(timeout=_BATCH_TIMEOUT)` 等待，超时则释放线程避免堆积，并由 `_finalize_history_on_exception()` 兜底将历史记录更新为 `failed`。单商品采集超时 60 秒（`_DETAIL_TIMEOUT`）。

**Q9：配置 `interval_minutes` 修改后立即生效吗？**
A：是。`PATCH /config` 后端调用 `scheduler.reschedule_job("batch_refresh", trigger="interval", minutes=interval_minutes)` 立即重排定时任务。`enabled` 仅修改标志位，不影响已注册的 job，下次启动时按此标志决定是否注册。调度器未启动时仍允许更新全局 config 单例，下次启动时生效。

**Q10：批量采集会触发通知吗？**
A：本模块本身不发送通知，但采集到的变更（如已售状态）会通过 `mark_sold()` 触发 `task_links.display` 更新，任务级别的通知由任务调度器在商品状态变化时触发。

**Q11：断点续传时如何处理暂停期间已售的商品？**
A：`_load_resumable_progress()` 读取 pending_item_ids 后，调用 `list_items_by_ids()` 获取完整 item dict，然后过滤掉 `it.get("is_sold")` 为 True 的商品。这样避免重复采集已售商品。

**Q12：为什么任务控制端点能立即返回？**
A：三个端点（pause/resume/stop）只更新内存中的 `_status` 和 `_pause_event`/`_stop_flag`，不等待当前 item 处理完成。实际暂停/停止在循环检查到标志后生效。这样保证 API 响应时间 <500ms，同时保证当前 item 的数据库写入完整。

**Q13：执行历史会保留多久？**
A：默认 90 天（`history_retention_days=90`）。启动时 `cleanup_batch_refresh_history_on_startup()` 自动清理超过此天数的记录。设为 0 表示永不清理。前端也提供「清理 30 天前」与「清空全部」按钮（分别调用 `DELETE /history?days=30` 与 `DELETE /history?days=0`）。

**Q14：`task_id` 是怎么生成的？跨进程重启会重置吗？**
A：调度器启动时从 `batch_refresh_history` 表 `MAX(task_id)` 初始化 `_current_task_id`，跨进程重启不重置。`trigger_now()`（手动）与 `_run_batch_job()`（定时）均先 `+=1` 再使用，保证单调递增。

**Q15：执行历史的 `error_messages` 字段上限多少条？**
A：单批次累积上限 50 条（`_MAX_ERROR_MESSAGES=50`），FIFO 丢弃最旧。单条错误内容截断为 500 字符，避免超长堆栈。无错误时该字段为 NULL。

**Q16：历史记录的 `status` 有哪些值？分别什么含义？**
A：`running`=执行中 / `completed`=正常完成 / `cancelled`=用户停止 / `failed`=连续失败熔断。批次开始时插入 `running`，结束时由 `_compute_final_status()` 决定终态。

**Q17：触发后为什么前端要立即开启高频轮询？**
A：`trigger_now()` 通过 `run_coroutine_threadsafe` 异步提交到主事件循环，`status` 不会立即变为 `running`。默认 10s 低频轮询会让用户感觉「页面未更新」。`startForceFastPoll()` 强制 3s 高频，30s 兜底超时：status 进入运行态后解除，超时则恢复低频避免无意义请求。

**Q18：`PATCH /config` 在调度器未启动时调用会怎样？**
A：仍允许更新全局 config 单例的 `interval_minutes`/`enabled` 字段，下次启动时按此配置生效。响应中 `batch_size`/`max_items_per_run` 也从 config 读取返回。这是为了让用户在调度器未启动时也能预先调整配置。
