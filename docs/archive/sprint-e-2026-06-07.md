## 1. O-09 SSE 重连回放

### 1.1 痛点

- Dashboard 实时事件流依赖浏览器 `EventSource('/api/events/stream')`
- 断网 / 服务重启 / 标签页休眠等场景下，**断线期间产生的事件会丢失**
- 用户体感："系统明明在跑，我这边事件列表却卡住没动"
- 痛点定位：UX-11 用户研究中 5/8 受访者反馈"事件流有过丢失"

### 1.2 设计决策

#### 1.2.1 协议层：SSE 原生 `Last-Event-ID` 机制

HTML5 EventSource 规范原生支持：
- 服务端发的每条 `id: <n>` 帧，浏览器自动缓存到 `EventSource.lastEventId`
- 下次重连（无论自动还是手动）时，浏览器自动注入 `Last-Event-ID: <n>` 请求头
- 业务层**零侵入**，零依赖

#### 1.2.2 双保险：URL query `?last_event_id=`

浏览器 EventSource 只在 `Last-Event-ID` header 里传，**不会**写 query。
- 实际场景里部分反代 / 调试工具会丢失 header
- 前端显式拼 `?last_event_id=${this._esLastId}` 兜底
- 服务端 query 优先于 header（便于 Python smoke 测试和调试覆盖更准确的值）

#### 1.2.3 后端回放：仅在客户端显式传 last_id 时回放

- **不传 last_id** = "我是新会话" = **不回放**历史事件（避免首次连接被 1000+ 条历史事件淹没 UI）
- **显式传 last_id**（含 0）= "请帮我从 last_id 之后回放"（浏览器自动注入的语义）

#### 1.2.4 心跳节流：2s → 3s

之前 2s 一帧太频繁，前端控制台被 ping 淹没。
- 改 3s 后：断线检测时间从 2s 拉到 3s（可接受）
- 选 3s 而非 15s：15s 让"重连后等到下一次推送"也变 15s，断线后事件明显延迟
- 3s 是 push 实时性 + 控制台噪音的折中

#### 1.2.5 回放上限：单连接最多 1000 条

- 防止数据库积压时一次刷爆连接
- 触发上限时通过 `hello.replayed` 字段返回实际回放数，前端可显示"已回放 N 条"

### 1.3 实现

#### 1.3.1 后端 [api_stats.py](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/routes/api_stats.py) `events_stream` 端点

```python
@router.get("/events/stream")
async def events_stream(
    container: Container = Depends(get_container),
    last_event_id: int | None = Query(default=None, ge=0, description="P3-O-09..."),
    last_event_id_header: int | None = Header(default=None, alias="Last-Event-ID", ge=0),
) -> StreamingResponse:
    client_provided_last = last_event_id is not None or last_event_id_header is not None
    effective_last_id = last_event_id if last_event_id is not None else (last_event_id_header or 0)
    should_replay = client_provided_last

    async def gen():
        # 0) 立即回放：last_id 之后的所有事件（最多 REPLAY_LIMIT 条）
        replayed = 0
        cursor = 0
        if should_replay:
            replay_rows = container.repo.list_events(
                since_id=effective_last_id, ascending=True, limit=1000
            ) or []
            for ev in replay_rows:
                ev_id = int(ev.get("id") or 0)
                if ev_id <= effective_last_id:
                    continue
                yield _format_sse_event(ev, ev_id)
                cursor = ev_id
                replayed += 1

        # 1) hello 帧（带服务端 latest id + 本次回放条数）
        latest = container.repo.max_event_id()
        yield f"event: hello\ndata: {json.dumps({..., 'latest_id': latest, 'replayed': replayed, ...})}\n\n"

        # 2) 进入 3s 轮询模式
        while True:
            await asyncio.sleep(3)
            cur = container.repo.max_event_id()
            if cur > cursor:
                new_rows = container.repo.list_events(since_id=cursor, ascending=True, limit=200)
                for ev in new_rows:
                    ev_id = int(ev.get("id") or 0)
                    if ev_id <= cursor: continue
                    yield _format_sse_event(ev, ev_id)
                    cursor = ev_id
            yield f"event: ping\ndata: {json.dumps({'ts': ...})}\n\n"
```

#### 1.3.2 仓储层 [repository.py](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/infra/repository.py) 新增 `since_id` / `max_event_id`

```python
def list_events(self, ..., since_id: int | None = None, ascending: bool = False, ...):
    stmt = select(EventRow).order_by(EventRow.id.asc() if ascending else EventRow.created_at.desc())
    if since_id is not None:
        stmt = stmt.where(EventRow.id > since_id)
    ...

def max_event_id(self) -> int:
    return int(self.engine.connect().execute(select(func.max(EventRow.id))).scalar() or 0)
```

- `since_id` + `ascending=True` 是回放的标准组合：拉区间 `(since_id, +∞)` 并按 id 升序
- `max_event_id` 用于 3s 心跳轮询时快速判断"是否有新事件"

#### 1.3.3 前端 [base.html](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/templates/base.html) `connectEventStream`

```javascript
connectEventStream() {
  const q = this._esLastId ? `?last_event_id=${this._esLastId}` : '';  // 双保险
  const es = new EventSource('/api/events/stream' + q);
  this._es = es;
  es.addEventListener('app_event', (e) => {
    if (e.lastEventId) {  // 浏览器原生缓存 + 手动跟踪
      this._esLastId = Number(e.lastEventId);
      this._esLatestId = this._esLastId;
    }
    // ... 事件处理 ...
  });
  es.addEventListener('hello', (e) => {
    const d = JSON.parse(e.data);
    this._esLatestId = d.latest_id || 0;
    if (d.replayed && d.replayed > 0) {
      this.eventStreamStatus = `● 已连接（已回放 ${d.replayed} 条）`;
    }
  });
  es.addEventListener('error', () => {
    if (es.readyState === 0) {
      // 浏览器自动重连中（弱网）
      this._esReconnectCount++;
      this.eventStreamStatus = `↻ 重连中…（${this._esReconnectCount}）`;
    } else {
      // CLOSED：彻底断开 → 主动重建（避免依赖浏览器自动重连）
      try { es.close(); } catch (_) {}
      this._es = null;
      if (document.visibilityState === 'visible') {
        this.connectEventStream();  // 立即重建（不等 setTimeout），保证新连接带 _esLastId query
      }
    }
  });
}
```

### 1.5 关键技术细节

1. **断线检测时序**：
   - 服务端 3s 心跳 → 浏览器 native 自动重连（带 `Last-Event-ID`）
   - 服务端连接关闭 → 浏览器触发 `error` + readyState=2 → Alpine 主动重建（带 query）
2. **重连 URL 拼接的双保险**：浏览器 native 自动重连走 header（零业务），Alpine 主动重建走 query（覆盖 header 丢失场景）
3. **不传 last_id 不回放**：避免"首次连接刷屏 1000+ 历史事件"的反模式
4. **回放上限 1000**：通过 `hello.replayed` 告知前端，前端可提示"还有 N 条未回放"

### 1.6 已知限制

- **Web 进程与 Run 进程独立**：event_bus 不跨进程，所以断线期间 Run 进程产生的事件只能从 DB 重新查（O-09 已实现，REPLAY_LIMIT=1000）
- **更老的事件可能丢失**：若断线时间很长且事件量超过 1000，最老的会被截断（生产环境事件 3s/条 × 1000 = 50 分钟，断网 50 分钟以上才会丢）
- **跨标签页不共享 lastEventId**：每个标签页独立维护 `_esLastId`，多开不会互相覆盖

## 2. UX-08 任务批量操作真实语义（收尾）

### 2.1 范围

- 真实语义：5 个 action（pause/resume/stop/restart/delete）走 `/api/tasks/batch-control` 端点
- **inline 二次确认**：stop / delete 走 batch-confirm-bar（不再 `window.confirm`）
- 自动撤销：5s 未点确认 → `_confirmTarget` 自动清空

### 2.2 痛点

- 之前 `window.confirm()` 阻塞主线程、打破 P3-UX-06 原则（"打断感小、可逆"）
- 多任务批量操作缺少"批量级"确认提示，5s 计时撤销与单任务一致

### 2.3 设计决策

#### 2.3.1 复用 `_armConfirm` 状态机

- 单任务的 stop/delete 已经用 `_armConfirm(taskId, action, label, hint)` 状态机（5s 自动撤销 + 渲染 confirm-bar）
- 批量场景下用 `'__batch__'` 作为占位 id，复用同一个状态机
- 避免在每行重复渲染"删除确认按钮"

#### 2.3.2 区分"可逆"与"不可逆"操作

- pause / resume / restart：可逆，**直接执行**（不弹确认）
- stop / delete：不可逆，走 inline 二次确认
- 5s 计时器超时自动撤销（_confirmTarget = null + bar 自动隐藏）

#### 2.3.3 抽离 `_execBatchControl`

把真正调 API 的部分拆成单独方法：

```javascript
async batchControl(action) {
  if (this.selectedIds.length === 0) return;
  if (action === 'stop' || action === 'delete') {
    // 走 _armConfirm，等用户点 batch-confirm-bar 上的"确认"再执行
    const label = action === 'delete' ? '批量删除' : '批量停止';
    const hint = action === 'delete'
      ? `将软删除 ${this.selectedIds.length} 个任务（数据可恢复）`
      : `将停止 ${this.selectedIds.length} 个任务（可恢复）`;
    this._armConfirm('__batch__', action, label, hint);
    return;
  }
  return this._execBatchControl(action);  // pause/resume/restart 直接执行
},
async _execBatchControl(action) {
  this._cancelConfirm();
  this.batchBusy = true;
  try {
    const r = await fetch('/api/tasks/batch-control', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ task_ids: [...this.selectedIds], action }),
    });
    // 200/207 → toast + reload；非 2xx → toast err
  } finally {
    this.batchBusy = false;
  }
}
```

```python
def _payload_text(payload: Any) -> str:
    """把 payload 序列化成可搜索的文本
    - dict/list → json
    - str → 原样
    - None/其他 → 空串
    """
    if payload is None:
        return ""
    if isinstance(payload, str):
        return payload
    try:
        return json.dumps(payload, ensure_ascii=False, default=str)
    except Exception:
        return str(payload)
```
