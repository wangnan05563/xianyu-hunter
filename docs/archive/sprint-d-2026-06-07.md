## 1. F-OB1 业务指标看板

### 1.1 现状问题
- Dashboard 已有 4 张 sparkline 卡（24h 短期趋势）和异常雷达（今日 err 数量）
- 但"过去 30 天系统跑得怎么样"没有量化指标
- 硬核用户问"我这一个月捡漏命中率多少" / "推送是不是最近老失败"——只能翻 orders/events 表人工聚合

### 1.2 实施细节

**后端** [api_stats.py](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/routes/api_stats.py)：
- `GET /api/stats/business-kpi?range_days=30`：
  - 4 项指标 + 同期对比基线（前 30 天 vs 后 30 天）+ 样本量
  - `range_days` clamp 到 `[1, 365]`，避免 0/负/超大值

**指标设计**（每项含 `value + delta_pct + sample_size + hint + is_pct`）：
| id | 标题 | 分子 | 分母 | 反向？ |
|---|---|---|---|---|
| `items_discovered` | 发现商品数 | evaluations 去重 item_id | / | 正向 |
| `eval_pass_rate` | 评估通过率 | risk_level='low' 数 | 总评估数 | 正向 |
| `order_success_rate` | 抢单成功率 | status IN (paid, confirmed) | 总订单数 | 正向 |
| `notify_failure_rate` | 推送失败率 | events.stage LIKE '%notify%' AND level='err' | events.stage LIKE '%notify%' | **反向**（低=好） |

**同期对比逻辑** [`_safe_pct_change`](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/routes/api_stats.py#L701-L712)：
- `previous=0 && current=0` → 0.0（"无变化"）
- `previous=0 && current≠0` → `None`（前端显示"新建"标签）
- 正常情况 → `(current - previous) / previous * 100` 保留 2 位小数

**Repository 通用方法** [repository.py](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/infra/repository.py)：
- [`db_count_by_predicate`](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/infra/repository.py#L227-L271)：在时间窗内做"满足额外条件 / 总数"二元计数，省去业务端 2 次手写 SQL
- [`db_distinct_items_in_window`](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/infra/repository.py#L273-L295)：返回时间窗内去重 item_id 列表
- 抽出这两个方法目的：F-OB1 / F-OB2 / 未来的统计接口都能复用

**前端** [dashboard.html](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/templates/dashboard.html) + [app.css](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/static/app.css)：
- 4 张 KPI 卡放在 sparkline 卡下方一行（grid-4 mt-16）
- 视觉差异化：左侧 border 用 4 种主色（蓝/绿/橙/红）让 4 张卡不"一片白"
- delta 标签：绿=up / 红=down / 灰=flat / 灰=na（推送失败率自动反转方向）
- 拉取频率：init 一次 + 5 分钟轮询（30 天聚合是"长期健康度"指标，秒级无价值）
- 失败静默：网络/服务异常 → 控制台 warn，不弹 toast（KPI 是次要数据）

**`fmtKpiValue` / `deltaCls` / `deltaText` 三个辅助方法**：
- 数字 0% / 100% 边界用整数显示，中间值 1 位小数（"78.5%" 比 "78.500000%" 顺眼）
- delta 颜色：正向指标 `delta>0→绿`、反向指标 `delta<0→绿`（推送失败率降低是好事）
- 文本：`+12.5%` / `-3.2%` / `持平` / `新建`（4 种语义）

## 4. O-01 Toast 严重度分级

### 4.1 现状问题
- 旧 `xhToast(msg, type)` 只区分 ok/err 两个级别，且 err 永久不消失
- 真实场景里"信息性提示"（如「已复制」）、"提醒"（如「即将过期」）、"错误"（如「保存失败」）、"致命"（如「登录态失效」）的视觉权重应当不同
- 把"提醒"用 err 红色展示会造成疲劳；把"致命"用 info 灰色展示会被忽略

### 4.2 设计要点
- **4 级严重度**：`info` / `warn` / `err` / `critical`（含别名 `warning` / `error` / `crit`）
- **不同 duration**：
  - `info` 3.5s 自动消失
  - `warn` 5s
  - `err` 8s + 关闭后入 `localStorage[xh.errlog.v1]`（复用 Sprint C UX-11 错误日志抽屉）
  - `critical` 永不自动消失 + 呼吸边框动画 + 点击 → 跳转 errlog 抽屉
- **视觉差异化**：4 色左边框 + 不同背景透明度，扫一眼能分级
- **backward compat**：旧调用 `xhToast('msg')` / `xhToast('msg', 'ok')` / `xhToast('msg', 'err')` 全部仍工作

|---|---|---|
| 前端 | [base.html](file:///d:/code/otherProjects/17_xianyu/src/xianyu_hunter/web/templates/base.html) | `xhToast` 函数支持 4 级严重度 + `criticalPulse` 动画 |

## 5. F-04 配置分享脱敏

### 5.1 现状问题
- 配置里含 serverchan_send_key / pushplus_token / bark_key / browser.user_data_dir 等敏感字段
- 用户想把"我的筛选策略"分享给同事 / 论坛求助时，复制 YAML 直接发会泄露密钥
- 缺一个"分享专用"视图

### 5.2 设计要点
- **新端点**：`GET /api/config/share`
  - 返回 `summary`（人类可读的 Markdown 风格文本）+ `config`（脱敏 dict）+ `redacted_fields`（被移除的字段路径列表）
- **脱敏规则**：`_SHARE_REDACT_PATHS` 维护敏感路径：
  - `serverchan_send_key` / `pushplus_token` / `bark_key`
  - `browser.user_data_dir` / `waf.*` 等含本地路径的字段
  - 被脱敏字段值统一替换为 `***`，并在 summary 里说明哪些字段被脱敏
- **summary 用途**：直接贴群里/贴 issue，比导 YAML 更易读
- **不动原配置导入/导出**：导入/导出保留全部字段（运维/迁移场景需要），仅 share 脱敏

## 6. F-01 AI 自然语言建任务

### 6.1 现状问题
- "新增任务"表单有 5 个字段（关键词 / 任务名 / 价格区间 / 模式 / 排除词），新用户经常填错或填不全
- 想建 5 个类似任务时，要重复点 5 次表单 = 30 秒×5 = 2.5 分钟
- 缺一个"一句话建任务"入口

### 6.2 设计要点
- **后端新端点**：`POST /api/ai/parse-task`
  - 优先调 LLM（OpenAI 兼容 chat completions，支持 OpenAI / DeepSeek / 智谱 等；用现有 `openai_api_key` + `openai_base_url`）
  - **零新增依赖**：用 httpx（已装）直调，不引 openai 库
  - **降级策略**：未配 Key 或 LLM 失败 → 自动切换到**规则解析**（regex 提价格 + 关键词 + 模式 + 排除词）
  - **30s 超时**：与前端 AbortController 对齐
- **前端 Modal**：在「任务管理」页 + 新增任务按钮旁加 `✨ 智能建任务` 按钮
  - 用户输入自然语言（如 "我想买 95 新索尼 A7M4 套机，1.2w 以内"）
  - 点击 `✨ 开始解析` → spinner + 状态文案
  - 解析成功 → 展示 `解析结果（可继续微调）` 平铺（关键词 / 任务名 / 价格区间 / 模式 / 排除词 / 备注 + 解析依据）
  - 错误 → inline 错误框 + 顶 toast
  - 确认 → `用此结果继续 →` 把字段填入**现有「新增任务」form** → 用户二次微调 → 提交
- **设计取舍**：**不**直接在 AI modal 提交，因为用户经常需要"AI 给的大致对了，但我想再调一下价格/补一些词"——复用现有 form 流程 = 复用 name 必填校验 + 草稿恢复逻辑

## 9. UX-12 时间线严重度过滤（Sprint D 收尾）

### 9.1 现状问题
timeline 页每天累积几百条 events（evaluate / heartbeat / notify），用户排障时只想看 warn/err；但旧版只能"全部看到"或者"切到 events 然后全文搜索 err"——两条路径都太重。

### 9.2 设计要点（为什么这么做）
- **多选而非单选**：`info+err` 组合也常见（"想看 error 但保留评估 info"），单选把这种语义逼死成"先点 info 再点 err 两次切换"
- **默认全选（`['all']`）**：保留"看到全部"这条最短路径；UX 上不该要求用户先点 4 次才能"什么都没过滤"
- **`['all']` 显式标记而非空数组**：空数组会和"主动全部取消"语义歧义；用关键字 `all` 在 URL / state 里都能一眼识别
- **orders 不受 level 过滤影响**：订单有自己的 `status` 维度（paid/failed/pending），不该被 level 概念覆盖
- **URL 同步（`?levels=err,warn`）**：支持深链 / 分享 / 浏览器历史回退；用 `replaceState` 不污染历史栈（pill 切换不该让"返回"键卡住）
- **`'all'` 不写入 URL**：默认值，分享链接里没必要带"无过滤"这个冗余参数；测试用例 [6] "点 全部 后 URL 中 levels 参数被移除" 即验证此点
