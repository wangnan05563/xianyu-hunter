# XianyuHunter 客户体验优化方案 v2

日期：2026-06-05
阶段：基于 v1（登录引导 / 用户信息 / 直方图产品标签 / 面包屑 / 响应式列表）已落地的成果，做前瞻性优化
输入：项目代码 + 用户原始诉求"全面评估并提出便于操作的优化方案"
受众：产品 / 前端 / 测试
评估方法：界面走查 + 流程推演 + 既有数据接口盘点 + 行业最佳实践对照

---

## 摘要：5 个核心判断

1. **核心症结是"流程效率"而非"页面美观"**。v1 已经把信息可读性问题（登录、账户信息、产品标签）解决了。下一阶段最大杠杆点是"高频重复操作"——加任务、人工接管、配置切换、问题排查。
2. **缺乏"统一时间线"是结构性短板**。事件 / 日志 / 订单 / 评估四套数据本质都是"事情的发生与结果"，用户为追一个失败订单要切换 3 个页面。
3. **移动端体验基本缺位**。系统强运营/出差场景，没有响应式断点适配，移动端几乎不可用。
4. **键盘 / 快捷键 / Command Palette 是被严重低估的杠杆**。高频用户（运营、客服）一天触发几十次相同动作，少 1 秒就是数十次/天。
5. **数据可视化停留在"看个大概"层级**。直方图只展示静态分布，没有时间趋势；评估分没有分布；任务成功率没有折线。看不见趋势就做不出决策。

## 2. 详细前端功能优化建议

> 下面每个优化点都按"交互逻辑 / 视觉设计 / 信息架构"三维度展开。

### P0-1 任务快速复用 + 表单可恢复

**交互逻辑**
- 任务列表行尾加"📋 复制"按钮，弹出 modal **预填** 新任务表单，关键词 / 名称 / 价格区间 / 模式都带过来，用户改一两处即可提交。
- 关闭"新增任务"modal 时，把当前填写值存到 `localStorage('xh.task-draft')`，下次打开自动恢复。

**视觉设计**
- 复制按钮用次级色 ghost 按钮 + 📋 图标，与"删除"（danger）明显区分。
- Draft 恢复时在 modal 顶部加一行淡色提示"已恢复上次草稿 [×清除]"，避免误提交。

**信息架构**
- 任务表头加"创建时间"以外的"最近活跃"列（按最后一次事件时间），让运营知道哪些任务值得复制。

**为什么这能提升体验**
加任务是最高频操作之一。复制场景占新任务的 30%+（同一关键词多价格段），可从 ~25s 降到 ~5s。

---

### P0-2 Dashboard"异常雷达"模式

**交互逻辑**
- 顶部增加"⚠ 异常"切换开关：
  - **关（默认）**：现有 4 卡 + 事件流。
  - **开**：把页面折叠为"异常中心"——失败订单 / 超时未支付 / 评估分数异常的任务，全部置顶 + 红点。
- 每个统计卡片点击下钻到对应的明细页（订单 → `/orders?status=failed`）。

**视觉设计**
- 4 卡底色用状态色编码：成功 = 绿边、待支付 = 黄边、失败 = 红边、运行中 = 橙边。
- 失败卡 > 0 时，整个卡片轻微 pulse 动画（2s 一次），从视野里"刺"出来。

**信息架构**
- 在"系统状态"卡片里增加"今日新增"指标：今日订单数 / 今日评估数 / 今日事件数（按小时分组的迷你 sparkline）。

**为什么这能提升体验**
运营每天的核心动作是"看有没有出问题"。当前要肉眼扫 4 卡 + 翻 50 条事件，找异常耗时长（>10s）。异常雷达模式可降到 <2s。

---

### P0-3 统一时间线 + 跨数据过滤

**交互逻辑**
- 新增"事件中心"页面 `/timeline`，把 4 套数据（事件 / 订单 / 评估 / 日志）按时间合并展示：
  - 左侧过滤器：数据源多选（事件/订单/评估/日志）+ 时间范围（1h/24h/7d/自定义）+ 任务多选
  - 右侧时间线：每行 = 一次行为（订单创建/评估通过/日志告警），点击展开看 payload JSON
- 顶栏铃铛"🔔"点击直达 `/timeline`，未读数 = "上次访问之后的新事件数"。

**视觉设计**
- 时间线用"颜色 + 图标"区分数据源：🟦 事件 / 🟧 订单 / 🟩 评估 / ⬜ 日志
- 异常项（failed / error）左边一条 4px 红色边，hover 自动展开

**信息架构**
- 用 `?from=order&ref=o123` 让其他页面跳转过来时自动定位到对应项（"→ 在时间线中查看"链接）

**为什么这能提升体验**
失败订单排查是核心客服场景。现状：3 个页面跳转 + 关键词搜索。优化后：1 个页面 1 步过滤，~5s 完成。

### P1-1 配置 Diff 预览 + 一键回滚

**交互逻辑**
- 改任意配置项时（特别是价格阈值、评估权重），**禁止直接 POST 写入**。
- 点击"应用" → 后端返回 `diff`（before/after 字段值变化）→ 前端弹 diff 预览 modal → 用户"确认写入"才真写。
- 每次写入前自动备份 `.bak`，成功后页面顶部出现"已保存 v123 · [回滚]"链接（24 小时内可回滚）。

**视觉设计**
- Diff 用绿/红双色 + 旧值划线 + 新值高亮（VSCode 风格），让差异一眼可见。
- 危险项（auto 模式开启、阈值放大 > 2x）用 ⚠ 图标前置 + 二次确认。

**信息架构**
- 配置页面右侧加"最近 5 次修改"小卡片，列出"时间 + 修改字段 + [回滚]"。

**为什么这能提升体验**
配置改坏 = 整个系统失灵。Diff + 回滚 = 把"不可逆"变成"可逆"，心理压力降低 80%。

---

### P1-2 人工接管体验升级

**交互逻辑**
- "🖐 人工接管"点击后弹 modal（非浏览器 confirm）：
  - 显示订单详情（商品 / 价格 / 卖家 / 闲鱼链接）
  - 显示倒计时（"⏰ 距自动放弃还有 X 分钟"，倒计时 < 60s 红色加粗）
  - 三个按钮："已支付" / "我放弃" / "我再想想"
- 状态流转：点击"已支付" → 状态置为 succeeded；"我放弃" → 状态置为 cancelled。

**视觉设计**
- Modal 顶部有订单状态 pill 颜色（待支付=黄，已接管=橙，已成功=绿）。
- 倒计时条做进度条样式，最后 10s 闪烁。

**信息架构**
- 抢单记录表里 pending 订单加"⏰ X 分钟前创建"列，> 5 分钟的标红警示"即将超时"。

**为什么这能提升体验**
当前用浏览器 confirm 简单粗暴，缺反馈、缺后续、缺超时提示。Modal + 倒计时 + 状态联动 = 用户能"放心"接管。

---

### P1-3 任务列表分页 + 虚拟滚动

**交互逻辑**
- 任务 > 10 个时启用分页：每页 20 个 + 跳转。
- 表格列加排序：按"关联数 / 状态 / 创建时间"可排序。
- 关联数按钮 hover 浮窗显示"商品 N · 卖家 M · URL K"预览。

**视觉设计**
- 窄屏 < 768px 时表格自动转为卡片列表（每任务一张卡，含所有关键信息 + 折叠操作）。

**信息架构**
- 增加"按状态过滤"Tab：全部 / 运行中 / 暂停 / 已停止 / 已删除（与原"已删"标识一致）。

**为什么这能提升体验**
> 50 任务时页面滚动 + 操作定位会变得痛苦。分页 + 过滤是表格类页面的"基本盘"。

---

### P1-4 Toast 升级为 Notification Center

**交互逻辑**
- 保留轻量 toast（3s 自动消失，用于"✓ 已保存"类成功反馈）。
- 新增持久通知（用于错误、超时、待处理事项）：右下角堆叠卡片，**不自动消失**，用户可手动关闭或"全部已读"。
- 顶栏铃铛的"未读数" = 持久通知的未读数（与时间线统一）。

**视觉设计**
- 严重程度四级：info（蓝）/ success（绿）/ warn（黄）/ error（红），左侧 4px 色边。
- 错误通知带"→ 查看详情"链接，跳到日志/时间线对应条目。

**信息架构**
- 通知按"产生时间倒序"堆叠，最多 5 张可见；超出折叠"查看全部 →"。

**为什么这能提升体验**
失败原因现在直接蒸发。改成持久通知 + 可追溯 = 用户不再"我刚才那个错哪儿了？"。

---

### P1-5 移动端响应式

**交互逻辑**
- < 768px：顶栏改为"汉堡菜单 + 标题 + 头像"三件套；侧栏抽屉化（左滑出现）。
- 表格页面自动切换为卡片列表（与 P1-3 联动）。
- 顶栏铃铛 / 主题 / 账户 chip 在窄屏合并为"⋯"更多菜单。

**视觉设计**
- 字号在 768px 以下上调 1px（移动端阅读距离远）。
- 按钮高度从 32px 调到 40px（防误触）。

**信息架构**
- 移动端优先展示"行动"信息：异常订单数 / 任务运行状态 / 账户登录态。

**为什么这能提升体验**
运营出差 / 通勤时需要看"有没有出单"。当前 < 768px 几乎不可用，移动端友好 = 7×24 可监控。

### P2-1 键盘快捷键 + Command Palette

**交互逻辑**
- 全局快捷键：
  - `g d` → 跳 Dashboard
  - `g t` → 跳任务
  - `g o` → 跳订单
  - `g c` → 跳配置
  - `?` → 打开快捷键说明
  - `Ctrl/Cmd+K` → 打开命令面板
- 命令面板：模糊搜索任务名、订单 ID、评估项、配置项；回车跳转；Esc 关闭。

**视觉设计**
- 命令面板用 macOS Spotlight / VSCode 风格：居中深色卡片 + 输入框 + 列表。
- 快捷键提示悬浮 tooltip，2s 后淡出。

**为什么这能提升体验**
高频用户节省鼠标移动 = 每天省下分钟级时间。

---

### P2-2 数据可视化升级

**交互逻辑**
- 任务详情页增加"近 7 日"折线图：事件数（按小时聚合）、订单成功率、评估分中位数。
- Dashboard 价格直方图旁边加"分位数线"（P25 / P50 / P75），让用户知道自己的定价在哪一档。

**视觉设计**
- 折线图用 SVG（与现有直方图同技术栈，无新依赖）。
- hover 显示具体值 tooltip。

**为什么这能提升体验**
"看趋势"比"看快照"更利于决策（值不值得加价、任务要停还是要继续）。

---

### P2-3 配置导入 / 导出 / 分享

**交互逻辑**
- 配置页右上角加"导出"按钮 → 下载当前配置 JSON（含版本 + 时间戳）。
- "导入"上传 JSON → diff 预览 → 确认覆盖。
- 分享：生成可复制的配置摘要（不含敏感字段，如 token）。

**为什么这能提升体验**
团队协作 / 备份 / 故障复盘都需要可传输配置。当前是手抄 / 复制 YAML。

---

### P2-4 日志可标记 / 搜索 / 导出

**交互逻辑**
- 日志行右键菜单：标记 / 复制 / 排除（按内容过滤）。
- 顶部"按级别过滤"（info/warn/error）+ 关键词搜索（带正则模式）。
- "导出"按钮下载过滤后的日志。

**为什么这能提升体验**
"那一行报错了" 现在只能滚轮翻。搜索 + 标记 + 导出 = 排查效率 5x+。

## 3. 实现思路、技术可行性、预期效果（按 P0 详写，P1/P2 简表）

### 3.1 P0 详细分析

#### P0-1 任务快速复用

| 维度 | 说明 |
|---|---|
| **实现思路** | 1) tasks/list.html 新增"复制"按钮（行尾 ghost 按钮）；2) 复制 → 把 `t` 写入 `form` + `showAdd=true`；3) draft 自动保存到 `localStorage`；4) modal 打开时检测 draft 并恢复 |
| **技术可行性** | 现有 Alpine.js 组件 + Jinja 模板，零后端改动；纯前端 ~50 行 JS |
| **风险** | draft 恢复可能让用户误以为当前是上次提交值 → 顶部加"已恢复"提示 + 清除按钮 |
| **预期效果** | 加任务耗时 ↓ 80%（25s → 5s）；周活用户加任务频次 ↑ 30% |

#### P0-2 Dashboard 异常雷达

| 维度 | 说明 |
|---|---|
| **实现思路** | 1) 顶栏加 `mode: 'normal' \| 'alert'` 开关；2) alert 模式下，stats API 优先返回异常项；3) 4 卡加 click handler 跳详情页（带 query string）；4) 新增 `/api/stats/today` 返回今日指标 |
| **技术可行性** | 后端需扩展 stats API（~50 行）；前端 Alpine 加 store，~100 行；无新依赖 |
| **风险** | alert 模式下信息密度可能反而下降 → 保留"恢复普通模式"按钮常驻 |
| **预期效果** | 异常发现时间 ↓ 80%（10s → 2s）；运营每天节省 ~10 分钟 |

#### P0-3 统一时间线

| 维度 | 说明 |
|---|---|
| **实现思路** | 1) 新增 `GET /api/timeline?types=...&from=...&to=...&task_id=...` 聚合端点；2) 内部 union 4 张表（events/orders/evaluations/logs）；3) 新模板 `timeline.html`；4) 顶栏铃铛加 `?from=bell` 跳转 |
| **技术可行性** | 后端聚合查询 ~150 行（可加缓存层，30s TTL）；前端列表 + 过滤，~200 行 |
| **风险** | 数据量大会慢 → 强制分页 + 时间窗默认 24h；可加 ?limit=200 限制 |
| **预期效果** | 故障排查时间 ↓ 60%（30s → 12s）；客服满意度 ↑ |

## 4. 实施路径与资源需求

### 4.1 分 4 个迭代

| 迭代 | 时间 | 内容 | 人力 |
|---|---|---|---|
| **Sprint 1（P0）** | 第 1-2 周 | P0-1 任务复用 / P0-2 异常雷达 / P0-3 统一时间线 | 1 前端 + 0.5 后端 |

## 5. 效果衡量指标与验证方法

### 5.1 指标体系（HEART 框架）

| 维度 | 指标 | 现状（v1） | 目标（v2） | 验证方法 |
|---|---|---|---|---|
| **Happiness 满意度** | 内部用户 NPS（季度） | 未测 | ≥ 8 分 | 季度问卷 |
| **Engagement 参与度** | 周活跃用户数 | 基准 | ↑ 30% | 访问日志 |
| **Adoption 功能使用率** | 任务复制 / 异常雷达 / 时间线使用占比 | 0% | 复制 50% / 雷达 40% / 时间线 60% | 埋点 |
| **Retention 留存** | 次月回访率 | 基准 | ↑ 20% | 访问日志 |
| **Task Success 任务成功率** | 加任务耗时 / 异常发现时间 / 故障排查时间 | 25s / 10s / 30s | 5s / 2s / 12s | 操作埋点 + 用户访谈 |

### 5.2 验证方法

1. **可用性测试**：每个 P0 上线前找 3 个内部用户做"任务走查"（think-aloud），记录痛点
2. **A/B 测试**：P0-1 复制按钮可做 A/B（开启/关闭），看使用率与任务数关系
3. **数据埋点**：前端引入轻量埋点（点击 + 时长），服务端加 `?metrics=1` 模式
4. **回归测试**：每个迭代结束用 `scripts/full_api_test.py`（已 46/46 通过）+ Playwright UI 测试

### 5.3 上线门槛

- P0 优化需通过 `bemp-auto-tester` 端到端测试 + 1 名运营人员走查
- P1 优化需通过 API 回归 + 移动端真机 / 模拟器截图
- P2 优化直接走 API 测试 + 视觉对比
