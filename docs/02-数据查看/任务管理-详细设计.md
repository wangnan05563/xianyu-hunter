## 2. 功能概述

**一句话说明**：提供任务的增删改查、启停控制、批量操作、依赖关系管理、内容关联、智能建任务与模板市场能力，是整个系统的运行入口。

**核心价值**：
- 统一管理所有闲鱼监控任务的生命周期（running/paused/stopped/error/deleted）；
- 通过任务级配置覆盖机制（search/price/eval/antidetect 四类 JSON），兼顾全局默认与单任务个性化；
- 通过 F-16 任务依赖机制，支持订单成功后自动激活下游 paused 任务；
- 任务-内容关联（task_links）支持 DB 模式浏览与 SSE 实时搜索双轨；
- 智能建任务（AI 解析自然语言）与模板市场（分类模板库）降低用户配置门槛。

## 3. 用户场景

### 场景一：新建监控任务
用户在 TaskList 页面点击"新建任务"进入 TaskEditor 6 步向导，依次填写关键词、价格区间、闲鱼筛选标签、搜索参数、AI 评估配置、调度模式（cron 或固定间隔）。提交后任务以 `running` 状态进入调度队列。

### 场景二：批量暂停任务
夜间维护时，用户在 TaskList 勾选多个任务（最多 200 个），点击"批量暂停"，调用 `/api/tasks/batch-control` 一次性将多个任务切换到 `paused` 状态。响应返回 `success_count`/`failure_count` 与成功失败列表。

### 场景三：查看任务运行历史
用户点击某任务进入 TaskDetail，查看运行历史 Tab。系统从 events 表按时间窗（默认 24 小时）聚合 runs（5 分钟一个 bucket）与 idle_gaps（>30 分钟间隔），展示事件数/命中数/错误数趋势图。

### 场景四：依赖任务编排
用户在 TaskDetail 依赖关系 Tab 添加上游依赖：A 任务依赖 B 任务。当 B 任务产生的订单进入 `succeeded` 状态时，A 任务若处于 `paused` 会被自动激活为 `running`（F-16 机制）。

### 场景五：智能建任务
用户点击"智能建任务"，输入自然语言描述（如"监控上海地区二手相机，价格 500-2000 元"），调用 `/api/ai/parse-task` 由 AI 解析为 TaskCreate 参数，预填到 TaskEditor。

## 5. 接口定义

### 5.1 任务 CRUD API（`api_tasks.py`，prefix=`/api/tasks`）

| 方法   | 路径                              | 说明                | 请求参数                                                                                                                                                       | 响应字段                                                                                                |
| ------ | --------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| GET    | `/api/tasks`                      | 任务列表（多用户隔离）| Query: `status?`, `limit?=50`(1-200), `offset?=0`                                                                                                               | `items[]`, `count`, `total`, `limit`, `offset`                                                          |
| POST   | `/api/tasks`                      | 新建任务            | Body (`TaskCreate`): 见 §6.5                                                                                                                                   | `{ ok, id, task }`                                                                                      |
| GET    | `/api/tasks/{task_id}`            | 任务详情（解析 JSON）| Path: `task_id`                                                                                                                                                | 完整 TaskRow（含已解析的 `search_config`/`price_config`/`antidetect_config`/`eval_config` dict）        |
| PATCH  | `/api/tasks/{task_id}`            | 更新任务（部分更新）| Body (`TaskUpdate`)                                                                                                                                             | `{ ok, task }`                                                                                          |
| DELETE | `/api/tasks/{task_id}`            | 删除任务            | Path: `task_id`                                                                                                                                                | `{ ok, id, cascade:{links,items,events,orders,deps,evaluations} }`                                     |
| GET    | `/api/tasks/{task_id}/runs`       | 任务运行历史        | Query: `range_hours?=24`(1-720)                                                                                                                                | `{ task_id, runs[], idle_gaps[], total_runs, total_events, total_hits }`                                |
| POST   | `/api/tasks/{task_id}/control`    | 任务控制            | Query: `action?=pause`(pause/resume/stop/restart)                                                                                                              | `{ ok, id, status, note }`                                                                              |
| POST   | `/api/tasks/batch-control`        | 批量控制            | Body: `task_ids: list[str]`(1-200), `action: str`(pause/resume/stop/restart/delete)                                                                            | `{ ok, action, new_status, success_count, failure_count, successes[], failures[] }`                    |

**关键说明**：
- 更新接口为 **PATCH**（非 PUT），使用 `model_dump(exclude_unset=True)` 区分"未传"与"传 null"。
- list 接口**不支持** `mode`/`keyword` 过滤；分页用 `limit/offset`（非 `page/page_size`）。
- control 的 `action` 是 **Query 参数**，不是 Body。
- 批量操作请求字段是 `task_ids`（非 `ids`）；单次上限 200。
- 删除任务为**混合删除**：物理删除 task_links/items/events/orders/task_deps/evaluations 六张表关联数据，任务行 status 置为 `deleted`（任务行本身保留）。
- `task_runs` 表**不存在**，runs 接口由 `repo_events.get_task_runs` 从 events 表按时间窗聚合（5 分钟一个 bucket，30 分钟以上记为 idle_gap）。

### 5.5 任务控制动作语义

| 动作     | 目标状态   | 说明                                                                      |
| -------- | ---------- | ------------------------------------------------------------------------- |
| pause    | paused     | 暂停调度（DB 直接更新；scheduler 模式调用 `scheduler.pause()`）          |
| resume   | running    | 恢复调度（scheduler 模式 `scheduler.resume()`，Cookie 失效时抛 400）     |
| stop     | stopped    | 停止任务（scheduler 模式 `await scheduler.stop()`）                      |
| restart  | running    | 重置运行上下文并启动（stop + start；未注册到 scheduler 的任务需重启服务） |

> **注意**：代码层**无前置状态校验**，任何状态可调用任何 action（DB 直接更新）。仅 scheduler 层面有 `ResumeBlockedError`（Cookie 失效或冷却期内拒绝恢复）。批量控制仅改 DB status，不同步 scheduler 内存对象（避免串行 await N 次阻塞事件循环）。

### 6.4 TaskStatus 与 TaskMode 枚举（`domain/task.py`）

**TaskStatus**（5 种）：
- `RUNNING = "running"`
- `PAUSED = "paused"`
- `STOPPED = "stopped"`
- `ERROR = "error"`（由内部异常设置，control 不支持 `action=error`）
- `DELETED = "deleted"`（任务行保留，关联数据已物理删除）

**TaskMode**（4 种）：
- `AUTO = "auto"`（全自动直接拍）
- `SEMI_AUTO = "semi_auto"`（推送确认后拍）
- `CONFIRM = "confirm"`（仅推送不拍，默认最保守）
- `NOTIFY_ONLY = "notify"`（仅推送）

## 7. 业务逻辑

### 7.1 任务状态机

```
        ┌──────────┐
   ┌───→│  running  │←──resume────┐
   │    └────┬─────┘              │
   │         │                    │
   │       pause                resume
   │         │                    │
   │         ▼                    │
   │    ┌──────────┐              │
   │    │  paused  │──────────────┘
   │    └────┬─────┘
   │         │ stop
   │         ▼
   │    ┌──────────┐  restart   ┌──────────┐
   │    │ stopped  │───────────→│ running  │
   │    └──────────┘            └──────────┘
   │         ▲
   │         │ 内部异常
   │    ┌──────────┐
   │    │  error   │
   │    └──────────┘
   │
   └─── (deleted 为终态，任务行保留但关联数据物理删除)
```

> **代码层无前置状态校验**：任何状态可调用任何 action（DB 直接更新）。仅 scheduler 层面有 `ResumeBlockedError`（Cookie 失效或冷却期内拒绝恢复）。

### 7.2 任务级配置覆盖机制

四个 JSON 字段：`search_config` / `price_config` / `antidetect_config` / `eval_config`。

- **存储**：JSON 字符串序列化存 DB（None 或空 dict 表示沿用全局）。
- **读取**：`GET /api/tasks/{id}` 时后端解析为 dict 返回前端。
- **合并算法**（在 `startup.py` 中实现，任务级覆盖全局，深度合并）：
  - 任务级 `None` → 完全沿用全局；
  - 任务级 `dict` → 与全局深度合并，任务级键优先；
  - 列表类型直接替换（不做元素合并）。
- **`antidetect_config`**：字段保留兼容旧数据，但前端 UI 已移除任务级反检测覆盖（F4 修复），原因是 AntiDetect 是 container 级共享单例，任务级覆盖架构上不可行，前端始终传 null。
- **`eval_threshold`**：独立字段（高频单字段），`eval_config` 是 dict 容纳低频覆盖字段（如 `auto_collect_official`/`auto_collect_max_per_run`）。

### 7.3 调度执行流程

```
1. 调度器（modules/scheduler.py）根据 use_cron/interval_seconds 调度任务
2. 唤醒时检查 status == running，否则跳过
3. 执行搜索（collector.live_search）→ 落库 items → 触发评估
4. 评估通过 → 按 mode 决定抢单（auto）/通知确认（semi_auto）/仅通知（confirm/notify）
5. 评估/抢单结果写入 events 表（task.search_done/eval.scored/buy.succeeded 等）
6. 计算下次调度时间（cron 推算 或 now + interval_seconds）
```

> 运行记录不写入独立的 `task_runs` 表，而是通过 events 表的 `task.search_done`/`eval.scored`/`buy.*` 等事件聚合得到。

### 7.4 任务运行记录聚合（`repo_events.get_task_runs`）

```
1. 查询 events 表中 task_id = {task_id} 且 created_at >= now - range_hours 的所有事件
2. 按 5 分钟一个 bucket 聚合：
   - 每个 bucket 统计 event_count / hit_count / err_count / warn_count / duration_s
   - hit_count = item.discovered + item.found 事件数
   - err_count = level='err' 的事件数
3. 检测 idle_gaps：相邻 bucket 间隔 > 30 分钟记为 idle_gap
4. 返回 runs[]（按时间正序）+ idle_gaps[]（前 5 条）+ total_runs/total_events/total_hits
```

### 7.5 F-16 任务依赖自动激活

```
订单 succeeded 事件触发（api_orders._trigger_dependent_tasks 同步调用，非 EventBus）
        │
        ▼
1. 取 order.item_id（空则直接 return）
        │
        ▼
2. container.repo.get_item(item_id) → item.task_id
   (item 不存在或 task_id 为空则 return)
        │
        ▼
3. container.repo.list_dependent_tasks(upstream_task_id)
   (无下游则 return)
        │
        ▼
4. 遍历下游任务：
   ├── downstream.status == "paused" → update_task_status(downstream_id, "running")
   │                                 + save_event({stage:"dep_triggered", ...})
   ├── downstream.status == "running" → logger.info 跳过
   └── 其他状态（含 stopped）→ logger.info 跳过
```

**设计原则**：仅 `paused` 状态的下游任务会被自动激活，避免误启动用户主动停止的任务。触发条件是订单状态变为 `succeeded`（直接函数调用，不经过 EventBus），发布的是 `dep_triggered` stage 的 events 表记录（非 `task.started` 事件）。

## 9. 常见问题 FAQ

### Q1：任务有哪些状态？分别是什么含义？
**A**：任务共 5 个状态：`running`（运行中）、`paused`（已暂停）、`stopped`（已停止）、`error`（异常，由内部异常设置）、`deleted`（任务行保留但关联数据已物理删除）。注意 `error` 状态不能通过 control 接口主动设置。

### Q2：任务的 4 种模式有什么区别？
**A**：`auto` 全自动评估通过即抢单；`semi_auto` 评估通过后推送通知，用户确认后抢单；`confirm` 仅推送不拍（默认最保守）；`notify` 仅推送商品信息。TaskCreate 默认 `notify`，DB 默认 `confirm`。

### Q3：关键词长度有什么限制？
**A**：关键词长度限制为 1-80 字符，由 Pydantic 模型 `TaskCreate` 校验（`min_length=1, max_length=80`），超出范围返回 422 错误。

### Q4：interval_seconds 的取值范围是多少？
**A**：30-3600 秒（即最短 30 秒，最长 1 小时），由 Pydantic 校验 `ge=30, le=3600`。过短的间隔可能触发闲鱼反爬，建议根据 `antidetect_config` 合理设置。

### Q5：eval_threshold 的取值范围是多少？
**A**：0-100，由 Pydantic 校验 `ge=0, le=100`。评估得分 ≥ 该阈值的商品才会进入抢单流程。阈值为 None 时沿用全局配置。

### Q6：任务级配置覆盖是怎么工作的？
**A**：每个任务有 `search_config`、`price_config`、`antidetect_config`、`eval_config` 四个 JSON 字段。值为 `None` 表示完全沿用全局配置；值为 `dict` 则与全局配置深度合并，任务级键优先。`antidetect_config` 前端 UI 已移除（AntiDetect 是 container 级共享单例），始终传 null。

### Q7：批量控制接口一次最多操作多少个任务？
**A**：批量控制接口 `/api/tasks/batch-control` 接受 `task_ids[]` 数组，单次最多 200 个（`min_length=1, max_length=200`）。响应返回 `success_count`/`failure_count` 与 `successes[]`/`failures[]` 两个数组。批量操作仅改 DB status，不同步 scheduler 内存对象。

### Q8：停止状态的任务怎么重新启动？
**A**：`stopped` 状态的任务需要调用 `restart` 动作恢复为 `running`。代码层无前置状态校验，任何状态可调用任何 action，但语义上 `resume` 仅适用于 `paused` 状态。

### Q9：cron 和 interval_seconds 可以同时设置吗？
**A**：可以。两者不互斥，由 `use_cron` 布尔开关决定使用哪个：`use_cron=true` 按 cron 调度，`use_cron=false` 按 `interval_seconds` 固定间隔。两者都有默认值（cron 默认 `*/5 * * * *`，interval_seconds 默认 60.0）。

### Q10：闲鱼筛选标签有哪些？
**A**：共 8 个标签：`personal_idle`（个人闲置）、`verified`（验货宝官方验真）、`account_guarantee`（验号担保）、`free_shipping`（包邮）、`super_shop`（超赞鱼小铺）、`brand_new`（全新）、`strict_select`（严选）、`resale`（转卖）。在 TaskEditor 第 2 步以卡片多选形式勾选。

### Q11：任务运行历史存在哪张表？
**A**：**不存在独立的 `task_runs` 表**。`/api/tasks/{id}/runs` 接口由 `repo_events.get_task_runs` 从 events 表按时间窗聚合（5 分钟一个 bucket），统计 event_count/hit_count/err_count/warn_count，并检测 idle_gaps（>30 分钟间隔）。

### Q12：任务删除是软删除还是物理删除？
**A**：混合删除。`delete_task_cascade(task_id)` 物理删除 task_links/items/events/orders/task_deps/evaluations 六张表关联数据，然后 `update_task_status(task_id, "deleted")` 把任务行 status 置为 `deleted`（任务行本身保留）。

### Q13：F-16 任务依赖怎么工作？
**A**：在 `task_deps` 表中维护任务依赖关系（task_id 依赖 depends_on）。当上游任务产生的订单状态变为 `succeeded` 时，`_trigger_dependent_tasks` 同步函数遍历下游任务，仅激活 `paused` 状态的下游为 `running`，发布 `dep_triggered` stage 的 events 表记录。

### Q14：智能建任务和模板市场在哪里？
**A**：TaskList 工具栏有"智能建任务"按钮（调用 `/api/ai/parse-task` 解析自然语言）和"模板市场"按钮（调用 `/api/templates` 列出分类模板）。模板分类：全部/相机/游戏/球鞋/票务/数码/其他。
