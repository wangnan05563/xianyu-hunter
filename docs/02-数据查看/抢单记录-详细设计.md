## 2. 功能概述

**一句话说明**：管理抢单订单的全生命周期，支持人工接管、状态流转、手动抢单与 F-16 下游依赖任务自动激活。

**核心价值**：
- 统一查看所有抢单订单的状态与详情，支持按状态/任务/商品过滤；
- 通过 TakeoverModal 三阶段流程（confirm → progress → done），支撑人工接管闲鱼待付款订单；
- 通过接管超时调度器（5 分钟扫描，30 分钟超时），自动清理超时订单为 `failed`，避免用户支付已关闭订单；
- 通过 SSE 订阅 `/api/events/stream` 实时推送 `buy.succeeded`/`buy.failed` 事件，前端实时更新订单状态；
- F-16 依赖任务机制：订单 `succeeded` 后同步调用 `_trigger_dependent_tasks` 激活下游 `paused` 任务；
- 手动抢单接口突破纯自动模式限制，让用户在评估明细页面主动触发。

## 3. 用户场景

### 场景一：自动抢单成功
任务以 `auto` 模式运行，评估通过后自动触发抢单。订单状态从 `pending_pay` 流转到 `paid`（用户在闲鱼 App 完成支付后由 buyer 模块回写）。前端通过 SSE 收到 `buy.succeeded` 事件后实时刷新列表。

### 场景二：人工接管待付款订单
某订单进入 `pending_pay` 状态后，用户在抢单记录页点击"接管"，调用 `POST /api/orders/{id}/takeover` 将状态置为 `takeover_pending`，前端 TakeoverModal 启动 30 分钟倒计时。用户在闲鱼 App 完成支付后点击"确认支付完成"，调用 `/takeover/confirm` 将状态置为 `succeeded`。

### 场景三：接管超时清理
用户点击"接管"后 30 分钟内未完成支付，接管超时调度器（5 分钟扫描一次）将订单状态自动从 `takeover_pending` 置为 `failed`，避免用户去支付已被闲鱼自动关闭的订单。

### 场景四：手动抢单
用户在评估明细页对某商品点击"手动抢单"，调用 `POST /api/orders/manual-takeover`，后端校验 buyer 注入态与闲鱼登录态后，调用 `container.buyer.buy()` 触发抢单。幂等检查避免重复抢单。

### 场景五：F-16 依赖任务自动激活
订单状态变为 `succeeded` 时（无论通过 `takeover_confirm` 还是 `update_order_status`），后端同步调用 `_trigger_dependent_tasks`：通过 `item_id` 反查 `items.task_id`，查询所有依赖此任务的下游任务，将 `paused` 状态的下游任务自动激活为 `running`，并写入 `dep_triggered` stage 事件。

## 7. 业务逻辑

### 7.1 接管超时调度器

```python
class TakeoverTimeoutScheduler:
    """接管超时清理调度器
    
    线程模型：BackgroundScheduler 在独立线程定时触发 _run_cleanup_job，
    直接调用 repo.expire_takeover_pending_orders 完成 DB 操作，
    无需通过 run_coroutine_threadsafe 提交到主事件循环
    （不依赖 Playwright/async 资源）
    """
    
    def _run_cleanup_job(self):
        """定时任务：扫描并清理超时的 takeover_pending 订单"""
        expired = self._container.repo.expire_takeover_pending_orders(self._timeout_min)
        # 超时订单状态从 takeover_pending → failed（不是 cancelled）
        # 为什么 failed：用户未完成支付是异常情况，cancelled 会被误认为是用户主动取消
```

**为什么 5 分钟扫描**：平衡时效性与 DB 开销。1 分钟扫描过于频繁（每分钟一次全表扫描），10 分钟扫描会让超时订单多卡 10 分钟才清理。

**为什么流转到 `failed` 而非 `cancelled`**：用户未完成支付是异常情况，`cancelled` 会被误认为是用户主动取消，影响统计准确性。

### 7.2 TakeoverModal 三阶段

| 阶段     | 触发条件                          | 用户操作               | 后端调用                              |
| -------- | --------------------------------- | ---------------------- | ------------------------------------- |
| confirm  | 用户点击"接管"按钮                | 确认商品信息，点击"确认接管" | `POST /api/orders/{id}/takeover`      |
| progress | confirm 成功后自动进入            | 切到闲鱼 App 完成支付   | 无（前端倒计时 30 分钟）              |
| done     | 用户点击"确认支付完成"或超时      | 关闭弹窗               | `POST /takeover/confirm` 或调度器自动清理 |

**状态机白名单**：仅 `pending_pay` 可被接管。
- 拒绝 `takeover_pending → takeover_pending`：避免用户无限点击重置 30 分钟倒计时，违背"30 分钟内必须完成支付"的业务约束。
- 拒绝 `succeeded`/`failed`/`cancelled → takeover_pending`：终态订单不可复活。
- 用户若需重新接管已 cancel 的订单，需先通过 `PATCH /status` 回退到 `pending_pay`。

### 7.3 F-16 依赖任务自动激活

```python
def _trigger_dependent_tasks(container: Container, order: dict) -> None:
    """F-16：订单成功后，检查是否有下游任务依赖此订单所属任务，自动激活它们
    
    触发条件：
    1. 订单状态变为 succeeded
    2. 订单关联了一个 item_id（通过 item_id 反查 items 表获取 task_id）
    3. 该 task_id 有下游依赖任务（task_deps 表）
    4. 下游任务当前状态为 paused（等待上游成功）
    
    实现方式：同步函数调用（非 EventBus），直接修改 task.status
    发布事件：stage='dep_triggered'（不是 type='task.started'）
    """
    item = container.repo.get_item(item_id)
    upstream_task_id = item["task_id"]
    
    dependents = container.repo.list_dependent_tasks(upstream_task_id)
    for dep in dependents:
        downstream_task = container.repo.get_task(dep["task_id"])
        # 仅 paused 状态的下游任务需要激活（其他状态保持不变）
        if downstream_task.get("status") != "paused":
            continue
        container.repo.update_task_status(downstream_task_id, "running")
        # 记录事件，方便追溯"谁触发了谁"
        container.repo.save_event({
            "task_id": downstream_task_id,
            "stage": "dep_triggered",
            "level": "info",
            "message": f"上游任务 {upstream_task_id} 订单成功，自动激活下游任务",
            "payload": f'{{"upstream_task": "{upstream_task_id}", "order_id": "{order_id}", "triggered_by": "dep_chain"}}',
        })
```

**为什么仅激活 `paused` 状态**：`running` 状态跳过（已在运行），`stopped` 状态跳过（避免误启动用户主动停止的任务），`error`/`deleted` 状态跳过（不可激活）。

### 7.5 接管倒计时计算

```python
def _apply_takeover_deadline(o: dict, now: datetime) -> None:
    """为 takeover_pending 订单附加 deadline/remaining_sec 两个字段
    
    SQLite 读回的 confirmed_at 是 naive datetime，_utcnow() 须同步去时区，
    否则 deadline(naive) - now(aware) 会抛 TypeError
    （与 repo_chatbot.recall_message 同根因）
    """
    ts_dt = _parse_takeover_ts(o.get("confirmed_at"))
    if ts_dt is not None:
        deadline = ts_dt + timedelta(minutes=TAKEOVER_TIMEOUT_MIN)
        remaining = int((deadline - now).total_seconds())
        o["takeover_deadline"] = deadline.isoformat(timespec="seconds")
        o["takeover_remaining_sec"] = max(0, remaining)
```

## 9. 常见问题 FAQ

### Q1：OrderStatus 枚举有哪些取值？
**A**：`domain/order.py` 中 `OrderStatus` 枚举仅定义 4 个核心值：`pending_pay`（已拍下待支付）/ `paid`（已支付）/ `cancelled`（已取消）/ `failed`（失败）。v1.0 文档列出的 `submitting`/`paying`/`succeeded`/`takeover_pending` 在枚举中不存在，但 `takeover_pending` 和 `succeeded` 会作为 OrderRow.status 的扩展值存储到数据库。

### Q2：takeover_pending 和 succeeded 为什么不在枚举中？
**A**：`takeover_pending` 是接管流程的中间态，由 `POST /takeover` 接口设置，不允许手动修改；`succeeded` 是历史遗留值，与 `paid` 等价。两者都不希望被业务代码直接引用，故未放入枚举。

### Q3：接管超时是多久？多久扫描一次？超时后流转到什么状态？
**A**：超时 30 分钟（`TAKEOVER_TIMEOUT_MIN=30`），对应闲鱼待付款订单 30 分钟自动关闭的业务规则。调度器每 5 分钟扫描一次（`_DEFAULT_SCAN_INTERVAL_MIN=5`），平衡时效性与 DB 开销。超时后订单状态自动从 `takeover_pending` 流转到 `failed`（不是 `cancelled`，因为用户未完成支付是异常情况）。

### Q4：TakeoverModal 有哪几个阶段？
**A**：三阶段：`confirm`（确认接管，展示商品与价格）→ `progress`（支付进行中，倒计时 30 分钟）→ `done`（展示结果）。阶段严格顺序流转，不可跳过。`progress` 阶段无后端调用，前端独立倒计时。

### Q5：接管状态机白名单是什么？
**A**：仅 `pending_pay` 可被接管。拒绝 `takeover_pending → takeover_pending`（避免重置倒计时）、拒绝终态订单（`succeeded`/`failed`/`cancelled`）复活。用户若需重新接管已 cancel 的订单，需先通过 `PATCH /status` 回退到 `pending_pay`。

### Q6：F-16 依赖任务会激活哪些状态的任务？
**A**：仅激活 `paused` 状态的下游依赖任务。`running` 状态跳过（已在运行），`stopped` 状态跳过（避免误启动用户主动停止的任务），`error`/`deleted` 状态跳过（不可激活）。

### Q7：F-16 是怎么实现的？发布什么事件？
**A**：同步函数调用 `_trigger_dependent_tasks`（非 EventBus 消息机制）。通过 `item_id` 反查 `items.task_id`，查询 `task_deps` 表中所有依赖此任务的下游任务，直接修改 `task.status` 为 `running`，并写入 `stage='dep_triggered'` 的事件（不是 `type='task.started'`）。

### Q8：手动抢单和自动抢单有什么区别？
**A**：自动抢单由任务以 `auto` 模式触发，评估通过后自动调用 `container.buyer.buy()`；手动抢单由用户在卖家评估页点击"手动抢单"调用 `POST /api/orders/manual-takeover`，突破纯自动模式限制（如 with_browser=False 或评分≥80 但风险等级非 LOW 时）。两者都通过 `container.buyer.buy()` 实际下单。

### Q9：手动抢单的幂等检查是怎么做的？
**A**：通过 `find_order_by_task_item(task_id, item_id)` 查询同任务+同商品是否已存在订单。若存在则返回 `outcome=skipped_duplicate`，避免重复抢单。

### Q10：SSE 事件从哪个端点推送？
**A**：从 `/api/events/stream` 推送（不是 `/api/logs/stream`）。`/api/events/stream` 每 3 秒轮询 events 表，推送新增事件，事件类型为 `app_event`。前端通过 `addEventListener('app_event', ...)` 接收 `buy.succeeded`/`buy.failed` 等事件。

### Q11：接管倒计时是怎么计算的？
**A**：后端在 `list_orders` 中为 `takeover_pending` 状态订单附加 `takeover_deadline`（截止时间）和 `takeover_remaining_sec`（剩余秒数）两个字段。计算公式：`deadline = confirmed_at + 30min`，`remaining = max(0, (deadline - now).total_seconds())`。前端按 `takeover_remaining_sec` 实时倒计时。

### Q12：订单可以删除吗？
**A**：可以。`DELETE /api/orders/{order_id}` 物理删除订单记录。设计上保留此接口用于清理测试数据或误操作产生的脏数据，生产环境建议优先使用 `PATCH /status` 流转到 `cancelled`。

### Q13：v1.0 文档提到的"利润计算器"还在吗？
**A**：当前代码中**未找到**独立的利润计算器接口。`api_orders.py` 中无 `calc_profit` 相关函数。若前端有利润展示需求，应在任务配置或商品详情中查找相关字段。v1.0 文档描述的"0.6%/1.6% 费率、1.2 倍转售价、margin 字段"在当前代码中不存在。
