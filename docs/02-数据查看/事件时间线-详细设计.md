## 2. 功能概述

**一句话说明**：统一时间线展示订单与事件，支持 21 种事件类型过滤，从通知配置同步订阅规则，前端分页加载。

**核心价值**：
- 将订单状态变更与系统事件统一在一条时间线上展示，便于全链路追溯；
- 通过 21 种事件类型精细化分类，支持按需过滤；
- 从通知配置同步事件订阅规则，避免配置漂移；
- 客户端事件类型过滤 + 前端分页，平衡灵活性与性能。

## 3. 用户场景

### 场景一：全链路追溯
用户对某笔抢单订单有疑问，进入时间线页按 `task_id` 过滤，查看该任务下所有订单与事件，按时间顺序还原完整业务流程。

### 场景二：聚焦异常事件
用户在统计卡片看到"抢单失败"数量异常，点击"抢单失败"卡片快速过滤出所有 `buy.failed` 事件，逐条排查失败原因。

### 场景三：订阅规则同步
用户在通知配置页调整了事件订阅规则，回到时间线页发现默认事件类型集合已同步更新，无需手动重新勾选。

### 5.1 API 路由表

| 方法 | 路径           | 说明           | 请求参数                                                                                                       | 响应字段                                                                                                |
| ---- | -------------- | -------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| GET  | `/api/timeline`| 统一时间线     | `types` (默认 "orders,events", 逗号分隔), `task_id` (可选), `limit` (默认 200), `before_id` (可选，游标分页) | `items[]`, `has_more`, `next_cursor`                                                                    |

### 5.2 types 参数说明

`types` 参数控制时间线数据来源：
- `orders`：包含订单状态变更（pending/succeeded/failed 等）
- `events`：包含系统事件（21 种事件类型）
- 默认值 `"orders,events"` 表示同时拉取两类数据，按 `created_at` 统一排序

### 6.3 ENUM_TO_DOT 映射

数据库存储大写枚举名（如 `BUY_SUCCEEDED`），对外暴露为小写点分格式（如 `buy.succeeded`）。

| 数据库枚举         | 对外点分格式       |
| ------------------ | ------------------ |
| ITEM_DISCOVERED    | item.discovered    |
| EVAL_PASSED        | eval.passed        |
| BUY_SUCCEEDED      | buy.succeeded      |
| BUY_FAILED         | buy.failed         |
| WAF_BLOCKED        | waf.blocked        |
| LOGIN_EXPIRED      | login.expired      |
| TASK_STARTED       | task.started       |
| SYSTEM_ERROR       | system.error       |
| ...                | ...                |

映射规则：大写枚举名 → 转小写 → 下划线替换为点。

## 7. 业务逻辑

### 7.1 三段式判断避免配置漂移

```python
def resolve_event_subscription(
    user_filter: set[str] | None,
    notify_config: set[str] | None,
    default_types: set[str],
) -> set[str]:
    """
    三段式判断事件订阅规则，避免配置漂移：
    1. 用户当前页面显式筛选 → 优先使用
    2. 通知配置中的订阅规则 → 次优先
    3. 系统默认事件类型集合 → 兜底
    """
    if user_filter is not None:
        return user_filter
    if notify_config is not None:
        return notify_config
    return default_types
```

**设计意图**：当用户在通知配置页调整订阅规则后，时间线页默认事件类型集合自动同步，避免两处配置不一致。

### 7.2 时间线数据合并算法

```
1. 解析 types 参数，拆分为 orders / events 两类来源
2. 并行查询 orders 表与 events 表（按 task_id 过滤）
3. 各自按 created_at 倒序排列
4. 归并排序合并两条流，保持时间顺序
5. 截取 limit 条返回
6. 返回 next_cursor 供下次分页使用
```

### 7.3 前端分页策略

### 7.4 _to_utc_iso() 时间统一函数

```python
def _to_utc_iso(dt: datetime | str | None) -> str | None:
    """
    统一时间格式为带 UTC 标记的 ISO 字符串。
    处理三种输入：datetime 对象、ISO 字符串、None。
    确保时间线按时间排序时格式一致。
    """
    if dt is None:
        return None
    if isinstance(dt, str):
        dt = datetime.fromisoformat(dt.replace("Z", "+00:00"))
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(timezone.utc).isoformat()
```

### 7.5 事件类型过滤流程

```
1. 用户在 TimelineFilter 勾选事件类型
2. 客户端按 type 字段过滤当前已加载的 200 条数据
3. 翻页时若不足，触发后端拉取（带新 types 参数）
4. 统计卡片数字实时更新（基于已加载数据）
```

## 9. 常见问题 FAQ

### Q1：时间线展示哪些数据？
**A**：统一展示订单状态变更（orders）与系统事件（events）两类数据，按 `created_at` 倒序合并。默认 `types="orders,events"` 同时拉取两类，可通过参数单独指定。

### Q2：有多少种事件类型？
**A**：21 种事件类型，涵盖商品（item.*）、评估（eval.*）、抢单（buy.*）、通知（notify.*）、WAF（waf.*）、登录（login.*）、任务（task.*）、系统（system.*）与维护（maintenance.*）九大类。

### Q3：types 参数怎么用？
**A**：`types` 参数为逗号分隔字符串，控制数据来源。`orders` 拉取订单状态变更，`events` 拉取系统事件，默认 `"orders,events"` 同时拉取。可配合 `task_id` 过滤特定任务。

### Q4：为什么数据库存的是大写枚举，对外却是小写点分？
**A**：数据库存储大写枚举名（如 `BUY_SUCCEEDED`）便于索引与查询；对外通过 `ENUM_TO_DOT` 映射转为小写点分格式（如 `buy.succeeded`），更符合 API 规范与前端可读性。

### Q5：时间线是怎么分页的？
**A**：采用"后端游标分页 + 前端分页"双层策略。后端单次拉取 `limit=200` 条（使用 `before_id` 游标避免 offset 性能问题），前端按 `PAGE_SIZE=30` 分页展示，翻页不足时再触发后端拉取。

### Q6：统计卡片的数字是怎么算的？
**A**：统计卡片（订单事件/系统事件/抢单成功/抢单失败）基于当前已加载的数据实时统计。点击卡片可快速过滤对应事件类型（如点击"抢单失败"过滤 `buy.failed`）。

### Q7：事件订阅规则会和通知配置同步吗？
**A**：会。通过三段式判断：用户当前页面显式筛选优先；若无，则使用通知配置中的订阅规则；若都无，使用系统默认事件类型集合。这避免了时间线与通知配置两处配置漂移。

### Q8：时间格式为什么不统一？
**A**：数据库中时间字段可能为 datetime 对象、ISO 字符串或 None。通过 `_to_utc_iso()` 函数统一转为带 UTC 标记的 ISO 字符串，确保时间线排序时格式一致。

### Q9：可以用 task_id 过滤时间线吗？
**A**：可以。`/api/timeline` 接口接受可选的 `task_id` 参数，过滤特定任务下的订单与事件，便于全链路追溯单任务业务流程。

### Q10：maintenance.* 是什么事件？
**A**：`maintenance.*` 是通配事件类型，包含 `maintenance.started`、`maintenance.finished` 等子类型，记录系统维护操作（如数据库清理、向量库重建等）。
