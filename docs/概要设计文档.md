## 1. 项目概述

### 1.1 项目背景

闲鱼（Goofish）作为国内最大的二手交易平台之一，存在大量低价优质商品，但因信息更新快、竞争激烈，普通用户难以实时监控并抢到心仪商品。本项目旨在构建一套**自动化闲鱼捡漏与抢单系统**，通过浏览器自动化、反检测技术、智能评估和多渠道通知，帮助用户在秒级内发现并抢购目标商品。

### 1.2 项目目标

| 编号 | 目标 | 指标 |
|------|------|------|
| G1 | 自动发现低价商品 | 从上架到通知 < 60 秒 |
| G2 | 4 维卖家评估 | 职业卖家识别、信用资质、历史纠纷、价格异常 |
| G3 | 第一时间抢单 | 从评估通过到下单 < 10 秒 |
| G4 | 即时通知 | 多渠道推送延迟 < 30 秒 |

### 1.3 核心能力

- **多任务并发监控**：支持关键词、价格区间、地域、闲鱼筛选标签等多维度搜索
- **智能反检测**：stealth 脚本注入、Beta 分布延迟、贝塞尔曲线鼠标轨迹、WAF 熔断
- **4 维卖家评估**：加权评分 + 一票否决机制，识别职业卖家与高风险卖家
- **自动抢单**：并发安全、内存+DB 双层幂等、价格容差校验
- **多渠道通知**：Server酱、PushPlus、Bark、Telegram、企业微信、钉钉、Webhook
- **Web 控制台**：FastAPI + Jinja2 + htmx + Alpine.js，SSE 实时推送
- **AI 增强**：自然语言建任务、多模态成色评估、深度图片分析
- **多账号轮换**：账号池 + 代理池，降低单账号风控触发概率

### 1.4 用户角色

| 角色 | 描述 | 主要操作 |
|------|------|----------|
| 普通用户 | 单机部署使用者 | 创建任务、查看 Dashboard、接管订单、配置通知 |
| 系统管理员 | 运维人员 | 部署、配置、监控日志、处理异常 |

## 2. 系统架构

### 2.1 分层架构

系统采用**分层架构 + 依赖注入容器（DI）**模式，自上而下分为四层：

```
┌─────────────────────────────────────────────────────────┐
│  表示层（Presentation Layer）                            │
│  - CLI（Typer）                                          │
│  - Web 控制台（FastAPI + Jinja2 + htmx + Alpine.js）     │
│    · 旧版控制台：/  （htmx 服务端渲染，SSE 实时推送）     │
│    · SPA 可视化配置控制台：/app/  （React 18 + AntD 5）  │
│  - SSE 实时推送                                          │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  应用层（Application Layer）                             │
│  - TaskScheduler（多任务调度）                           │
│  - TaskWorker（单任务流水线）                            │
│  - AuthManager（认证管理）                               │
│  - NotificationEngine（业务通知规则引擎）                │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  核心域（Domain Layer）                                  │
│  - Collector（数据采集）                                 │
│  - Evaluator（卖家评估）                                 │
│  - Buyer（自动抢单）                                     │
│  - PriceStrategy（价格策略）                             │
│  - AntiDetect（反检测）                                  │
│  - NotifierHub（通知聚合）                               │
│  - EventBus（事件总线）                                  │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  基础设施层（Infrastructure Layer）                      │
│  - Repository（数据访问，Mixin 组合）                    │
│  - BrowserManager（Playwright 浏览器封装）               │
│  - DB Models（SQLAlchemy ORM）                           │
│  - Logger（loguru 日志）                                 │
│  - Secrets（keyring 加密存储）                           │
│  - YAML Config（配置管理）                               │
└─────────────────────────────────────────────────────────┘
```

### 2.1.1 双前端共存策略

系统同时维护两套前端，通过路由前缀隔离，互不干扰：

| 前端 | 路径 | 技术栈 | 定位 |
|------|------|--------|------|
| 旧版控制台 | `/*` | htmx + Alpine.js + Jinja2 | 实时监控、SSE 日志流、抢单记录浏览 |
| SPA 可视化控制台 | `/app/*` | React 18 + AntD 5 + Vite | 配置可视化编辑、拖拽交互、实时预览 |

**集成方式**：
- SPA 构建产物输出到 `src/xianyu_hunter/web/static/spa/`
- FastAPI 在 `create_app()` 中挂载 `/app/assets` 静态资源
- `/app/{full_path:path}` catch-all 路由服务 `index.html`，由 React Router 处理客户端路由
- `/app/` 加入认证白名单（页面可加载），API 调用仍需 Bearer Token
- SPA 通过 Axios `withCredentials: true` + Bearer Token 复用旧版认证体系

**构建命令**：
```bash
cd frontend
npm install
npm run build    # 输出到 ../src/xianyu_hunter/web/static/spa/
```

### 2.2 依赖注入容器（Composition Root）

系统通过 `container.py` 中的 `Container` dataclass 作为**组合根**，集中管理所有单例依赖的构造与注入：

```python
@dataclass
class Container:
    config: AppConfig
    repo: Repository
    event_bus: EventBus
    browser: Any | None              # BrowserManager（可选，with_browser=False 时为 None）
    antidetect: AntiDetect | None    # 反检测（可选）
    collector: Collector | None      # 采集器（可选）
    dedup: ItemDedup | None          # 去重器（可选）
    price_strategy: PriceStrategy | None  # 价格策略（可选）
    evaluator: Evaluator | None      # 评估器（可选）
    buyer: Buyer | None              # 抢单器（可选）
    notifier_hub: NotifierHub
    scheduler: TaskScheduler
    browser_lock: asyncio.Lock        # 浏览器互斥锁
```

**关键设计决策**：
- `with_browser=False` 模式：Web 进程跳过浏览器启动，节省内存（约 200MB/实例）
- `wire_notifier`：将 NotifierHub 订阅到 EventBus，实现事件驱动的通知推送
- 单例模式：所有依赖在容器构造时一次性创建，避免运行时重复初始化

### 2.3 数据流

```
用户创建任务
    ↓
TaskScheduler 按 cron 调度
    ↓
TaskWorker.run_once()
    ├──→ Collector.search()        搜索商品列表
    ├──→ Dedup.filter()            去重（task_links 表）
    ├──→ Collector.detail()        拉取商品详情
    ├──→ Collector.seller_profile() 拉取卖家画像
    ├──→ PriceStrategy.check()     价格策略过滤
    ├──→ Evaluator.evaluate()      4 维卖家评估
    ├──→ Buyer.buy()               自动抢单（mode=auto）
    │     └──→ 发布 BUY_SUCCEEDED 事件
    └──→ NotifierHub.fan_out()     多渠道通知
```

### 2.4 事件驱动架构

系统通过 `EventBus`（基于 `asyncio.Queue`）实现模块间解耦：

- **生产者**：Collector、Evaluator、Buyer、Scheduler 等业务模块
- **消费者**：NotifierHub（推送通知）、SSE Stream（推送到前端）
- **持久化**：所有事件写入 `events` 表，支持断线回放
- **异常隔离**：`_safe_call` 捕获所有订阅者异常，避免单点故障扩散

## 4. 核心功能设计

### 4.1 任务调度（F-15）

**设计目标**：支持多任务并发调度、Cron 表达式、任务依赖触发、连续失败自动暂停。

**核心类**：`TaskScheduler`

**关键设计**：
- `_run_lock`：全局并发锁，串行化 `run_once` 避免多窗口弹出
- `_workers_lock`：字典并发保护锁，保护 `_workers` 字典
- `_WorkerHandle`：单任务运行时句柄，持有 `TaskWorker` 实例和 asyncio.Task
- **F-16 依赖触发**：上游任务成功后自动激活下游 paused 任务
- **P1-7 Cron 模式**：按 `Task.cron` 表达式计算下次运行时间
- **连续失败保护**：连续失败 10 次自动暂停任务

**任务状态机**：

```
created → running ⇄ paused
              ↓
          stopped
              ↓
           deleted
```

**任务模式（TaskMode）**：

| 模式 | 行为 |
|------|------|
| `AUTO` | 全自动抢单 |
| `SEMI_AUTO` | 通知 + 自动抢单（需确认） |
| `CONFIRM` | 通知 + 人工确认 |
| `NOTIFY_ONLY` | 仅通知 |

### 4.2 数据采集（F-2）

**设计目标**：高效采集闲鱼商品搜索结果、详情、卖家画像。

**核心类**：`Collector`

**关键技术**：
- **route 拦截**：通过 Playwright 的 `page.route` 拦截 mtop API 响应，直接解析 JSON
- **DOM 回退**：API 拦截失败时回退到 DOM 选择器解析
- **会话失效检测**：检测 `RGV587_ERROR`，触发登录态恢复
- **窗口复用**：单个详情页 + 单个卖家页复用（窗口数从 6 降到 2）

**采集流程**：

```
search(keyword, filters)
    ├──→ page.route 拦截 mtop API
    ├──→ 解析 JSON 响应
    └──→ DOM 回退（API 失败时）

detail(item_id)
    └──→ 导航详情页 → 解析标题/价格/图片/描述

seller_profile(seller_id)
    └──→ 导航卖家主页 → 解析信用/在售/已售/评价
```

### 4.3 价格策略（F-3）

**设计目标**：支持多种价格过滤策略，精准识别低价商品。

**核心类**：`PriceStrategy`

**4 种策略**：

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| 硬性上限 | `price <= max_price` | 预算控制 |
| 硬性下限 | `price >= min_price` | 防低价陷阱 |
| 低于市场参考价 | `price < market_median * ratio` | 捡漏识别 |
| 同类低价 TopN | `cheaper_count < N` | 竞争力排序 |

**MarketContext**：市场参考上下文，包含中位数和所有价格列表，用于"低于市场参考价"策略。

### 4.4 卖家评估（F-4）

**设计目标**：4 维加权评分 + 一票否决，识别职业卖家与高风险卖家。

**核心类**：`Evaluator`

**4 维评分模型**：

| 维度 | 权重 | 评估内容 |
|------|------|----------|
| 职业卖家识别 | 30 分 | 在售数、30 天发帖数、主营品类集中度 |
| 信用与资质 | 30 分 | 信用分、注册天数、实名认证 |
| 历史纠纷 | 25 分 | 差评数、纠纷率 |
| 价格与竞价异常 | 15 分 | 低价异常、想要数异常 |

**一票否决条件**：
- 卖家在黑名单中
- 信用分 < 600

**防高分掩盖机制**：`final_score = min(dimension_scores) + 40`，避免单维度满分掩盖其他维度低分。

**风险等级**：

| 等级 | 分数范围 | 处理 |
|------|----------|------|
| low | ≥ 80 | 自动通过 |
| medium | ≥ 60 | 通过（可配置） |
| high | ≥ 40 | 需人工确认 |
| extreme | < 40 | 自动拒绝 |

### 4.5 自动抢单（F-5）

**设计目标**：秒级抢单，并发安全，幂等保证。

**核心类**：`Buyer`

**关键设计**：
- **并发安全**：`_lock` 串行锁，避免同一商品被多次购买
- **内存幂等**：`_task_item_set` 记录已购买的 (task_id, item_id)
- **DB 幂等**：订单表唯一约束
- **价格容差校验**：下单前校验实际价格与预期价格偏差

**抢单流程**：

```
buy(task_id, item_id)
    ├──→ 检查幂等（内存 + DB）
    ├──→ 导航商品详情页
    ├──→ 点击"立即购买"
    ├──→ 等待"提交订单"按钮
    ├──→ 提取订单号
    ├──→ 价格容差校验
    └──→ 发布 BUY_SUCCEEDED / BUY_FAILED 事件
```

**异常处理**：
- `ButtonNotFoundError`：按钮未找到
- `OutOfStockError`：库存不足
- `PriceMismatchError`：价格不匹配

### 4.6 反检测（F-7）

**设计目标**：模拟真人行为，规避闲鱼 WAF 风控。

**核心类**：`AntiDetect`、`WAFGuard`

**反检测技术栈**：

| 技术 | 实现 | 目的 |
|------|------|------|
| Stealth 脚本注入 | `STEALTH_SCRIPT` + `STEALTH_SCRIPT_V2` | 修复 Canvas/AudioContext/Font 指纹 |
| Token 自动刷新 | `M5TK_AUTO_REFRESH_SCRIPT` | 自动刷新 `_m_h5_tk` token |
| 人类延迟 | `human_delay_seconds`（Beta 分布） | 模拟真人操作间隔 |
| 鼠标轨迹 | `random_mouse_path`（贝塞尔曲线） | 模拟真人鼠标移动 |
| QPS 限流 | 滑动窗口 | 控制请求频率 |
| WAF 熔断 | `WAFGuard`（滑动窗口 + threshold） | 风控触发时自动暂停 |

**WAF 熔断器**：
- 滑动窗口统计错误数
- 超过阈值触发熔断
- 熔断期间暂停所有采集操作
- 定时尝试恢复

### 4.7 通知系统（F-8）

**设计目标**：多渠道聚合推送，支持免打扰时段。

**核心类**：`NotifierHub`

**通知渠道**：

| 渠道 | 实现 | 适用场景 |
|------|------|----------|
| Server酱 | HTTP POST | 个人微信推送 |
| PushPlus | HTTP POST | 微信公众号推送 |
| Bark | HTTP GET | iOS 推送 |
| Telegram | Bot API | 跨平台推送 |
| 企业微信 | Webhook | 企业群推送 |
| 钉钉 | Webhook | 企业群推送 |
| Webhook | HTTP POST | 自定义集成 |

**关键设计**：
- **fan-out 推送**：同一事件并发推送到所有渠道
- **P3-F-10 免打扰时段**：支持跨午夜、周末生效，critical 级别仍可达
- **DEFAULT_NOTIFY_EVENTS**：`EVAL_PASSED`、`BUY_SUCCEEDED`

**业务通知规则引擎**（`notification_engine.py`）：
- **OrderTimeoutRule**：订单超时告警（5min/15min/30min 三级）
- **AuthDownRule**：登录态失效告警
- **零侵入**：通过现有 API 端点"顺手"触发，不引入新定时器
- **幂等**：`dedup_key` 去重，升级阈值时换 key

| 统一登录 | `/api/auth/login` | 推荐，扫码登录 |
| 浏览器登录 | `/api/auth/browser-login/*` | Playwright 浏览器登录 |
| WebView 登录 | `/api/auth/webview-login/*` | 已废弃，保留兼容 |
| Cookie 注入 | `/api/auth/cookie` | 手动 Cookie 注入 |
| 浏览器导入 | `/api/auth/import-from-browser` | 从系统浏览器导入 |

**Cookie 存储双源设计**：
- **JSON 文件**（主数据源）：登录子进程写入，立即可见
- **browser-data SQLite**（从数据源）：Worker 读取用，异步同步

**扫码登录状态机**：
```
idle → starting → opening → qr_ready → success / timeout / error / cancelled
```

**Web 认证**：
- Bearer Token + Cookie 双重认证
- `hmac.compare_digest()` 防时序攻击
- 公开路径白名单（auth 相关、SSE 流、通知 API）

### 6.2 关键技术决策

#### 6.2.1 为什么选择 Playwright 而非 Selenium？

- **现代 API**：async/await 原生支持
- **CDP 模式**：可连接系统 Edge，指纹最真实
- **稳定性**：自动等待机制，减少 flaky 测试
- **生态**：Microsoft 维护，长期支持

#### 6.2.2 为什么选择 SQLite 而非 PostgreSQL？

- **单机部署**：项目定位为个人工具，无需分布式
- **零配置**：无需安装数据库服务
- **WAL 模式**：支持并发读写
- **性能**：单机场景下性能优于 PostgreSQL

#### 6.2.3 为什么选择 htmx + Alpine.js 而非 React/Vue？

- **零构建**：无需 Node.js 工具链
- **SSE 友好**：htmx 原生支持 SSE
- **轻量**：减少前端体积
- **服务端渲染**：Jinja2 模板直接渲染，SEO 友好

#### 6.2.3.1 为什么在 htmx 之外引入 React SPA？

旧版 htmx + Alpine.js 适合"实时监控 + 表单提交"场景，但在"可视化配置"场景存在短板：
- **复杂交互**：拖拽排序、双滑块、雷达图联动等在 Alpine.js 中实现成本高
- **实时预览**：配置改动需即时反映到图表/URL 预览，SPA 的客户端状态管理更顺手
- **组件生态**：AntD 的 Slider/TimePicker/DraggableList/Timeline 等开箱即用

**取舍方案**：双前端共存
- 旧版 htmx 控制台保持不变（实时监控、SSE 日志流、抢单记录）
- 新增 SPA 仅承担"可视化配置"职责，挂在 `/app/` 路径下
- 两套前端共享同一套后端 API + 认证体系，零侵入
- SPA 构建产物为静态文件，由 FastAPI 直接服务，无需额外 Node 运行时

#### 6.2.4 为什么选择 FastAPI 而非 Flask/Django？

- **异步原生**：与 Playwright/asyncio 生态契合
- **类型安全**：Pydantic 集成，自动校验
- **OpenAPI**：自动生成 API 文档
- **性能**：基于 Starlette，性能优异

## 7. 开发规范

### 7.1 代码规范

#### 7.1.1 Python 代码规范

- **PEP 8**：遵循 PEP 8 风格指南
- **类型提示**：所有公开函数必须添加类型提示
- **docstring**：模块/类/公开函数必须添加 docstring
- **注释原则**：注释解释"为什么"而非"做什么"
- **异步优先**：I/O 操作使用 async/await
- **f-string**：字符串格式化优先使用 f-string

#### 7.1.2 文件命名

- Python 文件：`snake_case.py`
- 模板文件：`snake_case.html`
- 配置文件：`snake_case.yaml`
- 测试文件：`test_*.py`

#### 7.1.3 目录规范

- `src/xianyu_hunter/`：主源码
- `tests/`：测试代码
- `docs/`：文档
- `config/`：配置文件
- `data/`：运行时数据（不纳入版本控制）
- `scripts/`：辅助脚本

### 7.2 安全规范

- **Token 比较**：使用 `hmac.compare_digest()` 防时序攻击
- **敏感字段**：不记录 token 长度等敏感信息，仅记录布尔匹配结果
- **Token 写入失败**：触发 `logging.warning()` 告警
- **401 响应**：返回 JSON `{"detail": "Unauthorized"}` 而非纯文本
- **前端请求**：必须包含 `credentials: 'include'`
- **htmx 凭证**：使用官方 `<meta>` 配置确保初始化时机可靠
- **认证白名单**：`/api/auth/cookie`、`/api/auth/me`、`/api/auth/import-from-browser`、`/import-from-browser/status`、`/api/events/stream`、`/api/notifications`、`/api/notifier/` 必须加入白名单

### 7.3 数据库规范

- **时区**：所有 datetime 列统一使用 UTC（`datetime.now(UTC)`）
- **索引**：`task_id`、`seller_id`、`first_seen`、`publish_time`、`created_at` 必须有索引
- **复合索引**：Dashboard 核心查询路径必须有复合索引
- **COUNT 查询**：`_overview()` 中的 COUNT 查询必须使用 CASE WHEN 聚合，减少 DB 调用
- **WAL 模式**：SQLite 必须启用 WAL 模式 + 外键约束
- **删除任务**：必须级联删除关联数据，避免垃圾数据

### 7.4 浏览器规范

- **WebView2 子进程**：使用 `CREATE_NEW_CONSOLE` 标志而非 `CREATE_NO_WINDOW`，防止 GUI 闪退
- **stdout/stderr**：不重定向到 DEVNULL，保留调试输出
- **private_mode**：`webview.start()` 必须设置 `private_mode=False`
- **storage_path**：指定唯一 `storage_path`（格式 `webview_data_{pid}_{timestamp}`），持久化 Cookie 并防止冲突
- **进程清理**：`_cleanup_orphan_processes` 清理残留 msedge 进程
- **锁文件清理**：`_cleanup_lock_files` 清理 SingletonLock 等锁文件
- **Web 进程模式**：必须使用 `with_browser=False` 模式节省内存

### 7.5 数据规范

- **闲鱼内容关联**：必须实时从官方网站获取，不使用数据库缓存
- **去重**：基于 `task_links` 表，避免重复采集

### 7.6 导入规范

- **模块级导入**：所有导入必须在模块级别，避免函数内重复导入
- **缺失导入**：`re`、`threading` 等必须添加，防止运行时 NameError

### 7.7 测试规范

- **测试框架**：pytest
- **测试覆盖**：核心业务模块必须有单元测试
- **测试命名**：`test_{函数名}_{场景}`
- **测试隔离**：每个测试用例独立数据库/临时目录

| 风险 | 影响 | 概率 | 应对措施 |

### 9.5 法律合规风险

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 违反闲鱼用户协议 | 账号封禁 | 高 | 反检测技术、合理频率、人工确认模式 |
| 自动化抢单合规性 | 法律风险 | 中 | 仅用于个人监控、不批量抢购、遵守平台规则 |
| 数据隐私 | 法律风险 | 低 | 仅存储必要数据、不分享、本地部署 |

### 9.6 应急预案

#### 9.6.1 WAF 触发应急预案

1. WAF 熔断器自动触发，暂停所有采集
2. 系统发送 `WAF_BLOCKED` 事件（critical 级别）
3. 通知中心推送告警到所有渠道
4. 等待冷却时间（默认 30 分钟）
5. 定时尝试恢复，成功后自动恢复采集

#### 9.6.2 登录态失效应急预案

1. 检测到 `RGV587_ERROR` 或 Cookie 失效
2. 系统发送 `AUTH_EXPIRED` 事件
3. 通知中心推送"登录态失效"告警
4. 暂停所有任务的抢单操作
5. 等待用户重新登录
6. 登录成功后自动恢复

#### 9.6.3 数据库故障应急预案

1. 检测到数据库写入失败
2. 触发 `logging.warning()` 告警
3. 重试机制（tenacity）自动重试
4. 重试失败后暂停相关任务
5. 通知用户手动干预
