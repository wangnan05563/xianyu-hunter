本版本相对 v1.0 的关键修订：

## 3. 功能概述

**一句话说明**：统一管理 7 个前端渠道（后端注册表含 ntfy 共 8 个）的开关与凭据，配置免打扰时段（支持跨午夜）+ 22 种事件订阅 + 拖拽排序，通过 `/api/notifier/test` 一键测试推送；同一事件触发后通过 `asyncio.gather` 并发 fan-out 到所有已启用的渠道。

**核心价值**：
- 7 个前端渠道（serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook）+ 后端 ntfy 共 8 个
- 渠道凭据以 **YAML 顶层字段明文存储**（keyring 作为可选 fallback，详见 §7.2）
- 免打扰时段支持跨午夜（如 23:00-07:00）、critical_only、weekend_only
- 22 种事件订阅 Checkbox.Group，severity 三色标签（info=blue/important=orange/critical=red）
- 拖拽排序（@dnd-kit）写入 `default_channels`，**仅决定渠道初始化顺序，不影响推送优先级**（推送是并发 fan-out）
- 分类排序（free/freemium/paid）+ 自定义排序双模式
- 通知模板 `templates.py` 的 `render(event)` 路由到具体模板
- **`_DB_ONLY_EVENTS`** 过滤 10 种仅用于时间线/DB 的事件，不通过 NotifierHub 推送

## 4. 用户场景

### 场景 1：配置 Server酱微信推送
用户希望通过微信接收通知。开启 `serverchan` 渠道开关，填入 SendKey（从 sct.ftqq.com 获取），点击"发送测试"验证。系统调用 `/api/notifier/test` 用前端传入的凭据创建 Notifier 实例发送测试消息。

### 场景 2：设置免打扰时段
用户不希望深夜被通知打扰。开启免打扰，设置 23:00-07:00（跨午夜），勾选"仅 critical 级别可推送"。系统在免打扰时段内仅推送 critical 级别事件（如 BUY_SUCCEEDED），其他事件落本地"待发摘要"。

### 场景 3：仅订阅关键事件
用户只关心评估通过和抢单成功。在事件订阅 Checkbox.Group 中仅勾选 `EVAL_PASSED` 和 `BUY_SUCCEEDED`（默认订阅），其他事件不推送。系统持久化 `subscribed_events` 到 YAML。

### 场景 4：多渠道同时推送
用户同时配置了 Server酱、PushPlus、Bark 三个渠道并全部开启。当 `BUY_SUCCEEDED` 事件触发时，`NotifierHub` 通过 `asyncio.gather` 并发向三个渠道同时推送，互不影响。某个渠道失败不影响其他渠道的推送。

### 5.2 关键交互
- **渠道开关**：每个 ChannelCard 标题处有 Switch，切换时同步到 `config.notifier.channels[key]`。
- **凭据编辑**：每个渠道的 fields（如 serverchan_send_key）在 ChannelCard 内部 Input，`onFieldChange` 回调直接 `update({[fieldKey]: value})` 写入 config 顶层。
- **发送测试**：点击"发送测试"按钮，前端收集该渠道所有凭据字段，POST `/api/notifier/test`，后端用前端传入凭据创建 Notifier 实例发送测试消息。
- **拖拽排序**：`@dnd-kit/core` + `@dnd-kit/sortable`，`handleDragEnd` 中 `arrayMove` 重排后写入 `default_channels`。
- **分类排序**：`groupedChannels` useMemo 按 pricing 分组，组内按 enabled + featureScore 排序。
- **免打扰时间轴**：`QuietHoursTimeline` 组件可视化 24 小时静默窗口。
- **事件订阅**：Checkbox.Group 22 项，每项带 severity 颜色 Tag（info=blue/important=orange/critical=red）。

## 6. 接口定义

### 6.1 通用配置接口（渠道开关、凭据、订阅事件）

| 方法 | 路径 | 用途 | 请求参数 | 响应字段 |
|------|------|------|----------|----------|
| GET | `/api/config` | 读取 `notifier` 配置 | 无 | `notifier: {default_channels, channels, quiet_hours, subscribed_events}` |
| POST | `/api/config/preview` | 预览改动 | `{payload: {notifier: {...}}}` | `{diffs, validation, new_yaml}` |
| POST | `/api/config/save` | 保存配置 | `{payload: {notifier: {...}}, dry_run: bool}` | `{ok, dry_run, saved_at, diffs, backup, restart_required}` |

### 6.2 通知专用接口（免打扰、测试推送）

| 方法 | 路径 | 用途 | 请求参数 | 响应字段 |
|------|------|------|----------|----------|
| GET | `/api/notifier/quiet-hours` | 读取免打扰配置 + 运行时状态 | 无 | `{config, is_quiet_now, next_end_iso, suppressed_count, suppressed_last_at}` |
| PUT | `/api/notifier/quiet-hours` | 更新免打扰配置（**热生效**） | `{enabled, start, end, critical_only, weekend_only}` | `{ok, config, is_quiet_now}` |
| POST | `/api/notifier/quiet-hours/reset` | 清空累计静默计数 | 无 | `{ok, suppressed_count: 0}` |
| POST | `/api/notifier/test` | 发送测试消息 | `{channel, credentials: {...}}` | `{ok, channel, attempts, response, error}` |

> **热更新边界**：仅 `PUT /api/notifier/quiet-hours` 会在写盘 + reload_config 后额外调用 `container.notifier_hub.set_quiet_hours()` 立即更新 hub 内的免打扰配置；其他配置（渠道开关、凭据、订阅事件）通过通用 `/api/config/save` 写盘 + reload_config，但 `NotifierHub` 实例需重启才会重建（详见 §10.3）。

## 8. 业务逻辑

### 8.1 渠道注册表 `NotifierRegistry`

后端 `backend/xianyu_hunter/modules/notifier/registry.py` 维护 8 个渠道的注册表，将渠道 key 映射到具体 Notifier 类。`NotifierRegistry.default()` 返回默认实例，`registry.create(channel, **credentials)` 用传入凭据创建 Notifier。

注册的 8 个渠道：serverchan / pushplus / bark / telegram / wecom / dingtalk / webhook / **ntfy**。

### 8.2 通知模板 `templates.py`

`templates.py` 的 `render(event)` 方法根据事件类型路由到具体模板。每种事件类型有对应的标题、内容、severity 等级。模板渲染后通过 Notifier 发送。

### 8.3 免打扰时段判定

位置：`backend/xianyu_hunter/modules/notifier/quiet_hours.py`

- `is_quiet_now(cfg)`：判断当前是否处于静默窗口
- `next_quiet_end(cfg)`：返回静默窗口下次结束的 ISO 时间
- **跨午夜支持**：start > end 时（如 23:00-07:00），静默窗口跨午夜
- **critical_only**：静默窗口内仅 critical 级别事件可推送，其他事件落本地"待发摘要"
- **weekend_only**：仅周末启用静默，工作日保持全量推送
- **suppressed_count**：进程内累计被静默的事件数，可通过 `/api/notifier/quiet-hours/reset` 清空

### 8.4 事件订阅过滤

#### 8.4.1 订阅事件过滤
- 事件触发时检查 `subscribed_events` 列表，未订阅的事件不推送
- severity 三级：`info`（蓝色）/ `important`（橙色）/ `critical`（红色）
- 默认订阅 `EVAL_PASSED`（评估通过）+ `BUY_SUCCEEDED`（抢单成功）
- 22 种事件覆盖任务生命周期、商品评估、购买、通知、安全、认证、系统、维护

#### 8.4.2 `_DB_ONLY_EVENTS` 过滤（v2.0 补充）

位置：`backend/xianyu_hunter/container.py` 第 59-73 行

```python
_DB_ONLY_EVENTS: frozenset[str] = frozenset({
    "TASK_STOPPED",
    "TASK_SEARCH_DONE",
    "ITEM_FOUND",
    "EVAL_SCORED",
    "WAF_BLOCKED",
    "AUTH_EXPIRED",
    "SYSTEM_ERROR",
    "MAINTENANCE_DATABASE",
    "MAINTENANCE_LOGS",
    "MAINTENANCE_CACHE",
})
```

**共 10 种事件**仅用于时间线 / DB 持久化，**不通过 NotifierHub 推送**。`_resolve_subscribed_events` 函数在解析用户配置的 `subscribed_events` 时会跳过这些事件类型，并打印 info 日志告知用户。

**为什么定义为模块级常量**：避免 `wire_notifier` 内联大集合推高认知复杂度，同时便于在测试中通过模块级 patch 替换。

### 8.5 测试推送逻辑

位置：`backend/xianyu_hunter/web/routes/api_notifier.py` `test_notify()` 方法

1. 校验 `channel` 是否在 `_CHANNEL_CREATION_PARAMS` 注册表中（共 8 个渠道映射）
2. 构造测试事件 `Event(type=EventType.TASK_STARTED, payload={"message": "测试消息"})`
3. 用前端传入的凭据 `registry.create(channel, **credentials)` 创建 Notifier
4. 调用 `notifier.send(test_event)` 发送
5. 返回 `{ok, channel, attempts, response, error}`

**为什么用前端传入凭据而非已保存的凭据**：用户可能正在修改配置，需要验证新值是否有效。

### 8.6 拖拽排序写入
- `handleDragEnd` 中 `arrayMove(channelOrder, oldIndex, newIndex)` 重排
- `update({notifier: {...config.notifier, default_channels: newOrder}})` 写入 config
- 保存时持久化到 YAML `notifier.default_channels`

> **重要澄清（v2.0 修正）**：`default_channels` 仅决定**渠道初始化顺序**，**不决定推送优先级**。推送时所有已启用渠道并发 fan-out（详见 §8.7）。v1.0 文档中"按顺序尝试推送，失败则降级到下一个渠道"的描述**是错误的**。

### 8.7 渠道分类排序
`groupedChannels` useMemo 按 `pricing`（free/freemium/paid）分组：
- **free**：完全免费（bark/telegram/wecom/dingtalk/webhook）
- **freemium**：免费有额度限制（serverchan/pushplus）
- **paid**：纯收费（当前无）

组内按 `enabled`（启用优先）+ `featureScore`（功能完整性 1-5）降序。

### 8.8 校验规则
- **HH:MM 格式**：`QuietHoursBody._check_hhmm` field_validator 校验 start/end 格式，非法值返回 422
- **时间越界**：00:00-23:59，越界返回 422
- **凭据必填**：测试推送前前端检查必填字段是否为空，空则提示"请先填写 xxx"

### 8.9 热更新机制（v2.0 修正）

| 配置项 | 热更新路径 | 立即生效范围 |
|--------|------------|--------------|
| `quiet_hours`（免打扰时段） | `PUT /api/notifier/quiet-hours` → 写盘 + `reload_config()` + `container.notifier_hub.set_quiet_hours()` | **立即生效**（hub 内 quiet_hours 配置实时更新） |
| 渠道开关、凭据、订阅事件 | `POST /api/config/save` → 写盘 + `reload_config()` | **写盘与单例重载生效**，但 `NotifierHub` 实例需重启才会重建（详见 §10.3） |

**为什么仅 quiet_hours 走专用端点热生效**：免打扰时段是高频调整项，且 `NotifierHub.set_quiet_hours()` 提供了无需重建 hub 的轻量更新接口；其他配置项变更需要重建 `NotifierHub` 实例（重新构造 Notifier 列表、重新订阅事件），开销较大，且通常只在初始化时执行一次。

### 8.10 渠道能力对比

| 渠道 | 定价 | Markdown 支持 | 多端覆盖 | 凭据复杂度 | 推荐场景 |
|------|------|---------------|----------|------------|----------|
| `serverchan` | freemium | 否 | 微信 | 低（1 个 SendKey） | 微信用户首选 |
| `pushplus` | freemium | 否 | 微信 | 低（1 个 Token） | 一对多推送 |
| `bark` | free | 否 | iOS | 中（Server+Key） | iPhone 用户自建 |
| `telegram` | free | 是 | 全平台 | 中（Bot Token+Chat ID） | 跨平台 + Markdown |
| `wecom` | free | 是 | 微信 | 低（1 个 Webhook） | 企业团队协作 |
| `dingtalk` | free | 是 | 钉钉 | 中（Webhook+Secret） | 钉钉团队 |
| `webhook` | free | 自定义 | 自定义 | 低（1 个 URL，可选 Token） | 接入第三方系统 |

**featureScore 评分维度**（1-5 分）：消息格式丰富度 + 平台覆盖 + 安全特性 + 可配置性。

### 8.11 通知推送的并发 fan-out 策略（v2.0 修正）

位置：`backend/xianyu_hunter/modules/notifier/hub.py` `NotifierHub.send()` 方法

**实际实现**：使用 `asyncio.gather` 并发 fan-out 到所有已配置渠道，**没有降级逻辑**：

```python
# hub.py 中的关键代码（简化示意）
results = await asyncio.gather(
    *(n.send(event) for n in self._notifiers),
    return_exceptions=False,
)
```

```
事件触发
  ↓
NotifierHub.send(event)
  ↓
检查免打扰时段 → 若静默且非 critical，落"待发摘要"，返回
  ↓
asyncio.gather 并发 fan-out 到所有已启用渠道
  ↓
┌──────────┬──────────┬──────────┐
│ 渠道 A    │ 渠道 B    │ 渠道 C    │  （同时推送，互不依赖）
└──────────┴──────────┴──────────┘
  ↓
所有渠道推送完成（成功/失败各自记录）
```

**为什么用并发而非顺序降级**：
1. **可靠性**：单一渠道故障不应阻断通知送达；并发推送保证多渠道冗余
2. **实时性**：用户配置多渠道的目的是"同时收到"而非"依次尝试"
3. **避免噪音是靠订阅与免打扰，不靠降级**：通过 `subscribed_events` 与 `quiet_hours` 控制通知频率，而不是靠"成功即停止"的降级

> **重要修正**：v1.0 §7.11 描述的"按 `default_channels` 顺序尝试，成功即停止，失败降级到下一个渠道"是**错误的**。`default_channels` 仅决定渠道在 `NotifierHub` 初始化时的注册顺序，推送时所有已启用渠道同时并发。

## 10. 已知 Bug 与限制（v2.0 新增）

> 本节列出代码调研中发现的潜在问题，**未修复**，仅供排错参考与边界说明。

### 10.1 Bug：`_check_notifier` 访问不存在的 `hub.channels` 属性

**位置**：`backend/xianyu_hunter/web/app.py` 第 95-102 行

```python
def _check_notifier(container: Any) -> str:
    try:
        hub = container.notifier_hub
        channels = getattr(hub, "channels", []) or []  # ← Bug: hub 暴露的是 notifiers 不是 channels
        return "configured" if channels else "not_configured"
    except Exception:
        return "unknown"
```

**根因**：`NotifierHub` 实际暴露的属性是 `notifiers`（返回 Notifier 实例列表），而非 `channels`。`getattr(hub, "channels", [])` 永远返回默认值 `[]`，导致 `_check_notifier` 永远返回 `"not_configured"`。

**实际表现**：`/healthz` 端点中的 notifier 检查项始终显示未配置（即使已配置多个渠道）。

**正确修复方向**：将 `getattr(hub, "channels", [])` 改为 `getattr(hub, "notifiers", [])`。

### 10.2 Bug：`_SHARE_REDACT_PATHS` 脱敏遗漏 ntfy 与 webhook_token

**位置**：`backend/xianyu_hunter/web/routes/api_config.py` 第 300-313 行

```python
_SHARE_REDACT_PATHS = [
    ("notifier", "channels"),
    ("serverchan_send_key",),
    ("pushplus_token",),
    ("bark_server",),
    ("bark_key",),
    ("telegram_bot_token",),
    ("telegram_chat_id",),
    ("wecom_webhook",),
    ("dingtalk_webhook",),
    ("dingtalk_secret",),
    ("webhook_url",),
    # ← 遗漏：ntfy_server / ntfy_topic / ntfy_token / webhook_token
    ("browser", "user_data_dir"),
]
```

**根因**：分享配置时（`GET /api/config/share`）会按此列表脱敏，但 ntfy 凭据与 webhook_token 未列入。当前因为 `AppConfig` 顶层未声明 ntfy 字段，泄露风险仅限"用户手动在 YAML 中添加 ntfy 字段"的场景；webhook_token 同理。

**实际表现**：若用户手动在 `config.yaml` 顶层添加 `ntfy_token: "****"` 或 `webhook_token: "****"`，分享配置时这些字段不会被脱敏，存在泄露风险。

**正确修复方向**：在 `_SHARE_REDACT_PATHS` 中追加 `("ntfy_server",)`、`("ntfy_topic",)`、`("ntfy_token",)`、`("webhook_token",)`。

### 10.3 限制：`NotifierHub` 实例需重启才重建

**位置**：`backend/xianyu_hunter/container.py` 第 211-250 行 `wire_notifier` 方法

**现象**：通用 `/api/config/save` 写盘后调用 `reload_config()` 重置 `_config` 单例，但 `container.notifier_hub` 实例**不会自动重建**。`NotifierHub` 在 `wire_notifier()` 中构造，而 `wire_notifier()` 通常仅在启动时调用一次。

**实际表现**：用户在前端修改渠道开关或凭据后保存，配置文件已更新、内存单例已重置，但**正在运行的 `NotifierHub` 实例仍使用旧配置**，需要重启服务才能让新渠道配置生效。

**为什么 quiet_hours 不受此限制**：`PUT /api/notifier/quiet-hours` 端点在写盘 + reload_config 后，额外调用 `container.notifier_hub.set_quiet_hours()` 主动更新 hub 内的免打扰配置，因此免打扰可热生效。

**临时方案**：修改渠道开关或凭据后需要重启服务。未来若需热更新，可在 `api_config.save` 中检测 `notifier` 段变更后触发 `container.wire_notifier()` 重建 hub。

### 10.4 限制：`_build_yaml_credentials` 未构建 ntfy 凭据

**位置**：`backend/xianyu_hunter/container.py` 第 76-109 行

**现象**：`_build_yaml_credentials` 函数从 `AppConfig` 顶层字段构建 7 个渠道的凭据字典（serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook），**未包含 ntfy**。

**根因**：`AppConfig` 顶层未声明 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段，因此 `_build_yaml_credentials` 无从读取。

**实际表现**：即使用户在 YAML 中手动添加 ntfy 凭据并启用 ntfy 渠道，`NotifierHub` 初始化时也拿不到 ntfy 凭据，ntfy 推送会失败。

**正确修复方向**：
1. 在 `AppConfig` 中追加 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段（与 `secrets.py` 中的 `KEY_NTFY_*` 常量对齐）
2. 在 `_build_yaml_credentials` 中追加 ntfy 凭据构建分支
3. 在 `_SHARE_REDACT_PATHS` 中追加 ntfy 字段脱敏
4. 在前端 `defaultChannels` 中追加 ntfy 渠道定义

### 10.5 限制：前端 ntfy 渠道缺失

**位置**：`frontend/src/pages/Config/NotifierChannels/constants.ts` 第 31-121 行

**现象**：前端 `defaultChannels` 数组定义 7 个渠道，**未包含 ntfy**。用户无法通过前端界面配置 ntfy 渠道，只能通过直接编辑 YAML 启用。

### 10.6 限制：前端 webhook_token 字段缺失

**位置**：`frontend/src/pages/Config/NotifierChannels/constants.ts` webhook 渠道定义

**现象**：前端 webhook 渠道的 fields 仅有 `webhook_url`，**缺 `webhook_token`**。用户无法通过前端界面配置 webhook 鉴权 token。

## 11. 常见问题 FAQ

### Q1：8 个渠道都有哪些？前端为什么只显示 7 个？
**A**：后端注册表支持 8 个渠道：serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook/ntfy。前端 `defaultChannels` 仅定义 7 个（未含 ntfy），ntfy 只能通过直接编辑 YAML 启用，且当前因 `_build_yaml_credentials` 未构建 ntfy 凭据（详见 §10.4），ntfy 推送会失败。每个渠道凭据字段不同，详见数据结构 §7.2。

### Q2：免打扰时段支持跨午夜吗？
**A**：支持。当 start > end 时（如 23:00-07:00），系统识别为跨午夜静默窗口。`QuietHoursTimeline` 组件会可视化 24 小时静默区间。`is_quiet_now(cfg)` 自动处理跨午夜判定。

### Q3：critical_only 是什么意思？
**A**：免打扰时段内，若 `critical_only=true`，仅 critical 级别事件（如 BUY_SUCCEEDED/WAF_TRIGGERED/SYSTEM_ERROR）可推送，其他事件（如 TASK_STARTED/EVAL_SCORED）落本地"待发摘要"。`suppressed_count` 统计被静默的事件数。

### Q4：测试推送使用哪个凭据？
**A**：使用前端当前填写的凭据（不是 YAML 中已保存的值）。这样用户修改配置时可以验证新值是否有效。后端 `registry.create(channel, **credentials)` 用传入凭据创建临时 Notifier 实例。

### Q5：拖拽排序有什么用？
**A**：`default_channels` 仅决定渠道在 `NotifierHub` 初始化时的注册顺序，**不决定推送优先级**。推送时所有已启用渠道通过 `asyncio.gather` 并发 fan-out，互不依赖。详见 §8.11。

### Q6：22 种事件都有哪些？severity 怎么区分？
**A**：覆盖任务生命周期（TASK_STARTED/STOPPED/PAUSED/ERROR/SEARCH_DONE）、商品评估（ITEM_DISCOVERED/EVAL_PASSED/REJECTED/SCORED）、购买（BUY_REQUESTED/SUCCEEDED/FAILED）、通知（NOTIFY_SENT）、安全（WAF_TRIGGERED/BLOCKED）、认证（LOGIN_EXPIRED/AUTH_EXPIRED）、系统（SYSTEM_ERROR）、维护（MAINTENANCE_*）。severity 三级：info（蓝色）/ important（橙色）/ critical（红色）。

### Q7：默认订阅哪些事件？
**A**：默认订阅 `EVAL_PASSED`（评估通过）和 `BUY_SUCCEEDED`（抢单成功）。这两个是用户最关心的关键事件。其他事件需手动勾选订阅。订阅列表持久化到 YAML `notifier.subscribed_events`。

### Q8：渠道凭据存在哪里？安全吗？
**A**：渠道凭据以 **YAML 顶层字段明文存储**（如 `serverchan_send_key: "SCT****"`）。`secrets.py` 中定义了 keyring 加密存储的辅助函数（`set_secret` / `get_secret`），但 `NotifierHub` 初始化时优先从 `_build_yaml_credentials` 读取 YAML 明文作为 fallback，保证"配置已保存但 keyring 中无值"时通知仍能发送。分享配置时（`/api/config/share`）凭据字段会被替换为 `***`，详见 `_SHARE_REDACT_PATHS`（v2.0 已标注 ntfy / webhook_token 脱敏遗漏，详见 §10.2）。

### Q9：weekend_only 是什么意思？
**A**：`weekend_only=true` 表示仅周末（周六/日）启用免打扰，工作日保持全量推送。适合"工作日全天接收通知，周末不被打扰"的场景。与 `enabled` 是 AND 关系——必须 `enabled=true` 且 `weekend_only` 条件满足才静默。

### Q10：保存后免打扰立即生效吗？
**A**：**免打扰时段立即生效**——通过专用接口 `PUT /api/notifier/quiet-hours` 更新，写盘 + `reload_config()` + `container.notifier_hub.set_quiet_hours()` 三步联动，立即生效。其他配置（渠道开关、订阅事件、凭据）通过通用 save 接口写盘 + reload_config，但 `NotifierHub` 实例需重启才会重建（详见 §10.3）。

### Q11：`_DB_ONLY_EVENTS` 是什么？（v2.0 新增）
**A**：`_DB_ONLY_EVENTS` 是 `container.py` 中定义的 10 种事件类型集合（TASK_STOPPED/TASK_SEARCH_DONE/ITEM_FOUND/EVAL_SCORED/WAF_BLOCKED/AUTH_EXPIRED/SYSTEM_ERROR/MAINTENANCE_DATABASE/MAINTENANCE_LOGS/MAINTENANCE_CACHE）。这些事件**仅用于时间线 / DB 持久化**，不通过 NotifierHub 推送。即使用户在 `subscribed_events` 中配置了这些事件，`_resolve_subscribed_events` 也会跳过并打印 info 日志。详见 §8.4.2。

### Q12：为什么我配置了 ntfy 渠道但不工作？（v2.0 新增）
**A**：ntfy 渠道当前存在多个未实现的环节（详见 §10.4-§10.6）：
1. 前端 `defaultChannels` 未定义 ntfy，无法通过界面配置
2. `AppConfig` 顶层未声明 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段
3. `_build_yaml_credentials` 未构建 ntfy 凭据字典
4. 即使手动在 YAML 中添加 ntfy 字段并启用，`NotifierHub` 初始化时也拿不到凭据

ntfy 渠道目前在后端注册表中存在但前端到后端的完整链路未打通，建议暂不使用。

### Q13：为什么修改了渠道开关后推送还是用旧配置？（v2.0 新增）
**A**：这是 `NotifierHub` 实例未热重建的限制（详见 §10.3）。通用 `/api/config/save` 写盘 + reload_config 后，`_config` 单例已重置，但 `container.notifier_hub` 实例仍使用旧配置。需要重启服务才能让新渠道配置生效。免打扰时段不受此限制（有专用热更新端点）。
