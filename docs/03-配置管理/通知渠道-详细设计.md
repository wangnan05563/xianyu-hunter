## 2. 功能概述

**一句话说明**：统一管理 7 个前端渠道（后端注册表含 ntfy 共 8 个）的开关与凭据，配置免打扰时段（支持跨午夜）+ 22 种事件订阅 + 拖拽排序，通过 `/api/notifier/test` 一键测试推送。

**核心价值**：
- 7 个前端渠道（serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook）+ 后端 ntfy 共 8 个
- 渠道凭据通过 keyring 加密存储，不写入 YAML 明文
- 免打扰时段支持跨午夜（如 23:00-07:00）、critical_only、weekend_only
- 22 种事件订阅 Checkbox.Group，severity 三色标签（info=blue/important=orange/critical=red）
- 拖拽排序（@dnd-kit）写入 `default_channels`，按顺序尝试推送
- 分类排序（free/freemium/paid）+ 自定义排序双模式
- 通知模板 `templates.py` 的 `render(event)` 路由到具体模板

## 3. 用户场景

### 场景 1：配置 Server酱微信推送
用户希望通过微信接收通知。开启 `serverchan` 渠道开关，填入 SendKey（从 sct.ftqq.com 获取），点击"发送测试"验证。系统调用 `/api/notifier/test` 用前端传入的凭据创建 Notifier 实例发送测试消息。

### 场景 2：设置免打扰时段
用户不希望深夜被通知打扰。开启免打扰，设置 23:00-07:00（跨午夜），勾选"仅 critical 级别可推送"。系统在免打扰时段内仅推送 critical 级别事件（如 BUY_SUCCEEDED），其他事件落本地"待发摘要"。

### 场景 3：仅订阅关键事件
用户只关心评估通过和抢单成功。在事件订阅 Checkbox.Group 中仅勾选 `EVAL_PASSED` 和 `BUY_SUCCEEDED`（默认订阅），其他事件不推送。系统持久化 `subscribed_events` 到 YAML。

- **发送测试**：点击"发送测试"按钮，前端收集该渠道所有凭据字段，POST `/api/notifier/test`，后端用前端传入凭据创建 Notifier 实例发送测试消息。
- **拖拽排序**：`@dnd-kit/core` + `@dnd-kit/sortable`，`handleDragEnd` 中 `arrayMove` 重排后写入 `default_channels`。
- **分类排序**：`groupedChannels` useMemo 按 pricing 分组，组内按 enabled + featureScore 排序。
- **免打扰时间轴**：`QuietHoursTimeline` 组件可视化 24 小时静默窗口。
- **事件订阅**：Checkbox.Group 22 项，每项带 severity 颜色 Tag（info=blue/important=orange/critical=red）。

## 7. 业务逻辑

### 7.1 渠道注册表 `NotifierRegistry`

后端 `src/xianyu_hunter/modules/notifier/registry.py` 维护 8 个渠道的注册表，将渠道 key 映射到具体 Notifier 类。`NotifierRegistry.default()` 返回默认实例，`registry.create(channel, **credentials)` 用传入凭据创建 Notifier。

### 7.2 通知模板 `templates.py`

`templates.py` 的 `render(event)` 方法根据事件类型路由到具体模板。每种事件类型有对应的标题、内容、severity 等级。模板渲染后通过 Notifier 发送。

### 7.3 免打扰时段判定

位置：`src/xianyu_hunter/modules/notifier/quiet_hours.py`

- `is_quiet_now(cfg)`：判断当前是否处于静默窗口
- `next_quiet_end(cfg)`：返回静默窗口下次结束的 ISO 时间
- **跨午夜支持**：start > end 时（如 23:00-07:00），静默窗口跨午夜
- **critical_only**：静默窗口内仅 critical 级别事件可推送，其他事件落本地"待发摘要"
- **weekend_only**：仅周末启用静默，工作日保持全量推送
- **suppressed_count**：进程内累计被静默的事件数，可通过 `/api/notifier/quiet-hours/reset` 清空

### 7.4 事件订阅过滤
- 事件触发时检查 `subscribed_events` 列表，未订阅的事件不推送
- severity 三级：`info`（蓝色）/ `important`（橙色）/ `critical`（红色）
- 默认订阅 `EVAL_PASSED`（评估通过）+ `BUY_SUCCEEDED`（抢单成功）
- 22 种事件覆盖任务生命周期、商品评估、购买、通知、安全、认证、系统、维护

### 7.5 测试推送逻辑

位置：`src/xianyu_hunter/web/routes/api_notifier.py` `test_notify()` 方法（第 145-187 行）

1. 校验 `channel` 是否在 `_CHANNEL_CREATION_PARAMS` 注册表中
2. 构造测试事件 `Event(type=EventType.TASK_STARTED, payload={"message": "测试消息"})`
3. 用前端传入的凭据 `registry.create(channel, **credentials)` 创建 Notifier
4. 调用 `notifier.send(test_event)` 发送
5. 返回 `{ok, channel, attempts, response, error}`

**为什么用前端传入凭据而非 keyring**：用户可能正在修改配置，需要验证新值是否有效。

### 7.6 拖拽排序写入
- `handleDragEnd` 中 `arrayMove(channelOrder, oldIndex, newIndex)` 重排
- `update({notifier: {...config.notifier, default_channels: newOrder}})` 写入 config
- 保存时持久化到 YAML `notifier.default_channels`
- 推送时按 `default_channels` 顺序尝试，失败则降级到下一个渠道

### 7.7 渠道分类排序
`groupedChannels` useMemo 按 `pricing`（free/freemium/paid）分组：
- **free**：完全免费（bark/telegram/wecom/dingtalk/webhook）
- **freemium**：免费有额度限制（serverchan/pushplus）
- **paid**：纯收费（当前无）

组内按 `enabled`（启用优先）+ `featureScore`（功能完整性 1-5）降序。

### 7.8 校验规则
- **HH:MM 格式**：`QuietHoursBody._check_hhmm` field_validator 校验 start/end 格式，非法值返回 422
- **时间越界**：00:00-23:59，越界返回 422
- **凭据必填**：测试推送前前端检查必填字段是否为空，空则提示"请先填写 xxx"

### 7.9 热更新机制
- 渠道开关、凭据、订阅事件：通过通用 `/api/config/save` 保存，写盘 + `reload_config()`
- 免打扰时段：通过 `PUT /api/notifier/quiet-hours` 专用接口，写盘 + `reload_config()` + `container.notifier_hub.set_quiet_hours()` 立即生效
- 通知 Hub 实时读取最新配置，无需重启服务

### 7.10 渠道能力对比

| 渠道 | 定价 | Markdown 支持 | 多端覆盖 | 凭据复杂度 | 推荐场景 |
|------|------|---------------|----------|------------|----------|
| `serverchan` | freemium | 否 | 微信 | 低（1 个 SendKey） | 微信用户首选 |
| `pushplus` | freemium | 否 | 微信 | 低（1 个 Token） | 一对多推送 |
| `bark` | free | 否 | iOS | 中（Server+Key） | iPhone 用户自建 |
| `telegram` | free | 是 | 全平台 | 中（Bot Token+Chat ID） | 跨平台 + Markdown |
| `wecom` | free | 是 | 微信 | 低（1 个 Webhook） | 企业团队协作 |
| `dingtalk` | free | 是 | 钉钉 | 中（Webhook+Secret） | 钉钉团队 |
| `webhook` | free | 自定义 | 自定义 | 低（1 个 URL） | 接入第三方系统 |
| `ntfy` | free | 是 | 全平台 | 中（Server+Topic+Token） | 自建推送服务 |

**featureScore 评分维度**（1-5 分）：消息格式丰富度 + 平台覆盖 + 安全特性 + 可配置性。

### 7.11 通知推送的容错策略

`default_channels` 顺序决定推送优先级，系统按顺序尝试推送：

```
按 default_channels 顺序遍历
  ↓
[渠道开关开启 + 凭据完整]
  ↓ [是] 尝试推送
  ↓      ├─ [成功] → 标记 sent，结束
  ↓      └─ [失败] → 记录错误，尝试下一个渠道
  ↓ [否] 跳过该渠道
  ↓
所有渠道都失败 → 落本地"待发摘要" + 记录 error 日志
```

**为什么不全渠道并发推送**：避免重复通知打扰用户。按优先级顺序尝试，成功即停止，既保证可达性又避免噪音。

## 9. 常见问题 FAQ

### Q1：8 个渠道都有哪些？前端为什么只显示 7 个？
**A**：后端注册表支持 8 个渠道：serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook/ntfy。前端 `defaultChannels` 仅定义 7 个（未含 ntfy），ntfy 可通过直接编辑 YAML 启用。每个渠道凭据字段不同，详见数据结构 6.2。

### Q2：免打扰时段支持跨午夜吗？
**A**：支持。当 start > end 时（如 23:00-07:00），系统识别为跨午夜静默窗口。`QuietHoursTimeline` 组件会可视化 24 小时静默区间。`is_quiet_now(cfg)` 自动处理跨午夜判定。

### Q3：critical_only 是什么意思？
**A**：免打扰时段内，若 `critical_only=true`，仅 critical 级别事件（如 BUY_SUCCEEDED/WAF_TRIGGERED/SYSTEM_ERROR）可推送，其他事件（如 TASK_STARTED/EVAL_SCORED）落本地"待发摘要"。`suppressed_count` 统计被静默的事件数。

### Q4：测试推送使用哪个凭据？
**A**：使用前端当前填写的凭据（不是 keyring 中的值）。这样用户修改配置时可以验证新值是否有效。后端 `registry.create(channel, **credentials)` 用传入凭据创建临时 Notifier 实例。

### Q5：拖拽排序有什么用？
**A**：`default_channels` 顺序决定推送优先级。系统按顺序尝试推送，失败则降级到下一个渠道。例如 `["serverchan", "pushplus"]` 表示先尝试 Server酱，失败再尝试 PushPlus。

### Q6：22 种事件都有哪些？severity 怎么区分？
**A**：覆盖任务生命周期（TASK_STARTED/STOPPED/PAUSED/ERROR/SEARCH_DONE）、商品评估（ITEM_DISCOVERED/EVAL_PASSED/REJECTED/SCORED）、购买（BUY_REQUESTED/SUCCEEDED/FAILED）、通知（NOTIFY_SENT）、安全（WAF_TRIGGERED/BLOCKED）、认证（LOGIN_EXPIRED/AUTH_EXPIRED）、系统（SYSTEM_ERROR）、维护（MAINTENANCE_*）。severity 三级：info（蓝色）/ important（橙色）/ critical（红色）。

### Q7：默认订阅哪些事件？
**A**：默认订阅 `EVAL_PASSED`（评估通过）和 `BUY_SUCCEEDED`（抢单成功）。这两个是用户最关心的关键事件。其他事件需手动勾选订阅。订阅列表持久化到 YAML `notifier.subscribed_events`。

### Q8：渠道凭据存在哪里？安全吗？
**A**：渠道凭据通过 keyring 加密存储，不写入 YAML 明文。YAML 中仅存渠道开关（bool）。分享配置时（`/api/config/share`）凭据字段会被替换为 `***`，详见 `_SHARE_REDACT_PATHS`。

### Q9：weekend_only 是什么意思？
**A**：`weekend_only=true` 表示仅周末（周六/日）启用免打扰，工作日保持全量推送。适合"工作日全天接收通知，周末不被打扰"的场景。与 `enabled` 是 AND 关系——必须 `enabled=true` 且 `weekend_only` 条件满足才静默。

### Q10：保存后免打扰立即生效吗？
**A**：是。免打扰通过专用接口 `PUT /api/notifier/quiet-hours` 更新，写盘 + `reload_config()` + `container.notifier_hub.set_quiet_hours()` 三步联动，立即生效。其他配置（渠道开关、订阅事件）通过通用 save 接口，写盘 + reload 后下一轮通知即用新配置。
