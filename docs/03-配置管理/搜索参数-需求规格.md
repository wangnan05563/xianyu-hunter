## 1. 引言

### 1.1 编写目的

本需求规格说明书定义「配置管理 → 搜索参数」二级菜单的完整需求规格，作为前端/后端开发、测试与验收的唯一依据。

**目标读者**：
- 后端开发工程师：依据 §3-§6、§8 进行模块实现与扩展
- 前端开发工程师：依据 §4、§7 进行页面开发
- 测试工程师：依据 §7 编写测试用例与执行验收
- 项目经理：依据 §2、§7 进行范围与里程碑管理
- 智能客服 KB 训练：本文档与 [搜索参数-详细设计.md](搜索参数-详细设计.md) 共同作为 KB 检索素材

### 1.2 项目背景

闲鱼猎人（XianyuHunter）是一个闲鱼自动捡漏与抢单工具，已具备任务管理、商品采集、AI 评估、自动下单、多渠道通知等完整能力（详见 [requirements.md](../requirements.md)、[design.md](../design.md) 与 [概要设计文档.md](../概要设计文档.md)）。

随着系统运行规模扩大，**搜索参数相关的核心能力目前分散在多个配置块**（`antidetect` / `search` / `task_scheduler`），且涉及反检测、频率伪装、Cookie 自愈、MTOP 拦截、熔断机制等多层防护机制，缺乏统一的配置入口，导致以下痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| 反检测与搜索参数混用 | 用户分不清 `antidetect` 与 `search` 的边界 | 误改全局 QPS 影响所有 HTTP 请求 |
| 等效 QPS 不直观 | 用户改延迟时不知道对应的请求频率 | 容易触发风控 |
| 熔断机制语义模糊 | v1.0 文档误描述为"滑动窗口"，实际为连续失败计数器 | 用户误以为时间窗口可清零失败计数 |
| 任务调度默认值缺失 | 新建任务时 `interval_seconds` 无统一兜底 | 每个任务都要单独配置 |
| 配置回滚能力弱 | 误改后需手动查找备份文件 | 运维效率低 |
| 配置跨机器迁移难 | A 机器调优的参数无法快速同步到 B 机器 | 多机器部署重复劳动 |
| 预设标签断层 Bug | 前端中文标签 vs 后端英文 key 静默失效 | 用户看到"包邮"选中但搜索 URL 不拼接参数 |
| 频率伪装不透明 | `FreqDisguise` 对数正态分布 + 15% 噪声请求未文档化 | 用户无法理解实际请求频率 |
| Cookie 自愈机制隐式 | 实时搜索时静默补注入，缺前端反馈 | 用户不知道为什么重登录后仍能搜 |
| MTOP 拦截 + DOM 回退 | 搜索主流程双链路设计未文档化 | 故障排查时难以定位 |

**解决方案**：将 `antidetect` / `search` / `task_scheduler` 三个配置块通过 `/api/config/*` 11 个端点 + 1 个前端页面（`/config/search`）统一暴露；同时定义闲鱼筛选标签契约、任务级配置深度合并语义、频率伪装机制、Cookie 三层架构与自愈机制，**让搜索参数可视化、可回滚、可迁移、可覆盖**。

## 2. 总体描述

### 2.1 产品定位

「搜索参数」是闲鱼猎人系统的**搜索行为配置入口**，定位为：

> 将分散在 `antidetect` / `search` / `task_scheduler` 三个配置块中的搜索相关参数**统一暴露**给前端，让用户在一个页面里完成"操作延迟调整 → 排序方式选择 → 地区过滤 → 筛选标签 → 任务调度默认值 → 配置预览 → 配置备份/回滚/分享/导入导出"全流程操作。

**核心价值**：
1. **参数可视化**：操作延迟、等效 QPS、每页数量、排序方式、超时、重试次数、地区、标签全部实时展示
2. **熔断可配置**：`fail_pause_threshold` 可调，连续失败 N 次自动暂停任务（成功清零）
3. **任务调度默认值**：`default_interval_seconds` 与 `auto_search_enabled` 统一兜底
4. **配置可回滚**：多版本备份（保留 10 个）+ 一键回滚 + 指定备份恢复
5. **配置可迁移**：JSON 导出/导入 + 强制 dry_run 二次确认
6. **配置可分享**：脱敏摘要文本，便于社区求助
7. **任务级覆盖**：`search_config` dict 深度合并，单任务个性化调整

### 2.2 用户角色与特征

| 角色 | 特征 | 使用场景 | 关注重点 |
|------|------|----------|----------|
| 新部署用户 | 首次启动系统，使用默认配置 | 进入页面查看默认值，按需调整操作延迟 | 操作延迟、等效 QPS、每页数量 |
| 风控调优 | 已被闲鱼风控，需降低频率 | 调高操作延迟、降低 QPS、减少每页数量 | 操作延迟、等效 QPS、失败重试次数 |
| 捡漏优化 | 希望优先看到低价商品 | 切换排序方式为 `price_asc`，设置地区过滤 | 排序方式、地区过滤、筛选标签 |

## 3. 功能需求

### FR-1 配置读取

**FR-1.1** `GET /api/config` 读取完整配置（脱敏）
- 响应：完整 AppConfig dict（含 `antidetect` / `search` / `task_scheduler` 等 17 个子配置块）
- 脱敏规则：`_redact(cfg.model_dump())` 替换 cookie/cookies/session_id 为 `"***"`
- **通知渠道凭据不脱敏**（`serverchan_send_key` 等）：前端用 `Input.Password` 回显已配置值，脱敏会导致用户误以为未持久化
- **`user_agent` 不脱敏**：前端表单需直接编辑该字段，脱敏会引入假 diff

**FR-1.2** `GET /api/config/raw` 读取 YAML 原文
- 响应：`{raw: "yaml 文本"}`
- 敏感字段保留末 4 位（如 `"***abcd"`），便于用户识别但不泄露完整值
- 用于高级调试场景，普通用户使用 `GET /api/config` 即可

### FR-2 配置预览与保存

**FR-2.1** `POST /api/config/preview` 预览改动（不写盘）
- 请求体：`{payload: {antidetect: {...}, search: {...}, task_scheduler: {...}}}`
- 响应：`{diffs, validation, new_yaml}`
- `diffs` 列表项：`{path, old_value, new_value, op}`
- 用于保存前预览变更，避免误操作

**FR-2.2** `POST /api/config/save` 保存配置（支持 `dry_run`）
- 请求体：`{payload: {...}, dry_run: bool}`
- `dry_run=true` 时仅返回 diff，不写盘（与 `preview` 等价，但语义上用于"保存前确认"）
- `dry_run=false` 时执行完整保存流程：
  1. 写入 `config/config.yaml.bak` 旧备份（兼容路径）
  2. 写入 `config/backups/config.yaml.bak.<时间戳>` 新备份
  3. 超过 `BACKUP_KEEP=10` 的旧备份自动清理（`_prune_backups`）
  4. 原子写入 `config/config.yaml`
  5. 调用 `reload_config()` 重置单例
  6. 写盘失败时回滚到刚做的备份
- 响应：`{ok, dry_run, saved_at, diffs, backup, restart_required}`
- `restart_required=true` 提示"重启 run 调度器后生效"

**FR-2.3** 前端 Diff 预览 Modal
- 保存前调用 `POST /api/config/save` with `dry_run=true`
- 返回 `diffs` 列表，前端以表格展示 `{path, old_value, new_value, op}`
- 用户确认后调用 `confirmSave` 实际写盘

### FR-3 操作延迟与等效 QPS

**FR-3.1** 前端"操作延迟"InputNumber（1-30 秒）
- 用户输入秒为单位（直观），保存时映射到后端毫秒
- 映射规则：`min_delay_ms = searchInterval * 1000`，`max_delay_ms = searchInterval * 1500`
- **为什么 max_delay = 1.5x min_delay**：模拟人类操作的随机性，固定间隔容易被风控识别为机器人

**FR-3.2** 等效 QPS 自动计算（只读展示）
- 公式：`Math.round(60 / searchInterval)`
- 单位：次/分钟（前端已标注，避免与严格 QPS 混淆）
- 用户改延迟时实时更新
- 示例：3 秒 → 20 次/分钟；5 秒 → 12 次/分钟；10 秒 → 6 次/分钟

**FR-3.3** 操作延迟与任务循环间隔的区别
- **操作延迟**（`min_delay_ms`/`max_delay_ms`）：单次操作之间的人类行为模拟延迟（如点击搜索后等待 3 秒再点击下一个）
- **任务循环间隔**（`interval_seconds`/`cron`）：两次完整任务执行之间的间隔，在"任务管理"页面按任务配置
- 前端 Form.Item 的 extra 已明确说明"模拟人类操作的间隔时间（非任务循环间隔）"

### FR-4 每页数量与排序方式

**FR-4.1** 每页结果数量 Select（4 档固定选项）
- 选项：20 / 40 / 60 / 100
- **为什么只有 4 档**：闲鱼搜索 API 对 `page_size` 有严格限制，仅支持这 4 个值
- 默认值：20（最安全）
- 设置 100 有风控风险，建议配合较长操作延迟（≥5 秒）

**FR-4.2** 排序方式 Select（5 种固定选项）

| 选项值 | 中文名 | 闲鱼返回顺序 | 适用场景 |
|--------|--------|--------------|----------|
| `default` | 综合 | 综合排序（闲鱼算法） | 通用监控 |
| `newest` | 最新发布 | 最新发布优先 | 抢首发捡漏 |
| `price_asc` | 价格最低 | 价格升序 | 最低价优先 |
| `price_desc` | 价格最高 | 价格降序 | 高端商品监控 |
| `want_count` | 想要最多 | "想要"数降序 | 热门商品发现 |

**FR-4.3** 排序方式对采集策略的影响
- `default`：可能偏向推广商品
- `newest`：新品数据可能不全
- `price_asc`：易遇 1 元引流商品（建议配合价格策略下限）
- `price_desc`：高价商品风控较严
- `want_count`：热门商品竞争激烈

### FR-5 搜索超时与失败重试

**FR-5.1** 搜索超时 InputNumber（10-120 秒，step=5）
- 默认值：30 秒
- **设置过长的影响**：
  - 任务调度卡顿：一个请求阻塞 2 分钟，影响后续任务执行
  - 风控风险：长时间挂起的请求可能被闲鱼识别为异常
  - 资源浪费：Playwright 页面长时间占用内存
- 建议：保持默认 30 秒，网络不稳定时最多调到 60 秒
- 超时后计入 `consecutive_errors`，可能触发熔断

**FR-5.2** 失败重试次数 InputNumber（0-10）
- 前端"失败重试次数"实际写入后端 `fail_pause_threshold` 字段
- 语义：**连续失败 N 次后触发熔断暂停任务**（非"失败后重试 N 次"）
- 0 表示不重试（失败即熔断）
- 默认值：3

**FR-5.3** 熔断机制（**v1.0 修正：连续失败计数器，非滑动窗口**）
- 实现位置：`backend/xianyu_hunter/modules/scheduler.py` 第 425-479 行
- `consecutive_errors` 计数器在 `_WorkerHandle` 实例上维护，**进程内不持久化**
- `run_once` 抛出异常时 `consecutive_errors += 1`
- **成功一轮后立即清零**（`h.consecutive_errors = 0`）
- `consecutive_errors >= fail_pause_threshold`（默认 3）时触发 `_pause_if_exceeded_fail_threshold`：
  - `h.pause_event.clear()`
  - `h.task.status = TaskStatus.PAUSED`
  - 同步 DB 到 `paused`
  - 主循环 `break` 退出

**FR-5.4** `fail_window_sec` 字段的现状
- `fail_window_sec`（默认 3600 秒）在 `AntiDetectConfig` 中保留
- **仅被 `WAFGuard` 组件使用**（`anti_detect.py` 第 410-462 行），使用滑动窗口 + deque 实现
- **scheduler 主流程未直接调用 `WAFGuard.record_failure`**，而是用 `consecutive_errors` 计数器
- `WAFGuard` 作为预留组件存在，未来可能接入

**FR-5.5** 为什么用连续失败而非滑动窗口
- 闲鱼风控通常是"连续触发"模式（如连续 3 次验证码即封禁）
- 连续失败计数更贴合风控逻辑
- 滑动窗口在小样本下波动大（如 1 小时内仅 2 次失败但分散），可能误判或漏判

### FR-6 地区过滤与筛选标签

**FR-6.1** 地区过滤 Input（逗号分隔）

**FR-6.3** 预设快捷标签 Button 组（5 个）

**FR-6.4** 地区与标签的 AND 关系

### FR-15 Cookie 三层架构与自愈

**FR-15.1** Cookie 三层架构
- **identity 层**：身份 Cookie（cookie2/sgcookie/unb），缺失即失效
- **session 层**：会话 Cookie（_m_h5_tk 等），过期可刷新
- **tracking 层**：追踪 Cookie（mtop_partitioned_detect 等），不影响搜索

**FR-15.2** Cookie 自愈机制（缺失/过期/陈旧三类检测 + 自动补注入）
- **missing**：浏览器缺失的 identity cookie
- **expired**：浏览器中已过期的 identity cookie（session cookie 不计，`expires <= 0` 视为 session）
- **stale**：浏览器持有但值与 JSON 不一致的 identity cookie
- 补注入流程：从 CookieStore JSON 读取 → `add_cookies` 注入到浏览器内存 → 同步 CookieRotator 层状态

**FR-15.3** 错误码
- `expired` → 440 "闲鱼登录 Cookie 已过期"
- `stale` → 440 "闲鱼登录 Cookie 未刷新"
- `missing` → 403 "闲鱼登录 Cookie 不完整"

**FR-15.4** 本页面不直接处理 Cookie 自愈
- Cookie 自愈在「反爬登录管理」菜单和实时搜索流程中处理
- 本页面仅配置搜索参数，不涉及 Cookie 操作

### FR-16 会话失效冷却期

**FR-16.1** `_RESUME_COOLDOWN_SECONDS = 300`（5 分钟）
- 位置：`backend/xianyu_hunter/modules/scheduler.py` 第 31 行
- 任务 `run_once` 检测到 `result.should_pause=True`（RGV587/搜索超时）时：
  - 自动暂停任务（`h.pause_event.clear()`）
  - 记录冷却期结束时间戳（`time.monotonic() + 300`）
  - 同步 DB 到 `paused`

**FR-16.2** 冷却期内拒绝恢复
- 冷却期内 `resume/start` 会被 `ResumeBlockedError` 拒绝
- 提示文案：`任务会话失效冷却期内，请 {int(remaining)} 秒后重试，或重新登录后再恢复`

**FR-16.3** 为什么用 `time.monotonic` 而非 `time.time`
- `monotonic` 不受系统时钟调整影响
- 适合测量相对时间间隔
- 避免 NTP 校时导致冷却期异常缩短或延长

**FR-16.4** 本页面不直接配置冷却期
- `_RESUME_COOLDOWN_SECONDS` 硬编码，不在本页面调整
- 用户通过操作延迟和失败重试间接影响会话失效触发频率

### FR-17 配置热更新

**FR-17.1** `reload_config()` 热更新入口
- 位置：`backend/xianyu_hunter/infra/yaml_config.py` 第 611-615 行
- 保存配置后调用，重置单例
- 搜索调度流程每次执行都通过 `get_config().search` / `get_config().antidetect` 实时获取新参数

**FR-17.2** 热更新不影响进行中的请求
- 正在执行的搜索请求会用旧参数完成
- 下一轮调度才用新参数
- **有意设计**：中断进行中的请求可能导致 Playwright 状态异常

**FR-17.3** 熔断状态不随配置变更重置
- `consecutive_errors` 计数在进程内维护
- 配置变更（如提高 `fail_pause_threshold`）**不影响**已触发的熔断
- 仅影响下次熔断判定

### 8.4 FAQ / 设计权衡

**Q1：为什么 `antidetect` 和 `search` 配置块要分离？**
A：反检测参数（如 QPS、延迟）对所有 HTTP 请求通用（搜索、详情、卖家主页等），而搜索参数（如排序、每页数量）仅对搜索请求有意义。任务调度默认值与运行时调度行为相关，与单次请求参数解耦。分离后便于后续扩展其他模块（如详情采集）的专用参数。

**Q2：为什么熔断机制用连续失败而非滑动窗口？**
A：闲鱼风控通常是"连续触发"模式（如连续 3 次验证码即封禁），连续失败计数更贴合风控逻辑。滑动窗口在小样本下波动大（如 1 小时内仅 2 次失败但分散），可能误判或漏判。`fail_window_sec` 字段保留是兼容 `WAFGuard` 组件，scheduler 主流程未直接消费。

**Q3：为什么操作延迟的 max_delay = 1.5x min_delay？**
A：模拟人类操作的随机性。固定间隔容易被风控识别为机器人，1.5x 范围内的随机延迟更接近真实用户行为。例如 min_delay=3000ms，max_delay=4500ms，实际延迟在 3000-4500ms 之间随机。

**Q4：为什么预设标签断层 Bug 不在本版本修复？**
A：修复方案涉及前端/后端/映射表多处改动，需评估对历史数据的影响。本版本仅记录 Bug，提供临时规避方案（用户手动输入英文 key）。修复方案见详细设计 §7.8。

**Q5：为什么配置导入强制 dry_run 二次确认？**
A：导入配置会覆盖当前所有配置，强制二次确认避免误操作。`confirm != true` 时返回 diff 列表，用户确认后才真正写盘。

**Q6：为什么 `BACKUP_KEEP=10`？**
A：10 个备份足够覆盖近期所有变更，过多会占用磁盘空间。每个备份约 2-5KB，10 个共 20-50KB，可忽略。

**Q7：为什么通知渠道凭据不脱敏？**
A：前端用 `Input.Password` 回显已配置值，脱敏会导致用户误以为未持久化，重复配置。`user_agent` 同理，前端表单需直接编辑该字段，脱敏会引入假 diff。

**Q8：为什么任务级 `search_config` 用深度合并而非直接替换？**
A：深度合并允许任务级仅覆盖需要调整的字段，其他字段沿用全局配置，减少配置冗余。列表类型直接替换是因为元素合并语义不明确（如 filter_tags 是 AND 还是 OR？）。

**Q9：为什么 `auto_search_concurrency` >1 时仅警告不抛错？**
A：并发 >1 可能触发风控，但不影响功能正确性。警告提示用户风险，由用户决定是否调整。抛错会阻断配置保存，影响用户体验。

**Q10：为什么热更新不影响进行中的请求？**
A：中断进行中的请求可能导致 Playwright 状态异常（如页面未关闭、Cookie 未同步）。有意设计：正在执行的搜索用旧参数完成，下一轮调度才用新参数。
