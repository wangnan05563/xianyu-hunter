## 2. 功能概述

**一句话说明**：通过 4 维权重雷达图（职业度/信誉/纠纷/价格，和必须 = 100）+ 阈值配置 + Sigmoid 渐进扣分 + 动态 buffer 防高分掩盖 + AI Vision 评估集成，对卖家与商品进行综合评分，决定是否通过、是否自动抢单。

**核心价值**：
- 4 维加权评分模型，权重可视化拖拽调整，支持字段级回滚
- 一票否决机制（黑名单/信用分过低）防高风险卖家
- 数据质量三级分级（full / partial / insufficient）应对卖家数据缺失
- Sigmoid 渐进式扣分替代硬阈值，避免评分跳变
- 防高分掩盖（动态 buffer 基于方差）避免单维度高分掩盖其他维度风险
- AI Vision 多模态评估集成，Prompt 热更新 + 价格区间注入 + 评估缓存
- 任务级 eval_config 覆盖机制（与全局配置合并，支持单任务个性化）
- 自动官方采集 + 失败退避机制（连续失败暂停 + EventBus 告警）
- pass_score / auto_buy_score 双阈值控制通知与自动抢单
- 评估分布热力图、F-15 阈值建议、F-12 卖家价格趋势辅助决策

## 3. 用户场景

### 场景 1：调整评估权重偏好
用户更关注卖家信誉，希望降低职业度权重、提高信誉权重。通过雷达图下方的 4 个滑块调整 `professional=20, credit=40, dispute=25, price=15`，点击"一键归一化"确保总和为 100。每项滑块支持字段级回滚（点击回滚按钮恢复原始值）。

### 场景 2：开启 AI 自动评估
用户希望对通过规则评估的商品自动调用 AI 视觉评估，开启 `ai_auto_eval=true`。系统会对通过 pass_score 的商品调用 LLM Vision 分析图片成色（最多 4 张图），结合同类物品价格区间判定价格合理性，结果缓存到 `evaluations.dimension_scores.ai_condition_eval`，并实质性影响总分与风险等级。

### 场景 3：调整自动抢单阈值
用户希望更严格地控制自动抢单，将 `auto_buy_score` 从 80 提高到 85。配置后只有评分 ≥85 且风险等级为 LOW 的商品才会触发全自动拍下，60–84 分仅推送给用户确认。

### 场景 4：任务级配置覆盖
用户为高价值任务单独配置更严格的评估规则：在任务编辑器 Step 4 设置 `eval_config={"auto_collect_official": true, "auto_collect_max_per_run": 5}`。Worker 在执行时通过 `_effective_eval_cfg()` 合并全局配置与任务级覆盖，仅该任务启用官方采集且上限提升到 5，其他任务仍用全局默认。

### 场景 5：查看评估分布与阈值建议
用户在评估分布热力图 Card 查看近 7 天（168 小时）的价格 × 评分二维分布，识别价格洼地与评分集中区域。点击"阈值建议"调用 F-15 算法，系统基于历史评估数据二分查找通过率 75% 对应的分数作为 pass_score 建议值。

### 场景 6：AI 成色评估遇到纯文本模型
用户配置的 `vision_model` 不支持多模态（如 DeepSeek-Chat），系统通过 `_is_vision_capable()` 检测后自动追加"特别说明"到 Prompt，要求 LLM 仅基于标题/描述/价格/价格区间评估，并在 risk_signals 中加入"无图片参考"，避免 LLM 强行编造"我看了图片"导致评估失真。

| -------------- | ----- | ------ | ------------ |

| 字段                  | 类型    | 默认值 | 说明                       |

### 6.3 任务级 eval_config 覆盖

位置：`backend/xianyu_hunter/domain/task.py` 的 `Task.eval_config: dict[str, Any] | None`

任务级覆盖字段稀疏存储为 dict（JSON 序列化存 DB），`None` 或空 dict 表示沿用全局配置。可覆盖字段为 `EvalConfig` 的任意字段，常见覆盖项：
- `auto_collect_official`：单任务启用官方采集
- `auto_collect_max_per_run`：调整单任务采集上限
- `pass_score` / `auto_buy_score`：单任务自定义阈值
- `ai_auto_eval`：单任务启用 AI 评估

**合并逻辑**（`worker._effective_eval_cfg()`）：
1. `task.eval_config` 为 `None` 或空 dict → 直接返回全局单例（无副本开销）
2. 非 None 时过滤 `None` 值（None 表示"不覆盖此字段"）和未知字段（防 Pydantic v2 `model_copy` 直接 setattr 脏数据）
3. 用 `model_copy(update=updates)` 创建副本，避免污染全局单例

## 7. 业务逻辑

### 7.1 评分算法

位置：`backend/xianyu_hunter/modules/evaluator.py` `Evaluator.evaluate()` 方法

#### 数据质量三级分级

| 等级          | 有效维度数 | 评估策略                                       | 上限  |
| ------------- | ---------- | ---------------------------------------------- | ----- |
| `full`        | ≥ 4        | 正常 4 维加权评估（`_evaluate_full`）          | 100   |
| `partial`     | 2-3        | 仅有效维度归一化加权（`_evaluate_partial`）    | 80    |
| `insufficient`| 1（仅 price）| `price(0.6) + popularity(0.4)` 双维度加权    | 65    |

**有效维度判定**（`_get_valid_dimensions(seller)`）：
- `professional`：`on_sale_count >= 1` 或 `post_count_30d >= 1`
- `credit`：`credit_score >= 400` 或 `register_days >= 1`
- `dispute`：`on_sale_count >= 1` 或 `register_days >= 1`（闲鱼不公开差评数，但有在售/注册数据时认为 dispute 维度可评估）
- `price`：始终有效（来自 `item`，不依赖卖家数据）

#### full 模式 4 维评分（`_evaluate_full`）

1. **一票否决** `_veto(seller)`：
   - 黑名单命中 → `platform_blacklist`
   - `credit_score < credit_score_min` → `credit_score {x} < min {y}`
   - 命中即返回 `score=0, risk_level=EXTREME`
2. **职业度** `_eval_professional`：Sigmoid 渐进扣分 + 关键词硬扣 + 贩子信号扣分
3. **信誉** `_eval_credit`：信用分未知扣 10、信用 600-700 扣 5、注册天数不足扣 20、已售 <5 扣 10
4. **纠纷** `_eval_dispute`：差评数 > `bad_review_max` 扣 50，差评 1-3 每个扣 5
5. **价格** `_eval_price`：5 项检查（引流价/异常低价/价格诱饵/邮费陷阱/无图风险）

#### 加权汇总 + 防高分掩盖

```
weighted_total = sum(scores[k] * weights[k] for k in scores) // weight_sum
min_dim = min(scores.values())
buffer = max(30, int(50 - std * 0.4))   # 动态 buffer，基于维度方差
total = min(weighted_total, min_dim + buffer)
```

**动态 buffer 公式**（v1.0 文档错误，此处为正确实现）：
- 计算 4 维分数的标准差 `std = sqrt(variance)`
- `buffer = max(30, int(50 - std * 0.4))`
- 各维度分数接近时（`std` 小）→ `buffer=50`，允许高分
- 某维度远低于其他时（`std` 大）→ `buffer=30`，严格拉低总分
- `std` 范围约 0-50，映射到 `buffer` 50→30
- 单维度回退场景（`len(score_values) < 2`）→ `buffer=40`

#### partial 模式（`_evaluate_partial`）

```
valid_weight_sum = sum(weights[k] for k in scores if k in weights)
weighted_total = sum(scores[k] * weights[k] for k in scores) // valid_weight_sum
capped = min(weighted_total, min_dim + 30)   # buffer=30，比 full 更严格
total = min(int(capped * 0.8), 80)            # 0.8 系数惩罚，上限 80
```

#### insufficient 模式（`_evaluate_insufficient`，v1.0 文档错误，此处为正确实现）

```
price_score = _eval_price(item)              # 价格维度
popularity_score = _eval_popularity(item)    # 热度维度（基于 want_cnt）
weighted = int(price_score * 0.6 + popularity_score * 0.4)
total = min(65, weighted)                    # 上限 65
```

**热度评分逻辑**（`_eval_popularity`，insufficient 模式专用）：
- `want_cnt == 0` → 扣 30 分（无人问津，可能有问题）
- `want_cnt 1-5` → 扣 10 分（关注度低）
- `want_cnt 6-49` → 不扣分（正常范围）
- `want_cnt >= 50` → 加 10 分（受欢迎，上限 100）

**为什么 insufficient 模式上限 65**：可以 `pass_score(60)` 触发通知，但不会达到 `auto_buy_score(80)`，确保数据不足的卖家不会触发自动下单，允许用户手动审查。

#### 风险等级（`_score_to_risk`）

| 等级      | 条件                          |
| --------- | ----------------------------- |
| `LOW`     | `score >= auto_buy_score`     |
| `MEDIUM`  | `score >= pass_score`         |
| `HIGH`    | `score >= 40`                 |
| `EXTREME` | `score < 40` 或一票否决       |

### 7.2 Sigmoid 渐进扣分公式（v1.0 文档错误，此处为正确实现）

位置：`evaluator.py` `_sigmoid_deduction` 静态方法

```python
def _sigmoid_deduction(value: float, threshold: float, max_deduction: float, k: float = 0.15) -> float:
    return max_deduction / (1 + math.exp(-k * (value - threshold)))
```

**关键说明**：
- `max_deduction` **由调用方传入**，并非固定 100（v1.0 文档错误描述）
- `k=0.15` 控制过渡陡峭度，越小过渡越平缓

**调用点**：

| 维度              | 阈值                | max_deduction | 说明                          |
| ----------------- | ------------------- | ------------- | ----------------------------- |
| 在售数            | `on_sale_count(30)` | `40`          | `_apply_on_sale_deduction`    |
| 30 天发帖数       | `post_count_30d(15)`| `30`          | `_apply_post_count_30d_deduction` |

**扣分示例**（在售数，阈值 30，max_deduction=40）：
- `on_sale=10` → 扣 ~1 分
- `on_sale=30` → 扣 20 分（= max_deduction / 2）
- `on_sale=50` → 扣 ~38 分
- `on_sale=70` → 扣 ~40 分（趋近 max_deduction）

**其他职业度扣分项**：
- 类目集中度 `top_category_ratio > 0.8` → 硬扣 20 分
- 描述关键词命中 → 硬扣 15 分（命中即提前返回，跳过贩子检测避免重复扣分）
- 贩子信号（`detect_dealer`）→ 扣 `dealer_result.score_deduction` 分

### 7.3 校验规则

| 校验项                          | 层级       | 失败行为                                          |
| ------------------------------- | ---------- | ------------------------------------------------- |
| 权重和 = 100                    | Pydantic   | `_check_weight_sum` 抛 `ValueError`，保存失败     |
| `pass_score <= auto_buy_score`  | Pydantic   | `_check_score_order` 抛 `ValueError`              |
| `ai_suggestion_interval >= 1`   | Pydantic   | 防 `len(history) % interval` 的 ZeroDivisionError |
| `auto_collect_max_per_run >= 0` | Pydantic   | 负数会让 `stats.official_collected < max` 永远为 False，静默禁用 |
| 权重和 ≠ 100（运行时）          | 运行时     | 按比例归一化并 `logger.warning`，不崩溃           |
| 双阈值联动                      | 前端       | Alert 红色警告 + 禁用保存按钮                     |

### 7.5 AI 评估集成详细流程

位置：`backend/xianyu_hunter/web/routes/api_ai.py` `evaluate_condition` 端点

```
1. 获取商品信息
   ├─ 优先 items 表（数据最完整，含 description/image_urls）
   └─ items 表无记录时从 eval 事件 payload 回退（伪 item dict）

2. 检查缓存
   ├─ 查 evaluations 表 dimension_scores.ai_condition_eval
   └─ 命中则直接返回 {**cached_eval, "cached": True}，避免重复 LLM 调用

3. 查询同类物品已售价格区间（捡漏价格参考）
   ├─ 优先近 30 天数据（_query_price_range → sold_range）
   ├─ 近 30 天无数据时回退到全部历史数据
   └─ 查询失败不阻断主流程（捕获异常返回 None）

4. 调用 LLM Vision 或规则模拟
   ├─ 有 API Key → _call_llm_vision（httpx.AsyncClient，超时 60s）
   │   ├─ Vision 能力检测：_is_vision_capable(vision_model)
   │   │   └─ 纯文本模型自动追加"特别说明"到 Prompt，移除看图要求
   │   ├─ Prompt 热更新：get_active_prompt("evaluate_condition")
   │   ├─ 价格区间注入：text_content 追加 bargain_price/max_price/median_price/sample_size
   │   ├─ 图片 URL 处理：协议相对路径补全为 https://，最多 4 张
   │   └─ 预算检查：check_budget() 超限则抛 RuntimeError 降级
   └─ 无 API Key 或 LLM 失败 → _rule_eval_condition（规则模拟）

5. 归一化结果（_normalize_condition_result）
   ├─ verdict 规范化：recommend / caution（其他值按 condition_score 推断）
   ├─ condition_score 限制 1-10
   └─ 各项评分 _clamp_score 限制 1-10

6. 缓存到 evaluations 表
   ├─ 已有记录 → 更新 dimension_scores（保留其他维度数据）
   └─ 无记录 → 创建新评估（score = condition_score * 10 映射到 0-100）

7. 返回结果
   {verdict, condition_score, appearance_score, consistency_score,
    price_reasonability, risk_signals, reason, detail, source,
    cached: false, price_range?}
```

**AI 评估结果集成到规则评分**（`Evaluator.apply_ai_eval`）：

| AI verdict       | 总分调整                  | 风险等级                  |
| ---------------- | ------------------------- | ------------------------- |
| `reject`         | 总分 = 0                  | `EXTREME`                 |
| `caution`        | 总分 × 0.85               | 至少 `MEDIUM`             |
| `recommend` + `condition_score >= 8` | 总分 + 5（最高 100） | 重新计算                  |
| `recommend` + `condition_score <= 3` | 总分 × 0.7          | 重新计算 + 追加 `ai_low_condition` 原因 |

**token 消耗控制**：
- `ai_auto_eval` 每次消耗 1000-3000 tokens（4 张图片 + 文字）
- `ai_auto_deep_analyze` 消耗 3000-8000 tokens（更详细分析）
- 建议在"AI 服务"页面设置 `daily_token_limit` 预算上限，超出后 `check_budget()` 自动降级到规则模拟

### 7.6 自动官方采集退避机制

位置：`backend/xianyu_hunter/modules/worker.py` `_run_official_collect` 方法

**触发条件**（4 个 AND 条件全满足）：
1. `eval_cfg.auto_collect_official == True`
2. `self.official_collect_fn is not None`（回调已注入）
3. `not stats.official_collect_paused`（未暂停）
4. `stats.official_collected < eval_cfg.auto_collect_max_per_run`（配额未耗尽）

**失败退避流程**：
1. 采集失败 → `_consecutive_collect_failures += 1`
2. 达到 `auto_collect_fail_pause_threshold`（默认 3）→ `stats.official_collect_paused = True`
3. 通过 `EventBus.publish_nowait` 发送 `TASK_ERROR` 事件（payload 含 `reason="auto_collect_paused"`、`consecutive_failures`、`threshold`）
4. 暂停本轮剩余商品的采集，下一轮 `run_once` 开头重置计数器自动重试
5. 采集成功时重置 `_consecutive_collect_failures = 0`（偶发失败不累积）

**前端展示**：
- `useAutoRefresh` hook 60s 自动刷新 `/api/evaluations/auto-collect-stats`
- 显示 `is_paused` 状态 + Top3 失败原因
- 仅在 `auto_collect_official=true` 时启用刷新

### 7.7 任务级 eval_config 覆盖机制

位置：`backend/xianyu_hunter/modules/worker.py` `_effective_eval_cfg()` 方法

```python
def _effective_eval_cfg(self) -> EvalConfig:
    global_cfg = get_config().eval
    task_override = getattr(self.task, "eval_config", None)
    if not task_override:
        return global_cfg                    # 无覆盖，返回全局单例
    known_fields = type(global_cfg).model_fields
    updates = {
        k: v for k, v in task_override.items()
        if v is not None and k in known_fields   # 过滤 None 和未知字段
    }
    if not updates:
        return global_cfg
    return global_cfg.model_copy(update=updates)  # 创建副本，不污染全局
```

**为什么过滤未知字段**：Pydantic v2 的 `model_copy(update=...)` 会直接 `setattr` 未知键，不校验是否为模型字段，导致脏数据残留。

**为什么过滤 None 值**：`None` 表示"不覆盖此字段"，与传 `False` 显式关闭语义不同。

## 9. 常见问题 FAQ

### Q1：权重总和不是 100 会怎样？
**A**：保存时 Pydantic `_check_weight_sum` 校验器会抛 `ValueError`，保存失败。前端会显示 Alert 警告并提供"一键归一化"按钮。如果通过其他方式（如直接改 YAML）写入非 100 值，运行时评估器会按比例归一化并记录 warning 日志，不会崩溃。

### Q2：pass_score 可以大于 auto_buy_score 吗？
**A**：不可以。Pydantic `_check_score_order` 校验器强制 `pass_score <= auto_buy_score`，否则抛错。前端双滑块联动校验，违反时显示红色 Alert 并禁用保存。逻辑上"通过线高于自动抢单线"是矛盾的。

### Q3：AI 自动评估会消耗多少 token？
**A**：每次评估调用一次 LLM Vision（最多 4 张图片 + 文字描述 + 价格区间），单次约消耗 1000-3000 tokens。建议先在"AI 服务"配置页面设置每日预算上限（`daily_token_limit`），超出后 `check_budget()` 自动降级到规则模拟。

### Q4：自动官方采集失败后会永久禁用吗？
**A**：不会。连续失败达到 `auto_collect_fail_pause_threshold`（默认 3）后仅暂停本轮剩余商品的采集，下一轮 `run_once` 开头重置 `_consecutive_collect_failures` 自动重试。前端采集统计卡片会显示"已暂停"状态 + Top3 失败原因。同时通过 EventBus 发送 `TASK_ERROR` 事件触发告警通知。

### Q5：评估分布热力图为什么有时为空？
**A**：热力图数据来自 `/api/evaluations/distribution`（注意是 `evaluations` 复数），反映近 7 天（168 小时）真实评估结果。如果系统刚部署或近 7 天没有评估记录，会显示"暂无评估分布数据"占位图。运行几轮采集评估后即可看到分布。响应中的 `insufficient_count` 反映数据质量不足的评估数，可用于监控数据采集质量。

### Q6：职业关键词支持中文吗？支持多少个？
**A**：完全支持中文，无数量限制。常见关键词包括"批发、代理、代购、大量、店铺、厂家、直发、一手"等。商品描述中包含这些关键词时，职业度评分会被扣 15 分并提前返回（跳过贩子检测避免重复扣分）。可拖拽排序，但不影响匹配逻辑（仅影响展示顺序）。

### Q7：数据质量分级是什么意思？
**A**：评估器根据卖家数据完整性分三级：
- `full`（4 维有效）正常 4 维加权，上限 100
- `partial`（2-3 维有效）仅有效维度归一化加权，0.8 系数惩罚，上限 80
- `insufficient`（仅 price 有效）`price(0.6) + popularity(0.4)` 双维度加权，上限 65

这避免了卖家数据缺失时给出虚假高分。insufficient 模式可以 pass(60) 但不能 auto_buy(80)。

### Q8：动态 buffer 是如何工作的？（v1.0 公式已修正）
**A**：基于 4 维分数的标准差（`std`）。公式为 `buffer = max(30, int(50 - std * 0.4))`：
- 各维度分数接近（`std` 小）→ `buffer=50`，允许高分
- 某维度远低于其他（`std` 大）→ `buffer=30`，严格拉低总分
- 单维度回退场景 → `buffer=40`

最终 `total = min(weighted_total, min_dim + buffer)`。这防止了"3 维 100 分 + 1 维 0 分"仍得到 75 分的高分掩盖问题。

### Q9：AI 多轮优化建议多久生成一次？
**A**：每 `ai_suggestion_interval` 轮（默认 5 轮）生成一次。太小浪费 token，太大反馈滞后。生成后会调用 LLM 分析累积的运行数据，输出趋势洞察与策略调优方向，与单轮结论互补。

### Q10：保存后立即生效吗？
**A**：是。保存接口写盘后调用 `reload_config()` 重置单例，评估器 `evaluate()` 每次调用都从 `get_config()` 实时读取配置。无需重启服务。任务级 `eval_config` 覆盖则在下一轮 `run_once` 通过 `_effective_eval_cfg()` 重新合并生效。

### Q11：权重归一化算法是什么？
**A**：前端"一键归一化"按钮的算法（EvalRules.tsx）：
```
factor = 100 / weightsTotal
newWeight = Math.round(weight * factor)
```
例如权重 `[25, 35, 25, 25]`（总和 110），`factor=100/110≈0.909`，归一化后 `[23, 32, 23, 23]`（总和 101，因 `Math.round` 四舍五入）。如果归一化后总和仍非 100，会微调最大权重项补差。

### Q12：数据质量分级的 valid_dims 如何判定？
**A**：`_get_valid_dimensions(seller)` 检测卖家数据有效性：
- `professional`：`on_sale_count >= 1` 或 `post_count_30d >= 1`
- `credit`：`credit_score >= 400` 或 `register_days >= 1`
- `dispute`：`on_sale_count >= 1` 或 `register_days >= 1`（闲鱼不公开差评数，但有在售/注册数据时认为可评估）
- `price`：始终有效（来自 item）

价格维度始终有效，因此最多 4 维有效，最少 1 维有效。`len(valid_dims) >= 4` 走 full 模式，`>= 2` 走 partial 模式，否则走 insufficient 模式。

### Q13：partial 模式下为什么最高只能 80 分？
**A**：partial 模式施加 0.8 系数惩罚（`total = min(int(capped * 0.8), 80)`）。原因：
- 数据不完整的卖家风险更高（缺失维度可能隐藏问题）
- 80 分是 `auto_buy_score` 的默认值，partial 模式下无法触发自动抢单
- 仍可达到 `pass_score`（60 分）触发通知，用户手动审查

这确保数据不足的卖家不会因部分维度高分而获得虚假的高总分。

### Q14：Sigmoid 扣分的 max_deduction 是固定的吗？（v1.0 错误已修正）
**A**：不是。`max_deduction` 由调用方传入：
- 在售数扣分：`max_deduction=40`（`_apply_on_sale_deduction`）
- 30 天发帖数扣分：`max_deduction=30`（`_apply_post_count_30d_deduction`）
- 类目集中度：硬阈值扣 20 分（非 Sigmoid）
- 描述关键词：硬扣 15 分（非 Sigmoid，命中即提前返回）

公式为 `deduction = max_deduction / (1 + exp(-0.15 * (value - threshold)))`。`value == threshold` 时扣分 = `max_deduction / 2`。

### Q15：任务级 eval_config 覆盖如何与全局配置合并？
**A**：Worker 在每轮 `run_once()` 调用 `_effective_eval_cfg()` 合并：
1. `task.eval_config` 为 `None` 或空 dict → 返回全局单例（无副本开销）
2. 非 None 时过滤 `None` 值（None 表示"不覆盖"）和未知字段（防 Pydantic v2 `model_copy` 直接 setattr 脏数据）
3. 用 `model_copy(update=updates)` 创建副本，避免污染全局单例

可覆盖字段为 `EvalConfig` 的任意字段，常见覆盖项：`auto_collect_official`、`auto_collect_max_per_run`、`pass_score`、`auto_buy_score`、`ai_auto_eval`。

### Q16：AI 评估遇到纯文本模型（不支持 Vision）怎么办？
**A**：系统通过 `_is_vision_capable(model_name)` 检测当前 `vision_model` 是否支持多模态（关键字白名单维护在 `api_ai.py` `_VISION_CAPABLE_KEYWORDS`）。纯文本模型时：
1. 自动追加"特别说明"到 Prompt，要求 LLM 仅基于标题/描述/价格/价格区间评估
2. 不传入图片 URL（避免 400 报错 + 用量浪费）
3. `risk_signals` 中加入"无图片参考"

这避免了 LLM 强行编造"我看了图片"导致评估失真。

### Q17：AI 评估结果如何缓存？
**A**：缓存存储在 `evaluations` 表的 `dimension_scores` JSON 字段中的 `ai_condition_eval` 子字段。下次评估同一商品时：
1. 查询 `get_latest_evaluation(item_id)` 获取已有评估
2. `_get_cached_ai_eval` 从 `dimension_scores.ai_condition_eval` 提取缓存
3. 命中则直接返回 `{**cached_eval, "cached": True}`，避免重复 LLM 调用

缓存与评估记录绑定，重新评估（如配置变更后 `recompute`）会覆盖缓存。

### Q18：F-15 阈值建议算法是如何工作的？
**A**：`GET /api/evaluations/threshold-suggestion` 端点基于历史评估数据（默认近 30 天）：
1. 收集所有评估分数分布
2. 二分查找使通过率（`score >= pass_score` 的比例）达到 `target_pass_rate`（默认 0.75）的分数
3. 返回 `suggested_pass_score`、`suggested_auto_buy_score`（通常 +20）、`current_pass_rate`、`sample_size`

样本数过少时建议保守（不调整），避免噪声影响。
