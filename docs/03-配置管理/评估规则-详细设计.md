## 2. 功能概述

**一句话说明**：通过 4 维权重雷达图（职业度/信誉/纠纷/价格，和必须=100）+ 阈值配置 + AI 评估集成，对卖家与商品进行综合评分，决定是否通过、是否自动抢单。

**核心价值**：
- 4 维加权评分模型，权重可视化拖拽调整
- 一票否决机制（信用分过低/差评过多）防高风险卖家
- 数据质量三级分级（full/partial/insufficient）应对卖家数据缺失
- Sigmoid 渐进式扣分替代硬阈值，避免评分跳变
- 防高分掩盖（动态 buffer）避免单维度高分掩盖其他维度风险
- AI 自动评估、深度分析、官方采集全链路集成
- pass_score / auto_buy_score 双阈值控制通知与自动抢单

## 3. 用户场景

### 场景 1：调整评估权重偏好
用户更关注卖家信誉，希望降低职业度权重、提高信誉权重。通过雷达图下方的 4 个滑块调整 `professional=20, credit=40, dispute=25, price=15`，点击"一键归一化"确保总和为 100。

### 场景 2：开启 AI 自动评估
用户希望对通过规则评估的商品自动调用 AI 视觉评估，开启 `ai_auto_eval=true`。系统会对通过 pass_score 的商品调用 LLM Vision 分析图片成色，结果实质性影响总分与风险等级。

### 场景 3：调整自动抢单阈值
用户希望更严格地控制自动抢单，将 `auto_buy_score` 从 80 提高到 85。配置后只有评分 ≥85 的商品才会触发全自动拍下，60–84 分仅推送给用户确认。

## 7. 业务逻辑

### 7.1 评分算法

位置：`src/xianyu_hunter/modules/evaluator.py` `Evaluator.evaluate()` 方法（第 114-148 行）

#### 数据质量三级分级
- **full**：3+ 维度有效 → 正常 4 维加权评估（`_evaluate_full`）
- **partial**：1-2 维度有效 → 仅有效维度归一化加权（`_evaluate_partial`）
- **insufficient**：0 维度有效 → 仅价格维度保守评分（`_evaluate_insufficient`）

价格维度始终有效（来自 `item`，不依赖卖家数据）。

#### 4 维评分（_evaluate_full）
1. **一票否决**：`_veto(seller)` 检查黑名单/信用分过低 → 返回 `score=0, risk_level=EXTREME`
2. **职业度** `_eval_professional`：Sigmoid 渐进式扣分替代硬阈值，避免阈值附近评分跳变
3. **信誉** `_eval_credit`：芝麻信用分/实名认证/注册天数综合评分
4. **纠纷** `_eval_dispute`：差评数/退款率/投诉减分
5. **价格** `_eval_price`：商品价/市场价比率评分

#### 加权汇总 + 防高分掩盖
```
weighted_total = sum(scores[k] * weights[k] for k in scores) // weight_sum
```

**动态 buffer**（第 191-200 行）：基于维度方差的动态缓冲
- 各维度分数接近时（std 小）→ buffer=50，允许高分
- 某维度远低于其他时（std 大）→ buffer=30，严格拉低总分
- 公式：`buffer = 50 - 20 * (std / 50)`，将 std 范围 0-50 映射到 buffer 50→30

#### 风险等级
- `LOW`：`score >= auto_buy_score`
- `MEDIUM`：`score >= pass_score`
- `HIGH`：`score >= 40`
- `EXTREME`：一票否决或 `score < 40`

### 7.2 校验规则
- **权重和=100**：Pydantic `model_validator` 强制校验；运行时若非 100 会按比例归一化并 `logger.warning`。
- **pass_score ≤ auto_buy_score**：Pydantic 校验 + 前端 Alert 双重保险。
- **ai_suggestion_interval ≥ 1**：防 `len(history) % interval` 的 ZeroDivisionError。
- **auto_collect_max_per_run ≥ 0**：负数会让 `stats.official_collected < max` 永远为 False，静默禁用。

### 7.3 热更新机制
- `Evaluator.__init__` 接受可选覆盖参数（仅测试用），生产环境不传参。
- 每次 `evaluate()` 调用时通过 `get_config().eval` 实时获取 weights/thresholds/keywords，确保配置页面保存后立即生效。
- `EvaluationThresholds.from_config(config)` 工厂方法从 `EvalConfig` 构造运行时阈值。

### 7.4 AI 评估集成
- **ai_auto_eval**：调度流程对通过规则评估的商品自动调用 `POST /api/ai/evaluate-condition`（LLM Vision），结果缓存到 `evaluations.dimension_scores.ai_condition_eval`。
- **ai_auto_deep_analyze**：对通过 AI 评估的商品调用深度分析（消耗更多 token），分析成色、真伪、性价比。
- **auto_collect_official**：对通过评估的商品调用官方采集，提取评价/留言等爬虫无法获取的数据。
- **ai_multi_run_suggestion**：累积 `ai_suggestion_interval` 轮后调用 LLM 生成趋势洞察与优化建议，与单轮结论互补。

### 7.5 自动官方采集退避机制
- 每轮采集失败累计 `consecutive_failures`，达到 `auto_collect_fail_pause_threshold`（默认 3）后暂停本轮剩余商品的采集。
- 通过 `notifier` 发送告警通知用户。
- 下一轮自动重试（不永久禁用）。
- 前端 60s 自动刷新统计，显示 `is_paused` 状态 + Top3 失败原因。

### 7.6 Sigmoid 渐进扣分公式

职业度维度（`_eval_professional`）使用 Sigmoid 函数替代硬阈值，避免评分在阈值附近跳变：

```
score = 100 - 100 / (1 + exp(-k * (metric - threshold)))

其中：
- metric：实际指标值（如 on_sale_count）
- threshold：配置阈值（如 on_sale_count=30）
- k：陡度系数（控制过渡区间宽度）
```

**对比硬阈值的改进**：
- 硬阈值：`on_sale_count=29` 得 100 分，`on_sale_count=30` 得 0 分（评分跳变 100 分）
- Sigmoid：`on_sale_count=29` 得 52 分，`on_sale_count=30` 得 50 分，`on_sale_count=31` 得 48 分（平滑过渡）

**为什么用 Sigmoid**：硬阈值会导致评分不连续，卖家数据微小波动就会引起评分大幅跳变，影响评估稳定性。Sigmoid 函数在阈值附近平滑过渡，远端仍能拉开差距，兼顾稳定性与区分度。

### 7.7 AI 评估集成详细流程

```
规则评估完成（EvalResult.score >= pass_score）
  ↓
[ai_auto_eval=true] 调用 POST /api/ai/evaluate-condition
  ↓
LLM Vision 分析商品图片（最多 4 张）+ 标题/描述
  ↓
返回 ai_verdict (accept/caution/reject) + ai_condition_score (1-10)
  ↓
Evaluator.apply_ai_eval(result, ai_verdict, ai_condition_score)
  ↓
按 verdict 调整总分：
  - reject → 总分=0，风险=EXTREME
  - caution → 总分×0.85，风险≥MEDIUM
  - accept + score>=8 → 总分+5（最高100）
  - accept + score<=3 → 总分×0.7
  ↓
[ai_auto_deep_analyze=true] 对通过 AI 评估的商品调用深度分析
  ↓
返回最终 EvalResult（含 ai_condition/ai_verdict 维度分数）
```

**token 消耗控制**：
- `ai_auto_eval` 每次消耗 1000-3000 tokens（4 张图片 + 文字）
- `ai_auto_deep_analyze` 消耗 3000-8000 tokens（更详细分析）
- 建议在"AI 服务"页面设置 `daily_token_limit` 预算上限，超出后自动降级

## 9. 常见问题 FAQ

### Q1：权重总和不是 100 会怎样？
**A**：保存时 Pydantic `_check_weight_sum` 校验器会抛 `ValueError`，保存失败。前端会显示 Alert 警告并提供"一键归一化"按钮。如果通过其他方式（如直接改 YAML）写入非 100 值，运行时评估器会按比例归一化并记录 warning 日志，不会崩溃。

### Q2：pass_score 可以大于 auto_buy_score 吗？
**A**：不可以。Pydantic `_check_score_order` 校验器强制 `pass_score <= auto_buy_score`，否则抛错。前端双滑块联动校验，违反时显示红色 Alert 并禁用保存。逻辑上"通过线高于自动抢单线"是矛盾的。

### Q3：AI 自动评估会消耗多少 token？
**A**：每次评估调用一次 LLM Vision（最多 4 张图片 + 文字描述），单次约消耗 1000-3000 tokens。建议先在"AI 服务"配置页面设置每日预算上限（`daily_token_limit`），超出后自动降级到规则模拟。

### Q4：自动官方采集失败后会永久禁用吗？
**A**：不会。连续失败达到 `auto_collect_fail_pause_threshold`（默认 3）后仅暂停本轮剩余商品的采集，下一轮自动重试。前端采集统计卡片会显示"已暂停"状态 + 主要失败原因。

### Q5：评估分布热力图为什么有时为空？
**A**：热力图数据来自 `/api/eval/distribution`，反映近 7 天真实评估结果。如果系统刚部署或近 7 天没有评估记录，会显示"暂无评估分布数据"占位图。运行几轮采集评估后即可看到分布。

### Q6：职业关键词支持中文吗？支持多少个？
**A**：完全支持中文，无数量限制。常见关键词包括"批发、代理、代购、大量、店铺、厂家、直发、一手"等。商品描述中包含这些关键词时，职业度评分会被扣减。可拖拽排序，但不影响匹配逻辑（仅影响展示顺序）。

### Q7：数据质量分级是什么意思？
**A**：评估器根据卖家数据完整性分三级：full（3+ 维度有效）正常 4 维加权；partial（1-2 维度有效）仅有效维度归一化加权；insufficient（0 维度有效）仅价格维度保守评分。这避免了卖家数据缺失时给出虚假高分。

### Q8：动态 buffer 是如何工作的？
**A**：基于 4 维分数的标准差（std）。各维度分数接近（std 小）时 buffer=50，允许高分；某维度远低于其他（std 大）时 buffer=30，严格拉低总分。这防止了"3 维 100 分 + 1 维 0 分"仍得到 75 分的高分掩盖问题。

### Q9：AI 多轮优化建议多久生成一次？
**A**：每 `ai_suggestion_interval` 轮（默认 5 轮）生成一次。太小浪费 token，太大反馈滞后。生成后会调用 LLM 分析累积的运行数据，输出趋势洞察与策略调优方向，与单轮结论互补。

### Q10：保存后立即生效吗？
**A**：是。保存接口写盘后调用 `reload_config()` 重置单例，评估器 `evaluate()` 每次调用都从 `get_config()` 实时读取配置。无需重启服务。

### Q11：权重归一化算法是什么？
**A**：前端"一键归一化"按钮的算法（EvalRules.tsx 第 130-146 行）：
```
factor = 100 / weightsTotal
newWeight = Math.round(weight * factor)
```
例如权重 `[25, 35, 25, 25]`（总和 110），factor=100/110≈0.909，归一化后 `[23, 32, 23, 23]`（总和 101，因 Math.round 四舍五入）。如果归一化后总和仍非 100，会微调最大权重项补差。

### Q12：数据质量分级的 valid_dims 如何判定？
**A**：`_get_valid_dimensions(seller)` 检测卖家数据有效性：
- **professional**：`on_sale_count >= 1` 或 `post_count_30d >= 1`
- **credit**：`credit_score >= 400` 或 `register_days >= 1`
- **dispute**：默认有效（闲鱼不公开差评数）
- **price**：始终有效（来自 item）

价格维度始终有效，因此最多 4 维有效，最少 1 维有效。`len(valid_dims) >= 4` 走 full 模式，`>= 2` 走 partial 模式，否则走 insufficient 模式。

### Q13：partial 模式下为什么最高只能 80 分？
**A**：partial 模式施加 0.8 系数惩罚（`total = min(int(capped * 0.8), 80)`）。原因：
- 数据不完整的卖家风险更高（缺失维度可能隐藏问题）
- 80 分是 auto_buy_score 的硬阈值，partial 模式下无法触发自动抢单
- 仍可达到 pass_score（60 分）触发通知，用户手动审查

这确保数据不足的卖家不会因部分维度高分而获得虚假的高总分。
