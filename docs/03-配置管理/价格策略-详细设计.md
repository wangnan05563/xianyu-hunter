## 2. 功能概述

**一句话说明**：通过 4 种独立开关的价格策略（硬性上限、硬性下限、低于市场参考价、同类低价 TopN）对采集到的闲鱼商品进行价格维度过滤，并实时以直方图形式预览策略命中分布。

**核心价值**：
- 防止"1 元引流"陷阱（硬性下限策略）
- 避免高价商品误入评估流程（硬性上限策略）
- 自动剔除明显偏离市场中位数的商品（低于市场参考价策略）
- 仅保留同类中价格最低的前 N 个商品（TopN 策略）
- 通过 ECharts 直方图实时可视化策略命中情况，所见即所得

## 3. 用户场景

### 场景 1：二手手机捡漏
用户监控"iPhone 13 128G"，希望只接收 ¥1500–¥4000 价格区间的商品。配置 `enabled_max=true, max_price=4000, enabled_min=true, min_price=1500`，超出区间的商品会被直接过滤，不再进入评估流程。

### 场景 2：配件类商品防 1 元引流
用户监控"苹果原装充电器"，市场上存在大量 ¥1 标价引流商品。开启 `enabled_min=true, min_price=20`，1 元商品直接被过滤，避免无意义的通知打扰。

### 场景 3：同类低价 TopN 筛选
用户希望只关注同类商品中价格最低的 5 个。开启 `enabled_top_n=true, top_n=5`，每次采集后只有最便宜的前 5 个会保留下来，其余被过滤。

## 7. 业务逻辑

### 7.1 4 种策略 `check()` 逻辑

位置：`src/xianyu_hunter/modules/price_strategy.py` `PriceStrategy.check()` 方法（第 69-116 行）

策略按顺序执行，任一策略拒绝都会将 `pass_` 标记为 `False` 并记录 `reasons`：

1. **硬性上限**：`max_price is not None and item.price > max_price` → 拒绝，理由 `price {p} > max {m}`
2. **硬性下限**：`min_price is not None and item.price < min_price` → 拒绝，理由 `price {p} < min {m}`
3. **低于市场参考价**：需同时满足 `market_ratio < 1.0`、`market.median_price is not None`、`market.sample_size >= 3`（至少 3 个样本）、`item.price > market.median_price * market_ratio` → 拒绝，理由 `price {p} > median*ratio {v}`
4. **同类 TopN**：需 `market.sample_size > top_n`，再从 `market.all_prices` 计算 `cheaper_count = sum(1 for p in all_prices if p < item.price)`，若 `cheaper_count >= top_n` → 拒绝，理由 `not_in_top_{n} (cheaper_count={c})`

### 7.2 校验规则
- **样本数门槛**：低于市场参考价策略要求 `sample_size >= 3`，避免样本过少导致中位数失真。
- **TopN 样本门槛**：TopN 策略要求 `sample_size > top_n`，否则不应用（避免样本数小于 N 时全部拒绝）。
- **market_ratio 范围**：策略仅在 `market_ratio < 1.0` 时生效（≥1.0 意味着"高于市场价"才拒绝，与策略语义不符）。

### 7.3 热更新机制
- 前端保存时调用 `POST /api/config/save`，后端写盘后调用 `reload_config()` 重置单例 `_config = None`，下次 `get_config()` 触发完整重载。
- 评估调度流程每次执行都通过 `get_config().price_strategy` 实时获取最新配置，无需重启服务。
- 写盘失败时自动从刚生成的备份恢复，保证配置文件不损坏。

### 7.4 实时直方图预览算法
前端在 `previewResults` 中按区间估算策略命中：
1. 对每个直方图 bin，解析 bin 标签为价格数值（处理 `k`/`+` 后缀）。
2. 仅应用硬性上限与硬性下限策略估算（市场价比与 TopN 需要运行时上下文，前端无法预览）。
3. 累计 `pass` / `reject` / `total` 三个统计值在右侧 Statistic 卡片展示。

### 7.5 与评估流程的集成关系

价格策略在评估调度流程中作为**前置过滤层**，位于 `Evaluator.evaluate()` 之前：

```
搜索采集 → 价格策略.check() → [通过] → Evaluator.evaluate() → [评分≥pass_score] → 通知/抢单
                              ↓ [拒绝]
                              记录 reasons，跳过评估（节省 LLM token 与算力）
```

**为什么前置过滤**：
- 被价格策略拒绝的商品（如 1 元引流、超上限）即使卖家评分高也无意义，提前过滤可避免调用 AI 评估消耗 token。
- `PriceVerdict.reasons` 会被写入评估记录的 `reject_reasons` 字段，便于后续审计与策略调优。
- 价格策略与评估规则**完全解耦**：价格策略只看 `item.price` 与 `MarketContext`，不依赖卖家数据；评估规则则综合 4 维数据。

### 7.6 直方图接口 `/api/price/histogram` 详解

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `range_hours` | `int` | `168` | 统计时间窗口（小时），168=7 天 |
| `bins` | `int` | `20` | 直方图分桶数量 |

**响应字段**：
- `bins: string[]`：桶标签数组（如 `["0-100", "100-200", ...]`）
- `counts: number[]`：每个桶的商品数量
- `prices: number[]`：每个桶的代表价格（用于 markLine）

**降级策略**：接口失败时前端使用 `mockHistogram()` 生成 20 个桶的模拟数据（价格区间 0-10000），保证 UI 可用，并在控制台输出 warning。

### 7.7 策略命中估算的边界情况

`previewResults` 在以下边界情况下会跳过估算：
- **bin 标签无法解析**：如 `"10000+"`（含 `+` 后缀）会被解析为 10000，但 `"未知"` 等非数字标签会被跳过。
- **策略全部关闭**：所有 bin 都标记为 pass，`reject=0`。
- **max_price < min_price**：用户误配置时，所有 bin 都会被标记为 reject（同时被上下限拒绝），UI 会通过 Diff 预览提示。

## 9. 常见问题 FAQ

### Q1：为什么我设置了"低于市场参考价 80%"但没有商品被过滤？
**A**：该策略要求至少 3 个同类样本才会生效（`sample_size >= 3`）。如果当前关键词下采集到的商品少于 3 个，中位数无法稳定计算，策略自动跳过。请检查搜索结果数量或等待更多采集。

### Q2：TopN 策略为什么有时不生效？
**A**：TopN 策略要求 `sample_size > top_n`。例如设置 `top_n=5` 但同关键词只有 5 个商品时，策略不生效；需要有 6 个以上商品才会过滤掉第 6 名之后的商品。

### Q3：4 个策略可以同时开启吗？
**A**：可以，4 个策略完全独立，按顺序执行。任一策略拒绝即视为过滤，拒绝理由会累计到 `reasons` 列表，便于排查。

### Q4：直方图为什么显示模拟数据？
**A**：直方图通过 `/api/price/histogram` 接口获取最近 7 天数据。接口失败（如服务未启动、数据库为空）时降级为模拟数据展示，保证 UI 可用。模拟数据仅用于演示策略效果，不反映真实采集情况。

### Q5：保存配置后需要重启服务吗？
**A**：不需要。保存接口在写盘后调用 `reload_config()` 重置单例，评估调度流程下次执行时自动获取新配置。响应中 `restart_required=true` 仅是建议提示（针对长跑任务可能继续使用旧配置直至下一轮）。

### Q6：修改时不小心改错了怎么回滚？
**A**：每个数值字段右侧都有回滚按钮（仅当值与原始值不同时显示），点击即可单独回滚该字段。若已保存，可通过"配置版本管理"页面一键回滚到上一版本，每次保存都会自动创建带时间戳的备份。

### Q7：market_ratio 设置 1.0 为什么不生效？
**A**：策略代码中显式判断 `market_ratio < 1.0` 才生效。1.0 意味着"高于市场价才拒绝"，与策略"低于市场参考价"的语义相反。如需"高于市场价过滤"，请使用硬性上限策略。

### Q8：价格策略与评估规则是什么关系？
**A**：价格策略是评估流程的**前置过滤**，先过滤掉明显不合理的价格，再进入评估器（Evaluator）做 4 维评分。被价格策略拒绝的商品不会进入评估流程，节省算力。

### Q9：直方图中红色柱子代表什么？
**A**：红色（`#ff4d4f`）表示该价格区间的商品会被当前策略过滤；绿色（`#52c41a`）表示通过。直方图下方的黄色（`#faad14`）和红色 markLine 分别标记下限和上限位置。

### Q10：为什么前端直方图只预览了硬性上下限策略？
**A**：低于市场参考价和 TopN 策略需要运行时 `MarketContext`（中位数、样本数、全价格列表），前端在配置页面无法获取这些上下文，因此直方图仅按硬性上下限估算。完整 4 策略效果在采集调度流程中实时计算。

### Q11：直方图的 bin 标签格式是什么？如何解析？
**A**：后端返回的 bin 标签格式为 `"下限-上限"`（如 `"100-200"`）。前端 `previewResults` 中用 `parseFloat(bin.split('-')[0])` 解析下限作为代表价格。对于 `"10000+"` 这种带 `+` 后缀的开放式桶，会先 `replace('+', '')` 再解析。无法解析的桶会被跳过，不影响其他桶的估算。

### Q12：价格策略与"搜索参数"中的排序方式有什么区别？
**A**：搜索参数的 `sort_type=price_asc` 是让闲鱼搜索 API 返回价格升序结果（影响采集顺序）；价格策略的 `enabled_min/enabled_max` 是对采集到的商品做过滤（影响是否进入评估）。两者**互补**：先用排序优化采集（便宜优先），再用价格策略过滤（剔除异常值），双重保障。

### Q13：MarketContext 的数据来源是什么？
**A**：`MarketContext` 由调度流程在同关键词下所有采集到的商品中计算得出：
- `median_price`：同关键词商品价格中位数
- `sample_size`：同关键词商品样本数
- `all_prices`：所有商品价格列表（升序）
- `cheaper_seller_count`：通过 `cheaper_count_for(price)` 实时计算

数据来源是搜索 API 返回的同关键词商品列表，不依赖外部市场价格 API。

### Q14：top_n 策略中"同类"是如何定义的？
**A**："同类"指**同一搜索关键词**下的商品。例如监控关键词"iPhone 13 128G"，所有采集到的该关键词商品都属于同类。TopN 策略在该同类集合中保留价格最低的前 N 个，其余被过滤。跨关键词的商品不参与 TopN 计算。

### Q15：价格策略配置错了导致所有商品被过滤怎么办？
**A**：可以通过三种方式恢复：
1. **字段级回滚**：每个数值字段右侧有回滚按钮，单独恢复某个字段。
2. **整体重置**：点击顶部"重置"按钮，恢复所有字段到上次保存的值。
3. **版本回滚**：通过"配置版本管理"页面回滚到上一版本备份（每次保存都会自动创建带时间戳的备份，最多保留 10 个）。

### Q16：market_ratio 设为 0.5 会怎样？
**A**：意味着"价格高于市场价 50% 才拒绝"。例如市场中位数 1000 元，商品价格 1500 元（=1000×1.5）才会被拒绝。这相对宽松，适合希望接受略高于市场价商品的场景。注意仍需 `sample_size >= 3` 才生效。

### Q17：4 种策略的执行顺序是什么？会短路吗？
**A**：执行顺序固定为：硬性上限 → 硬性下限 → 低于市场参考价 → 同类 TopN。**会短路**——任一策略拒绝后，`pass_` 标记为 False 并记录 reason，但后续策略仍会继续执行（不 return），以便累计所有命中原因。这意味着一个商品可能同时命中多个策略（如既超上限又不在 TopN），所有 reason 都会写入 `PriceVerdict.reasons` 列表，便于排查。

### Q18：直方图的 markLine 颜色代表什么？
**A**：markLine 用于在直方图上标记策略阈值位置：
- **黄色 markLine**（`#faad14`）：标记 `min_price` 下限位置
- **红色 markLine**（`#ff4d4f`）：标记 `max_price` 上限位置
当用户拖动 Slider 调整上下限时，markLine 位置实时移动，下方的柱状颜色（绿/红）也立即重新计算。

### Q19：PriceConfig 的 has_any_rule() 方法有什么用？
**A**：`has_any_rule()` 判断是否配置了任一价格规则（min/max/market_ratio/top_n 至少一个非 None）。调度流程在采集前会先调用此方法，若返回 False 则跳过价格策略检查（直接通过），避免无意义的方法调用开销。这是一个性能优化，避免在未配置价格策略时仍执行 4 个 if 判断。

### Q20：保存配置时 restart_required=true 需要重启吗？
**A**：不需要。`restart_required=true` 仅是**建议提示**，表示长跑任务可能继续使用旧配置直至下一轮调度。实际上保存接口已调用 `reload_config()` 重置单例，新配置立即生效。建议提示是给用户一个心理预期——如果有正在执行的任务，它可能会用旧配置完成本轮，下一轮才用新配置。

### Q21：硬性上限和硬性下限可以同时关闭吗？
**A**：可以。4 个策略开关完全独立，全部关闭时 `PriceConfig.has_any_rule()` 返回 False，调度流程会跳过价格策略检查（直接通过）。这种情况下所有商品都进入评估流程，依赖评估规则做过滤。适合对价格不敏感、希望综合评估的场景。

### Q22：直方图接口 `/api/price/histogram` 的数据来源是哪里？
**A**：数据来自数据库中近 7 天（`range_hours=168`）的采集记录。后端按 `item.price` 字段分桶统计，每个桶代表一个价格区间。如果系统刚部署或近 7 天无采集记录，接口返回空数组，前端降级为模拟数据展示。

### Q23：market_ratio 和 TopN 策略可以同时开启吗？
**A**：可以，但需要注意两者都依赖 `MarketContext`（同关键词样本）。如果同关键词商品少于 3 个，market_ratio 策略自动跳过；如果少于 top_n+1 个，TopN 策略自动跳过。两者同时生效时，商品需同时满足"价格不高于市场价×ratio"且"在 TopN 内"才通过。

### Q24：PriceVerdict.reasons 中的 reason 格式是什么？
**A**：reason 是字符串列表，每种策略有固定格式：
- 硬性上限：`"price {p} > max {m}"`（如 `"price 12000 > max 10000"`）
- 硬性下限：`"price {p} < min {m}"`（如 `"price 50 < min 100"`）
- 市场参考价：`"price {p} > median*ratio {v}"`（如 `"price 1500 > median*ratio 1200"`）
- TopN：`"not_in_top_{n} (cheaper_count={c})"`（如 `"not_in_top_5 (cheaper_count=8)"`）

格式固定便于日志分析和 Dashboard 展示。

### Q25：价格策略配置保存后多久生效？
**A**：立即生效。保存接口写盘后调用 `reload_config()` 重置单例，下一轮调度流程通过 `get_config().price_strategy` 获取最新配置。正在执行的调度轮次可能仍用旧配置完成（取决于执行阶段），但下一轮必定用新配置。无需重启服务。

### Q26：为什么 PriceConfig 用 dataclass 而非 Pydantic 模型？
**A**：`PriceConfig` 是运行时 dataclass（`@dataclass`），`PriceStrategyConfig` 是 Pydantic 模型。区别：
- **Pydantic 模型**：用于配置文件解析与校验，支持 YAML 序列化/反序列化、字段校验、类型转换。
- **dataclass**：用于运行时计算，轻量级，无校验开销，适合在 `PriceStrategy.check()` 中传递参数。

调度流程启动时从 `PriceStrategyConfig`（Pydantic）转换为 `PriceConfig`（dataclass）传入 `PriceStrategy`，分离配置层与运行时层。

### Q27：4 种策略的拒绝率如何统计？
**A**：调度流程在每次价格策略检查后记录 `PriceVerdict` 到数据库，Dashboard 提供"价格策略拒绝率"统计：
- `pass_count / total_count` = 通过率
- 按 reason 分类统计（如"超上限"占比、"1 元引流"占比）
- 按时间维度展示趋势（折线图）

用户可根据拒绝率调优策略：如果拒绝率 > 90%，说明策略过严；如果 < 10%，说明策略过松。

### Q28：直方图接口失败时会显示什么？
**A**：接口失败时前端调用 `mockHistogram()` 生成模拟数据：
- 20 个桶，价格区间 0-10000，每桶 500 元
- 桶内商品数按正态分布模拟（中间多、两端少）
- 控制台输出 `console.warn('histogram API failed, using mock data')`

模拟数据仅用于演示策略效果（拖动 Slider 时直方图颜色变化），不反映真实采集情况。用户看到模拟数据时应检查后端服务状态。

### Q29：market_ratio 设为 0.9 和 0.7 有什么区别？
**A**：
- `market_ratio=0.9`：价格高于市场价 90% 就拒绝。例如市场中位数 1000 元，商品价格 > 900 元被拒绝。**严格**，仅保留低于市场价 10% 以上的商品。
- `market_ratio=0.7`：价格高于市场价 70% 才拒绝。商品价格 > 700 元被拒绝。**宽松**，允许接近市场价的商品通过。

ratio 越小越严格（拒绝越多），越大越宽松。建议从 0.8 开始，根据拒绝率调整。

### Q30：价格策略和评估规则中的价格维度有什么区别？
**A**：
- **价格策略**（`price_strategy`）：硬性过滤，只看 `item.price` 与 `MarketContext`，通过/拒绝二元判定，拒绝的商品不进入评估。
- **评估规则的价格维度**（`eval.weights.price`）：软性评分，计算 `price_score`（0-100 分），与其他 3 维加权汇总。

两者**互补**：价格策略做粗筛（剔除明显异常），评估规则做细评（综合评分）。被价格策略拒绝的商品不会进入评估，因此不会消耗 AI 评估 token。

### Q31：TopN 策略中 all_prices 是如何排序的？
**A**：`MarketContext.all_prices` 在调度流程构建 `MarketContext` 时按升序排序。`cheaper_count_for(price)` 通过 `sum(1 for p in all_prices if p < price)` 计算比目标价格便宜的卖家数。由于 `all_prices` 已排序，可用二分查找优化（`bisect_left`），但当前实现用线性遍历（商品数通常 < 100，性能足够）。

### Q32：价格策略配置变更后，已采集但未评估的商品会用新策略吗？
**A**：取决于评估阶段。如果商品已通过价格策略检查但尚未完成评估，会用旧策略结果（已通过）。下一轮采集的新商品才用新策略。`reload_config()` 重置单例后，`get_config().price_strategy` 返回新配置，但已进入评估流程的商品不会重新检查价格策略。

### Q33：MarketContext 的 cheaper_seller_count 字段有什么用？
**A**：`cheaper_seller_count` 记录比当前商品更便宜的卖家数，主要用于 TopN 策略判定。`cheaper_count_for(price)` 方法实时计算：如果 `cheaper_count >= top_n`，说明当前商品不在 TopN 内，会被拒绝。这个字段也用于 Dashboard 展示"价格竞争力"指标（比 X% 的同类商品便宜）。

### Q34：直方图预览的 pass/reject 统计准确吗？
**A**：仅硬性上下限策略的统计是准确的（基于 bin 标签价格直接判断）。市场参考价和 TopN 策略无法预览（依赖运行时 `MarketContext`）。因此 `reject` 计数可能少于实际拒绝数——实际运行时这两个策略会额外拒绝部分商品。直方图预览主要用于直观展示上下限策略的效果。

### Q35：价格策略的 4 个策略可以单独禁用吗？
**A**：可以。每个策略有独立的 `enabled_*` 开关：
- `enabled_max`：硬性上限开关
- `enabled_min`：硬性下限开关
- `enabled_market_ratio`：市场参考价开关
- `enabled_top_n`：TopN 开关

关闭某个策略后，该策略的阈值字段仍保留在配置中（便于重新开启），但 `check()` 时会跳过该策略的判定。`PriceConfig` 中对应字段为 `None`，`has_any_rule()` 检查时也会忽略 `None` 字段。

### Q36：PriceVerdict 的 pass_ 字段命名为什么带下划线？
**A**：`pass_` 是 Python 关键字 `pass` 的变体（加下划线避免冲突）。这是 Python 命名约定，用于保留关键字作为属性名。在代码中访问 `verdict.pass_` 而非 `verdict.pass`，后者会触发 `SyntaxError`。类似命名的还有 `class_`、`import_` 等。

### Q37：直方图的 bins 参数最大支持多少？
**A**：后端未硬编码上限，但建议 ≤ 50。过多的 bins 会导致每个桶内商品数过少（甚至为 0），直方图失去统计意义。默认 20 是经验值，平衡粒度与可读性。前端 InputNumber 的 `min=10, max=50`，超出范围会被前端校验拦截。

### Q38：价格策略保存后能撤销吗？
**A**：可以。每次保存都会自动创建带时间戳的备份文件（`config.yaml.bak.YYYYMMDD-HHMMSS`），最多保留 10 个。通过"配置版本管理"页面可查看所有备份并一键回滚到任意历史版本。回滚操作本身也会创建新备份（标记为"回滚来源"），确保操作可追溯。

### Q39：价格策略与"任务管理"中的关键词有什么关系？
**A**：价格策略是**全局配置**，对所有任务的所有关键词生效。"任务管理"中的关键词决定"采集哪些商品"，价格策略决定"过滤哪些商品"。例如监控关键词"iPhone 13"和"iPad Air"，两个关键词采集的商品都会应用同一套价格策略。如果需要按关键词差异化配置，建议通过 TopN 策略（按同类最低价过滤）实现，而非全局上下限。
