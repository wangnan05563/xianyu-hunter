## 2. 功能概述

**一句话说明**：通过 4 种独立开关的价格策略（硬性上限、硬性下限、低于市场参考价、同类低价 TopN）对采集到的闲鱼商品进行价格维度过滤，并实时以直方图形式预览策略命中分布。

**核心价值**：
- 防止"1 元引流"陷阱（硬性下限策略）
- 避免高价商品误入评估流程（硬性上限策略）
- 自动剔除明显偏离市场中位数的商品（低于市场参考价策略）
- 仅保留同类中价格最低的前 N 个商品（TopN 策略）
- 通过 ECharts 直方图实时可视化策略命中情况，所见即所得

**配置存储模型**（项目硬约束：YAML 文件 + 内存单例 + 任务级覆盖三态合并）：
- **全局配置**：`config/config.yaml` 中 `price_strategy:` 段，Pydantic `PriceStrategyConfig` 校验，进程内单例 `_config` 缓存
- **任务级覆盖**：`tasks.price_config` JSON 字段（DB Text），运行时深度合并到全局配置
- **热更新**：`POST /api/config/save` 写盘后调用 `reload_config()` 重置 `_config = None`，下次 `get_config()` 触发完整重载

## 3. 用户场景

### 场景 1：二手手机捡漏
用户监控"iPhone 13 128G"，希望只接收 ¥1500–¥4000 价格区间的商品。配置 `enabled_max=true, max_price=4000, enabled_min=true, min_price=1500`，超出区间的商品会被直接过滤，不再进入评估流程。

### 场景 2：配件类商品防 1 元引流
用户监控"苹果原装充电器"，市场上存在大量 ¥1 标价引流商品。开启 `enabled_min=true, min_price=20`，1 元商品直接被过滤，避免无意义的通知打扰。

### 场景 3：同类低价 TopN 筛选
用户希望只关注同类商品中价格最低的 5 个。开启 `enabled_top_n=true, top_n=5`，每次采集后只有最便宜的前 5 个会保留下来，其余被过滤。

### 场景 4：任务级价格策略覆盖
用户对全局配置了 `min_price=100, max_price=10000`，但有一个监控"iPhone 15 Pro Max"的任务需要单独放宽到 `min_price=3000, max_price=15000`。在该任务的 `price_config` 字段中存储 `{min_price: 3000, max_price: 15000}`，调度时优先使用任务级字段，全局配置作为兜底。

### 场景 5：直方图预览策略效果
用户在价格策略页面拖动 `max_price` Slider，右侧直方图实时重新计算柱状颜色（被过滤的桶红色、通过的桶绿色），并刷新「总商品数 / 通过 / 过滤」三个统计值，所见即所得。

#### 5.2.1 `bins` 参数语义

| 取值 | 行为 | 模式字段 |
|------|------|----------|
| `0`（默认） | 走固定刻度分桶 `_PRICE_TICKS = [0, 50, 100, 200, 500, 1000, 2000, 5000, 10000, 20000]`，共 10 个桶 | `mode: "fixed"` |

| 其他 | 等同 `0`，走固定刻度 | `mode: "fixed"` |

> **重要**：v1.0 文档写参数 `range_hours=168`，**实际接口没有该参数**。时间窗口（昨日/7日/30日）由后端在 `summary.compare` 字段中固定返回。

#### 5.2.2 响应字段详解


```python
class MarketContext:
    """市场参考上下文（采集器提供）"""
    median_price: float | None = None          # 同关键词中位数
    cheaper_seller_count: int = 0              # 比本商品更便宜的卖家数（逐商品计算）

    all_prices: list[float] | None = None      # 所有商品价格列表（排序后），供 TopN 策略逐商品计算

        return sum(1 for p in self.all_prices if p < price)
```

## 7. 业务逻辑

### 7.1 4 种策略 `check()` 逻辑

位置：`src/xianyu_hunter/modules/price_strategy.py` `PriceStrategy.check()` 方法（第 69-116 行）

策略按顺序执行，任一策略拒绝都会将 `pass_` 标记为 `False` 并记录 `reasons`（**不会短路**，所有命中策略都会写入 reasons，便于排查）：

1. **硬性上限**：`max_price is not None and item.price > max_price` → 拒绝，理由 `price {p} > max {m}`
2. **硬性下限**：`min_price is not None and item.price < min_price` → 拒绝，理由 `price {p} < min {m}`
3. **低于市场参考价**：需同时满足 `market_ratio is not None`、`market_ratio < 1.0`、`market is not None`、`market.median_price is not None`、`market.sample_size >= 3`（至少 3 个样本）、`item.price > market.median_price * market_ratio` → 拒绝，理由 `price {p} > median*ratio {v}`
4. **同类 TopN**：需 `top_n is not None`、`market is not None`、`market.sample_size > top_n`，再从 `market.all_prices` 计算 `cheaper = market.cheaper_count_for(item.price)`（fallback 到 `market.cheaper_seller_count`），若 `cheaper >= top_n` → 拒绝，理由 `not_in_top_{n} (cheaper_count={c})`

### 7.2 校验规则
- **样本数门槛**：低于市场参考价策略要求 `sample_size >= 3`，避免样本过少导致中位数失真。
- **TopN 样本门槛**：TopN 策略要求 `sample_size > top_n`，否则不应用（避免样本数小于 N 时全部拒绝）。
- **market_ratio 范围**：策略仅在 `market_ratio < 1.0` 时生效（≥1.0 意味着"高于市场价"才拒绝，与策略语义不符）。

### 7.3 热更新机制（项目硬约束）

价格策略遵循项目硬约束"配置存储：YAML 文件 + 内存单例 + 任务级覆盖三态合并"。

#### 7.3.1 三态模型

| 层级 | 存储介质 | 数据结构 | 生命周期 |
|------|----------|----------|----------|
| 全局配置（YAML） | `config/config.yaml` | `price_strategy:` 段 | 持久化，跨重启 |
| 全局配置（单例） | `yaml_config._config: AppConfig \| None` | `AppConfig.price_strategy: PriceStrategyConfig` | 进程内单例，热更新时重置 |
| 任务级覆盖 | `tasks.price_config` JSON | `dict` 子集 | 持久化到 DB，按任务维度隔离 |

#### 7.3.2 单例加载与重置

```python
# src/xianyu_hunter/infra/yaml_config.py

_config: AppConfig | None = None

def get_config() -> AppConfig:
    """单例获取 AppConfig"""
    global _config
    if _config is None:
        _config = _load_all()  # 加载 config/*.yaml + 深度合并
    return _config

def reload_config() -> AppConfig:
    """热更新：重置单例，下次 get_config() 触发完整重载"""
    global _config
    _config = None
    return get_config()
```

#### 7.3.3 保存流程

1. 前端 `confirmSave()` → `POST /api/config/save {payload, dry_run: false}`
2. 后端 `_load_yaml()` 读取当前 `config.yaml` → `_deep_merge(new, payload)` → `_validate(new)` 校验
3. 创建带时间戳备份 `config/backups/config.yaml.bak.YYYYMMDD-HHMMSS`
4. 写盘 `CONFIG_FILE.write_text(_dump_yaml(new))`
5. 调用 `reload_config()` 重置单例 `_config = None`
6. 写盘失败时从刚生成的备份恢复，保证配置文件不损坏
7. 返回 `{ok, saved_at, diffs, backup, restart_required: true, restart_note}`

> **注意**：`restart_required=true` 仅是**建议提示**——配置已通过 `reload_config()` 立即生效，但正在执行的调度轮次可能继续使用旧配置直至本轮结束，下一轮必定用新配置。无需重启服务。

### 7.4 实时直方图预览算法

前端 `previewResults`（`PriceStrategy.tsx:116-138`）按区间估算策略命中：

1. 对每个直方图 bin，解析 bin 标签为价格数值。
2. 解析逻辑：`Number.parseFloat(bin.replaceAll('k', '').replaceAll('+', '')) * (bin.includes('k') ? 1000 : 1)`，例如 `"1k"` → 1000，`"20k+"` → 20000。
3. 仅应用硬性上限与硬性下限策略估算（市场价比与 TopN 需要运行时上下文，前端无法预览）。
4. 累计 `pass` / `reject` / `total` 三个统计值在右侧 Statistic 卡片展示。

**柱状颜色判定**（`chartOption.series[0].data`）：被过滤显示红色 `#ff4d4f`，通过显示绿色 `#52c41a`。

### 7.5 与评估流程的集成关系

价格策略在评估调度流程中作为**前置过滤层**，位于 `Evaluator.evaluate()` 之前：

```
搜索采集 → 价格策略.check() → [通过] → Evaluator.evaluate() → [评分≥pass_score] → 通知/抢单
                              ↓ [拒绝]
                              记录 reasons，跳过评估（节省 LLM token 与算力）
```

**为什么前置过滤**：
- 被价格策略拒绝的商品（如 1 元引流、超上限）即使卖家评分高也无意义，提前过滤可避免调用 AI 评估消耗 token。
- `PriceVerdict.reasons` 会被写入评估记录的 `reject_reasons` 字段，便于后续审计与策略调优。
- 价格策略与评估规则**完全解耦**：价格策略只看 `item.price` 与 `MarketContext`，不依赖卖家数据；评估规则则综合 4 维数据。

### 7.6 直方图接口 `/api/prices/histogram` 详解

> **v2.0 修正**：v1.0 文档写为 `/api/price/histogram`（单数）且参数与响应字段均与实现不符，本节为准。

#### 7.6.1 请求参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `bins` | `int` | `0` | 0=固定刻度分桶（10 个桶），20=自动分桶（20 个等宽桶） |
| `task_id` | `str \| None` | `None` | 任务 ID；为空或 `"all"` 时查全部任务，否则限定在该任务范围内 |

#### 7.6.2 响应字段

见 §5.2.2 完整响应结构。

#### 7.6.3 数据来源与统计逻辑

- **数据来源**：`items` 表中 `price` 字段非 NULL 的记录（按 `task_id` 过滤）
- **样本上限**：单次查询 `LIMIT 10000`（防大表撑爆内存）；时间对比基线 `LIMIT 2000`（按 `publish_time` 倒序）
- **固定刻度分桶**（`bins=0`）：使用预定义 `_PRICE_TICKS = [0, 50, 100, 200, 500, 1000, 2000, 5000, 10000, 20000]`，尾桶为 `[20000, +∞)`
- **自动分桶**（`bins=20`）：基于 P5/P95 百分位裁剪极端值 + 任务定价范围融合，分 20 个等宽桶，首尾桶吸收范围外的极端值（保证商品计数不丢失）
- **分位数算法**：`_percentile` 使用 NumPy 默认的线性插值算法
- **时间对比**：`compare.yesterday`/`last7d`/`last30d` 分别为近 1/7/30 日均价，`diff_pct` = (昨日均价 - 7日均价) / 7日均价 × 100

### 7.7 任务级价格策略覆盖机制（v2.0 新增）

#### 7.7.1 三态合并优先级

价格策略在调度时有 3 个数据源，按优先级从高到低合并：

```
任务级 min_price/max_price（DB 列，最高优先级）
       ↓ None 时回退
任务级 price_config dict（DB JSON 字段）
       ↓ None 时回退
全局 AppConfig.price_strategy（YAML 单例）
```

具体合并规则（`container.build_task_price_strategy` 与 `api_task_links._build_live_price_strategy` 实现一致）：

| 字段 | 任务级 DB 列 | 任务级 `price_config` dict | 全局配置 |
|------|--------------|----------------------------|----------|
| `min_price` | `TaskRow.min_price` 优先 | DB 列为 None 时取 `price_config.min_price` | 都为 None 时沿用全局 |
| `max_price` | `TaskRow.max_price` 优先 | DB 列为 None 时取 `price_config.max_price` | 都为 None 时沿用全局 |
| `market_ratio` | — | `price_config.market_ratio` 优先 | 沿用全局 |
| `top_n` | — | 不读取（**直接使用全局**） | 全局 `top_n` |
| `enabled_*` | — | 不读取（**PriceConfig 用 None 表达禁用**） | 全局 `enabled_*` 转换为 None/具体值 |

> **注意**：`top_n` 在 live 链路（`_build_live_price_strategy`）中直接使用全局值，不读 `price_config.top_n`。`build_task_price_strategy` 也未读取 `top_n`。这是当前实现的一致行为，未来如需任务级 top_n 覆盖，需在两个函数中同步补充。

#### 7.7.2 三个调用路径

| 路径 | 文件位置 | 触发场景 | 实现 |
|------|----------|----------|------|
| Worker 注入 | `container.build_worker_from_raw_task` | 调度器启动 / 任务注册时构造 `TaskWorker` | 调用 `build_task_price_strategy(raw)` 构造 `PriceStrategy` 注入 `worker.price` |
| 评估重算 | `container.build_task_price_strategy(raw)` | recompute / batch_evaluate / collection_service 三条评估写入路径 | 公共方法，避免逻辑漂移 |
| Live SSE 链路 | `api_task_links._build_live_price_strategy` | 实时搜索 SSE 流式响应中按 task_id 现取任务字段 | 独立函数，与 startup 注入路径行为一致 |

#### 7.7.3 三态语义（PATCH 任务时）

`PATCH /api/tasks/{id}` 时，`price_config` 字段使用 `model_dump(exclude_unset=True)` 区分三态：

- **未传** `price_config`：字段被排除，跳过更新（保留原覆盖）
- **传 `null`**：字段被包含，清除覆盖（`price_config` 设为 NULL，运行时回退全局）
- **传 `dict`**：字段被包含，JSON 序列化存 DB（设置/替换覆盖）

序列化逻辑见 `api_tasks._serialize_config_overrides`：`json.dumps(val) if val else None`（空 dict 也视为 None）。

#### 7.7.4 MarketContext 构建

`MarketContext` 由调度流程在同关键词下所有采集到的商品中计算（`worker._compute_market_context`）：

```python
def _compute_market_context(self, items: list) -> MarketContext | None:
    """从当前批次的商品中估算市场参考价"""
    prices = [i.price for i in items if getattr(i, "price", None) is not None]
    if len(prices) < 3:
        return None  # 样本不足，市场价比与 TopN 策略自动跳过
    prices.sort()
    n = len(prices)
    median = prices[n // 2] if n % 2 == 1 else (prices[n // 2 - 1] + prices[n // 2]) / 2
    return MarketContext(median_price=median, sample_size=n, all_prices=prices)
```

Live SSE 链路在 `api_task_links._build_live_price_strategy` 中复用同样逻辑（从当前批次 items 计算 median + all_prices）。

### 7.8 策略命中估算的边界情况

`previewResults` 在以下边界情况下会跳过估算：
- **bin 标签无法解析**：如 `"未知"` 等非数字标签会被 `Number.parseFloat` 解析为 `NaN`，比较时永远不命中（视为通过）。
- **策略全部关闭**：所有 bin 都标记为 pass，`reject=0`。
- **max_price < min_price**：用户误配置时，所有 bin 都会被标记为 reject（同时被上下限拒绝），UI 会通过 Diff 预览提示。

```typescript
const bins = data.bins.map(b => `${b.min}-${b.max ?? '+'}`)
const counts = data.bins.map(b => b.count)
```

## 10. 常见问题 FAQ

### Q1：为什么我设置了"低于市场参考价 80%"但没有商品被过滤？
**A**：该策略要求至少 3 个同类样本才会生效（`sample_size >= 3`）。如果当前关键词下采集到的商品少于 3 个，中位数无法稳定计算，策略自动跳过。请检查搜索结果数量或等待更多采集。

### Q2：TopN 策略为什么有时不生效？
**A**：TopN 策略要求 `sample_size > top_n`。例如设置 `top_n=5` 但同关键词只有 5 个商品时，策略不生效；需要有 6 个以上商品才会过滤掉第 6 名之后的商品。

### Q3：4 个策略可以同时开启吗？
**A**：可以，4 个策略完全独立，按顺序执行。任一策略拒绝即视为过滤，拒绝理由会累计到 `reasons` 列表，便于排查。**不会短路**——所有命中策略都会写入 reasons。

### Q4：直方图为什么显示为空 / 模拟数据？
**A**：这是 v2.0 标注的已知 Bug（§8.1）。后端 `/api/prices/histogram` 返回的 `bins` 是 `list[dict]`（含 `min`/`max`/`count`），前端判断 `data.counts`（实际不存在）导致 `setHistogram` 不被调用，直方图区域显示为空。修复方向见 §8.1。

### Q5：保存配置后需要重启服务吗？
**A**：不需要。保存接口在写盘后调用 `reload_config()` 重置单例，评估调度流程下次执行时自动获取新配置。响应中 `restart_required=true` 仅是建议提示（针对长跑任务可能继续使用旧配置直至下一轮）。

### Q6：修改时不小心改错了怎么回滚？
**A**：每个数值字段右侧都有回滚按钮（仅当值与原始值不同时显示），点击即可单独回滚该字段。若已保存，可通过"配置版本管理"页面一键回滚到上一版本，每次保存都会自动创建带时间戳的备份（保留最近 10 个）。

### Q7：market_ratio 设置 1.0 为什么不生效？
**A**：策略代码中显式判断 `market_ratio < 1.0` 才生效。1.0 意味着"高于市场价才拒绝"，与策略"低于市场参考价"的语义相反。如需"高于市场价过滤"，请使用硬性上限策略。

### Q8：价格策略与评估规则是什么关系？
**A**：价格策略是评估流程的**前置过滤**，先过滤掉明显不合理的价格，再进入评估器（Evaluator）做 4 维评分。被价格策略拒绝的商品不会进入评估流程，节省算力。

### Q9：直方图中红色柱子代表什么？
**A**：红色（`#ff4d4f`）表示该价格区间的商品会被当前策略过滤；绿色（`#52c41a`）表示通过。

### Q10：为什么前端直方图只预览了硬性上下限策略？
**A**：低于市场参考价和 TopN 策略需要运行时 `MarketContext`（中位数、样本数、全价格列表），前端在配置页面无法获取这些上下文，因此直方图仅按硬性上下限估算。完整 4 策略效果在采集调度流程中实时计算。

### Q11：MarketContext 的数据来源是什么？
**A**：`MarketContext` 由调度流程在同关键词下所有采集到的商品中计算得出（`worker._compute_market_context`）：
- `median_price`：同关键词商品价格中位数
- `sample_size`：同关键词商品样本数
- `all_prices`：所有商品价格列表（升序）
- `cheaper_seller_count`：通过 `cheaper_count_for(price)` 实时计算

数据来源是搜索 API 返回的同关键词商品列表，不依赖外部市场价格 API。样本数 < 3 时返回 `None`，市场价比与 TopN 策略自动跳过。

### Q12：top_n 策略中"同类"是如何定义的？
**A**："同类"指**同一搜索关键词**下的商品。例如监控关键词"iPhone 13 128G"，所有采集到的该关键词商品都属于同类。TopN 策略在该同类集合中保留价格最低的前 N 个，其余被过滤。跨关键词的商品不参与 TopN 计算。

### Q13：价格策略配置错了导致所有商品被过滤怎么办？
**A**：可以通过三种方式恢复：
1. **字段级回滚**：每个数值字段右侧有回滚按钮，单独恢复某个字段。
2. **整体重置**：点击顶部"重置"按钮，恢复所有字段到上次保存的值。
3. **版本回滚**：通过"配置版本管理"页面回滚到上一版本备份（每次保存都会自动创建带时间戳的备份，最多保留 10 个）。

### Q14：4 种策略的执行顺序是什么？会短路吗？
**A**：执行顺序固定为：硬性上限 → 硬性下限 → 低于市场参考价 → 同类 TopN。**不会短路**——任一策略拒绝后，`pass_` 标记为 False 并记录 reason，但后续策略仍会继续执行（不 return），以便累计所有命中原因。这意味着一个商品可能同时命中多个策略（如既超上限又不在 TopN），所有 reason 都会写入 `PriceVerdict.reasons` 列表，便于排查。

### Q15：PriceConfig 的 has_any_rule() 方法有什么用？
**A**：`has_any_rule()` 判断是否配置了任一价格规则（min/max/market_ratio/top_n 至少一个非 None）。调度流程在采集前会先调用此方法，若返回 False 则跳过价格策略检查（直接通过），避免无意义的方法调用开销。

### Q16：保存配置时 restart_required=true 需要重启吗？
**A**：不需要。`restart_required=true` 仅是**建议提示**，表示长跑任务可能继续使用旧配置直至下一轮调度。实际上保存接口已调用 `reload_config()` 重置单例，新配置立即生效。

### Q17：硬性上限和硬性下限可以同时关闭吗？
**A**：可以。4 个策略开关完全独立，全部关闭时 `PriceConfig.has_any_rule()` 返回 False，调度流程会跳过价格策略检查（直接通过）。这种情况下所有商品都进入评估流程，依赖评估规则做过滤。

### Q18：直方图接口 `/api/prices/histogram` 的数据来源是哪里？
**A**：数据来自数据库中 `items` 表的 `price` 字段（按 `task_id` 过滤，单次最多 10000 条）。后端按价格分桶统计，每个桶代表一个价格区间。如果系统刚部署或所选范围内无采集记录，接口返回空 `bins: []` 与 `summary.count=0`。

### Q19：market_ratio 和 TopN 策略可以同时开启吗？
**A**：可以，但需要注意两者都依赖 `MarketContext`（同关键词样本）。如果同关键词商品少于 3 个，market_ratio 策略自动跳过；如果少于 top_n+1 个，TopN 策略自动跳过。两者同时生效时，商品需同时满足"价格不高于市场价×ratio"且"在 TopN 内"才通过。

### Q20：PriceVerdict.reasons 中的 reason 格式是什么？
**A**：reason 是字符串列表，每种策略有固定格式：
- 硬性上限：`"price {p} > max {m}"`（如 `"price 12000 > max 10000"`）
- 硬性下限：`"price {p} < min {m}"`（如 `"price 50 < min 100"`）
- 市场参考价：`"price {p} > median*ratio {v}"`（如 `"price 1500 > median*ratio 1200"`，`v` 取整数）
- TopN：`"not_in_top_{n} (cheaper_count={c})"`（如 `"not_in_top_5 (cheaper_count=8)"`）

格式固定便于日志分析和 Dashboard 展示。

### Q21：价格策略配置保存后多久生效？
**A**：立即生效。保存接口写盘后调用 `reload_config()` 重置单例 `_config = None`，下一轮调度流程通过 `get_config().price_strategy` 获取最新配置。正在执行的调度轮次可能仍用旧配置完成（取决于执行阶段），但下一轮必定用新配置。无需重启服务。

### Q22：为什么 PriceConfig 用 dataclass 而非 Pydantic 模型？
**A**：`PriceConfig` 是运行时 dataclass（`@dataclass`），`PriceStrategyConfig` 是 Pydantic 模型。区别：
- **Pydantic 模型**：用于配置文件解析与校验，支持 YAML 序列化/反序列化、字段校验、类型转换。
- **dataclass**：用于运行时计算，轻量级，无校验开销，适合在 `PriceStrategy.check()` 中传递参数。

调度流程启动时从 `PriceStrategyConfig`（Pydantic）转换为 `PriceConfig`（dataclass）传入 `PriceStrategy`，分离配置层与运行时层。

### Q23：任务级 price_config 覆盖是如何生效的？
**A**：调度流程在构造 `TaskWorker` 时调用 `container.build_worker_from_raw_task(raw)`，内部调用 `build_task_price_strategy(raw)` 按 §7.7.1 三态合并优先级构造 `PriceStrategy` 实例并注入 `worker.price`。Live SSE 链路在 `_build_live_price_strategy(container, task_id, items)` 中按相同合并优先级独立构造。**两条路径行为一致**，避免逻辑漂移。

### Q24：任务级 price_config 支持哪些字段？
**A**：当前实现支持 `min_price`、`max_price`、`market_ratio` 三个字段的任务级覆盖。`top_n` 在两条调用路径中均**直接使用全局值**，不读 `price_config.top_n`（这是当前实现的一致行为）。`enabled_*` 开关也不在任务级覆盖范围内——`PriceConfig` 用 `None` 表达"禁用"，因此任务级覆盖一旦提供 `min_price` 就视为开启下限策略。

### Q25：直方图的 markLine 颜色代表什么？为什么我看不到？
**A**：markLine 用于在直方图上标记策略阈值位置：
- **黄色 markLine**（`#faad14`）：标记 `min_price` 下限位置
- **红色 markLine**（`#ff4d4f`）：标记 `max_price` 上限位置

但 v2.0 标注了已知 Bug（§8.2）：当前代码将 `markLine` 放在 `chartOption` 顶层而非 `series[0].markLine`，ECharts 不会渲染。修复方向是将 `markLine` 移入 `series[0]`。

### Q26：「刷新预览数据」按钮为什么没反应？
**A**：v2.0 标注的已知 Bug（§8.3）。按钮的 `onClick` 仅用 `setTimeout` 模拟 500ms 加载，然后 `message.success('预览已刷新')`，**没有调用 `priceApi.histogram()` 重新拉取数据**，也没有重新计算 `previewResults`。用户看到提示但直方图未变化。

### Q27：价格策略和评估规则中的价格维度有什么区别？
**A**：
- **价格策略**（`price_strategy`）：硬性过滤，只看 `item.price` 与 `MarketContext`，通过/拒绝二元判定，拒绝的商品不进入评估。
- **评估规则的价格维度**（`eval.weights.price`）：软性评分，计算 `price_score`（0-100 分），与其他 3 维加权汇总。

两者**互补**：价格策略做粗筛（剔除明显异常），评估规则做细评（综合评分）。被价格策略拒绝的商品不会进入评估，因此不会消耗 AI 评估 token。

### Q28：TopN 策略中 all_prices 是如何排序的？
**A**：`MarketContext.all_prices` 在调度流程构建 `MarketContext` 时按升序排序（`prices.sort()`）。`cheaper_count_for(price)` 通过 `sum(1 for p in all_prices if p < price)` 计算比目标价格便宜的卖家数。当前实现用线性遍历（商品数通常 < 100，性能足够），未做二分查找优化。

### Q29：MarketContext 的 cheaper_seller_count 字段有什么用？
**A**：`cheaper_seller_count` 是 `MarketContext` 的字段，记录比当前商品更便宜的卖家数，主要用于 TopN 策略判定。但实际调度流程中更倾向使用 `cheaper_count_for(price)` 方法（基于 `all_prices` 实时计算），`cheaper_seller_count` 字段是 fallback：当 `all_prices` 为空时才使用。

### Q30：直方图预览的 pass/reject 统计准确吗？
**A**：仅硬性上下限策略的统计是准确的（基于 bin 标签价格直接判断）。市场参考价和 TopN 策略无法预览（依赖运行时 `MarketContext`）。因此 `reject` 计数可能少于实际拒绝数——实际运行时这两个策略会额外拒绝部分商品。直方图预览主要用于直观展示上下限策略的效果。

### Q31：价格策略的 4 个策略可以单独禁用吗？
**A**：可以。每个策略有独立的 `enabled_*` 开关：
- `enabled_max`：硬性上限开关
- `enabled_min`：硬性下限开关
- `enabled_market_ratio`：市场参考价开关
- `enabled_top_n`：TopN 开关

关闭某个策略后，该策略的阈值字段仍保留在配置中（便于重新开启），但 `check()` 时会跳过该策略的判定（`PriceConfig` 对应字段为 `None`）。`has_any_rule()` 检查时也会忽略 `None` 字段。

### Q32：PriceVerdict 的 pass_ 字段命名为什么带下划线？
**A**：`pass_` 是 Python 关键字 `pass` 的变体（加下划线避免冲突）。这是 Python 命名约定，用于保留关键字作为属性名。在代码中访问 `verdict.pass_` 而非 `verdict.pass`，后者会触发 `SyntaxError`。类似命名的还有 `class_`、`import_` 等。

### Q33：直方图的 bins 参数最大支持多少？
**A**：后端未硬编码上限，但建议 ≤ 50。过多的 bins 会导致每个桶内商品数过少（甚至为 0），直方图失去统计意义。当前实现仅支持两种取值：`bins=0`（固定 10 个桶）和 `bins=20`（自动 20 个桶），其他值等同于 `0`。前端目前**没有** bins 输入框（v1.0 文档 Q37 描述有误），`bins=20` 硬编码在 `useEffect` 中。

### Q34：价格策略保存后能撤销吗？
**A**：可以。每次保存都会自动创建带时间戳的备份文件（`config/backups/config.yaml.bak.YYYYMMDD-HHMMSS`），最多保留 10 个。通过"配置版本管理"页面可查看所有备份并一键回滚到任意历史版本。回滚操作本身也会创建新备份，确保操作可追溯。

### Q35：价格策略与"任务管理"中的关键词有什么关系？
**A**：**全局价格策略**对所有任务的所有关键词生效；**任务级 price_config** 仅对该任务生效。"任务管理"中的关键词决定"采集哪些商品"，价格策略决定"过滤哪些商品"。如果需要按关键词差异化配置，可通过任务级 `price_config` 字段实现，或通过 TopN 策略（按同类最低价过滤）实现。

### Q36：直方图接口失败时会显示什么？
**A**：接口失败时（如服务未启动、网络异常）前端调用 `catch` 分支设置模拟数据：
```typescript
setHistogram({
  bins: ['0', '500', '1k', '2k', '3k', '5k', '8k', '10k', '15k', '20k+'],
  counts: [5, 12, 28, 35, 22, 18, 10, 6, 3, 1],
  prices: [],
})
```

模拟数据仅用于演示策略效果（拖动 Slider 时直方图颜色变化），不反映真实采集情况。但需注意 §8.1 Bug——即使接口成功，前端也可能因 `data.counts` 字段不存在而无法使用真实数据。
