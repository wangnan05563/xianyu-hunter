## 1. 引言

### 1.1 编写目的

本需求规格说明书定义「配置管理 → 评估规则」二级菜单的完整需求规格，作为前端/后端开发、测试与验收的唯一依据。

**目标读者**：
- 后端开发工程师：依据 §3-§6、§8、§10 进行模块实现与扩展
- 前端开发工程师：依据 §4、§9 进行页面开发
- 测试工程师：依据 §7、§11 编写测试用例与执行验收
- 项目经理：依据 §2、§11 进行范围与里程碑管理
- 智能客服 KB 训练：本文档与 [评估规则-详细设计.md](评估规则-详细设计.md) 共同作为 KB 检索素材

### 1.2 项目背景

闲鱼猎人（XianyuHunter）是一个闲鱼自动捡漏与抢单工具，已具备任务管理、商品采集、AI 评估、自动下单、多渠道通知等完整能力。

**评估规则是整个系统的决策核心**——决定采集到的商品是否值得推送、是否自动抢单。随着系统演进，评估规则模块从早期的"硬阈值 + 简单加权"演进为"4 维加权 + Sigmoid 渐进扣分 + 动态 buffer + AI Vision 多模态评估 + 任务级配置覆盖"的复杂决策系统，存在以下痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| API 路径不一致 | 评估明细 API 前缀为 `/api/evaluations`（复数），但早期文档误写为 `/api/eval` | 前端调用失败、KB 训练素材错误 |
| 动态 buffer 公式错误 | 实际为 `max(30, int(50 - std * 0.4))`，文档误写为 `50 - 20 * (std / 50)` | 评分计算偏差 |
| Sigmoid 参数说明错误 | `max_deduction` 由调用方传入（40/30），文档误称固定 100 | 公式理解偏差 |
| insufficient 模式逻辑错误 | 实际使用 `price(0.6) + popularity(0.4)` 双维度，文档误称仅价格维度 | 数据缺失场景评分失真 |
| 字段缺失 | `auto_collect_dedup_window_minutes`、`auto_collect_fail_pause_threshold` 未文档化 | 配置项无法维护 |
| 任务级覆盖无机制 | 单任务无法独立配置评估规则 | 高价值任务无法个性化 |
| AI 评估无缓存 | 同一商品重复评估浪费 token | 成本失控 |
| Prompt 无热更新 | 修改 Prompt 需重启服务 | 迭代效率低 |
| 价格区间无注入 | AI 评估缺少价格合理性参考 | 评估准确度不足 |
| 纯文本模型未适配 | 不支持 Vision 的模型强行传图导致 400 报错 | 评估失败率高 |
| 采集失败无退避 | 连续失败无暂停机制 | 配额浪费 |
| 阈值无建议算法 | 用户凭感觉设置 pass_score | 通过率失控 |

**解决方案**：通过 1 个前端页面（6 个 Card）+ 21 个 API 端点 + 3 个 Pydantic 模型，统一暴露评估规则的全生命周期管理能力；同时定义任务级 eval_config 覆盖合并语义、AI 评估缓存机制、Prompt 热更新、价格区间注入、Vision 能力检测、自动采集失败退避、F-15 阈值建议算法，**让评估规则可视化、可覆盖、可缓存、可降级、可建议**。

| 启动钩子外层 except 用 `logger.exception()` | 适用 | 评估器初始化不涉及；AI 评估异常捕获用 `logger.warning` 不丢失堆栈 |

## 2. 总体描述

### 2.1 产品定位

评估规则是闲鱼猎人的决策核心模块，负责对采集到的商品进行综合评分，决定：
1. 是否通过（`score >= pass_score`）→ 触发通知
2. 是否自动抢单（`score >= auto_buy_score` 且 `risk_level == LOW`）→ 触发全自动拍下

### 2.2 用户特征

| 用户角色 | 使用场景 | 技术水平 |
|----------|----------|----------|
| 普通用户 | 调整权重偏好、开关 AI 评估、查看分布热力图 | 低，需可视化引导 |
| 进阶用户 | 任务级配置覆盖、阈值建议、历史重算 | 中，理解评估逻辑 |
| 运维用户 | 采集统计监控、失败退避排查、Prompt 热更新 | 高，能读日志与 API |

### 2.3 运行环境

| 组件 | 环境 |
|------|------|
| 后端 | Python 3.10+ / FastAPI 0.136.3 / SQLite WAL |
| 前端 | React 18 + TypeScript 5.5 + Ant Design 5.21 + ECharts 5.5 |
| AI 服务 | OpenAI 兼容 API（DeepSeek/智谱/GPT-4 Vision 等） |
| 浏览器 | Chrome 90+ / Edge 90+ / WebView2 |

### 2.4 假设与依赖

- 假设用户已配置至少 1 个任务并完成 1 轮采集（否则热力图无数据）
- 假设 AI 评估依赖外部 LLM 服务可用（不可用时降级规则模拟）
- 假设 `evaluations` 表已通过迁移创建（`init_db()` 中初始化）
- 依赖 `api_config.py` 提供配置读写能力
- 依赖 `api_prompts.py` 提供 Prompt 热更新能力
- 依赖 `price_dashboard.sold_range` 提供价格区间查询

## 4. 功能需求

### FR-1：4 维权重配置

**需求描述**：用户可配置 4 维评分权重（professional/credit/dispute/price），权重和必须 = 100。

**输入**：
- `weights.professional`：int，默认 30
- `weights.credit`：int，默认 30
- `weights.dispute`：int，默认 25
- `weights.price`：int，默认 15

**校验规则**：
- 四项之和 = 100（Pydantic `_check_weight_sum`）
- 前端实时计算 `weightsTotal`，不等于 100 时显示 Alert + "一键归一化"按钮
- 归一化算法：`factor = 100 / weightsTotal; newWeight = Math.round(weight * factor)`

**输出**：保存后立即生效，下次 `evaluate()` 调用即用新权重。

**优先级**：P0

### FR-2：阈值配置

**需求描述**：用户可配置 6 项评估阈值。

**输入**：
- `thresholds.on_sale_count`：int，默认 30，职业卖家识别阈值
- `thresholds.post_count_30d`：int，默认 15，30 天发帖数阈值
- `thresholds.top_category_ratio`：float，默认 0.8，主营品类占比阈值
- `thresholds.credit_score_min`：int，默认 600，信用分下限（一票否决）
- `thresholds.bad_review_max`：int，默认 3，差评数上限（一票否决）
- `thresholds.register_days_min`：int，默认 30，注册天数下限

**校验规则**：无跨字段校验，各字段独立。

**输出**：保存后立即生效。

**优先级**：P0

### FR-3：双阈值控制

**需求描述**：用户可配置 `pass_score` 和 `auto_buy_score`，控制通知与自动抢单门槛。

**输入**：
- `pass_score`：int，默认 60，通过分数
- `auto_buy_score`：int，默认 80，自动抢单分数

**校验规则**：
- `pass_score <= auto_buy_score`（Pydantic `_check_score_order`）
- 前端双滑块联动校验，违反时显示红色 Alert 并禁用保存

**输出**：
- `score >= pass_score` → 触发 `EVAL_PASSED` 事件 → 通知用户
- `score >= auto_buy_score` 且 `risk_level == LOW` → 触发全自动拍下

**优先级**：P0

### FR-4：数据质量三级分级

**需求描述**：评估器根据卖家数据完整性分三级评估，避免数据缺失时给出虚假高分。

**分级策略**：

| 等级 | 有效维度数 | 评估策略 | 上限 |
|------|------------|----------|------|
| full | ≥ 4 | 正常 4 维加权 | 100 |
| partial | 2-3 | 仅有效维度归一化加权，0.8 系数惩罚 | 80 |
| insufficient | 1（仅 price） | `price(0.6) + popularity(0.4)` 双维度加权 | 65 |

**有效维度判定**（`_get_valid_dimensions`）：
- `professional`：`on_sale_count >= 1` 或 `post_count_30d >= 1`
- `credit`：`credit_score >= 400` 或 `register_days >= 1`
- `dispute`：`on_sale_count >= 1` 或 `register_days >= 1`
- `price`：始终有效（来自 item）

**优先级**：P0

### FR-5：Sigmoid 渐进扣分

**需求描述**：职业度维度使用 Sigmoid 函数替代硬阈值，避免评分在阈值附近跳变。

**公式**：
```
deduction = max_deduction / (1 + exp(-k * (value - threshold)))
```

**参数**：
- `k = 0.15`（控制过渡陡峭度）
- `max_deduction` 由调用方传入：
  - 在售数：`max_deduction = 40`，阈值 = `on_sale_count`
  - 30 天发帖数：`max_deduction = 30`，阈值 = `post_count_30d`

**示例**（在售数，阈值 30，max_deduction=40）：
- `on_sale=10` → 扣 ~1 分
- `on_sale=30` → 扣 20 分（= max_deduction / 2）
- `on_sale=50` → 扣 ~38 分
- `on_sale=70` → 扣 ~40 分（趋近 max_deduction）

**优先级**：P1

### FR-6：动态 buffer 防高分掩盖

**需求描述**：基于 4 维分数的标准差动态调整 buffer，防止单维度高分掩盖其他维度风险。

**公式**：
```
std = sqrt(variance)
buffer = max(30, int(50 - std * 0.4))
total = min(weighted_total, min_dim + buffer)
```

**行为**：
- 各维度分数接近（std 小）→ buffer=50，允许高分
- 某维度远低于其他（std 大）→ buffer=30，严格拉低总分
- 单维度回退场景 → buffer=40

**优先级**：P1

### FR-7：AI 自动评估集成

**需求描述**：对通过规则评估的商品自动调用 AI Vision 多模态评估，结果实质性影响总分与风险等级。

**输入**：`ai_auto_eval: bool`（默认 False）

**流程**：
1. 规则评估完成，`score >= pass_score`
2. 调用 `POST /api/ai/evaluate-condition`（含缓存检查 + 价格区间注入）
3. LLM Vision 分析商品图片（最多 4 张）+ 标题/描述
4. 返回 `ai_verdict`（recommend/caution/reject）+ `ai_condition_score`（1-10）
5. `Evaluator.apply_ai_eval()` 集成到规则评分：
   - `reject` → 总分 = 0，风险 = EXTREME
   - `caution` → 总分 × 0.85，风险 ≥ MEDIUM
   - `recommend` + `score >= 8` → 总分 + 5（最高 100）
   - `recommend` + `score <= 3` → 总分 × 0.7

**缓存机制**：结果缓存到 `evaluations.dimension_scores.ai_condition_eval`，命中则直接返回。

**降级策略**：
- 无 API Key → 规则模拟（`_rule_eval_condition`）
- LLM 失败 → 规则模拟
- 预算超限（`check_budget`）→ 规则模拟
- 纯文本模型（`_is_vision_capable` 返回 False）→ 移除看图要求，仅文字评估

**优先级**：P1

### FR-8：自动官方采集 + 失败退避

**需求描述**：对通过评估的商品自动调用官方采集，提取评价/留言等爬虫无法获取的数据；连续失败时暂停本轮采集。

**输入**：
- `auto_collect_official: bool`（默认 False）
- `auto_collect_max_per_run: int`（默认 3）
- `auto_collect_dedup_window_minutes: int`（默认 30）
- `auto_collect_fail_pause_threshold: int`（默认 3）

**触发条件**（4 个 AND 条件全满足）：
1. `eval_cfg.auto_collect_official == True`
2. `official_collect_fn is not None`
3. `not stats.official_collect_paused`
4. `stats.official_collected < eval_cfg.auto_collect_max_per_run`

**失败退避**：
1. 采集失败 → `_consecutive_collect_failures += 1`
2. 达到 `auto_collect_fail_pause_threshold` → `stats.official_collect_paused = True`
3. 通过 EventBus 发送 `TASK_ERROR` 事件（payload 含 `reason="auto_collect_paused"`、`consecutive_failures`、`threshold`）
4. 下一轮 `run_once` 重置计数器自动重试
5. 采集成功时重置 `_consecutive_collect_failures = 0`

**前端展示**：60s 自动刷新采集统计，显示 `is_paused` 状态 + Top3 失败原因。

**优先级**：P1

### FR-9：任务级 eval_config 覆盖

**需求描述**：单个任务可独立配置评估规则，覆盖全局配置。

**存储**：`Task.eval_config: dict[str, Any] | None`（JSON 序列化存 DB）

**合并逻辑**（`worker._effective_eval_cfg()`）：
1. `task.eval_config` 为 None 或空 dict → 返回全局单例
2. 非 None 时过滤 None 值（None 表示"不覆盖"）和未知字段
3. 用 `model_copy(update=updates)` 创建副本，避免污染全局单例

**可覆盖字段**：`EvalConfig` 的任意字段（如 `auto_collect_official`、`auto_collect_max_per_run`、`pass_score`、`auto_buy_score`、`ai_auto_eval`）

**优先级**：P1

### FR-10：评估分布热力图 + 阈值建议

**需求描述**：可视化近 7 天评估分布（价格 × 评分二维），并提供 F-15 阈值建议算法。

**API**：
- `GET /api/evaluations/distribution`：返回 buckets/marginals/total/insufficient_count/distribution/suggested_threshold/thresholds
- `GET /api/evaluations/threshold-suggestion`：F-15 二分查找通过率 75% 对应的 pass_score

**前端**：
- `computeHeatmapData`（模块级纯函数）处理数据
- `buildHeatmapOption`（模块级函数）构建 ECharts heatmap option

**优先级**：P2

### FR-11：Prompt 热更新 + 价格区间注入

**需求描述**：AI 评估的 Prompt 支持热更新（无需重启），并注入同类物品已售价格区间作为参考。

**Prompt 热更新**：
- `get_active_prompt("evaluate_condition")` 从 Prompt 编辑器读取最新内容
- 修改 Prompt 后立即生效，无需重启服务

**价格区间注入**：
- `_query_price_range(task_id, item_id, container)` 查询近 30 天同类已售价格
- 近 30 天无数据时回退到全部历史数据
- 注入到 LLM Prompt 的 `text_content`：bargain_price / max_price / median_price / sample_size / source_label
- 查询失败不阻断主流程（捕获异常返回 None）

**Vision 能力检测**：
- `_is_vision_capable(model_name)` 检测当前模型是否支持多模态
- 纯文本模型自动追加"特别说明"到 Prompt，移除看图要求
- 不传入图片 URL（避免 400 报错 + 用量浪费）
- `risk_signals` 中加入"无图片参考"

**优先级**：P2

## 8. 安全要求

### 8.1 认证与授权

- 所有 `/api/config/*`、`/api/evaluations/*`、`/api/ai/*` 端点必须走 `auth.py` 认证
- 不加入认证白名单
- 前端 fetch 必须含 `credentials: 'include'`
- 401 响应必须返回 JSON `{"detail": "Unauthorized"}`

### 8.2 敏感字段保护

- AI API Key 仅脱敏显示（`_mask_key`：仅保留末 4 位）
- 不记录原始 API Key 到日志
- `PUT /api/ai/config` 中 `api_key` 字段：
  - `"****xxxx"` 表示未修改，跳过更新
  - 空字符串表示清除
  - 其他值表示更新

### 8.3 输入校验

- 所有配置项通过 Pydantic 校验（类型 + 范围 + 跨字段）
- 任务级 eval_config 过滤未知字段（防 Pydantic v2 `model_copy` 直接 setattr 脏数据）
- 任务级 eval_config 过滤 None 值（None 表示"不覆盖"）

### 8.4 异常处理

- AI 评估失败不阻断主流程（降级规则模拟）
- 价格区间查询失败不阻断 AI 评估（返回 None）
- 缓存写入失败不阻断返回结果（仅 `logger.warning`）
- 自动采集失败触发退避（暂停本轮，不永久禁用）

## 12. 附录

### 12.1 评估分数计算示例

**场景**：卖家 on_sale_count=50，post_count_30d=20，credit_score=650，register_days=100，bad_review_count=1

**full 模式评估**：
1. 一票否决：credit_score=650 >= 600，通过
2. 职业度：
   - 在售数 Sigmoid 扣分：`40 / (1 + exp(-0.15 * (50 - 30)))` ≈ 38 分
   - 发帖数 Sigmoid 扣分：`30 / (1 + exp(-0.15 * (20 - 15)))` ≈ 19 分
   - 职业度得分：100 - 38 - 19 = 43 分
3. 信誉：credit_score=650 在 600-700 之间扣 5 分；register_days=100 >= 30 不扣；sold_count 假设 >= 5 不扣 → 95 分
4. 纠纷：bad_review=1，扣 5 分 → 95 分
5. 价格：假设无异常 → 100 分
6. 加权汇总：`(43*30 + 95*30 + 95*25 + 100*15) / 100 = 76.4` → 76 分
7. 动态 buffer：std 较大（43 vs 95/95/100），buffer ≈ 35
8. 最终：`min(76, 43 + 35) = min(76, 78) = 76` 分
9. 风险等级：76 >= pass_score(60) 且 < auto_buy_score(80) → MEDIUM
