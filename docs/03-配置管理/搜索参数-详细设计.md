## 2. 功能概述

**一句话说明**：控制闲鱼搜索行为的参数集合，包括操作延迟、每页数量、排序方式、超时、容错重试、地区过滤、筛选标签等，并通过等效 QPS 计算与熔断机制防风控。

**核心价值**：
- 操作延迟映射 `min_delay_ms` / `max_delay_ms`，模拟人类行为防风控
- 等效 QPS 自动计算（`Math.round(60/searchInterval)`）
- 熔断机制：连续失败 N 次触发暂停
- 5 种排序方式 + 4 档每页数量 + 5 个预设筛选标签
- 地区过滤支持逗号分隔多地区
- 通用反检测参数（`antidetect`）与搜索专用参数（`search`）分离存储

## 3. 用户场景

### 场景 1：调整搜索速度防风控
用户搜索频率过高被闲鱼风控，需要降低搜索速度。将"操作延迟"从 3 秒调整到 5 秒，系统自动计算等效 QPS = 60/5 = 12 次/分钟，并写入 `antidetect.min_delay_ms=5000, max_delay_ms=7500, qps=12`。

### 场景 2：按价格升序搜索捡漏
用户希望优先看到价格最低的商品。将"排序方式"设置为"价格最低"（`price_asc`），闲鱼搜索结果按价格升序返回，最便宜的商品优先被采集。

### 场景 3：地区过滤+包邮筛选
用户只关注北京/上海/广州的包邮商品。在"地区过滤"输入"北京,上海,广州"，在"筛选标签"添加"包邮"，系统搜索时只返回这三个地区且带包邮标签的商品。

## 5. 接口定义

搜索参数页面通过通用配置接口读写，涉及两个配置块：`antidetect`（通用反检测）和 `search`（搜索专用）。

| 方法 | 路径 | 用途 | 请求参数 | 响应字段 |
|------|------|------|----------|----------|
| GET | `/api/config` | 读取 `antidetect` + `search` 配置 | 无 | `antidetect: {qps, min_delay_ms, max_delay_ms, fail_pause_threshold, fail_window_sec}, search: {page_size, sort_type, timeout, regions, filter_tags}` |
| POST | `/api/config/preview` | 预览改动 | `{payload: {antidetect: {...}, search: {...}}}` | `{diffs, validation, new_yaml}` |
| POST | `/api/config/save` | 保存配置 | `{payload: {antidetect: {...}, search: {...}}, dry_run: bool}` | `{ok, dry_run, saved_at, diffs, backup, restart_required}` |

## 7. 业务逻辑

### 7.1 操作延迟映射算法

前端使用秒为单位（用户直观），保存时映射到后端毫秒：

```typescript
// 保存时的映射逻辑（SearchConfig.tsx 第 107-122 行）
update({
  antidetect: {
    ...config.antidetect,
    min_delay_ms: searchInterval * 1000,        // 秒 → 毫秒
    max_delay_ms: searchInterval * 1500,        // 最大延迟 = 1.5x 最小延迟
    qps: Math.round(60 / searchInterval),       // 等效 QPS 反推
    fail_pause_threshold: retryCount,           // 失败重试次数 → 熔断阈值
  },
  search: {
    page_size: pageSize,
    sort_type: sortType,
    timeout: timeout,
    regions: regions,
    filter_tags: filterTags,
  },
})
```

**为什么 max_delay = 1.5x min_delay**：模拟人类操作的随机性，固定间隔容易被风控识别为机器人，1.5x 范围内的随机延迟更接近真实用户行为。

### 7.2 等效 QPS 计算
```
等效 QPS = Math.round(60 / searchInterval)
```
- searchInterval=3 → QPS=20 次/分钟
- searchInterval=5 → QPS=12 次/分钟
- searchInterval=10 → QPS=6 次/分钟

**注意**：这里的 QPS 实际是"每分钟操作次数"（次/分钟），而非严格的 QPS（次/秒）。前端展示为"次/分钟"以避免歧义。

### 7.3 熔断机制

位置：`src/xianyu_hunter/infra/yaml_config.py` 第 39-40 行

- `fail_pause_threshold`（默认 3）：连续失败次数达到此值后触发熔断，暂停任务。
- `fail_window_sec`（默认 3600）：失败计数窗口（1 小时），窗口外失败不计入。
- 熔断后任务暂停，需用户手动恢复或等待下一轮调度。

**前端映射**：前端"失败重试次数"实际写入 `fail_pause_threshold`，语义上是"连续失败 N 次后暂停任务"。这与"重试次数"略有差异——重试次数通常指失败后重试的次数，而 `fail_pause_threshold` 是触发熔断的累计失败次数。

### 7.4 校验规则
- **操作延迟范围**：前端 InputNumber `min=1, max=30`（秒），对应 1000-30000 毫秒。
- **每页数量**：4 档固定选项 20/40/60/100，闲鱼搜索 API 限制。
- **排序方式**：5 种固定选项 `default/newest/price_asc/price_desc/want_count`。
- **搜索超时**：前端 `min=10, max=120`（秒），step=5。
- **失败重试次数**：前端 `min=0, max=10`，0 表示不重试（失败即熔断）。
- **地区过滤**：逗号分隔字符串，空字符串表示全国。

### 7.5 热更新机制
- 前端保存后调用通用 `/api/config/save` 接口，写盘 + `reload_config()` 重置单例。
- 搜索调度流程每次执行都通过 `get_config().search` / `get_config().antidetect` 实时获取，无需重启服务。
- 熔断状态在进程内维护，配置变更不影响已触发的熔断（需手动恢复或等下一轮）。

### 7.6 配置块分离设计
- `antidetect`：通用反检测参数，影响所有 HTTP 请求（搜索、详情、卖家主页等）。
- `search`：搜索专用参数，仅影响搜索请求。

**为什么分离**：反检测参数（如 QPS、延迟）对所有请求通用，而搜索参数（如排序、每页数量）仅对搜索请求有意义。分离后便于后续扩展其他模块（如详情采集）的专用参数。

### 7.7 预设标签完整列表与含义

前端硬编码 5 个预设快捷标签，对应闲鱼搜索 API 支持的固定筛选条件：

| 标签 | 闲鱼筛选含义 | 适用场景 |
|------|--------------|----------|
| `包邮` | 卖家承担运费 | 捡漏小件商品，避免运费占比过高 |
| `信用极好` | 卖家芝麻信用 ≥ 700 | 降低交易风险，优先高信誉卖家 |
| `同款` | 同款商品（图片相似度匹配） | 比价参考，发现同类低价 |
| `全新` | 商品状态为全新 | 购买新品的场景 |
| `可小刀` | 卖家接受小幅砍价 | 议价空间，可尝试还价 |

**与自定义标签的区别**：
- 预设标签：闲鱼 API 原生支持，100% 生效。
- 自定义标签（TagEditor 添加）：是否生效取决于闲鱼 API 是否识别该关键词，可能被忽略。

### 7.8 熔断机制详细流程

```
搜索请求执行
  ↓
[成功] → 清空 consecutive_failures 计数 → 返回结果
  ↓ [失败]
consecutive_failures += 1
  ↓
检查 fail_window_sec（默认 3600s）窗口内累计失败数
  ↓
[< fail_pause_threshold（默认 3）] → 继续下一轮调度
  ↓ [>= fail_pause_threshold]
触发熔断：暂停任务 + 发送 WAF_TRIGGERED 通知
  ↓
等待用户手动恢复 或 下一轮调度自动重试
```

**熔断状态维护**：
- `consecutive_failures` 计数在进程内维护，不持久化。
- `fail_window_sec` 窗口外的失败不计入（滑动窗口）。
- 熔断后任务状态变为 `paused`，需在 Dashboard 或任务管理页面手动恢复。
- 配置变更（如提高 `fail_pause_threshold`）**不影响**已触发的熔断，仅影响下次熔断判定。

**为什么用累计失败而非失败率**：闲鱼风控通常是"连续触发"模式（如连续 3 次验证码即封禁），累计失败数更贴合风控逻辑。失败率在小样本下波动大，容易误判。

### 7.9 排序方式对采集策略的影响

| 排序方式 | 闲鱼返回顺序 | 适用场景 | 风险提示 |
|----------|--------------|----------|----------|
| `default` | 综合排序（闲鱼算法） | 通用监控 | 可能偏向推广商品 |
| `newest` | 最新发布优先 | 抢首发捡漏 | 新品数据可能不全 |
| `price_asc` | 价格升序 | 最低价优先 | 易遇 1 元引流商品 |
| `price_desc` | 价格降序 | 高端商品监控 | 高价商品风控较严 |
| `want_count` | "想要"数降序 | 热门商品发现 | 热门商品竞争激烈 |

**推荐策略**：监控类任务用 `default`（综合）；捡漏类任务用 `price_asc` + 价格策略下限（过滤 1 元引流）；趋势分析用 `want_count`。

## 9. 常见问题 FAQ

### Q1：操作延迟和任务循环间隔是一回事吗？
**A**：不是。操作延迟（`min_delay_ms`/`max_delay_ms`）是**单次操作之间**的人类行为模拟延迟（如点击搜索按钮后等待 3 秒再点击下一个），防风控。任务循环间隔是两次完整任务执行之间的间隔，在"任务管理"页面按任务配置。页面 Form.Item 的 extra 已明确说明"模拟人类操作的间隔时间（非任务循环间隔）"。

### Q2：等效 QPS 是怎么算的？
**A**：`Math.round(60 / searchInterval)`。例如操作延迟 3 秒 → 等效 QPS = 60/3 = 20 次/分钟。注意这里展示的是"次/分钟"而非严格的"次/秒"，前端已标注单位。

### Q3：失败重试次数和熔断阈值是什么关系？
**A**：前端"失败重试次数"实际写入后端 `fail_pause_threshold` 字段，语义上是"连续失败 N 次后触发熔断暂停任务"。这与传统"重试次数"略有差异——不是失败后重试 N 次，而是累计失败 N 次后熔断。

### Q4：地区过滤支持哪些格式？
**A**：逗号分隔的中文地区名，如"北京,上海,广州"。空字符串表示全国（不过滤）。前端 Input 的 placeholder 示例为"例：北京,上海,广州"。注意用英文逗号分隔。

### Q5：5 个预设标签可以自定义吗？
**A**：预设标签（包邮/信用极好/同款/全新/可小刀）是闲鱼支持的固定筛选条件，前端硬编码。下方 TagEditor 支持添加任意自定义标签，与预设标签互不影响。自定义标签是否生效取决于闲鱼搜索 API 是否支持。

### Q6：max_delay 为什么是 min_delay 的 1.5 倍？
**A**：模拟人类操作的随机性。固定间隔容易被风控识别为机器人，1.5x 范围内的随机延迟更接近真实用户行为。例如 min_delay=3000ms，max_delay=4500ms，实际延迟在 3000-4500ms 之间随机。

### Q7：保存后搜索会立即用新参数吗？
**A**：是。保存接口写盘后调用 `reload_config()` 重置单例，搜索调度流程下次执行时通过 `get_config().search` 实时获取新参数。但**正在执行的搜索请求**不会中断，会使用旧参数完成。

### Q8：熔断后怎么恢复？
**A**：熔断后任务暂停，需在"任务管理"或 Dashboard 手动恢复，或等待下一轮调度自动重试。熔断状态在进程内维护，配置变更（如提高 `fail_pause_threshold`）不影响已触发的熔断。

### Q9：排序方式"想要最多"是什么意思？
**A**：`want_count` 排序，按商品"我想要"数量降序返回。想要数多的商品通常更受欢迎，适合发现热门商品。其他排序：`default`（综合）、`newest`（最新发布）、`price_asc`（价格最低）、`price_desc`（价格最高）。

### Q10：每页数量为什么只有 4 档？
**A**：闲鱼搜索 API 对 `page_size` 有严格限制，仅支持 20/40/60/100 四档。前端 Select 用固定选项避免提交非法值。设置过大可能被风控，建议默认 20。

### Q11：操作延迟设置 1 秒会有风控风险吗？
**A**：有风险。1 秒延迟意味着等效 QPS=60 次/分钟，接近闲鱼风控阈值。建议保持 3 秒以上（QPS≤20）。如果已被风控，建议设置 5-10 秒延迟，并配合"失败重试次数"降低到 2（更早熔断暂停，避免雪上加霜）。

### Q12：地区过滤用英文逗号还是中文逗号？
**A**：英文逗号 `,`。前端 Input 的 placeholder 示例为"例：北京,上海,广州"。如果用户误用中文逗号 `，`，后端不会自动转换，可能导致整个字符串被识别为单个地区名，过滤失效。建议从 placeholder 复制格式。

### Q13：filter_tags 为空和包含标签有什么区别？
**A**：
- **空列表 `[]`**：不应用任何筛选标签，返回所有商品（默认行为）。
- **包含标签 `["包邮"]`**：仅返回带"包邮"标签的商品，过滤掉非包邮商品。

多个标签是 AND 关系（同时满足），如 `["包邮", "全新"]` 表示既包邮又全新的商品。预设标签和自定义标签都写入同一个 `filter_tags` 列表。

### Q14：timeout 设置过长会有什么影响？
**A**：`timeout`（默认 30 秒）是单次搜索请求的最大等待时间。设置过长（如 120 秒）会导致：
- 任务调度卡顿：一个请求阻塞 2 分钟，影响后续任务执行
- 风控风险：长时间挂起的请求可能被闲鱼识别为异常
- 资源浪费：Playwright 页面长时间占用内存

建议保持默认 30 秒，网络不稳定时最多调到 60 秒。超时后计入 `consecutive_failures`，可能触发熔断。

### Q15：min_delay_ms 和 max_delay_ms 的关系是什么？
**A**：`min_delay_ms` 是单次操作的最小延迟，`max_delay_ms` 是最大延迟。实际延迟在两者之间随机取值（`random.uniform(min_delay, max_delay)`）。前端保存时按 `max_delay = min_delay * 1.5` 计算，例如操作延迟 3 秒 → min=3000ms, max=4500ms，实际延迟在 3000-4500ms 之间随机。

### Q16：fail_window_sec 窗口外的失败会清零吗？
**A**：不会自动清零，而是采用**滑动窗口**机制。每次失败时检查当前时间与首次失败时间的差值，超过 `fail_window_sec`（默认 3600 秒）则重置计数器。这意味着如果失败分散在长时间内（如 1 小时内仅 2 次失败），不会触发熔断；但如果短时间内密集失败（如 10 分钟内 3 次），会立即熔断。

### Q17：保存搜索参数后正在执行的任务会中断吗？
**A**：不会中断。正在执行的搜索请求会用旧参数完成，下一轮调度才用新参数。`reload_config()` 仅重置配置单例，不影响已启动的 Playwright 页面或 HTTP 请求。这是有意设计——中断进行中的请求可能导致 Playwright 状态异常。

### Q18：page_size 设置 100 会被风控吗？
**A**：有风险。闲鱼搜索 API 虽然支持 100 条/页，但单次返回大量数据可能触发风控（尤其是频繁请求时）。建议：
- 默认用 20（最安全）
- 监控类任务可用 40-60（平衡效率与风险）
- 100 仅用于低频任务（如每小时一次），且配合较长操作延迟（≥5 秒）

如果已触发风控，立即降回 20 并提高操作延迟。

### Q19：regions 和 filter_tags 同时设置会冲突吗？
**A**：不冲突，两者是 AND 关系。例如 `regions="北京,上海"` + `filter_tags=["包邮"]` 表示仅返回北京或上海地区的包邮商品。闲鱼搜索 API 会同时应用地区过滤和标签筛选，两者都满足才返回。如果结果为空，说明无商品同时满足条件，建议放宽其中一个条件。

### Q20：排序方式会影响采集质量吗？
**A**：会。不同排序方式返回的商品特征不同：
- `price_asc`：便宜商品优先，但易遇 1 元引流（需配合价格策略下限）
- `newest`：新品优先，但新品数据可能不全（卖家信息未完善）
- `want_count`：热门商品优先，但竞争激烈（可能已被他人抢走）
- `default`：综合排序，最稳定但可能偏向推广商品

建议监控类任务用 `default`，捡漏类任务用 `price_asc` + 价格策略下限过滤。
