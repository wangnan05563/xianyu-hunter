## 2. 功能概述

**一句话说明**：通过分数阈值（pass_score / auto_buy_score）+ 3 种任务级执行模式（notify / confirm / auto）+ 安全护栏，控制 auto 模式下的抢单行为，防止误拍与资金锁定风险。

**核心价值**：
- 复用 `EvalConfig.pass_score` / `auto_buy_score` 字段，避免配置冗余
- 3 种任务级模式覆盖从"仅通知"到"全自动"的全场景
- 安全护栏：auto_buy_score ≥ 80 才启用 auto、支付前暂停、单日抢单上限
- 数值防御：前端 `clamp` 函数确保分数在 [0, 100] 范围内
- 二次确认 + Diff 预览防止误操作

## 3. 用户场景

### 场景 1：保守用户——仅通知模式
用户希望系统只推送评估通过的商品，自己手动去闲鱼购买。所有任务设置为 `notify` 模式，`pass_score=60`，系统对评分 ≥60 的商品仅推送通知，不执行任何抢单动作。

### 场景 2：平衡用户——确认模式
用户希望系统推送后等待自己确认再抢单。任务设置为 `confirm` 模式，`pass_score=60, auto_buy_score=80`，评分 60-79 的商品推送通知等待确认，评分 ≥80 的商品可手动触发 auto 抢单。

### 场景 3：激进用户——全自动模式
用户充分测试后希望对高评分商品全自动拍下。任务设置为 `auto` 模式，`auto_buy_score=85`，评分 ≥85 的商品系统自动点击"立即购买"并提交订单，支付前暂停等待用户最后确认。

| `confirm_button_timeout` | `float` | `10.0` | 等待"提交订单"按钮出现的超时（秒），闲鱼 SPA 加载慢故 10s |

## 7. 业务逻辑

### 7.1 三种任务级模式

| 模式 | 触发条件 | 行为 | 风险等级 |
|------|----------|------|----------|
| `notify` | 任务配置为 notify | 仅推送通知，不抢单 | 最安全 |
| `confirm` | 任务配置为 confirm | 推送后等待用户在 Dashboard 确认 | 推荐 |
| `auto` | 任务配置为 auto **且** `auto_buy_score >= 80` **且** 商品评分 ≥ `auto_buy_score` | 全自动点击购买 + 提交订单，支付前暂停 | 高风险 |

**关键安全护栏**：即使任务设置为 `auto` 模式，若 `auto_buy_score < 80`，系统也不会执行自动抢单，仅降级为 `confirm` 模式。

### 7.2 校验规则
- **pass_score ≤ auto_buy_score**：Pydantic `_check_score_order` 校验器，违反时抛 `ValueError`。前端通过 `scoreOrderError` 变量实时检测并显示红色 Alert。
- **数值范围**：前端 `clamp(v)` 函数强制 [0, 100]，处理后端返回的 `null/NaN/undefined` 异常值。
- **auto 模式硬阈值**：`auto_buy_score >= 80` 才启用 auto 模式，硬编码在调度逻辑中（非配置项）。

### 7.3 安全护栏机制

页面"安全护栏"Card 明确列出 3 条规则：
1. **auto_buy_score ≥ 80 才启用 auto 模式**：硬编码门槛，防止用户误设低阈值导致自动抢单低质量商品。
2. **单日抢单上限**：在 `buyer_config.py` 中配置（待 UI 化），防止单日大量抢单导致资金锁定。
3. **支付前暂停**：默认开启，在 Dashboard 可手动接管。auto 模式下系统会点击"立即购买"并填写订单，但在最终支付步骤暂停，等待用户确认。

### 7.4 热更新机制
- 前端保存 `pass_score` / `auto_buy_score` 后，写盘 + `reload_config()` 重置单例。
- 调度流程每次执行都通过 `get_config().eval.pass_score` / `auto_buy_score` 实时获取，无需重启服务。
- `BuyerConfig` 运行时参数（click_retry_times 等）当前为硬编码，修改需重启服务（待 UI 化后会接入热更新）。

### 7.5 与评估规则的字段共享
抢单策略页面与"评估规则"页面**共享** `eval.pass_score` 和 `eval.auto_buy_score` 字段。在任一页面修改都会影响另一页面。这是有意设计：避免配置冗余，确保两页面看到的阈值一致。前端通过 `useConfigStore` 统一管理状态，修改任一页面都会同步到全局 config。

### 7.6 风险等级与分数映射

`Evaluator._score_to_risk()` 将总分映射到 4 级风险，决定后续动作：

| 总分范围 | 风险等级 | 后续动作 |
|----------|----------|----------|
| `score >= auto_buy_score`（默认 80） | `LOW` | 通知 + auto 模式下自动抢单 |
| `score >= pass_score`（默认 60） | `MEDIUM` | 仅通知，confirm 模式下等待用户确认 |
| `score >= 40` | `HIGH` | 不通知（仅记录），用户可在 Dashboard 查看 |
| `score < 40` 或一票否决 | `EXTREME` | 不通知，标记为高风险 |

**为什么 HIGH 级别不通知**：避免低质量商品打扰用户。HIGH 级别商品仍有查看价值（用户主动浏览 Dashboard 时可见），但不应主动推送。EXTREME 级别完全过滤，减少噪音。

### 7.7 BuyerConfig 运行时参数详解

`BuyerConfig`（`src/xianyu_hunter/modules/buyer_config.py`）是落单流程的可调参数，当前硬编码未 UI 化：

| 参数 | 默认值 | 作用 | 调优建议 |
|------|--------|------|----------|
| `click_retry_times` | `2` | "立即购买"按钮点击重试次数 | 网络不稳定时提高到 3 |
| `click_retry_interval` | `1.0s` | 两次点击退避秒数 | 风控严格时提高到 2s |
| `confirm_button_timeout` | `10.0s` | 等待"提交订单"按钮超时 | 闲鱼 SPA 加载慢，保持 10s |
| `price_tolerance` | `0.05` | 拍下价相对评估价的允许偏差 | 5% 防卖家临时涨价 |
| `min_interval_between_orders` | `0.0s` | 两次落单最小间隔 | 防手抖连点，建议设 2s |

**为什么未 UI 化**：这些参数需要根据实际落单情况反复调试，过早 UI 化会让普通用户困惑。先在代码中稳定，后续版本会接入"高级设置"页面。

### 7.8 自动抢单完整流程

```
商品评分 ≥ auto_buy_score (≥80)
  ↓
检查任务模式 == auto
  ↓ [否] → 降级为 confirm 模式（等待用户确认）
  ↓ [是]
检查 auto_buy_score >= 80（硬阈值）
  ↓ [否] → 降级为 confirm 模式
  ↓ [是]
检查单日抢单上限
  ↓ [超限] → 仅通知，不抢单
  ↓ [未超]
Playwright 打开商品页 → 点击"立即购买"（重试 click_retry_times 次）
  ↓
等待"提交订单"按钮（confirm_button_timeout 超时）
  ↓
校验拍下价格偏差 ≤ price_tolerance (5%)
  ↓ [超差] → 拒绝拍下，记录"价格异常"
  ↓ [正常]
点击"提交订单"
  ↓
[支付前暂停] 等待用户在 Dashboard 手动确认付款
```

**关键安全点**：
1. auto_buy_score 硬阈值 80 是代码级常量，非配置项，防止用户误调。
2. 价格校验在"提交订单"前进行，防卖家临时涨价。
3. 支付前暂停是最后防线，用户可审查订单详情后决定是否付款。

### 7.9 与评估规则的协作关系

抢单策略与评估规则在调度流程中紧密协作：

```
搜索采集 → 价格策略过滤 → Evaluator.evaluate() 4 维评分
                              ↓
                          [score >= auto_buy_score] → auto 模式自动抢单
                              ↓
                          [pass_score <= score < auto_buy_score] → 通知用户
                              ↓
                          [score < pass_score] → 不通知（仅记录）
```

**字段流向**：
- 评估规则页面配置 `weights`/`thresholds` → 影响评分计算
- 抢单策略页面配置 `pass_score`/`auto_buy_score` → 影响评分阈值判定
- 两页面共享 `eval` 配置块，前端 `useConfigStore` 统一管理

**为什么不在评估规则页面设置阈值**：阈值直接影响"是否通知"和"是否自动抢单"，属于业务决策而非评估算法。分离后职责清晰：评估规则页面管"怎么算分"，抢单策略页面管"分数怎么用"。

## 9. 常见问题 FAQ

### Q1：为什么 pass_score 和 auto_buy_score 在"评估规则"页面也能改？
**A**：这两个字段存储在 `eval` 配置块下，被"评估规则"和"抢单策略"两个页面共享。这是有意设计，避免配置冗余。在任一页面修改都会同步到另一页面（通过 `useConfigStore` 全局状态管理）。

### Q2：auto 模式下系统会自动付款吗？
**A**：不会。auto 模式下系统会自动点击"立即购买"并填写订单，但在最终支付步骤会暂停，等待用户在 Dashboard 手动确认付款。这是"支付前暂停"安全护栏，默认开启。

### Q3：为什么我设置了 auto 模式但没有自动抢单？
**A**：检查两个条件：(1) `auto_buy_score >= 80`（硬编码门槛）；(2) 商品评分 ≥ `auto_buy_score`。如果 `auto_buy_score=75`，即使任务为 auto 模式，系统也会降级为 confirm 模式。请将 `auto_buy_score` 提高到 80 以上。

### Q4：pass_score 可以大于 auto_buy_score 吗？
**A**：不可以。Pydantic `_check_score_order` 校验器强制 `pass_score <= auto_buy_score`。逻辑上"通过线高于自动抢单线"是矛盾的——意味着通过评估的商品反而不能自动抢单。

### Q5：单日抢单上限在哪里配置？
**A**：当前在 `src/xianyu_hunter/modules/buyer_config.py` 中硬编码（待 UI 化）。页面"安全护栏"Card 中明确标注"在 buyer_config.py 中配置（待 UI 化）"。后续版本会接入 UI。

### Q6：三种模式可以在运行中切换吗？
**A**：模式是任务级配置，在"任务管理"页面按任务独立设置。修改后下次调度执行时生效。本页面（抢单策略）仅配置分数阈值，不直接设置任务模式。

### Q7：auto_buy_score 设置 100 会怎样？
**A**：意味着只有满分商品才会自动抢单，实际上几乎不会触发。这相当于"禁用 auto 模式"的保守做法。建议设置 80-90 之间，平衡自动化效率与风险。

### Q8：保存时为什么需要二次确认？
**A**：抢单策略涉及资金安全，保存前会弹出 Diff 预览 Modal 展示具体变更项（path/op/old/new），用户确认后才真正写盘。这防止了误操作（如把 auto_buy_score 从 85 改成 50）导致大量低质量商品被自动拍下。

### Q9：confirm 模式下如何确认抢单？
**A**：confirm 模式下系统推送通知后，用户需要在 Dashboard 看到待确认订单并手动点击"确认抢单"按钮。系统会等待用户确认，超时后订单可能失效（闲鱼商品可能被他人抢走）。

### Q10：价格容忍度（price_tolerance）是什么？
**A**：`BuyerConfig.price_tolerance`（默认 0.05 = 5%）控制拍下价格相对预期价格的允许偏差。如果实际拍下价格与评估时价格偏差超过 5%，系统会拒绝拍下（防卖家临时涨价）。当前未 UI 化，硬编码在 `buyer_config.py`。

### Q11：clamp 函数如何处理异常输入？
**A**：`clamp(v)` 函数（BuyerStrategy.tsx 第 69-72 行）对 `auto_buy_score` 和 `pass_score` 做数值防御：
- `null/undefined/NaN` → 返回默认值（pass_score=60，auto_buy_score=80）
- `< 0` → 返回 0
- `> 100` → 返回 100
- 正常值 → 原值返回

这防止后端返回异常值（如配置文件损坏导致 null）时前端崩溃，也避免用户通过浏览器开发者工具输入超范围值。

### Q12：三种模式可以在保存后立即切换吗？
**A**：模式是任务级配置，在"任务管理"页面按任务设置。修改后**下次调度执行时生效**，不影响正在执行的任务。例如任务正在 auto 模式下抢单，用户改为 notify 模式，当前抢单流程会继续完成（包括支付前暂停），下一轮调度才用新模式。

### Q13：保存按钮为什么是橙色（#FF6200）？
**A**：使用闲鱼橙 `#FF6200` 突出抢单操作的重要性，与其他配置页面的蓝色主按钮区分。这是视觉警示设计——抢单策略涉及资金安全，橙色按钮提醒用户"这是高风险操作，请谨慎确认"。同时三种模式卡片也用颜色区分风险：notify=蓝色（安全）、confirm=黄色（注意）、auto=橙色（危险）。

### Q14：为什么 HIGH 级别（40-59 分）不通知？
**A**：避免低质量商品打扰用户。40-59 分的商品风险较高（接近 EXTREME），主动推送会造成通知噪音。但用户主动浏览 Dashboard 时仍可查看这些商品（有查看价值），只是不主动推送。这平衡了"信息可达性"与"通知纯净度"。

### Q15：auto 模式下如果 Playwright 操作失败会怎样？
**A**：系统会按 `click_retry_times`（默认 2 次）重试"立即购买"按钮点击。重试仍失败则记录 `BUY_FAILED` 事件并发送通知，不继续后续流程。不会自动降级到 confirm 模式（因为商品可能已被他人抢走）。用户可在 Dashboard 查看失败原因（如按钮未加载、网络超时）。

### Q16：单日抢单上限默认值是多少？如何修改？
**A**：当前 `BuyerConfig` 未定义 `daily_limit` 字段（待 UI 化），实际由调度流程的 `_daily_buy_count` 计数器控制，默认无上限（受 `auto_buy_score >= 80` 自然限制）。建议在代码中设置合理上限（如 10 单/天）防止资金锁定风险。后续版本会接入 UI 配置。

### Q17：pass_score 和 auto_buy_score 的推荐值是多少？
**A**：
- **保守**：pass_score=70, auto_buy_score=85（仅高质量商品通过，极少自动抢单）
- **平衡**：pass_score=60, auto_buy_score=80（默认值，兼顾质量与数量）
- **激进**：pass_score=50, auto_buy_score=80（更多商品通过，但 auto 仍受 80 硬阈值限制）

不建议 pass_score < 50，会引入大量低质量商品噪音。auto_buy_score 不建议 < 80（会被硬阈值降级为 confirm）。

### Q18：confirm 模式下用户确认有时效吗？
**A**：系统不强制时效，但闲鱼商品可能被他人抢走。一般建议 5 分钟内确认，超过 10 分钟商品大概率已售出。系统会在通知中显示"建议尽快确认"提示。用户可在 Dashboard 查看待确认订单列表，逐一确认或批量拒绝。

### Q19：三种模式切换会影响已采集的商品吗？
**A**：不会。模式切换仅影响后续调度流程的抢单行为。已采集并评估的商品记录保留在数据库中，Dashboard 仍可查看。例如从 auto 切换到 notify，之前 auto 模式下拍下的订单仍会正常处理（支付前暂停），只是新商品不再自动抢单。

### Q20：auto_buy_score=80 和 auto_buy_score=100 的实际差异？
**A**：
- `auto_buy_score=80`：评分 ≥80 的商品自动抢单。按 4 维评估模型，高质量卖家 + 合理价格即可达到，auto 模式实际触发频率中等。
- `auto_buy_score=100`：仅满分商品自动抢单。实际几乎不会触发（4 维都满分极罕见），相当于"禁用 auto 模式"的保守做法。

建议设置 80-90 之间，平衡自动化效率与风险。90 以上过于保守，失去 auto 模式的意义。

### Q21：price_tolerance 校验在哪个阶段执行？
**A**：在"提交订单"按钮点击前执行。系统读取页面上的实际拍下价格，与评估时记录的预期价格对比：
```
偏差 = abs(实际价格 - 预期价格) / 预期价格
如果 偏差 > price_tolerance (0.05) → 拒绝拍下，记录"价格异常"
```
这防止卖家在用户评估后临时涨价。如果价格偏差在 5% 以内（如运费微调），允许拍下。

### Q22：BuyerConfig 的 min_interval_between_orders 默认 0 会有问题吗？
**A**：默认 0 表示无最小间隔，理论上可能因手抖连点导致重复下单。但实际有其他保护：
- 支付前暂停：auto 模式下每个订单都需要用户手动确认付款
- 任务调度间隔：调度流程有循环间隔，不会瞬间触发多次
- 商品去重：同一商品不会重复抢单（数据库唯一约束）

建议手动设置为 2 秒（`min_interval_between_orders=2.0`），额外保险。后续 UI 化后会提供配置入口。

### Q23：notify 模式下会推送哪些信息？
**A**：notify 模式下，评分 ≥ pass_score 的商品会推送通知，包含：
- 商品标题、价格、卖家信息
- 评估分数与 4 维子分数
- 商品链接（点击跳转闲鱼）
- 评估理由（`reject_reasons` 中的正向原因）

通知渠道按 `notifier.default_channels` 顺序尝试推送，用户可在通知渠道配置页面自定义。
