## 2. 功能概述

**一句话说明**：通过分数阈值（`pass_score` / `auto_buy_score`）+ 4 种任务级执行模式（`AUTO` / `SEMI_AUTO` / `CONFIRM` / `NOTIFY_ONLY`）+ 安全护栏（90 秒超时、价格容差、冷却期、接管超时清理）+ 人工接管流程，控制 auto 模式下的抢单行为，防止误拍与资金锁定风险。

**核心价值**：
- 复用 `EvalConfig.pass_score` / `auto_buy_score` 字段，避免配置冗余
- 4 种任务级模式覆盖从"仅通知"到"全自动"的全场景
- **抢单全流程护栏**：90 秒总体超时、价格容差校验、内存 LRU + DB 双重幂等、`stop_on_first_buy` + `cooldown_after_buy` 防刷单
- **接管超时自动清理**：5 分钟扫描、30 分钟超时，自动将 `takeover_pending` 订单流转为 `failed`，避免用户支付已关闭订单
- **手动抢单接口**：突破纯自动模式限制，让用户在评估明细页主动触发
- **F-16 下游依赖自动激活**：订单 `succeeded` 后同步激活下游 `paused` 任务
- 数值防御：前端 `clamp` 函数确保分数在 [0, 100] 范围内
- 二次确认 + Diff 预览防止误操作
- **Pydantic + dataclass 双层架构**：配置层（`EvalConfig`）持久化到 YAML，运行时层（`BuyerConfig`）以默认值实例化

## 3. 用户场景

### 场景 1：保守用户——仅通知模式

用户希望系统只推送评估通过的商品，自己手动去闲鱼购买。所有任务设置为 `notify` 模式，`pass_score=60`，系统对评分 ≥60 的商品仅推送通知，不执行任何抢单动作。

### 场景 2：平衡用户——确认/半自动模式

用户希望系统推送后等待自己确认再抢单。任务设置为 `confirm` 或 `semi_auto` 模式，`pass_score=60, auto_buy_score=80`，评分 60-79 的商品推送通知等待确认，评分 ≥80 的商品可手动触发抢单（通过评估明细页的"手动抢单"按钮）。

### 场景 3：激进用户——全自动模式

用户充分测试后希望对高评分商品全自动拍下。任务设置为 `auto` 模式，`auto_buy_score=85`，评分 ≥85 的商品系统自动执行抢单全流程（导航→点击立即购买→等待订单页→点击提交→提取订单号→价格校验），订单落库后状态为 `pending_pay`，等待用户在闲鱼 App 完成支付。

### 场景 4：人工接管待付款订单

某订单进入 `pending_pay` 状态后，用户在抢单记录页点击"接管"，调用 `POST /api/orders/{id}/takeover` 将状态置为 `takeover_pending`，前端 TakeoverModal 启动 30 分钟倒计时。用户在闲鱼 App 完成支付后点击"确认支付完成"，调用 `/takeover/confirm` 将状态置为 `succeeded`。

### 场景 5：接管超时清理

用户点击"接管"后 30 分钟内未完成支付，接管超时调度器（5 分钟扫描一次）将订单状态自动从 `takeover_pending` 置为 `failed`，避免用户去支付已被闲鱼自动关闭的订单。

### 场景 6：手动抢单

用户在评估明细页对某商品点击"手动抢单"，调用 `POST /api/orders/manual-takeover`，后端校验 buyer 注入态与闲鱼登录态后，调用 `container.buyer.buy()` 触发抢单。幂等检查避免重复抢单。

### 场景 7：F-16 依赖任务自动激活

订单状态变为 `succeeded` 时（无论通过 `takeover_confirm` 还是 `update_order_status`），后端同步调用 `_trigger_dependent_tasks`：通过 `item_id` 反查 `items.task_id`，查询所有依赖此任务的下游任务，将 `paused` 状态的下游任务自动激活为 `running`，并写入 `dep_triggered` stage 事件。

## 6. 数据结构

### 6.1 配置层 Pydantic 模型（复用 `EvalConfig`）

抢单策略页面复用 `EvalConfig` 中的 `pass_score` 和 `auto_buy_score` 字段，**不单独定义 BuyerConfig Pydantic 模型**。

位置：`src/xianyu_hunter/infra/yaml_config.py`

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `pass_score` | `int` | `60` | 通过分数（≥ 此值通知用户） |
| `auto_buy_score` | `int` | `80` | 自动抢单分数（≥ 此值且任务为 `auto` 模式才自动拍下） |

**校验器**：`_check_score_order` 强制 `pass_score <= auto_buy_score`，违反时抛 `ValueError`。

> **重要澄清**：`auto_buy_score` 默认值 80 是**可配置项**，不是硬编码阈值。worker.py 的 `_attempt_buy` 通过 `eval_cfg.auto_buy_score if eval_cfg else 80` 读取，用户可将 `auto_buy_score` 设为 75、85 等任意 [0, 100] 值。v1.0 文档声称的"硬阈值 80"是错误的。

### 6.2 运行时层 dataclass `BuyerConfig`

位置：`src/xianyu_hunter/modules/buyer_config.py`

此 dataclass 用于落单流程的可调参数，**当前未 UI 化**，以默认值实例化。`AppConfig` 不含 `BuyerConfig`（运行时 dataclass，未持久化到 YAML）。

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `click_retry_times` | `int` | `2` | 点击"立即购买"按钮的重试次数 |
| `click_retry_interval` | `float` | `1.0` | 两次点击之间的退避秒数 |
| `confirm_button_timeout` | `float` | `10.0` | 等待"提交订单"按钮出现的超时（秒），闲鱼 SPA 加载慢故 10s |
| `price_tolerance` | `float` | `0.05` | 拍下价格相对预期价格的允许偏差（0.05 = 5%） |
| `min_interval_between_orders` | `float` | `0.0` | 两次落单间的最小间隔（秒），防手抖 |

> **重要澄清**：`BuyerConfig` 中**没有** `daily_limit` / `_daily_buy_count` 等单日抢单上限字段。v1.0 文档声称的"单日抢单上限"在代码中**完全不存在**。防刷单依靠 `stop_on_first_buy`（抢到 1 单停止本轮）和 `cooldown_after_buy`（30 秒冷却）实现。

### 6.3 任务级运行时配置 `TaskConfig`

位置：`src/xianyu_hunter/domain/task.py`

`TaskConfig` 是调度层运行时配置（不持久化到 DB），由调度器构造。与抢单策略相关字段：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `stop_on_first_buy` | `bool` | `True` | 抢到 1 单后立即停止本轮（防刷单） |
| `cooldown_after_buy` | `float` | `30.0` | 拍下后冷却秒数，期间不再下单 |
| `use_cron` | `bool` | `False` | 是否使用 cron 表达式调度 |
| `interval_seconds` | `float` | `60.0` | Worker 循环间隔（秒） |
| `max_items_per_run` | `int` | `20` | 每次循环最多处理多少件商品 |

## 7. 业务逻辑

### 7.1 4 种任务级模式

| 模式 | `TaskMode` 枚举 | 触发条件 | 行为 | 风险等级 |
|------|-----------------|----------|------|----------|
| `auto` | `AUTO` | 任务配置为 `auto` **且** 商品评分 ≥ `auto_buy_score` **且** 风险等级为 `LOW` | 全自动点击购买 + 提交订单，订单落库为 `pending_pay` | 高风险 |
| `semi_auto` | `SEMI_AUTO` | 任务配置为 `semi_auto` | 推送通知，用户确认后抢单 | 中风险 |
| `confirm` | `CONFIRM` | 任务配置为 `confirm` | 仅推送通知，不抢单（默认最保守） | 推荐 |
| `notify` | `NOTIFY_ONLY` | 任务配置为 `notify` | 仅推送通知，不抢单 | 最安全 |

**关键判定逻辑**（`worker.py` `_should_buy` + `_attempt_buy`）：

```python
def _should_buy(self) -> bool:
    """根据模式判断本轮是否执行真拍"""
    if self.task.mode == TaskMode.AUTO:
        return True
    if self.task.mode == TaskMode.NOTIFY_ONLY:
        return False
    # CONFIRM / SEMI_AUTO 都不在 Worker 拍（由用户在 App 内确认）
    return False

async def _attempt_buy(self, detail, eval_result, eval_cfg, stats, buy_results):
    if not self._should_buy():
        return None  # 非 AUTO 模式跳过抢单
    _auto_buy_score = eval_cfg.auto_buy_score if eval_cfg else 80  # 默认 80，可配置
    if not eval_result.should_auto_buy(_auto_buy_score):
        return None  # 未达 auto_buy_score 或非低风险
    if self._in_cooldown():
        return None  # 冷却期内
    # 执行抢单...
```

> **重要澄清**：`auto_buy_score` 是 `EvalConfig` 的可配置字段（默认 80），不是硬编码阈值。worker.py 通过 `eval_cfg.auto_buy_score` 读取，用户可在抢单策略页面修改为 75、85 等任意值。v1.0 文档声称的"硬阈值 80"是错误的。

### 7.2 校验规则

- **pass_score ≤ auto_buy_score**：Pydantic `_check_score_order` 校验器，违反时抛 `ValueError`。前端通过 `scoreOrderError` 变量实时检测并显示红色 Alert。
- **数值范围**：前端 `clamp(v)` 函数强制 [0, 100]，处理后端返回的 `null/NaN/undefined` 异常值。
- **风险等级判定**：`evaluator.py` `_score_to_risk` 使用 `thresholds.auto_buy_score` 和 `thresholds.pass_score`（非硬编码 80）映射风险等级。

### 7.3 风险等级与分数映射

`Evaluator._score_to_risk()` 将总分映射到 4 级风险，决定后续动作：

| 总分范围 | 风险等级 | 后续动作 |
|----------|----------|----------|
| `score >= auto_buy_score`（默认 80，可配置） | `LOW` | 通知 + `auto` 模式下自动抢单 |
| `score >= pass_score`（默认 60） | `MEDIUM` | 仅通知，`confirm`/`semi_auto` 模式下等待用户确认 |
| `score >= 40` | `HIGH` | 不通知（仅记录），用户可在 Dashboard 查看 |
| `score < 40` 或一票否决 | `EXTREME` | 不通知，标记为高风险 |

**为什么 HIGH 级别不通知**：避免低质量商品打扰用户。HIGH 级别商品仍有查看价值（用户主动浏览 Dashboard 时可见），但不应主动推送。EXTREME 级别完全过滤，减少噪音。

### 7.4 自动抢单完整流程

```
商品评分 ≥ auto_buy_score (默认 80，可配置)
  ↓
检查任务模式 == AUTO (worker._should_buy)
  ↓ [否] → 跳过抢单，仅推送通知
  ↓ [是]
检查风险等级 == LOW (eval_result.should_auto_buy)
  ↓ [否] → 跳过抢单
  ↓ [是]
检查冷却期 (worker._in_cooldown)
  ↓ [冷却中] → 跳过抢单
  ↓ [未冷却]
Buyer.buy() 入口
  ↓
[幂等检查] 内存 LRU (maxsize=10000) + DB find_order_by_task_item 双重保护
  ↓ [已存在] → 返回 SKIPPED_DUPLICATE
  ↓ [不存在]
[节流] min_interval_between_orders
  ↓
[频率伪装统计] record_freq_request(ActionType.LOGIN)
  ↓
[90 秒总体超时] asyncio.wait_for(self._do_buy(...), timeout=90.0)
  ↓
_do_buy 流程：
  1. 导航到详情页 (page.goto, domcontentloaded, 20s 超时)
  2. 检测已售 (_detect_sold) → 已售则抛 ItemSoldError
  3. 点击"立即购买" (重试 click_retry_times 次)
  4. 等待订单确认页 (_wait_for_order_page)
     - 检测登录页跳转 → 抛 BuyerError "未登录"
  5. 点击"提交订单/确认购买" (多文案匹配)
  6. 提取订单号 (_extract_order_no)
  7. 提取实际价格 (_extract_actual_price)
  8. 价格校验：偏差 > price_tolerance (5%) → 抛 PriceMismatchError
  ↓
[持久化] repo.upsert_order(order) + 发布 BUY_SUCCEEDED 事件
  ↓
[stop_on_first_buy] 抢到 1 单后停止本轮
  ↓
[cooldown_after_buy] 30 秒冷却期
```

**关键安全点**：
1. **90 秒总体超时**：防止浏览器操作无限阻塞（闲鱼页面加载异常或会话失效）。
2. **价格校验**：在"提交订单"后执行，防卖家临时涨价。
3. **LRU + DB 双重幂等**：内存 LRU 防进程内重复，DB 兜底防跨进程重启后重复。
4. **失败订单持久化**：`_save_failed_order` 将失败订单也写入 DB，便于后续分析。
5. **事件发布**：`BUY_SUCCEEDED` / `BUY_FAILED` 事件通过 EventBus 发布，前端通过 SSE 实时更新。

### 7.5 BuyerConfig 运行时参数详解

`BuyerConfig`（`src/xianyu_hunter/modules/buyer_config.py`）是落单流程的可调参数，当前硬编码未 UI 化：

| 参数 | 默认值 | 作用 | 调优建议 |
|------|--------|------|----------|
| `click_retry_times` | `2` | "立即购买"按钮点击重试次数 | 网络不稳定时提高到 3 |
| `click_retry_interval` | `1.0s` | 两次点击退避秒数 | 风控严格时提高到 2s |
| `confirm_button_timeout` | `10.0s` | 等待"提交订单"按钮超时 | 闲鱼 SPA 加载慢，保持 10s |
| `price_tolerance` | `0.05` | 拍下价相对评估价的允许偏差 | 5% 防卖家临时涨价 |
| `min_interval_between_orders` | `0.0s` | 两次落单最小间隔 | 防手抖连点，建议设 2s |

**为什么未 UI 化**：这些参数需要根据实际落单情况反复调试，过早 UI 化会让普通用户困惑。先在代码中稳定，后续版本会接入"高级设置"页面。

### 7.6 接管超时调度器

位置：`src/xianyu_hunter/modules/takeover_timeout_scheduler.py`

```python
class TakeoverTimeoutScheduler:
    """接管超时清理调度器
    
    线程模型：BackgroundScheduler 在独立线程定时触发 _run_cleanup_job，
    直接调用 repo.expire_takeover_pending_orders 完成 DB 操作，
    无需通过 run_coroutine_threadsafe 提交到主事件循环
    （不依赖 Playwright/async 资源）
    """
    
    def _run_cleanup_job(self):
        """定时任务：扫描并清理超时的 takeover_pending 订单"""
        expired = self._container.repo.expire_takeover_pending_orders(self._timeout_min)
        # 超时订单状态从 takeover_pending → failed（不是 cancelled）
        # 为什么 failed：用户未完成支付是异常情况，cancelled 会被误认为是用户主动取消
```

**为什么 5 分钟扫描**：平衡时效性与 DB 开销。1 分钟扫描过于频繁（每分钟一次全表扫描），10 分钟扫描会让超时订单多卡 10 分钟才清理。

**为什么流转到 `failed` 而非 `cancelled`**：用户未完成支付是异常情况，`cancelled` 会被误认为是用户主动取消，影响统计准确性。

**`expire_takeover_pending_orders` 实现**（`repo_orders.py`）：
- 批量 SQL 更新（一次 update，避免 N+1）
- 状态：`takeover_pending → failed`
- 清空 `confirmed_at`：与 `takeover_cancel` 一致，让订单可被重新接管
- 返回被清理的订单列表，供调用方发布事件/通知下游

### 7.8 F-16 下游依赖自动激活

位置：`src/xianyu_hunter/web/routes/api_orders.py` `_trigger_dependent_tasks`

```python
def _trigger_dependent_tasks(container: Container, order: dict) -> None:
    """F-16：订单成功后，检查是否有下游任务依赖此订单所属任务，自动激活它们
    
    触发条件：
    1. 订单状态变为 succeeded
    2. 订单关联了一个 item_id（通过 item_id 反查 items 表获取 task_id）
    3. 该 task_id 有下游依赖任务（task_deps 表）
    4. 下游任务当前状态为 paused（等待上游成功）
    
    实现方式：同步函数调用（非 EventBus），直接修改 task.status
    发布事件：stage='dep_triggered'（不是 type='task.started'）
    """
```

**设计原则**：仅 `paused` 状态的下游任务会被自动激活，避免误启动用户主动停止的任务。

**触发点**：`takeover_confirm` 和 `update_order_status`（当状态变为 `succeeded` 时）都会调用 `_trigger_dependent_tasks`。

### 7.10 安全护栏机制

页面"安全护栏" Card 列出的规则（含 v1.0 文档错误，需修正）：

| 规则 | v1.0 描述 | 实际实现 |
|------|-----------|----------|
| auto_buy_score 阈值 | "≥ 80 才启用 auto 模式（硬编码）" | **可配置默认值 80**，非硬阈值 |
| 单日抢单上限 | "在 buyer_config.py 中配置（待 UI 化）" | **字段不存在**，防刷单依靠 `stop_on_first_buy` + `cooldown_after_buy` |

**实际安全护栏**：
1. **90 秒总体超时**：`asyncio.wait_for(timeout=90.0)`，防止浏览器操作无限阻塞。
2. **价格容差校验**：`price_tolerance=0.05`（5%），防卖家临时涨价。
3. **LRU + DB 双重幂等**：内存 LRU（maxsize=10000）+ DB `find_order_by_task_item`。
4. **`stop_on_first_buy`**：抢到 1 单后停止本轮（防刷单）。
5. **`cooldown_after_buy`**：30 秒冷却期（防连点）。
6. **接管超时清理**：30 分钟超时，自动流转到 `failed`。
7. **buyer 注入态校验**：`with_browser=False` 模式下拒绝手动抢单。
8. **登录态校验**：Cookie 失效时拒绝抢单。
9. **浏览器锁**：`browser_lock.acquire(priority="high")` 串行化浏览器操作。

### 7.11 热更新机制

- 前端保存 `pass_score` / `auto_buy_score` 后，写盘 + `reload_config()` 重置单例。
- 调度流程每次执行都通过 `get_config().eval.pass_score` / `auto_buy_score` 实时获取，无需重启服务。
- `BuyerConfig` 运行时参数（click_retry_times 等）当前为硬编码，修改需重启服务（待 UI 化后会接入热更新）。
- `TakeoverTimeoutScheduler` 在服务启动时初始化，配置变更需重启服务。

### 7.12 与评估规则的字段共享

抢单策略页面与"评估规则"页面**共享** `eval.pass_score` 和 `eval.auto_buy_score` 字段。在任一页面修改都会影响另一页面。这是有意设计：避免配置冗余，确保两页面看到的阈值一致。前端通过 `useConfigStore` 统一管理状态，修改任一页面都会同步到全局 config。

### 7.13 与评估规则的协作关系

抢单策略与评估规则在调度流程中紧密协作：

```
搜索采集 → 价格策略过滤 → Evaluator.evaluate() 4 维评分
                              ↓
                          [score >= auto_buy_score] → auto 模式自动抢单
                              ↓
                          [pass_score <= score < auto_buy_score] → 通知用户
                              ↓
                          [score < pass_score] → 不通知（仅记录）
```

**字段流向**：
- 评估规则页面配置 `weights`/`thresholds` → 影响评分计算
- 抢单策略页面配置 `pass_score`/`auto_buy_score` → 影响评分阈值判定
- 两页面共享 `eval` 配置块，前端 `useConfigStore` 统一管理

**为什么不在评估规则页面设置阈值**：阈值直接影响"是否通知"和"是否自动抢单"，属于业务决策而非评估算法。分离后职责清晰：评估规则页面管"怎么算分"，抢单策略页面管"分数怎么用"。

## 9. 常见问题 FAQ

### Q1：为什么 pass_score 和 auto_buy_score 在"评估规则"页面也能改？

**A**：这两个字段存储在 `eval` 配置块下，被"评估规则"和"抢单策略"两个页面共享。这是有意设计，避免配置冗余。在任一页面修改都会同步到另一页面（通过 `useConfigStore` 全局状态管理）。

### Q2：auto 模式下系统会自动付款吗？

**A**：不会。auto 模式下系统会自动点击"立即购买"并提交订单，订单状态变为 `pending_pay`。用户需在闲鱼 App 完成支付，或在抢单记录页点击"接管"后通过 `takeover_confirm` 确认支付。

### Q3：为什么我设置了 auto 模式但没有自动抢单？

**A**：检查以下条件：
1. 任务模式为 `AUTO`（worker.py `_should_buy` 判定）
2. 商品评分 ≥ `auto_buy_score`（默认 80，可在抢单策略页面调整）
3. 风险等级为 `LOW`（`eval_result.should_auto_buy` 判定）
4. 不在冷却期内（`cooldown_after_buy` 默认 30 秒）
5. buyer 已注入（`XH_WITH_SCHEDULER=1` 模式启动）

### Q4：pass_score 可以大于 auto_buy_score 吗？

**A**：不可以。Pydantic `_check_score_order` 校验器强制 `pass_score <= auto_buy_score`。逻辑上"通过线高于自动抢单线"是矛盾的——意味着通过评估的商品反而不能自动抢单。

### Q5：v1.0 文档提到的"单日抢单上限"在哪里配置？

**A**：**v1.0 文档错误**。`BuyerConfig` 中**没有** `daily_limit` / `_daily_buy_count` 字段。防刷单依靠以下机制：
- `stop_on_first_buy=True`：抢到 1 单后停止本轮
- `cooldown_after_buy=30.0`：30 秒冷却期
- 任务调度间隔（`interval_seconds` 默认 60 秒）

如需限制单日抢单数，需在代码层扩展 `BuyerConfig` 字段并实现计数逻辑。

### Q6：4 种任务模式可以在运行中切换吗？

**A**：模式是任务级配置，在"任务管理"页面按任务独立设置。修改后**下次调度执行时生效**，不影响正在执行的任务。本页面（抢单策略）仅配置分数阈值，不直接设置任务模式。

### Q7：auto_buy_score 设置 100 会怎样？

**A**：意味着只有满分商品才会自动抢单，实际上几乎不会触发。这相当于"禁用 auto 模式"的保守做法。建议设置 80-90 之间，平衡自动化效率与风险。

### Q8：保存时为什么需要二次确认？

**A**：抢单策略涉及资金安全，保存前会弹出 Diff 预览 Modal 展示具体变更项（path/op/old/new），用户确认后才真正写盘。这防止了误操作（如把 auto_buy_score 从 85 改成 50）导致大量低质量商品被自动拍下。

### Q9：v1.0 文档提到的"auto_buy_score ≥ 80 硬阈值"是真的吗？

**A**：**v1.0 文档错误**。`auto_buy_score` 是 `EvalConfig` 的可配置字段（默认 80），不是硬编码阈值。worker.py 通过 `eval_cfg.auto_buy_score if eval_cfg else 80` 读取，用户可在抢单策略页面修改为任意 [0, 100] 值。前端 `BuyerStrategy.tsx` 第 218 行仍显示"auto_buy_score ≥ 80 才启用 auto 模式"是 UI 文案错误，待修正。

### Q10：90 秒总体超时是什么？

**A**：`Buyer.buy()` 使用 `asyncio.wait_for(self._do_buy(...), timeout=90.0)` 包裹整个落单流程。超时通常意味着闲鱼页面加载异常或会话失效（RGV587_ERROR），此时抛出 `asyncio.TimeoutError` 并记录"浏览器自动化流程超时（90秒），请检查闲鱼登录状态后重试"。

### Q11：接管超时调度器为什么 5 分钟扫描一次？

**A**：平衡时效性与 DB 开销。1 分钟扫描过于频繁（每分钟一次全表扫描），10 分钟扫描会让超时订单多卡 10 分钟才清理。5 分钟是经验值，确保超时订单在 30-35 分钟内被清理。

### Q12：接管超时为什么流转到 `failed` 而非 `cancelled`？

**A**：用户未完成支付是异常情况，`cancelled` 会被误认为是用户主动取消，影响统计准确性。`failed` 明确表示这是异常终止，便于运营分析。

### Q13：手动抢单和自动抢单有什么区别？

**A**：
- **自动抢单**：任务模式为 `AUTO`，调度流程自动触发，要求 `with_browser=True`（`XH_WITH_SCHEDULER=1`）。
- **手动抢单**：用户在评估明细页点击"手动抢单"按钮触发，调用 `POST /api/orders/manual-takeover`，前置校验 buyer 注入态与登录态后调用 `container.buyer.buy()`。突破纯自动模式限制，让用户保留决策权。

### Q14：F-16 下游依赖触发是什么？

**A**：订单状态变为 `succeeded` 时，后端同步调用 `_trigger_dependent_tasks`：通过 `item_id` 反查 `items.task_id`，查询所有依赖此任务的下游任务，将 `paused` 状态的下游任务自动激活为 `running`，并写入 `dep_triggered` stage 事件。仅 `paused` 状态的下游任务会被激活，避免误启动用户主动停止的任务。

### Q15：价格容忍度（price_tolerance）是什么？

**A**：`BuyerConfig.price_tolerance`（默认 0.05 = 5%）控制拍下价格相对预期价格的允许偏差。在"提交订单"后提取实际价格，与评估时记录的预期价格对比：
```
偏差 = abs(实际价格 - 预期价格) / 预期价格
如果 偏差 > price_tolerance (0.05) → 抛 PriceMismatchError，拒绝拍下
```
这防止卖家在用户评估后临时涨价。当前未 UI 化，硬编码在 `buyer_config.py`。

### Q16：clamp 函数如何处理异常输入？

**A**：`clamp(v)` 函数对 `auto_buy_score` 和 `pass_score` 做数值防御：
- `null/undefined/NaN` → 返回 0
- `< 0` → 返回 0
- `> 100` → 返回 100
- 正常值 → 原值返回

这防止后端返回异常值（如配置文件损坏导致 null）时前端崩溃，也避免用户通过浏览器开发者工具输入超范围值。

### Q17：LRU 幂等缓存是什么？

**A**：`Buyer._task_item_set` 使用 `LRUDict[tuple[str,str], None]` 模拟 set 语义，maxsize=10000。记录本次进程内已下过单的 `(task_id, item_id)` 组合。第二次调用同一组合时直接返回 `SKIPPED_DUPLICATE`，避免重复下单。LRU 驱逐后由 DB `find_order_by_task_item` 兜底，确保跨进程重启后仍能识别。

### Q18：BuyerError 异常体系有哪些？

**A**：
- `BuyerError`：落单流程异常基类
- `ButtonNotFoundError`：找不到「立即购买」按钮（页面结构变化）
- `ItemSoldError`：商品已售出（返回 409）
- `OutOfStockError`：商品已下架/无库存
- `PriceMismatchError`：价格偏差过大（超 5%）

不同异常对应不同业务语义，便于前端给出准确提示。

### Q19：pass_score 和 auto_buy_score 的推荐值是多少？

**A**：
- **保守**：pass_score=70, auto_buy_score=85（仅高质量商品通过，极少自动抢单）
- **平衡**：pass_score=60, auto_buy_score=80（默认值，兼顾质量与数量）
- **激进**：pass_score=50, auto_buy_score=75（更多商品通过，auto 触发更频繁）

不建议 pass_score < 50，会引入大量低质量商品噪音。

### Q20：semi_auto 模式和 confirm 模式有什么区别？

**A**：
- `CONFIRM`：仅推送通知，不抢单（默认最保守）
- `SEMI_AUTO`：推送通知，用户确认后抢单

两者在 worker.py `_should_buy` 中都返回 `False`（不在 Worker 自动拍），区别在于用户确认后是否触发抢单流程。`semi_auto` 是"半自动"，`confirm` 是"纯通知"。

### Q21：保存配置后需要重启服务吗？

**A**：`pass_score` / `auto_buy_score` 不需要。保存接口写盘后调用 `reload_config()` 重置单例，调度流程下次执行时自动获取新配置。`BuyerConfig` 运行时参数（click_retry_times 等）当前为硬编码，修改需重启服务。`TakeoverTimeoutScheduler` 配置变更也需重启服务。

### Q22：风险等级 HIGH（40-59 分）为什么不通知？

**A**：避免低质量商品打扰用户。40-59 分的商品风险较高（接近 EXTREME），主动推送会造成通知噪音。但用户主动浏览 Dashboard 时仍可查看这些商品（有查看价值），只是不主动推送。这平衡了"信息可达性"与"通知纯净度"。

### Q23：接管流程的状态机白名单是什么？

**A**：仅 `pending_pay` 可被接管。
- 拒绝 `takeover_pending → takeover_pending`：避免用户无限点击重置 30 分钟倒计时，违背"30 分钟内必须完成支付"的业务约束。
- 拒绝 `succeeded`/`failed`/`cancelled → takeover_pending`：终态订单不可复活。
- 用户若需重新接管已 cancel 的订单，需先通过 `PATCH /status` 回退到 `pending_pay`。

### Q24：manual-takeover 接口的浏览器锁优先级是什么？

**A**：`priority="high"`，优先于 Worker 后台搜索（normal 优先级）。超时 10 秒返回 503 "系统正在执行后台浏览器任务，请稍后重试手动抢单"。

### Q25：notify 模式下会推送哪些信息？

**A**：notify 模式下，评分 ≥ pass_score 的商品会推送通知，包含：
- 商品标题、价格、卖家信息
- 评估分数与 4 维子分数
- 商品链接（点击跳转闲鱼）
- 评估理由（`reject_reasons` 中的正向原因）

通知渠道按 `notifier.default_channels` 顺序尝试推送，用户可在通知渠道配置页面自定义。
