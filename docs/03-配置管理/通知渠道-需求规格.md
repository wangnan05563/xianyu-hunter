## 1. 引言

### 1.1 编写目的

本需求规格说明书定义「配置管理 → 通知渠道」二级菜单的完整需求规格，作为前端/后端开发、测试与验收的唯一依据。

**目标读者**：
- 后端开发工程师：依据 §3-§5、§7、§8 进行模块实现与扩展
- 前端开发工程师：依据 §3、§6 进行页面开发
- 测试工程师：依据 §7 编写测试用例与执行验收
- 项目经理：依据 §2、§7 进行范围与里程碑管理
- 智能客服 KB 训练：本文档与 [通知渠道-详细设计.md](通知渠道-详细设计.md) 共同作为 KB 检索素材

### 1.2 项目背景

闲鱼猎人（XianyuHunter）是一个闲鱼自动捡漏与抢单工具，已具备任务管理、商品采集、AI 评估、自动下单、多渠道通知等完整能力（详见 [requirements.md](../requirements.md)、[design.md](../design.md) 与 [概要设计文档.md](../概要设计文档.md)）。

随着系统运行规模扩大，**通知渠道相关能力目前分散在多个模块**（`modules/notifier/` / `web/routes/api_notifier.py` / `web/routes/api_config.py` / `infra/yaml_config.py` / `container.py` / `NotifierChannels/index.tsx`），缺乏统一的需求基线，导致以下痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| 推送策略描述与实现不符 | v1.0 详细设计描述"按顺序降级"，实际是 `asyncio.gather` 并发 fan-out | 文档误导开发与测试 |
| 凭据存储描述与实现不符 | v1.0 详细设计描述"keyring 加密"，实际 YAML 明文 + keyring fallback | 安全审计与排错困难 |
| 热更新机制不透明 | v1.0 未说明仅 quiet_hours 热生效，其他配置需重启 | 用户不知道修改后是否需要重启 |
| `_DB_ONLY_EVENTS` 过滤未文档化 | 10 种事件类型被过滤不推送，但需求未覆盖 | 用户配置这些事件后困惑为何不推送 |
| ntfy 渠道前端缺失 | 后端注册表 8 个渠道，前端仅 7 个，ntfy 缺失 | 用户无法通过界面配置 ntfy |
| `webhook_token` 前端缺失 | webhook 渠道仅 `webhook_url`，缺鉴权 token | 无法配置带鉴权的 webhook |
| 潜在 bug 未标注 | `_check_notifier` 访问 `hub.channels`（实际是 `notifiers`）；`_SHARE_REDACT_PATHS` 脱敏遗漏 | 健康检查误报 + 分享泄露风险 |

**解决方案**：将 `NotifierConfig`（Pydantic）+ `NotifierHub`（运行时）+ `NotifierRegistry`（注册表）+ `QuietHoursConfig`（免打扰）+ `NotifierChannels/index.tsx`（前端）+ 7 个 API 端点统一暴露；同时定义并发 fan-out 推送策略、YAML 明文凭据存储、quiet_hours 热更新边界、`_DB_ONLY_EVENTS` 过滤、4 个已知 Bug / 限制标注，**让通知渠道配置可视化、可测试、可订阅、可热更新（仅免打扰）**。

### 1.3 范围与约束

#### 1.3.1 包含范围（In-Scope）

- 7 个前端渠道（serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook）+ 后端 ntfy 共 8 个渠道的开关与凭据配置
- **并发 fan-out 推送策略**（`asyncio.gather`，非顺序降级）
- **YAML 顶层字段明文存储凭据**（keyring 作为可选 fallback）
- 22 种事件订阅 + severity 三色标签（info/important/critical）
- `_DB_ONLY_EVENTS` 过滤 10 种仅用于时间线/DB 的事件类型
- 免打扰时段（支持跨午夜、critical_only、weekend_only）
- 拖拽排序（@dnd-kit，写入 `default_channels`，仅决定初始化顺序）
- 分类排序（free/freemium/paid）+ 自定义排序双模式
- 测试推送（`POST /api/notifier/test`，使用前端传入凭据）
- **热更新机制**：仅 `quiet_hours` 通过 `PUT /api/notifier/quiet-hours` 热生效；其他配置通过通用 save 接口写盘 + reload_config，但 `NotifierHub` 实例需重启才重建
- 4 个 API 端点（`/api/notifier/quiet-hours` GET/PUT、`/api/notifier/quiet-hours/reset` POST、`/api/notifier/test` POST）
- 3 个通用配置端点（`/api/config` GET、`/api/config/preview` POST、`/api/config/save` POST）

#### 1.3.2 排除范围（Out-of-Scope）

- 不实现 ntfy 渠道的前端配置界面（前端 `defaultChannels` 缺失 ntfy）
- 不实现 `webhook_token` 字段的前端配置（webhook fields 仅有 `webhook_url`）
- 不实现 ntfy 凭据的 YAML 顶层字段声明（`AppConfig` 未声明 `ntfy_server` / `ntfy_topic` / `ntfy_token`）
- 不实现 ntfy 凭据的 `_build_yaml_credentials` 构建（即使手动添加 YAML 字段也读不到）
- 不修复 `_check_notifier` 健康检查 bug（访问不存在的 `hub.channels` 属性）
- 不修复 `_SHARE_REDACT_PATHS` 脱敏遗漏 bug（ntfy 凭据与 webhook_token 未列入）
- 不实现 `NotifierHub` 实例的热重建（修改渠道开关/凭据后需重启服务）
- 不实现独立的通知渠道 REST 路由（读写均通过通用配置接口 `/api/config`，仅免打扰与测试推送走专用端点）
- 不实现通知发送历史记录持久化（`suppressed_count` 仅进程内累计）
- 不实现通知模板的可视化编辑（模板硬编码在 `templates.py`）

## 2. 总体描述

### 2.1 产品定位

「通知渠道」是闲鱼猎人系统的**通知推送配置入口**，定位为：

> 通过 7 个前端渠道（后端注册表含 ntfy 共 8 个）的开关与凭据配置，结合 22 种事件订阅 + 免打扰时段 + 拖拽排序，让用户按需接收闲鱼商品评估、抢单、安全等关键事件通知；同一事件触发后通过 `asyncio.gather` 并发 fan-out 到所有已启用渠道，保证多渠道冗余与实时性。

**核心价值**：
1. **多渠道冗余**：并发 fan-out 推送，单一渠道故障不阻断通知送达
2. **细粒度订阅**：22 种事件 + severity 三色标签，用户按需订阅
3. **免打扰保护**：支持跨午夜、critical_only、weekend_only，避免深夜打扰
4. **凭据明文存储**：YAML 顶层字段明文，便于配置管理与备份（keyring 作为可选 fallback）
5. **免打扰热更新**：quiet_hours 通过专用端点立即生效，无需重启服务
6. **拖拽排序**：@dnd-kit 支持自定义渠道顺序（仅决定初始化顺序，不影响推送优先级）

### 2.2 用户角色与特征

| 角色 | 特征 | 使用场景 | 关注重点 |
|------|------|----------|----------|
| 新部署用户 | 首次配置通知渠道 | 进入 `/config/notifier` → 启用 serverchan → 填入 SendKey → 测试推送 | 默认配置、渠道选择、测试流程 |
| 日常运维 | 已配置渠道，关注送达率 | 查看测试推送结果、调整免打扰时段 | 测试推送响应、免打扰状态 |

## 3. 功能需求

### FR-1 渠道开关与凭据配置

**FR-1.1** 8 个渠道开关（`NotifierChannelsConfig`）
- 配置字段：`serverchan/pushplus/bark/telegram/wecom/dingtalk/webhook/ntfy`，均为 `bool`，默认 `True/True/True/False/False/False/False/False`
- 前端展示 7 个（缺 ntfy），ntfy 只能通过 YAML 启用
- 开关切换时同步到 `config.notifier.channels[key]`

**FR-1.2** 7 个前端渠道凭据字段（YAML 顶层明文存储）
- `serverchan`：`serverchan_send_key`（SendKey）
- `pushplus`：`pushplus_token`（Token）
- `bark`：`bark_server` + `bark_key`（Server URL + Device Key）
- `telegram`：`telegram_bot_token` + `telegram_chat_id`（Bot Token + Chat ID）
- `wecom`：`wecom_webhook`（Webhook URL）
- `dingtalk`：`dingtalk_webhook` + `dingtalk_secret`（Webhook URL + Secret）
- `webhook`：`webhook_url`（URL，**缺 `webhook_token` 前端字段**）

**FR-1.3** ntfy 渠道凭据（前端缺失，YAML 顶层字段未声明）
- 后端 `NotifierRegistry` 注册了 ntfy 渠道
- `secrets.py` 定义了 `KEY_NTFY_SERVER` / `KEY_NTFY_TOPIC` / `KEY_NTFY_TOKEN` 常量
- 但 `AppConfig` 顶层**未声明** `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段
- `_build_yaml_credentials` 函数**未构建** ntfy 凭据字典
- 即使手动在 YAML 中添加 ntfy 字段并启用，`NotifierHub` 初始化时也拿不到凭据

**FR-1.4** 凭据存储方式
- **主存储**：YAML 顶层字段明文（如 `serverchan_send_key: "SCT****"`）
- **可选 fallback**：`secrets.py` 提供 keyring 加密存储（Windows DPAPI），但 `NotifierHub` 初始化时优先从 `_build_yaml_credentials` 读取 YAML 明文
- **分享脱敏**：`GET /api/config/share` 按 `_SHARE_REDACT_PATHS` 列表脱敏，凭据字段替换为 `***`
- **已知 bug**：`_SHARE_REDACT_PATHS` 遗漏 ntfy 凭据与 `webhook_token`（详见 §6.4.2）

### FR-2 并发 fan-out 推送策略

**FR-2.1** 推送策略（`NotifierHub.send()`）
- 使用 `asyncio.gather` 并发 fan-out 到所有已启用渠道
- **没有降级逻辑**：单一渠道失败不影响其他渠道推送
- **没有"成功即停止"**：所有已启用渠道都会收到推送
- `return_exceptions=False`：异常会抛出但不会中断其他协程

**FR-2.2** `default_channels` 语义
- 仅决定渠道在 `NotifierHub` 初始化时的注册顺序
- **不决定推送优先级**（推送是并发 fan-out）
- 拖拽排序写入 `default_channels` 后保存，需重启服务才重建 `NotifierHub`（详见 §6.4.3）

**FR-2.3** 推送流程
1. 事件触发 → `EventBus` 分发到 `NotifierHub.send(event)`
2. 检查免打扰时段 → 若静默且非 critical，落"待发摘要"，返回
3. `asyncio.gather` 并发 fan-out 到所有已启用渠道
4. 各渠道独立推送（成功/失败各自记录）
5. 所有渠道推送完成

### FR-3 事件订阅与 `_DB_ONLY_EVENTS` 过滤

**FR-3.1** 22 种事件订阅
- 事件类型覆盖：任务生命周期（TASK_STARTED/STOPPED/PAUSED/ERROR/SEARCH_DONE）、商品评估（ITEM_DISCOVERED/EVAL_PASSED/REJECTED/SCORED）、购买（BUY_REQUESTED/SUCCEEDED/FAILED）、通知（NOTIFY_SENT）、安全（WAF_TRIGGERED/BLOCKED）、认证（LOGIN_EXPIRED/AUTH_EXPIRED）、系统（SYSTEM_ERROR）、维护（MAINTENANCE_*）
- severity 三级：`info`（蓝色）/ `important`（橙色）/ `critical`（红色）
- 默认订阅：`EVAL_PASSED` + `BUY_SUCCEEDED`
- 订阅列表持久化到 YAML `notifier.subscribed_events`

**FR-3.2** `_DB_ONLY_EVENTS` 过滤（10 种事件）
- 位置：`backend/xianyu_hunter/container.py` 第 59-73 行
- 集合内容：`TASK_STOPPED` / `TASK_SEARCH_DONE` / `ITEM_FOUND` / `EVAL_SCORED` / `WAF_BLOCKED` / `AUTH_EXPIRED` / `SYSTEM_ERROR` / `MAINTENANCE_DATABASE` / `MAINTENANCE_LOGS` / `MAINTENANCE_CACHE`
- 这些事件**仅用于时间线 / DB 持久化**，不通过 NotifierHub 推送
- `_resolve_subscribed_events` 函数在解析用户配置的 `subscribed_events` 时会跳过这些事件类型，并打印 info 日志告知用户
- 即使用户在 `subscribed_events` 中配置了这些事件，也不会被推送

**FR-3.3** 未知事件类型处理
- `_resolve_subscribed_events` 遇到未知事件名（不在 `EventType` 枚举中）时打印 warning 日志并跳过
- 例如 `chatbot.*` 事件不通过 NotifierHub 推送

### FR-4 免打扰时段

**FR-4.1** 免打扰配置（`QuietHoursConfig`）
- `enabled: bool=False`：免打扰总开关
- `start: str="23:00"`：开始时间（HH:MM）
- `end: str="07:00"`：结束时间（HH:MM，支持跨午夜）
- `critical_only: bool=True`：仅 critical 级别可推送
- `weekend_only: bool=False`：仅周末启用

**FR-4.2** 跨午夜支持
- 当 `start > end` 时（如 23:00-07:00），静默窗口跨午夜
- `is_quiet_now(cfg)` 自动处理跨午夜判定
- `QuietHoursTimeline` 组件可视化 24 小时静默区间

**FR-4.3** critical_only 语义
- 静默窗口内，若 `critical_only=true`，仅 critical 级别事件可推送
- 其他事件落本地"待发摘要"
- `suppressed_count` 统计被静默的事件数

**FR-4.4** weekend_only 语义
- `weekend_only=true` 表示仅周末（周六/日）启用免打扰
- 工作日保持全量推送
- 与 `enabled` 是 AND 关系

**FR-4.5** 热更新机制
- 通过 `PUT /api/notifier/quiet-hours` 端点更新
- 写盘 + `reload_config()` + `container.notifier_hub.set_quiet_hours()` 三步联动
- **立即生效**，无需重启服务

**FR-4.6** 静默计数重置
- `POST /api/notifier/quiet-hours/reset` 清空 `suppressed_count`
- 返回 `{ok, suppressed_count: 0}`

#### 5.1.5 单例加载与热更新

```python
# backend/xianyu_hunter/infra/yaml_config.py

_config: AppConfig | None = None

def get_config() -> AppConfig:
    """单例获取 AppConfig"""
    global _config
    if _config is None:
        _config = _load_all()  # 加载 config/*.yaml + 深度合并
    return _config

def reload_config() -> AppConfig:
    """热更新：重置单例，下次 get_config() 触发完整重载"""
    global _config
    _config = None
    return get_config()
```

**热更新流程**（通用 save 接口）：
1. 前端 `confirmSave()` → `POST /api/config/save {payload, dry_run: false}`
2. 后端 `_load_yaml()` 读取当前 `config.yaml` → `_deep_merge(new, payload)` → `_validate(new)` 校验
3. 创建带时间戳备份 `config/backups/config.yaml.bak.YYYYMMDD-HHMMSS`
4. 写盘 `CONFIG_FILE.write_text(_dump_yaml(new))`
5. 调用 `reload_config()` 重置单例 `_config = None`
6. 写盘失败时从刚生成的备份恢复
7. 返回 `{ok, saved_at, diffs, backup, restart_required: true, restart_note}`

**热更新流程**（免打扰专用接口）：
1. 前端 `PUT /api/notifier/quiet-hours {enabled, start, end, critical_only, weekend_only}`
2. 后端校验 HH:MM 格式
3. 写盘（更新 `notifier.quiet_hours` 段）
4. 调用 `reload_config()` 重置单例 `_config = None`
5. **额外调用 `container.notifier_hub.set_quiet_hours(new_config)`** 立即更新 hub 内的免打扰配置
6. 返回 `{ok, config, is_quiet_now}`

> **重要**：`restart_required=true` 仅是建议提示——配置已通过 `reload_config()` 立即生效，但 `NotifierHub` 实例需重启才重建（详见 §6.4.3）。仅 `quiet_hours` 通过专用端点热生效。

### 6.4 已知 Bug 与限制（v1.0 标注，未修复）

> 本节列出 v1.0 SRS 编写时调研发现的已知问题，**未修复**，仅供排错参考与验收边界说明。

#### 6.4.1 Bug：`_check_notifier` 访问不存在的 `hub.channels` 属性

**位置**：`backend/xianyu_hunter/web/app.py` 第 95-102 行

```python
def _check_notifier(container: Any) -> str:
    try:
        hub = container.notifier_hub
        channels = getattr(hub, "channels", []) or []  # ← Bug: hub 暴露的是 notifiers 不是 channels
        return "configured" if channels else "not_configured"
    except Exception:
        return "unknown"
```

**根因**：`NotifierHub` 实际暴露的属性是 `notifiers`（返回 Notifier 实例列表），而非 `channels`。`getattr(hub, "channels", [])` 永远返回默认值 `[]`，导致 `_check_notifier` 永远返回 `"not_configured"`。

**实际表现**：`/healthz` 端点中的 notifier 检查项始终显示未配置（即使已配置多个渠道）。

**正确修复方向**：将 `getattr(hub, "channels", [])` 改为 `getattr(hub, "notifiers", [])`。

#### 6.4.2 Bug：`_SHARE_REDACT_PATHS` 脱敏遗漏 ntfy 与 webhook_token

**位置**：`backend/xianyu_hunter/web/routes/api_config.py` 第 300-313 行

```python
_SHARE_REDACT_PATHS = [
    ("notifier", "channels"),
    ("serverchan_send_key",),
    ("pushplus_token",),
    ("bark_server",),
    ("bark_key",),
    ("telegram_bot_token",),
    ("telegram_chat_id",),
    ("wecom_webhook",),
    ("dingtalk_webhook",),
    ("dingtalk_secret",),
    ("webhook_url",),
    # ← 遗漏：ntfy_server / ntfy_topic / ntfy_token / webhook_token
    ("browser", "user_data_dir"),
]
```

**根因**：分享配置时（`GET /api/config/share`）会按此列表脱敏，但 ntfy 凭据与 webhook_token 未列入。当前因为 `AppConfig` 顶层未声明 ntfy 字段，泄露风险仅限"用户手动在 YAML 中添加 ntfy 字段"的场景；webhook_token 同理。

**实际表现**：若用户手动在 `config.yaml` 顶层添加 `ntfy_token: "****"` 或 `webhook_token: "****"`，分享配置时这些字段不会被脱敏，存在泄露风险。

**正确修复方向**：在 `_SHARE_REDACT_PATHS` 中追加 `("ntfy_server",)`、`("ntfy_topic",)`、`("ntfy_token",)`、`("webhook_token",)`。

#### 6.4.3 限制：`NotifierHub` 实例需重启才重建

**位置**：`backend/xianyu_hunter/container.py` 第 211-250 行 `wire_notifier` 方法

**现象**：通用 `/api/config/save` 写盘后调用 `reload_config()` 重置 `_config` 单例，但 `container.notifier_hub` 实例**不会自动重建**。`NotifierHub` 在 `wire_notifier()` 中构造，而 `wire_notifier()` 通常仅在启动时调用一次。

**实际表现**：用户在前端修改渠道开关或凭据后保存，配置文件已更新、内存单例已重置，但**正在运行的 `NotifierHub` 实例仍使用旧配置**，需要重启服务才能让新渠道配置生效。

**为什么 quiet_hours 不受此限制**：`PUT /api/notifier/quiet-hours` 端点在写盘 + reload_config 后，额外调用 `container.notifier_hub.set_quiet_hours()` 主动更新 hub 内的免打扰配置，因此免打扰可热生效。

**临时方案**：修改渠道开关或凭据后需要重启服务。未来若需热更新，可在 `api_config.save` 中检测 `notifier` 段变更后触发 `container.wire_notifier()` 重建 hub。

#### 6.4.4 限制：ntfy 渠道完整链路未打通

**位置**：多处

**现象**：ntfy 渠道当前存在多个未实现的环节：
1. 前端 `defaultChannels` 未定义 ntfy，无法通过界面配置（`constants.ts` 第 31-121 行）
2. `AppConfig` 顶层未声明 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段（`yaml_config.py` 第 530-539 行）
3. `_build_yaml_credentials` 未构建 ntfy 凭据字典（`container.py` 第 76-109 行）
4. 即使手动在 YAML 中添加 ntfy 字段并启用，`NotifierHub` 初始化时也拿不到凭据

**实际表现**：ntfy 渠道在后端注册表中存在但前端到后端的完整链路未打通，建议暂不使用。

**正确修复方向**：
1. 在 `AppConfig` 中追加 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段（与 `secrets.py` 中的 `KEY_NTFY_*` 常量对齐）
2. 在 `_build_yaml_credentials` 中追加 ntfy 凭据构建分支
3. 在 `_SHARE_REDACT_PATHS` 中追加 ntfy 字段脱敏
4. 在前端 `defaultChannels` 中追加 ntfy 渠道定义

#### 6.4.5 限制：前端 webhook_token 字段缺失

**位置**：`frontend/src/pages/Config/NotifierChannels/constants.ts` webhook 渠道定义

### 8.5 FAQ / 设计权衡

**Q1：为什么用并发 fan-out 而非顺序降级？**
A：三个原因：
1. **可靠性**：单一渠道故障不应阻断通知送达；并发推送保证多渠道冗余
2. **实时性**：用户配置多渠道的目的是"同时收到"而非"依次尝试"
3. **避免噪音是靠订阅与免打扰，不靠降级**：通过 `subscribed_events` 与 `quiet_hours` 控制通知频率，而不是靠"成功即停止"的降级

**Q2：为什么凭据用 YAML 明文存储而非 keyring 加密？**
A：`secrets.py` 提供了 keyring 加密存储，但 `NotifierHub` 初始化时优先从 `_build_yaml_credentials` 读取 YAML 明文作为 fallback。原因：
1. **数据流连贯**：用户在前端保存凭据时只写入 yaml，但 notifier `__init__` 优先从 keyring 读取；当 keyring 中没有时，用 yaml 明文兜底，避免"配置已保存但通知不发送"的数据流断裂
2. **配置可移植**：YAML 明文便于备份、迁移、分享（脱敏后）
3. **个人辅助工具的安全边界**：本项目是本地单用户工具，YAML 明文 + 文件权限限制已满足安全边界；keyring 提供更强保护但非必需

**Q3：为什么仅 quiet_hours 热生效，其他配置需重启？**
A：`NotifierHub.set_quiet_hours()` 提供了无需重建 hub 的轻量更新接口；其他配置项变更（渠道开关、凭据、订阅事件）需要重建 `NotifierHub` 实例（重新构造 Notifier 列表、重新订阅事件），开销较大，且通常只在初始化时执行一次。免打扰时段是高频调整项，因此单独提供热更新端点。

**Q4：`_DB_ONLY_EVENTS` 过滤 10 种事件，为什么这些事件不推送？**
A：这些事件（TASK_STOPPED/TASK_SEARCH_DONE/ITEM_FOUND/EVAL_SCORED/WAF_BLOCKED/AUTH_EXPIRED/SYSTEM_ERROR/MAINTENANCE_*）**仅用于时间线 / DB 持久化**，不需要即时通知用户。例如 `EVAL_SCORED` 是评估打分完成的内部事件，用户关心的是 `EVAL_PASSED`（评估通过）而非打分过程；`MAINTENANCE_*` 是维护任务完成事件，不需要打扰用户。即使用户在 `subscribed_events` 中配置了这些事件，`_resolve_subscribed_events` 也会跳过并打印 info 日志告知用户。

**Q5：为什么 ntfy 渠道前端缺失？**
A：ntfy 渠道在后端 `NotifierRegistry` 中注册了，但前端 `defaultChannels` 未定义 ntfy。同时 `AppConfig` 顶层未声明 `ntfy_server` / `ntfy_topic` / `ntfy_token` 字段，`_build_yaml_credentials` 也未构建 ntfy 凭据。即使手动在 YAML 中添加 ntfy 字段并启用，`NotifierHub` 初始化时也拿不到凭据。ntfy 渠道当前完整链路未打通，建议暂不使用（详见 §6.4.4）。

**Q6：为什么 `webhook_token` 前端缺失？**
A：前端 webhook 渠道的 fields 仅有 `webhook_url`，缺 `webhook_token`。同时 `AppConfig` 顶层未声明 `webhook_token` 字段。用户无法通过前端界面配置 webhook 鉴权 token（详见 §6.4.5）。

**Q7：为什么 `_check_notifier` 健康检查永远返回 not_configured？**
A：这是已知 bug（详见 §6.4.1）。`_check_notifier` 函数访问 `hub.channels` 属性，但 `NotifierHub` 实际暴露的属性是 `notifiers`。`getattr(hub, "channels", [])` 永远返回默认值 `[]`，导致永远返回 `"not_configured"`。修复方向：改为 `getattr(hub, "notifiers", [])`。

**Q8：为什么分享配置时 ntfy 凭据不会被脱敏？**
A：这是已知 bug（详见 §6.4.2）。`_SHARE_REDACT_PATHS` 列表遗漏了 `ntfy_server` / `ntfy_topic` / `ntfy_token` / `webhook_token`。当前因为 `AppConfig` 顶层未声明这些字段，泄露风险仅限"用户手动在 YAML 中添加"的场景。修复方向：在列表中追加这些字段。

**Q9：为什么修改了渠道开关后推送还是用旧配置？**
A：这是 `NotifierHub` 实例未热重建的限制（详见 §6.4.3）。通用 `/api/config/save` 写盘 + reload_config 后，`_config` 单例已重置，但 `container.notifier_hub` 实例仍使用旧配置。需要重启服务才能让新渠道配置生效。免打扰时段不受此限制（有专用热更新端点）。

**Q10：为什么 `default_channels` 不决定推送优先级？**
A：推送是 `asyncio.gather` 并发 fan-out，所有已启用渠道同时推送，没有"优先级"概念。`default_channels` 仅决定渠道在 `NotifierHub` 初始化时的注册顺序（影响 `notifiers` 列表的顺序，但不影响推送行为）。
