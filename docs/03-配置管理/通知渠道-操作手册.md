## 1. 功能简介

「通知渠道」是闲鱼猎人系统的**通知推送配置入口**，位于「配置管理」一级菜单下，是商品评估、抢单、安全等关键事件通知的核心配置页面。

通过本菜单，运营/管理员可以完成以下工作：

- **配置 7 个通知渠道**：Server酱、PushPlus、Bark、Telegram、企业微信、钉钉、自定义 Webhook
- **多渠道并发推送**：同一事件同时推送到所有已启用的渠道，单一渠道故障不影响其他渠道
- **发送测试推送**：每个渠道卡片内独立提供测试按钮，验证凭据是否有效
- **拖拽排序渠道顺序**：自定义渠道在初始化时的注册顺序
- **分类排序模式**：按定价（免费 / 免费有额度 / 收费）分组展示
- **配置免打扰时段**：支持跨午夜（如 23:00-07:00）、仅 critical 级别可推送、仅周末启用
- **订阅事件类型**：22 种事件 + severity 三色标签（信息 / 重要 / 严重），按需订阅
- **保存前预览变更**：Diff 弹窗展示具体改动项，避免误操作

> **提示**：通知渠道是闲鱼猎人接收关键事件通知的核心配置。建议新用户先阅读本手册第 4 章操作指南，至少配置一个渠道并完成测试推送。

## 2. 入口与导航

### 2.1 菜单入口

通知渠道位于系统左侧导航栏的「配置管理」分组下：

```
配置管理
  └── 通知渠道   （图标：铃铛，排序：第 104 位）
```

### 2.2 进入方式

| 方式 | 操作 | 说明 |
|------|------|------|
| 菜单点击 | 展开左侧「配置管理」→ 点击「通知渠道」 | 默认入口，推荐 |
| 命令面板 | 按 `Ctrl+K` → 输入"通知"或"notifier" → 选择对应命令 | 模糊搜索，支持任意关键词 |
| URL 直接访问 | 在浏览器地址栏输入通知渠道路径 | 刷新页面后自动恢复 |

### 2.3 子页面导航

通知渠道本身为单页面，无子页面跳转。但与以下菜单存在联动关系：

| 关联菜单 | 跳转方向 | 用途 |
|----------|----------|------|
| 任务管理 | 反向跳转 | 任务调度触发的事件会通过通知渠道推送 |
| 商品中心 | 反向跳转 | 商品评估通过/拒绝事件会触发通知 |
| 抢单记录 | 反向跳转 | 抢单成功/失败事件会触发通知 |
| 配置版本 | 同级菜单 | 通知渠道保存的备份在配置版本菜单统一管理 |

> **提示**：在配置通知渠道前，建议先到「任务管理」菜单确认已有运行中的任务，这样才能收到真实的事件通知用于验证。

### 3.2 渠道卡片说明

每个渠道卡片包含以下元素：

| 元素 | 位置 | 说明 |
|------|------|------|
| 渠道开关 | 卡片标题右侧 | 独立控制该渠道是否启用 |
| 凭据输入框 | 卡片内容区 | 填写该渠道所需的凭据（如 SendKey、Token、Webhook URL 等） |
| 发送测试按钮 | 卡片底部 | 用当前填写的凭据发送测试消息，验证是否有效 |

> **提示**：渠道开关关闭后，该渠道不会被推送。但凭据字段仍然可以编辑，方便用户预先配置。

### 3.3 右侧面板说明

| 区域 | 内容 | 说明 |
|------|------|------|
| 免打扰时段 | 启用开关 + 开始/结束时间 + 24h 时间轴 + 两个复选框 | 配置静默窗口，避免深夜打扰 |
| 事件订阅规则 | 22 个 Checkbox + severity 颜色标签 | 按需订阅事件类型 |

> **提示**：免打扰时段配置后**立即生效**，无需保存整个页面。事件订阅与渠道开关需要保存后才生效。

## 4. 操作指南

### 4.1 进入通知渠道页面

#### 操作步骤

1. 登录闲鱼猎人系统
2. 在左侧导航栏展开「配置管理」分组
3. 点击「通知渠道」菜单项
4. 页面加载完成，显示 7 个渠道卡片 + 免打扰时段 + 事件订阅规则

#### 操作结果

- 页面正确加载，7 个渠道卡片按 Server酱 / PushPlus / Bark / Telegram / 企业微信 / 钉钉 / Webhook 顺序排列
- 右侧免打扰时段卡片显示默认配置（23:00-07:00，仅严重级别可推送）
- 右侧事件订阅规则卡片显示 22 个事件 Checkbox，默认勾选"评估通过"和"抢单成功"

> **提示**：首次进入页面时，7 个渠道开关使用系统默认值：Server酱开启、PushPlus 开启、Bark 开启，其他渠道关闭。但都需要填写凭据后才能真正推送。

---

### 4.2 配置 Server酱微信推送

#### 操作步骤

1. 在「Server酱」卡片中，确认开关已开启（蓝色为开启状态）
2. 在「SendKey」输入框中填入从 sct.ftqq.com 获取的 SendKey
3. 点击「发送测试」按钮验证凭据是否有效
4. 收到微信推送通知表示配置成功

#### 参数说明

| 参数 | 含义 | 获取方式 | 默认值 |
|------|------|----------|--------|
| 开关 | 是否启用 Server酱 | — | 开启 |
| SendKey | Server酱推送密钥 | 访问 sct.ftqq.com 注册获取 | 空 |

#### 操作结果

- 开启时：事件触发后通过微信公众号推送消息
- 关闭时：该渠道不推送
- 测试推送成功表示凭据有效

> **提示**：Server酱是免费有额度限制的渠道（freemium），每日推送次数有上限。如需大量推送，建议同时配置其他渠道作为冗余。

---

### 4.3 配置 Bark 推送（iOS）

#### 操作步骤

1. 在 App Store 下载并安装 Bark 应用
2. 打开 Bark 应用，复制推送 URL（如 `https://api.day.app/****/`）
3. 在「Bark」卡片中，确认开关已开启
4. 在「Server URL」输入框中填入服务器地址（如 `https://api.day.app`）
5. 在「Device Key」输入框中填入设备密钥
6. 点击「发送测试」按钮验证

#### 参数说明

| 参数 | 含义 | 获取方式 | 默认值 |
|------|------|----------|--------|
| 开关 | 是否启用 Bark | — | 开启 |
| Server URL | Bark 服务器地址 | Bark 应用内显示 | 空 |
| Device Key | 设备推送密钥 | Bark 应用内显示 | 空 |

#### 操作结果

- 开启时：事件触发后通过 iOS 推送通知
- 关闭时：该渠道不推送

> **提示**：Bark 是完全免费的渠道（free），支持自建服务器。如担心公共服务器稳定性，可参考 Bark 官方文档自建。

---

### 4.4 配置 Telegram 推送

#### 操作步骤

1. 在 Telegram 中搜索 `@BotFather`，创建一个新 Bot，获取 Bot Token
2. 在 Telegram 中搜索 `@userinfobot`，获取你的 Chat ID
3. 在「Telegram」卡片中，点击开关开启（默认关闭）
4. 在「Bot Token」输入框中填入 Bot Token
5. 在「Chat ID」输入框中填入 Chat ID
6. 点击「发送测试」按钮验证

#### 参数说明

| 参数 | 含义 | 获取方式 | 默认值 |
|------|------|----------|--------|
| 开关 | 是否启用 Telegram | — | 关闭 |
| Bot Token | Telegram Bot 的令牌 | @BotFather 创建 Bot 后获取 | 空 |
| Chat ID | 接收消息的会话 ID | @userinfobot 获取 | 空 |

#### 操作结果

- 开启时：事件触发后通过 Telegram Bot 推送消息
- 关闭时：该渠道不推送

> **提示**：Telegram 是完全免费的渠道（free），支持 Markdown 格式，跨平台覆盖。需要能访问 Telegram 服务器（中国大陆需代理）。

---

### 4.5 配置企业微信 / 钉钉推送

#### 操作步骤（企业微信）

1. 在企业微信群中添加「群机器人」，获取 Webhook URL
2. 在「企业微信」卡片中，点击开关开启（默认关闭）
3. 在「Webhook URL」输入框中填入 Webhook URL
4. 点击「发送测试」按钮验证

#### 操作步骤（钉钉）

1. 在钉钉群中添加「自定义机器人」，获取 Webhook URL 和 Secret
2. 在「钉钉」卡片中，点击开关开启（默认关闭）
3. 在「Webhook URL」输入框中填入 Webhook URL
4. 在「Secret」输入框中填入加签密钥（如未启用加签可留空）
5. 点击「发送测试」按钮验证

#### 参数说明

| 参数 | 含义 | 获取方式 | 默认值 |
|------|------|----------|--------|
| 企业微信 Webhook URL | 群机器人推送地址 | 群设置 → 添加机器人 | 空 |
| 钉钉 Webhook URL | 自定义机器人推送地址 | 群设置 → 添加机器人 | 空 |
| 钉钉 Secret | 加签密钥（可选） | 机器人配置时显示 | 空 |

#### 操作结果

- 开启时：事件触发后通过企业微信 / 钉钉群推送消息
- 关闭时：该渠道不推送

> **提示**：企业微信和钉钉都是完全免费的渠道（free），适合团队协作场景。一个群只能添加一个机器人，Webhook URL 即机器人身份。

---

### 4.6 配置自定义 Webhook

#### 操作步骤

1. 准备一个可接收 POST 请求的 Web 服务（如自建 API、第三方集成平台）
2. 在「Webhook」卡片中，点击开关开启（默认关闭）
3. 在「Webhook URL」输入框中填入 Webhook 地址
4. 点击「发送测试」按钮验证

#### 参数说明

| 参数 | 含义 | 获取方式 | 默认值 |
|------|------|----------|--------|
| 开关 | 是否启用自定义 Webhook | — | 关闭 |
| Webhook URL | 接收推送的 URL | 自建或第三方平台提供 | 空 |

#### 操作结果

- 开启时：事件触发后向指定 URL 发送 POST 请求
- 关闭时：该渠道不推送

> **已知限制**：当前前端仅支持配置 Webhook URL，**不支持配置鉴权 Token**。如需带鉴权的 Webhook，需要直接编辑配置文件手动添加 `webhook_token` 字段（但该字段当前未在配置模型中声明，可能无法生效，详见 §7.5）。

---

### 4.7 发送测试推送

#### 操作步骤

1. 在目标渠道卡片中填写完整凭据
2. 点击该卡片底部的「发送测试」按钮
3. 等待系统调用第三方渠道 API 发送测试消息
4. 查看推送结果：
   - **成功**：在对应渠道收到测试消息，按钮下方显示"推送成功"
   - **失败**：按钮下方显示错误信息（如"SendKey 无效"、"网络超时"等）

#### 操作结果

- 测试推送使用**当前填写的凭据**（不是已保存的值）
- 用户可以边修改凭据边测试，验证新值是否有效
- 测试推送不会触发完整的事件订阅流程，仅验证渠道可达性

> **提示**：测试推送是验证凭据有效性的最佳方式。建议每次修改凭据后都发送测试，确保配置可用。测试推送可能因第三方服务延迟而较慢（最长 10 秒）。

---

### 4.8 拖拽排序渠道顺序

#### 操作步骤

1. 在「通道顺序」卡片中，按住某个渠道卡片左侧的拖拽手柄
2. 拖动到目标位置，释放鼠标
3. 渠道顺序立即更新，写入 `default_channels` 配置
4. 点击顶部「保存」按钮持久化

#### 操作结果

- 渠道顺序更新成功
- 保存后持久化到配置文件

> **重要澄清**：渠道顺序**仅决定渠道在初始化时的注册顺序，不影响推送优先级**。推送时所有已启用渠道会**同时并发推送**，不存在"先试 A 渠道，失败再用 B 渠道"的降级逻辑。详见 §7.1。

---

### 4.9 切换分类排序模式

#### 操作步骤

1. 在「渠道卡片墙」卡片顶部，找到「分类排序 / 自定义排序」切换按钮
2. 点击切换：
   - **分类排序模式**：按定价分组展示（免费 / 免费有额度 / 收费）
   - **自定义排序模式**：按 `default_channels` 顺序展示

#### 分类说明

| 分类 | 包含渠道 | 说明 |
|------|----------|------|
| 免费 | Bark / Telegram / 企业微信 / 钉钉 / Webhook | 完全免费，无额度限制 |
| 免费有额度 | Server酱 / PushPlus | 免费但有每日推送次数上限 |
| 收费 | 当前无 | 纯收费渠道 |

> **提示**：分类排序模式按"启用优先 + 功能完整性"排序，方便快速找到已启用的渠道。自定义排序模式按拖拽顺序展示，适合个性化布局。

### 4.10 配置免打扰时段

#### 操作步骤

1. 在右侧「免打扰时段」卡片中，点击「启用」开关开启（默认关闭）
2. 在「开始时间」选择器中设置静默开始时间（如 23:00）
3. 在「结束时间」选择器中设置静默结束时间（如 07:00）
4. 观察 24 小时时间轴预览，确认静默窗口
5. 根据需要勾选：
   - **仅严重级别可推送**：静默窗口内仅 critical 级别事件可推送
   - **仅周末启用**：仅周六/日启用静默，工作日全量推送
6. 免打扰配置**立即生效**，无需点击顶部「保存」按钮

#### 参数说明

| 参数 | 含义 | 取值范围 | 默认值 |
|------|------|----------|--------|
| 启用 | 免打扰总开关 | 开启/关闭 | 关闭 |
| 开始时间 | 静默开始时间 | 00:00-23:59 | 23:00 |
| 结束时间 | 静默结束时间 | 00:00-23:59 | 07:00 |
| 仅严重级别可推送 | 静默窗口内仅 critical 级别可推送 | 勾选/不勾选 | 勾选 |
| 仅周末启用 | 仅周末启用静默 | 勾选/不勾选 | 不勾选 |

#### 跨午夜支持

当开始时间 > 结束时间时（如 23:00-07:00），系统识别为**跨午夜静默窗口**。例如：
- 23:00-07:00：从当晚 23:00 到次日 07:00 静默
- 14:00-13:00：从当天 14:00 到次日 13:00 静默（几乎全天静默）

24 小时时间轴预览组件会可视化静默区间，方便确认配置是否符合预期。

#### 操作结果

- **立即生效**：免打扰配置通过专用接口更新，无需重启服务
- 静默窗口内，仅 critical 级别事件可推送（若勾选"仅严重级别可推送"）
- 其他事件落本地"待发摘要"，`suppressed_count` 统计被静默的事件数
- 可通过「重置静默计数」按钮清空累计计数

> **提示**：免打扰是高频调整项，因此提供专用接口立即生效。其他配置（渠道开关、凭据、订阅事件）需要保存后重启服务才能完全生效（详见 §7.3）。

## 6. 常见问题 FAQ

### Q1：保存配置后需要重启服务吗？

**A**：**视修改内容而定**：
- **免打扰时段**：通过专用接口更新，**立即生效**，无需重启
- **渠道开关、凭据、订阅事件**：写盘 + 重置内存单例后，**需要重启服务才能让通知总线重建**。响应中"需要重启"是真实提示，不是建议

这是因为通知总线实例在启动时构造，保存配置后不会自动重建。详见 §7.3。

### Q2：多个渠道会同时推送吗？

**A**：**会**。系统使用并发 fan-out 推送策略，同一事件会**同时推送到所有已启用的渠道**，互不影响。例如同时启用 Server酱、Bark、Telegram，当抢单成功事件触发时，三个渠道会同时收到推送。

单一渠道失败**不会**影响其他渠道的推送，也不存在"先试 A 渠道，失败再用 B 渠道"的降级逻辑。

### Q3：测试推送使用哪个凭据？

**A**：使用**当前填写的凭据**（不是已保存的值）。这样用户可以边修改凭据边测试，验证新值是否有效。例如修改 SendKey 后点击测试，系统会用新的 SendKey 发送测试消息。

### Q4：免打扰时段支持跨午夜吗？

**A**：支持。当开始时间 > 结束时间时（如 23:00-07:00），系统识别为跨午夜静默窗口，从当晚 23:00 到次日 07:00 静默。24 小时时间轴预览组件会可视化静默区间。

### Q5：为什么我订阅了"任务停止"事件但收不到通知？

**A**：这是因为"任务停止"属于**仅用于时间线记录的事件**，不会被推送。系统定义了 10 种仅用于时间线/数据库的事件类型（包括任务停止、搜索完成、商品发现、评估打分、WAF 拦截、认证过期、系统错误、数据库维护、日志维护、缓存维护），即使用户订阅也不会推送。这些事件是内部状态变更，不需要即时通知用户。详见 §7.2。

### Q6：为什么修改了渠道开关后推送还是用旧配置？

**A**：这是通知总线实例未热重建的限制。修改渠道开关或凭据后保存，配置文件已更新、内存单例已重置，但**正在运行的通知总线实例仍使用旧配置**，需要重启服务才能让新配置完全生效。

免打扰时段不受此限制（有专用热更新接口）。详见 §7.3。

### Q7：8 个渠道都有哪些？前端为什么只显示 7 个？

**A**：后端注册表支持 8 个渠道：Server酱 / PushPlus / Bark / Telegram / 企业微信 / 钉钉 / Webhook / **ntfy**。前端只显示 7 个（缺 ntfy），ntfy 渠道当前完整链路未打通，建议暂不使用。详见 §7.4。

### Q8：ntfy 渠道怎么配置？

**A**：**当前不支持通过前端配置 ntfy 渠道**。ntfy 渠道在后端注册表中存在，但前端界面缺失，且配置模型未声明 ntfy 凭据字段，即使手动编辑配置文件添加 ntfy 凭据也读不到。建议使用其他渠道替代。详见 §7.4。

### Q9：自定义 Webhook 怎么配置鉴权 Token？

**A**：**当前前端不支持配置 Webhook 鉴权 Token**。前端 Webhook 渠道仅有 URL 字段，缺 Token 字段。如需带鉴权的 Webhook，需要直接编辑配置文件手动添加 `webhook_token` 字段，但该字段当前未在配置模型中声明，可能无法生效。详见 §7.5。

### Q10：渠道顺序拖拽有什么用？

**A**：渠道顺序**仅决定渠道在初始化时的注册顺序，不影响推送优先级**。推送时所有已启用渠道会同时并发推送，不存在"先试 A 渠道，失败再用 B 渠道"的降级逻辑。拖拽排序主要是为了界面美观和管理便利。

### Q11：severity 三色标签是什么意思？

**A**：severity 是事件严重级别，分三级：
- **蓝色（信息）**：低重要性事件，如任务启动、商品发现
- **橙色（重要）**：中重要性事件，如评估通过、登录过期
- **红色（严重）**：高重要性事件，如抢单成功、系统错误

免打扰时段内若勾选"仅严重级别可推送"，仅红色标签的事件会推送，蓝色和橙色事件会被静默。

### Q12：分享配置会泄露凭据吗？

**A**：**正常情况下不会**，但存在已知 bug。分享配置时（通过配置版本菜单的分享功能）会按脱敏列表替换凭据字段为 `***`。但当前脱敏列表**遗漏了 ntfy 凭据和 webhook_token**（详见 §7.6），如果手动在配置文件中添加了这些字段，分享时不会被脱敏。建议分享前手动检查配置文件中是否包含敏感字段。

## 7. 注意事项与限制

### 7.1 渠道顺序不影响推送优先级

渠道顺序（拖拽排序写入的 `default_channels`）**仅决定渠道在初始化时的注册顺序，不影响推送优先级**。推送时所有已启用渠道会**同时并发推送**，不存在"先试 A 渠道，失败再用 B 渠道"的降级逻辑。如需控制通知频率，请通过事件订阅和免打扰时段配置。

### 7.2 10 种事件仅用于时间线，不会被推送

以下 10 种事件**仅用于时间线/数据库记录，不会被推送**，即使订阅也不会收到通知：

| 事件 | 说明 |
|------|------|
| 任务停止 | 任务被用户停止（内部状态变更） |
| 搜索完成 | 单轮搜索完成（内部流程） |
| 商品发现 | 发现新商品（信息量过大） |
| 评估打分 | AI 评估打分完成（用户关心的是评估通过，不是打分过程） |
| WAF 拦截 | 被 WAF 拦截（用户关心的是 WAF 触发，不是拦截结果） |
| 认证过期 | 认证过期（用户关心的是登录过期，不是认证过期） |
| 系统错误 | 系统错误（与"系统错误"事件重复，但仅时间线版本不推送） |
| 数据库维护 | 数据库维护完成（内部维护） |
| 日志维护 | 日志维护完成（内部维护） |
| 缓存维护 | 缓存维护完成（内部维护） |

如需查看这些事件，请到「事件日志」菜单查看完整时间线。

### 7.3 修改渠道开关/凭据后需重启服务才完全生效

修改渠道开关、凭据、订阅事件后保存，**配置文件已更新、内存单例已重置，但通知总线实例仍使用旧配置**，需要重启服务才能让新配置完全生效。

**不受此限制的配置**：
- **免打扰时段**：通过专用接口立即生效，无需重启

**临时方案**：修改渠道配置后重启服务。未来版本可能支持热重建通知总线。

### 7.4 ntfy 渠道完整链路未打通

ntfy 渠道当前存在多个未实现的环节：
1. 前端界面缺失 ntfy 渠道卡片
2. 配置模型未声明 ntfy 凭据字段
3. 凭据构建函数未包含 ntfy
4. 即使手动在配置文件中添加 ntfy 字段并启用，通知总线初始化时也拿不到凭据

**建议**：暂不使用 ntfy 渠道，使用其他 7 个渠道替代。未来版本会打通完整链路。

### 7.5 前端 Webhook 不支持鉴权 Token

前端 Webhook 渠道仅有 URL 字段，**缺鉴权 Token 字段**。如需带鉴权的 Webhook：
1. 直接编辑配置文件手动添加 `webhook_token` 字段
2. 但该字段当前未在配置模型中声明，**可能无法生效**

**建议**：如需鉴权，可在 Webhook 服务端使用 URL 中的 query 参数传递 token（如 `https://example.com/webhook?token=****`），作为临时方案。

### 7.6 分享配置脱敏遗漏 ntfy 与 webhook_token

分享配置时（通过配置版本菜单的分享功能）会按脱敏列表替换凭据字段为 `***`，但当前脱敏列表**遗漏了 ntfy 凭据和 webhook_token**。如果手动在配置文件中添加了这些字段，分享时不会被脱敏，存在泄露风险。

**临时方案**：分享前手动检查配置文件中是否包含 `ntfy_server` / `ntfy_topic` / `ntfy_token` / `webhook_token` 字段，如有请手动删除后再分享。

### 7.7 健康检查 notifier 项永远显示未配置

系统健康检查中的 notifier 项存在已知 bug，**永远显示"未配置"**，即使已配置多个渠道。这是健康检查函数访问了错误的属性名导致的，不影响实际推送功能。可忽略此检查项的显示。

### 7.8 免打扰时段立即生效

免打扰时段通过专用接口更新，**立即生效**，无需重启服务。修改后：
- 静默窗口立即按新配置判定
- `suppressed_count` 继续累计
- 可通过「重置静默计数」按钮清零

### 7.9 备份保留数量上限

每次保存自动创建带时间戳的备份，**最多保留 10 个**。超出后自动清理最旧的备份。如需长期保留某个版本，请手动复制备份文件到其他位置。

### 7.10 测试推送可能较慢

测试推送需要调用第三方渠道 API，可能因网络延迟或第三方服务响应慢而较慢（最长 10 秒）。如长时间无响应，请检查：
1. 凭据是否正确
2. 网络是否能访问第三方服务（如 Telegram 需要代理）
3. 第三方服务是否正常

### 7.11 凭据以明文存储

渠道凭据以**明文形式存储在配置文件**中（如 `serverchan_send_key: "SCT****"`）。系统提供 keyring 加密存储作为可选 fallback（Windows DPAPI），但主存储为明文。

**安全建议**：
1. 配置文件权限设置为仅当前用户可读写
2. 分享配置前确保已脱敏（注意 §7.6 的遗漏 bug）
3. 不要将配置文件提交到版本控制系统

### 7.12 默认订阅事件

系统默认订阅以下两个事件：
- **评估通过**（重要）：商品评估通过，值得购买
- **抢单成功**（严重）：抢单成功，已下单

其他事件需手动勾选订阅。建议只订阅关键事件，避免通知刷屏。

## 8. 关联功能

通知渠道与以下菜单存在联动关系：

| 关联菜单 | 联动关系 | 说明 |
|----------|----------|------|
| 任务管理 | 事件源 | 任务调度触发的事件（如评估通过、抢单成功）会通过通知渠道推送 |
| 商品中心 | 事件源 | 商品评估结果会触发通知 |
| 抢单记录 | 事件源 | 抢单成功/失败事件会触发通知 |
| 事件日志 | 时间线 | 10 种仅用于时间线的事件可在事件日志查看（不推送） |
| 配置版本 | 版本管理 | 通知渠道保存的备份在配置版本菜单统一管理，支持一键回滚 |
| 系统健康 | 健康检查 | notifier 检查项（已知 bug，永远显示未配置，详见 §7.7） |
| 安全防护 | 事件源 | WAF 触发、认证过期等安全事件会触发通知 |

> **提示**：通知渠道是闲鱼猎人接收关键事件通知的核心配置。建议至少配置一个渠道并完成测试推送，确保关键事件（如抢单成功）能及时收到通知。

### 10.3 免打扰时段配置流程图

```
用户配置免打扰时段
       ↓
通过专用接口更新（立即生效）
       ↓
写盘 + 重置内存单例 + 更新通知总线
       ↓
静默窗口立即按新配置判定
       ↓
事件触发时：
  ├─ 当前在静默窗口内
  │   ├─ 勾选"仅严重级别可推送" + 事件 severity=严重 → 推送

  └─ 当前不在静默窗口内 → 正常推送
```
