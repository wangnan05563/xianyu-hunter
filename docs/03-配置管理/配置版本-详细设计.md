## 2. 功能概述

**一句话说明**：通过版本号（系统构建版本 + 备份计数）+ 多版本备份（`BACKUP_KEEP=10`）+ 一键回滚 + 指定恢复 + 导入/导出 + 分享脱敏，实现配置的全生命周期管理与误操作回滚。

**核心价值**：
- **系统版本号来自 `/api/about`**（`_build_info.py` 写入的 `__version__`），不再使用备份数计数（备份数会因 `BACKUP_KEEP=10` 上限卡在 v10）
- 备份文件名 `config.yaml.bak.YYYYMMDD-HHMMSS`，秒级精度
- `BACKUP_KEEP=10`，超出自动清理旧备份
- 一键回滚（最近备份）+ 指定恢复（任意备份）双路径
- 回滚前自动备份当前配置（安全网）
- 白名单校验防目录穿越（filename 只含字母数字 + `-` `_` `.`）
- **写盘失败自动从备份恢复**（仅 `save_config` / `import_config`；`rollback` / `restore-backup` 缺失该保护）
- 导入流程：校验 schema → 预览 diff → Modal 确认 → 写盘
- 分享配置：前端调用 `/api/config/export` 后用 SENSITIVE_KEYS 4 项脱敏（绕过后端 `/api/config/share` 的 12 项脱敏）
- 字段级回滚：`configStore.getFieldOriginal` / `revertField` 支持点分路径

## 3. 用户场景

### 场景 1：误改配置后一键回滚
用户在"评估规则"页面误改了权重，保存后发现评分异常。进入"配置版本"页面，点击"一键回滚"，系统自动备份当前配置后用最近备份覆盖，配置恢复到上次保存的状态。

### 场景 2：从指定备份恢复
用户想恢复到 3 天前的配置版本。在版本时间线中找到对应备份，点击"恢复"按钮，系统从该备份恢复配置。回滚前会自动备份当前配置作为安全网。

### 场景 3：导出配置迁移到新机器
用户想在新机器上复用当前配置。点击"导出配置"，浏览器下载 `xianyu_hunter_config_YYYYMMDD_HHMMSS.json` 文件（含 schema + 元数据 + 脱敏配置）。在新机器点击"导入配置"上传该文件，预览 diff 后确认导入。

### 场景 4：分享配置给同事参考
用户想把自己的"参数调优思路"分享给同事。点击"分享配置"按钮，前端调用 `/api/config/export` 获取已脱敏配置（敏感凭证仅保留末 4 位），再用前端 SENSITIVE_KEYS 4 项二次脱敏（替换为 `***`），生成可复制的 JSON 文本。

### 场景 5：查看系统版本与构建信息
用户进入"配置版本"页面，顶部统计卡片显示系统版本（来自 `/api/about` 的 `__version__`），以及构建日期与 git SHA 前 7 位，便于判断版本新鲜度。

### 4.1 组件结构

```

│   └── 一键回滚按钮（danger，backups=0 时禁用）
├── 版本时间线 Card

│       ├── 最新版本（绿色 dot + CheckCircleOutlined）
│       └── 历史版本（灰色 dot）
│           ├── Tag（最新 / vN）
│           ├── 时间 + 文件大小
```

| 区域 | 交互行为 |

## 5. 接口定义

### 5.1 配置版本管理 API（`api_config.py`，prefix=`/api/config`）

| 方法 | 路径 | 用途 | 请求参数 | 响应字段 | 前端是否调用 |
|------|------|------|----------|----------|--------------|
| GET | `/api/config` | 返回当前生效配置（已脱敏） | 无 | 脱敏后的 AppConfig dict | 是（其他配置页） |
| GET | `/api/config/raw` | 返回 YAML 原始内容（脱敏） | 无 | `{raw: str}` | 是（其他配置页） |
| POST | `/api/config/preview` | 预览改动（不写盘） | `payload: dict` | `{diffs, validation, new_yaml?}` | 是（其他配置页） |
| POST | `/api/config/save` | 保存配置（带备份 + 写盘失败保护） | `{payload, dry_run}` | `{ok, dry_run, saved_at?, diffs, backup?, restart_required?, restart_note?}` | 是（其他配置页） |
| GET | `/api/config/backups` | 备份列表（按时间倒序） | 无 | `{backups[], count, keep}` | **是**（VersionManager） |
| POST | `/api/config/rollback` | 一键回滚到最近备份 | 无 | `{ok, rolled_back_to, rolled_back_file, version}` | **是**（VersionManager） |
| POST | `/api/config/restore-backup` | 从指定备份恢复 | `filename`（query） | `{ok, restored_from, restored_at}` | **是**（VersionManager） |
| GET | `/api/config/export` | 导出配置 JSON | 无 | JSON 文件下载（含 schema + 元数据 + 脱敏配置） | **是**（VersionManager 导出 + 分享） |
| POST | `/api/config/import` | 导入配置 JSON | `{schema, config, confirm?}` | `{ok, diffs, diff_count, backup, imported_at, restart_required} 或 {ok: false, needs_confirm, diffs, diff_count}` | **是**（VersionManager） |
| GET | `/api/config/version` | 获取备份数计数版本号 | 无 | `{version, latest_backup_ts, latest_backup_file}` | **❌ 僵尸接口**（前端不再调用） |
| GET | `/api/config/share` | 分享脱敏配置（后端 12 项） | 无 | `{summary, config, redacted_fields}` | **❌ 僵尸接口**（前端不再调用） |

## 7. 业务逻辑

### 7.1 版本号来源切换

> **v1.0 → v2.0 关键变更**：版本号不再等于备份数。

| 来源 | 用途 | 计算方式 | 上限 |
|------|------|----------|------|
| `/api/about` `version` | **前端展示** | `_build_info.__version__`（构建时写入） | 无上限 |
| `/api/config/version` `version` | 僵尸接口 | `len(_list_backups())` | 受 `BACKUP_KEEP=10` 限制，卡在 v10 |

**为什么切换**：备份数计数会因 `BACKUP_KEEP=10` 上限卡在 v10，无法反映系统真实版本。改用 `_build_info.__version__` 后，版本号随发布递增，与"关于"页一致。

### 7.2 备份文件命名与清理

#### 命名规则

位置：`api_config.py` `_new_backup_name()` 函数（第 102-104 行）

```
config.yaml.bak.YYYYMMDD-HHMMSS
```
- 秒级精度，足够日常区分
- 例：`config.yaml.bak.20260705-100000`

#### 自动清理

位置：`api_config.py` `_prune_backups()` 函数（第 133-150 行）

- `BACKUP_KEEP=10`：保留最近 10 个备份
- 超出的旧备份自动清理（按 mtime 倒序，保留前 10）
- 单个清理失败不影响其他（`except OSError: pass`）
- 不软删除/归档：备份仅为"误改后回滚"，无需审计

### 7.3 回滚逻辑

#### 一键回滚（最近备份）

位置：`api_config.py` `rollback_config()` 函数（第 578-611 行）

1. `_list_backups()` 获取备份列表
2. 若无备份 → 404 "没有可回滚的备份"
3. 取 `backups[0]`（最新备份）作为目标
4. **回滚前先备份当前配置**（安全网）：`pre_bak = BACKUP_DIR / _new_backup_name()`，写入当前配置
5. `_prune_backups()` 清理超出 `BACKUP_KEEP` 的旧备份
6. 用目标备份覆盖 `CONFIG_FILE`
7. `reload_config()` 重置单例
8. 返回 `{ok, rolled_back_to, rolled_back_file, version}`

**为什么回滚前先备份**：防止误操作后无法恢复。回滚本身也是一次"配置变更"，需要可追溯。

> **⚠️ 写盘失败保护缺失**：`rollback_config` 第 603 行 `CONFIG_FILE.write_text(...)` 未包裹 try/except，写盘失败（磁盘满/权限问题）会抛未捕获异常，配置文件可能损坏。对比 `save_config` / `import_config` 有 try/except 从备份回滚。

> **⚠️ restart_required 缺失**：`rollback_config` 返回值不含 `restart_required` 字段，前端无法提示用户"需重启调度器才生效"。对比 `save_config` / `import_config` 返回 `restart_required: True`。

#### 指定恢复（任意备份）

位置：`api_config.py` `restore_backup()` 函数（第 614-638 行）

1. 不传 filename → 回退到旧 `.yaml.bak`（兼容升级前已存在的备份）
2. 传 filename → `_resolve_backup(filename)` 校验白名单
3. 用目标备份覆盖 `CONFIG_FILE`
4. `reload_config()` 重置单例
5. 返回 `{ok, restored_from, restored_at}`

> **⚠️ 写盘失败保护缺失**：`restore_backup` 第 632 行 `CONFIG_FILE.write_text(...)` 未包裹 try/except，写盘失败会抛未捕获异常。

> **⚠️ restart_required 缺失**：`restore_backup` 返回值不含 `restart_required` 字段。

> **⚠️ 安全网缺失**：`restore_backup` 不像 `rollback_config` 那样在恢复前自动备份当前配置，用户误操作后无法回退到恢复前的状态。

### 7.4 白名单校验防目录穿越

位置：`api_config.py` `_resolve_backup()` 函数（第 153-166 行）

```python
def _resolve_backup(filename: str) -> Path:
    if not filename or not filename.startswith(BACKUP_PREFIX):
        raise HTTPException(status_code=400, detail="非法的备份文件名")
    if not all(c.isalnum() or c in "-_." for c in filename):
        raise HTTPException(status_code=400, detail="备份文件名包含非法字符")
    p = BACKUP_DIR / filename
    if not p.is_file():
        raise HTTPException(status_code=404, detail=f"备份 {filename} 不存在")
    return p
```

**为什么需要**：防止 `filename` 里塞 `../` 实现目录穿越读取任意文件。白名单字符集：字母数字 + 时间戳分隔符（`-`）+ `.` + `_`。

### 7.5 写盘失败保护（仅 save_config / import_config）

位置：`api_config.py` `save_config()` 函数（第 263-272 行）、`import_config()` 函数（第 539-545 行）

```python
try:
    CONFIG_FILE.write_text(_dump_yaml(new), encoding="utf-8")
    reload_config()
except Exception as e:
    if new_bak and new_bak.exists():
        CONFIG_FILE.write_text(new_bak.read_text(encoding="utf-8"), encoding="utf-8")
    raise HTTPException(status_code=500, detail=f"写入失败，已回滚: {e}")
```

**为什么需要**：写盘可能因磁盘满/权限问题失败。失败后从刚生成的备份恢复，保证配置文件不损坏。

> **⚠️ 保护范围**：仅 `save_config` 和 `import_config` 实现了该保护。`rollback_config` 和 `restore_backup` **未实现**，写盘失败时配置文件可能损坏。

### 7.6 导入流程

位置：`api_config.py` `import_config()` 函数（第 480-558 行）

1. 校验 `schema == "xianyu_hunter.config/v1"`，否则 400
2. 校验 `config` 是 dict，否则 400
3. `_validate(incoming)` 用 AppConfig 模型校验，失败 400
4. `_diff(current, incoming)` 计算 diff
5. 若未传 `confirm=true` → 返回 `{ok: false, needs_confirm: true, diffs, diff_count}`，前端二次确认
6. 传 `confirm=true` → 备份当前文件 + 写盘 + reload
7. 写盘失败从备份恢复（try/except 保护）
8. 返回 `{ok: true, diffs, diff_count, backup, imported_at, restart_required: True, restart_note}`

### 7.7 导出脱敏

位置：`api_config.py` `export_config()` 函数（第 444-477 行）

### 7.9 字段级回滚

## 9. 常见问题 FAQ

### Q1：版本号是怎么算的？
**A**：前端 VersionManager 显示的系统版本号来自 `/api/about` 的 `__version__` 字段（由 `_build_info.py` 在构建时写入），随发布递增，无上限。v1.0 文档误记为 `/api/config/version` 的备份数计数——后者会因 `BACKUP_KEEP=10` 上限卡在 v10，已弃用。

### Q2：备份会占用很多磁盘空间吗？
**A**：不会。`BACKUP_KEEP=10` 保留最近 10 个备份，超出的旧备份自动清理。单个配置文件通常几 KB，10 个备份总共也就几十 KB。

### Q3：一键回滚和指定恢复有什么区别？
**A**：
- **一键回滚**（`/api/config/rollback`）：自动取最新备份，不需要传 filename，回滚前会自动备份当前配置作为安全网。
- **指定恢复**（`/api/config/restore-backup?filename=xxx`）：从指定备份恢复，需传 filename（带白名单校验防穿越），**不自动备份当前配置**（无安全网）。

### Q4：回滚后还能再回滚回去吗？
**A**：一键回滚可以（回滚前会自动备份当前配置作为安全网）。指定恢复**不行**（不自动备份当前配置，恢复后无法回到恢复前的状态）。

### Q5：导入配置会覆盖现有配置吗？
**A**：会，但有保护流程：校验 schema → 预览 diff → Modal 确认 → 写盘。导入前会自动备份当前配置，写盘失败从备份恢复。未传 `confirm=true` 时返回 `needs_confirm`，前端必须二次确认。导入成功后返回 `restart_required: True`。

### Q6：导出的配置包含敏感信息吗？
**A**：导出时 `_sanitize_dict` 递归脱敏，10 个敏感凭证字段（serverchan_send_key/pushplus_token/bark_server/bark_key/telegram_bot_token/telegram_chat_id/wecom_webhook/dingtalk_webhook/dingtalk_secret/webhook_url）仅保留末 4 位（`****xxxx`）。但 UA/keyword 等工作参数不脱敏。

### Q7：分享配置会泄露我的 API Key 吗？
**A**：**存在部分泄露风险**。前端分享时调用 `/api/config/export` 获取已脱敏配置（10 项凭证保留末 4 位），再用前端 SENSITIVE_KEYS 4 项二次脱敏（替换为 `***`）。剩余 6 个凭证字段（telegram_*/wecom_*/dingtalk_*/webhook_url）以 `****xxxx` 形式出现在分享文本中，仍可能泄露末 4 位。`notifier.channels` 和 `browser.user_data_dir` 完全未脱敏。如需更严格脱敏，应改用后端 `/api/config/share` 接口（12 项脱敏）。

### Q8：filename 参数为什么要白名单校验？
**A**：防止目录穿越攻击。如果不校验，攻击者传 `../../../etc/passwd` 可能读取任意文件。`_resolve_backup` 校验 filename 只含字母数字 + `-` `_` `.`，且必须以 `config.yaml.bak.` 开头。

### Q9：写盘失败会怎样？
**A**：
- **save_config / import_config**：自动从刚生成的备份恢复。`try/except` 捕获写盘异常，从 `new_bak` 读取内容写回 `CONFIG_FILE`，保证配置文件不损坏。返回 500 错误提示"写入失败，已回滚"。
- **rollback_config / restore_backup**：**未实现写盘失败保护**，写盘失败会抛未捕获异常，配置文件可能损坏。这是已知缺陷。

### Q10：字段级回滚怎么用？
**A**：在配置编辑页面（如评估规则），每个数值字段右侧有回滚按钮（仅当值与原始值不同时显示）。点击调用 `revertField(path)`，将 config 中指定 path 恢复为 original 中的值。path 支持点分（如 `eval.pass_score`）。若已保存，需通过"配置版本"页面整体回滚。

### Q11：为什么 `/api/config/version` 和 `/api/config/share` 是僵尸接口？
**A**：
- **`/api/config/version`**：后端实现完整（返回备份数计数），但前端 VersionManager 已改用 `/api/about` 取系统版本号（`__version__`），不再调用此接口。原因：备份数受 `BACKUP_KEEP=10` 限制会卡在 v10，无法反映系统真实版本。
- **`/api/config/share`**：后端实现完整（12 项脱敏），但前端 VersionManager 改用 `/api/config/export` + 前端 4 项脱敏，不再调用此接口。原因：前端希望复用导出接口的 JSON 格式，且前端脱敏逻辑更简单。
- 两个接口保留用于兼容旧客户端，但前端代码已不引用。

### Q12：回滚 / 恢复后需要重启吗？
**A**：**需要**。回滚 / 恢复后配置已写入文件并 `reload_config()` 重置单例，但运行中的调度器/worker 仍持有旧配置引用。需重启服务才完全生效。但 `rollback_config` 和 `restore_backup` **未返回 `restart_required` 字段**，前端无法提示用户。对比 `save_config` / `import_config` 返回 `restart_required: True` + `restart_note`。

### Q13：导出 JSON 文件名格式是什么？
**A**：`xianyu_hunter_config_YYYYMMDD_HHMMSS.json`（如 `xianyu_hunter_config_20260705_100000.json`）。秒级精度，避免同秒多次导出文件名冲突。

### Q14：导入配置的 diff 是怎么计算的？
**A**：`_diff(current, incoming)` 递归比较两个 dict，生成 `{path, op, old, new}` 列表。`op` 由 av/bv 的 truthy 判定：均非空=modify、只剩 bv=add、只剩 av=remove。None 转空串便于前端渲染，非 None 用 JSON 序列化保留类型信息。
