## 2. 功能概述

**一句话说明**：系统总览仪表盘，集中展示任务/订单运行状态、业务 KPI 米其林星级、评估漏斗与转化指标、今日异常列表、价格分布直方图与 AI 分析、SSE 实时事件流，以及系统状态与可视化配置入口。

**核心价值**：
- 让运营人员一屏掌握整体运行状况，无需切换多个页面；
- 通过米其林星级 KPI 直观反映系统健康度；
- 通过 SSE 实时事件流和今日异常列表，第一时间发现并定位问题；
- 通过评估漏斗与价格直方图，量化业务转化与市场价格分布；
- 通过 AI 价格分析，结合分位数与时间对比基线给出策略建议。

## 3. 用户场景

### 场景一：日常巡检
运营人员每日登录后第一眼查看仪表盘，关注 KPI 卡片的星级是否为绿色（≥3 星），并扫读 AlertRadar 折叠卡片标题处的告警徽标，确认今日失败订单/超时待支付/低分评估是否为零，再查看 EventStreamSection 的连接状态是否为"已连接"。

### 场景二：异常定位
当 AlertRadar 展开后看到"抢单失败"或"待支付超时"列表中有红色条目时，运营人员点击条目跳转 `/orders?ref=<id>` 进入订单详情；"评估异常 score<0.5" 列表则展示评估低分事件，便于人工复核评估策略。

### 场景三：业务复盘
运营人员通过 EvalFunnelCard 顶部的 Segmented 切换 7/30/90 天范围，查看漏斗各阶段数量、占采集/上一阶段比例，以及命中率、误报率、抢单成功率、端到端率 4 个关键指标，分析业务转化瓶颈。

### 场景四：价格策略
运营人员在 PriceHistogramCard 顶部选择特定任务，观察直方图柱状分布、P25/P50/P75 分位数标线、7 日/30 日/今日均价基线、任务定价范围标线，并点击"AI 智能分析"按钮让 LLM 基于这些统计数据生成价格策略建议。

### 场景五：新用户引导
无任务的新用户首次进入仪表盘时，顶部显示"欢迎使用闲鱼猎人！"引导 Banner，提供"创建任务"和"查看引导"两个快捷动作，避免新用户面对空仪表盘不知所措。

## 4. 页面布局与交互

### 4.1 组件结构

仪表盘主页面 `frontend/src/pages/Dashboard/index.tsx`（注意目录首字母大写）由 7 个子组件 + 1 个可视化配置入口卡片组合而成：

```
DashboardPage
├── Alert (引导 Banner)              # 无任务时显示，提供创建任务/查看引导入口
├── Alert (调度器警告)               # 调度器未运行时显示警告
├── StatCardsSection                  # 顶部 4 张统计卡片 + Sparkline 小图
├── KpiSection                        # 业务 KPI 米其林星级卡片（近 30 天）
├── EvalFunnelCard                    # 评估漏斗图 + 4 个关键转化指标
├── AlertRadar                        # 今日异常列表（折叠式，3 列）
├── EventStreamSection                # 事件流（左 15/24） + 系统状态（右 9/24）
├── PriceHistogramCard                # 价格直方图 + 任务筛选 + AI 智能分析
├── Card (可视化配置入口)             # 11 个快捷配置/管理入口卡片网格
└── TrendModal                        # 趋势弹窗（按需触发，当前未绑定触发器）
```

### 5.2 SSE 事件格式

SSE 端点共推送 5 类事件，全部使用 `text/event-stream` 媒体类型：

```
# 1. hello：连接建立后立即推送，含补拉统计
event: hello
data: {"ts":"2026-07-05T10:23:11+00:00","latest_id":12345,"replayed":3,"replay_requested":true}

# 2. app_event：业务事件（id 字段启用断线回放）
id: 12345
event: app_event
data: {"type":"buy.succeeded","task_id":"t_001","item_id":"i_998","level":"info","message":"抢单成功","created_at":"2026-07-05T10:23:11+00:00"}

# 3. ping：3 秒心跳
event: ping
data: {"ts":"2026-07-05T10:23:14+00:00"}

# 4. warn：回放失败告警
event: warn
data: {"msg":"replay_failed","error":"..."}

# 5. error：连接超限或生成器异常
event: error
data: {"error":"SSE connections limit (10) reached"}
```

**SSE 连接限制**：服务端全局并发上限 10 个连接（`_MAX_SSE_CONNECTIONS`），通过 `asyncio.Lock` 保护的计数器 `_sse_connection_count` 实现。超限时直接推送 `error` 帧并关闭连接，防止多标签页或异常客户端耗尽服务端资源。

## 6. 数据结构

### 6.1 events 表（EventRow）

仪表盘的实时事件流和异常统计均来自 `events` 表。

| 字段         | 类型     | 说明                                          |
| ------------ | -------- | --------------------------------------------- |
| id           | INTEGER  | 主键，自增；SSE 帧 `id:` 字段对应此列         |
| type         | TEXT     | 事件类型（点分格式，如 `buy.succeeded`，可为空） |
| task_id      | TEXT     | 关联任务 ID（可为空，有索引）                 |
| item_id      | TEXT     | 关联商品 ID（可为空，有索引）                 |
| stage        | TEXT     | 阶段（search/eval/buy/notify 等，NOT NULL）   |
| level        | TEXT     | 级别（info/warning/error，NOT NULL）          |
| message      | TEXT     | 事件描述（可为空）                            |
| payload      | TEXT     | 事件负载（JSON 字符串，可为空）               |
| created_at   | DATETIME | 创建时间（默认 `_utcnow()`，有索引）          |
| request_id   | TEXT     | 全局流水号（可为空，有索引）                  |

**索引**：
- 单列索引：`type`、`task_id`、`item_id`、`created_at`、`request_id`
- 联合索引：`ix_events_task_created` (task_id, created_at) —— Dashboard 按任务+时间范围查事件的核心索引

### 6.2 KPI 阈值配置与 hint 文案

米其林星级采用 5 档阈值，覆盖 4 项核心 KPI（阈值定义于 `frontend/src/pages/Dashboard/utils.ts` 的 `STAR_THRESHOLDS`）：

| KPI 指标（id）       | title        | unit | 1 星     | 2 星     | 3 星     | 4 星     | 5 星     | hint 业务文案                      | 反向指标 |
| -------------------- | ------------ | ---- | -------- | -------- | -------- | -------- | -------- | ---------------------------------- | -------- |
| `eval_pass_rate`     | 评估通过率   | %    | [0,50)   | [50,70)  | [70,85)  | [85,95)  | [95,+∞)  | 低风险（可抢）评估 / 总评估        | 否       |
| `order_success_rate` | 抢单成功率   | %    | [0,40)   | [40,60)  | [60,75)  | [75,85)  | [85,+∞)  | 已支付订单 / 总订单                | 否       |
| `items_discovered`   | 发现商品数   | 件   | [0,200)  | [200,500)| [500,800)| [800,1500)| [1500,+∞)| 采集到的去重商品总数（来自闲鱼搜索）| 否       |
| `notify_failure_rate`| 推送失败率   | %    | (20,100] | (10,20]  | (5,10]   | (2,5]    | [0,2]    | 失败通知事件 / 总通知事件（越低越好）| 是       |

> 注：`notify_failure_rate` 为负向指标，数值越小星级越高；阈值数组在源码中按 `[50,20,10,5,2]` 递减存储，逻辑使用 `v <= th[i]` 判定。

**星级计算逻辑**（`kpiStar` 函数）：
- 正向指标：从 5 个阈值由低到高遍历，`v >= th[i]` 则得 `5-i` 星；
- 反向指标：从 5 个阈值由高到低遍历，`v <= th[i]` 则得 `5-i` 星；
- 数值非有限或阈值缺失时返回 0 星。

### 6.3 评估漏斗 5 阶段

```
discovered → evaluated → eval_pass → order_triggered → order_succeeded
(采集商品)   (已评估)    (评估通过)  (抢单触发)        (抢单成功)
```

- **discovered**：`task_links` 表 `link_type='item'` 的去重 `link_key` 数（按 `created_at` 时间窗过滤）
- **evaluated**：`evaluations` 表总行数（按 `created_at` 时间窗过滤）
- **eval_pass**：`evaluations` 表 `risk_level='low'` 行数
- **order_triggered**：`orders` 表总行数（按 `created_at` 时间窗过滤）
- **order_succeeded**：`orders` 表 `status in ('paid','confirmed','succeeded')` 行数 ⚠️ **已知问题：与 KPI 口径不一致，见 §6.4**

每阶段 `pct_of_first` = 当前/首阶段；`pct_of_prev` = 当前/上一阶段（首阶段为 100.0）。

### 6.4 4 个关键转化指标

| 指标                  | 计算公式                              | 业务含义                                 |
| --------------------- | ------------------------------------- | ---------------------------------------- |
| hit_rate              | eval_pass / evaluated                 | 评估通过率，反映评估策略宽松度           |
| false_positive_rate   | (order_triggered - order_succeeded) / order_triggered | 误报率，越低越好，反映评估+抢单策略准确性 |
| conversion_rate       | order_succeeded / order_triggered     | 抢单成功率，受库存/网络/风控影响         |
| overall_rate          | order_succeeded / discovered          | 端到端转化率，综合反映采集→评估→抢单能力 |

> ⚠️ **已知问题：KPI「抢单成功率」与漏斗「抢单成功率」口径不一致**
> - KPI `order_success_rate`（`business_kpi.py`）：分子 = `OrderRow.status == 'succeeded'`，分母 = `OrderRow` 全部行数
> - 漏斗 `conversion_rate`（`stats_eval_funnel.py`）：分子 = `OrderRow.status in ('paid','confirmed','succeeded')`，分母 = `OrderRow` 全部行数
> - 原因：`business_kpi.py` 注释明确说"原查询 `status in ('paid','confirmed')` 永远命中 0 行，因为生产代码抢单成功写入 `'pending_pay'`（已拍下待支付），人工接管确认支付后写入 `'succeeded'`。`'paid'`/`'confirmed'` 这两个值在整个代码库中从未被写入 orders 表"。但 `stats_eval_funnel.py` 仍保留三状态查询，未同步修复。
> - 影响：同一时间窗下，漏斗的 `conversion_rate` 数值会 ≥ KPI 的 `order_success_rate`。
> - 修复建议：将 `stats_eval_funnel.py` 的 `order_succeeded` 阶段也改为仅查 `status == 'succeeded'`，与 KPI 口径对齐。

### 6.5 今日异常 3 维度

| 维度              | 数据来源                                           | 阈值/规则                                  |
| ----------------- | -------------------------------------------------- | ------------------------------------------ |
| failed_orders     | `orders` 表 `status='failed'` 且 `created_at` 今日 | 列表展示前 20 条，含 id/title/amount       |
| timeout_pending   | `orders` 表 `status in (pending,submitting,paying)` 且 `created_at` < now-5min | 列表展示前 20 条，含 age_sec（创建距今秒数）|
| low_evaluations   | `events` 表 `type='eval.scored'` 且 `payload.score` < 0.5 | 列表展示前 20 条，含 message/type/score     |

> 注：后端查询每维度 limit=20，前端 AlertRadar 卡片渲染时 `slice(0, 5)` 仅显示前 5 条；`counts` 字段为精确总数。

## 7. 业务逻辑

### 7.1 SSE 断线回放机制

```
[Client]                              [Server]
   │ ── 建立 SSE 连接（无 last_event_id）─→ │
   │                                       │ (should_replay=false)
   │ ←── 推送 hello 帧 ─────────────────── │ (latest_id=N, replayed=0)
   │ ←── 推送 app_event id=N ───────────── │
   │                                       │
   │ (localStorage["xh.sse.lastEventId"]=N) │
   │                                       │
   │ ── 连接断开 ────────────────────────→ │
   │                                       │
   │ ── 重连 + ?last_event_id=N ─────────→ │
   │                                       │ (should_replay=true)
   │                                       │ (从 events 表查 id > N 的行)
   │ ←── 推送 app_event id=N+1 ─────────── │
   │ ←── 推送 app_event id=N+2 ─────────── │
   │ ←── 推送 hello 帧 ─────────────────── │ (replayed=2)
   │ ←── 推送 ping（每 3s）─────────────── │
```

**关键实现**（`frontend/src/pages/Dashboard/index.tsx`）：
1. 每收到一条 `app_event`，将 `event.lastEventId` 写入 `localStorage["xh.sse.lastEventId"]`（key 提取为模块级常量 `SSE_LAST_EVENT_ID_KEY`）；
2. `EventSource` `onerror` 触发时 `es.close()` 并 3 秒后重连（固定间隔，非指数退避）；
3. 重连 URL 附加 `?last_event_id=<N>`，服务端 `sse_stream.py` 同时支持 query 参数 `last_event_id` 与 header `Last-Event-ID`（query 优先）；
4. 服务端从 `events` 表查 `id > effective_last_id` 的行按升序回放，单次回放上限 1000 条；
5. 回放完成后推送 `hello` 帧告知客户端补拉数量 `replayed`；
6. 页面不可见（`document.visibilityState !== 'visible'`）时不建立 SSE 连接，恢复可见时自动重连。

### 7.2 轮询与 SSE 协同策略

- **KPI 轮询**：独立 5 分钟 `kpiTimer`，仅调用 `/api/stats/business-kpi?range_days=30`；
- **概览轮询**：60 秒 `refreshTimer`，调用 `loadOverview()` + `loadSparklines()`：
  - `loadOverview()` 并行调用 `statsApi.overview()` + `statsApi.businessKpi(30)` + `statsApi.recentEvents(15)` + `priceApi.histogram({bins:20, task_id})` + `taskApi.list({limit:100})`；
  - `loadSparklines()` 并行调用 `statsApi.trend({metric:'events',range_hours:24})` + `statsApi.trend({metric:'orders',range_hours:24})`；
- **SSE 实时性**：3 秒 ping 心跳保活，业务事件 `app_event` 实时推送，前端 prepend 到事件列表前 100 条；
- **可见性控制**：SSE 仅在页面可见时建立连接；轮询 timer 不受可见性影响（浏览器会自动节流后台 tab 的 setInterval）。

> ⚠️ **已知问题：60 秒轮询与 5 分钟 KPI timer 存在重复调用**
> - 60 秒 `refreshTimer` 内的 `loadOverview()` 已经调用了 `statsApi.businessKpi(30)`；
> - 5 分钟 `kpiTimer` 又独立调用一次 `statsApi.businessKpi(30)`；
> - 即每 5 分钟会有两次 `/api/stats/business-kpi` 请求（60 秒一次 + 5 分钟一次）；
> - 影响：服务器多承受一次 KPI 聚合查询（涉及 4 个 KPI 子查询），但不影响数据正确性；
> - 修复建议：从 `loadOverview()` 中移除 `statsApi.businessKpi(30)` 调用，统一由 5 分钟 `kpiTimer` 负责 KPI 刷新。

### 7.3 价格直方图分桶逻辑

后端 `price_histogram.py` 支持两种分桶模式：

**固定刻度模式**（`bins=0`，默认）：
- 使用预定义刻度 `[0, 50, 100, 200, 500, 1000, 2000, 5000, 10000, 20000]`，最后一桶为 `[20000, +∞)`；
- 优点：不同次请求桶边界一致，便于横向对比；
- `mode` 字段返回 `"fixed"`。

**自动分桶模式**（`bins=20`，前端默认调用）：
- 用 P5/P95 裁剪极端值确定 `[lo, hi]` 范围；
- 融合任务定价范围 `min_price/max_price`，确保分桶覆盖定价区间（`lo = min(P5, task_min_price)`，`hi = max(P95, task_max_price)`）；
- 20 个等宽桶，首桶吸收所有低于 `b_lo` 的极端低价，尾桶吸收所有高于 `b_hi` 的极端高价，保证计数不丢失；
- `mode` 字段返回 `"auto"`，前端据此判断是否显示分位数标线。

**时间对比基线修复**（P-09-30）：
- 修复前 `ts_rows` 为全表查询，导致选定任务时 `yesterday/last7d/last30d` 基线混入其它任务价格，时间对比指标完全失真；
- 修复后 `ts_rows` 与 `prices` 同源——按 `task_id` 过滤，保证时间对比基线仅来自当前任务样本。

### 7.4 AI 价格分析流程

`POST /api/prices/analyze?task_id=<id>` 的处理流程：
1. 校验 `settings.openai_api_key`，未配置则返回 `{analysis: "未配置 AI 服务密钥...", source: "error"}`；
2. 调用 `check_budget()` 校验 AI 调用预算，超限则返回 `{analysis: "AI 调用受限：...", source: "error"}`；
3. 复用 `prices_histogram(bins=20, task_id)` 获取统计快照；
4. 若 `summary.count == 0`，返回 `{analysis: "当前无商品数据，无法生成分析。", source: "empty"}`；
5. 组装 prompt（含商品数/价格范围/均价/中位数/P25/P75/7日均价/今日均价/较7日变化/分档列表）；
6. 调用 LLM `chat/completions`（`temperature=0.3, max_tokens=800, timeout=30s`），通过 `httpx.Client` 同步请求；
7. 通过 `record_usage("price_analyze", model, resp)` 记录用量；
8. 返回 `{analysis: <LLM 内容>, source: "ai", scope_label: <scope.label>}`；
9. 异常分支：超时返回 `"AI 分析超时，请稍后重试."`；网络错误返回 `"AI 服务网络错误: ..."`；非 200 返回 `"AI 服务返回错误 (status)，请检查 API 配置."`；解析失败返回 `"AI 返回格式异常，请重试."`。

前端超时设为 60 秒（`priceApi.analyze` 的 axios timeout），覆盖 LLM 30 秒超时 + 网络余量。

### 7.5 KPI 米其林星级渲染规则

`KpiSection` 组件对每张 KPI 卡片：
1. 调用 `kpiStar(k)` 计算 1-5 星；
2. 满星（5 星）卡片左侧添加金色（`token.colorWarning`）3px 边框，数值也用金色；
3. 涨跌箭头使用 `ArrowUpOutlined`/`ArrowDownOutlined`/`MinusOutlined`；
4. 反向指标 `notify_failure_rate`（`k.id === 'notify_failure_rate'`）的涨跌方向取反：上涨=红，下降=绿；
5. 涨跌 Tag 文案由 `deltaText(k)` 生成，格式为 `+x.x%` / `-x.x%` / `持平`；
6. 卡片底部展示 `k.hint` 业务说明文案；
7. 卡片右上角显示"基于 {sample_size} 条 · {range_days} 天"（取自 `kpiCards[0]`，所有 KPI 共享同时间窗）；
8. `kpiCards.length === 0` 时整块不渲染（避免空容器占用布局）。

**EvalFunnelCard 误报率红色高亮规则**：
- `false_positive_rate > 30` 时，`Statistic` 的 `valueStyle.color` 设为 `token.colorError`（红色）；
- 否则使用 `token.colorText`（默认色）；
- 其余 3 个指标（命中率/抢单成功率/端到端率）使用固定语义色（info/success/primary），不随数值变化。

### 7.6 业务 KPI 4 项计算逻辑

`business_kpi.py` 计算 4 项 KPI（按 `range_days` 时间窗，与上一周期对比 `delta_pct`）：

| KPI id               | 分子                                     | 分母                                   | delta_pct 计算             |
| -------------------- | ---------------------------------------- | -------------------------------------- | -------------------------- |
| `items_discovered`   | `task_links` 表 `link_type='item'` 去重 `link_key` 数（全表，无时间窗）| —（无分母，绝对值） | 与上一周期 `EvaluationRow` 去重 items 数对比 |
| `eval_pass_rate`     | `EvaluationRow` 且 `risk_level='low'` 行数（时间窗内） | `EvaluationRow` 总行数（时间窗内） | 当前通过率 vs 上一周期通过率 |
| `order_success_rate` | `OrderRow` 且 `status='succeeded'` 行数（时间窗内）⚠️ 已修复 | `OrderRow` 总行数（时间窗内） | 当前成功率 vs 上一周期成功率 |
| `notify_failure_rate`| `EventRow` 且 `stage like '%notify%'` 且 `level='err'` 行数（时间窗内）⚠️ 已修复 | `EventRow` 且 `stage like '%notify%'` 总行数（时间窗内） | 当前失败率 vs 上一周期失败率 |

**修复记录**：
- `order_success_rate`：原查询 `status in ('paid','confirmed')` 永远命中 0 行（这两个状态值在生产代码中从未被写入 `orders` 表，抢单成功写入 `'pending_pay'`，人工确认后写入 `'succeeded'`），已修复为仅查 `status='succeeded'`，与 `stats_overview.py` 口径一致。
- `notify_failure_rate`：原分母用 `EventRow` 全量事件数，与 hint 文案"总通知事件"不符，已修复为 `stage like '%notify%'` 事件总数，保证分子分母口径一致。
- `items_discovered`：当前值从 `task_links` 表统计（无 `created_at` 时间窗），上一周期值用 `EvaluationRow` 兜底（因为 `task_links` 表无历史快照），存在口径差异，但仅影响 `delta_pct` 计算。

## 9. 常见问题 FAQ

### Q1：仪表盘的数据多久刷新一次？
**A**：KPI 米其林卡片每 5 分钟轮询一次；StatCards、Sparkline、系统状态随概览每 60 秒轮询一次；EvalFunnel / AlertRadar / PriceHistogram 仅在初始加载或用户操作（切换范围/任务/展开）时拉取，不轮询；实时事件流通过 SSE 长连接实时推送，3 秒 ping 心跳保活。注意：60 秒轮询内已包含一次 KPI 调用，5 分钟独立 KPI timer 会再调用一次（已知冗余，详见 §7.2）。

### Q2：KPI 卡片上的星星是怎么计算的？
**A**：每项 KPI 有 5 档阈值，定义在 `frontend/src/pages/Dashboard/utils.ts` 的 `STAR_THRESHOLDS`。例如 `eval_pass_rate`：[0,50) 为 1 星，[50,70) 为 2 星，[70,85) 为 3 星，[85,95) 为 4 星，[95,+∞) 为 5 星。`notify_failure_rate` 是负向指标，使用 `v <= th[i]` 判定，[0,2] 为 5 星，(2,5] 为 4 星，依此类推。计算函数为 `kpiStar(k)`。满星（5 星）卡片左侧添加金色 3px 边框，数值也用金色。

### Q3：最近事件列表为什么有时候是空的？⚠️ 已知问题
**A**：这是前后端契约不一致导致的 bug。后端 `/api/events/recent` 返回 `{"items": rows, "count": len(rows)}`（字段名 `items`），但前端 `stats.ts` 类型声明为 `{ events: RecentEvent[] }`，`index.tsx` 中 `setEvents(ev.events || [])` 读取 `events` 字段。由于后端返回 `items` 而非 `events`，前端始终得到 `undefined`，fallback 到空数组。**影响**：仪表盘初始加载时事件流为空，只有 SSE 推送的新事件才会显示。**修复建议**：统一为 `events` 字段——后端 `stats_overview.py` 第123行将 `{"items": rows, "count": len(rows)}` 改为 `{"events": rows, "count": len(rows)}`，或前端 `stats.ts` 改为读取 `items`。

### Q4：SSE 连接失败会怎样？
**A**：`EventSource` `onerror` 触发时 `es.close()`，3 秒后（固定间隔，非指数退避）自动重连。若页面不可见则不重连，待 `visibilitychange` 事件触发可见时再重连。服务端有 10 个连接的全局并发上限（`_MAX_SSE_CONNECTIONS`），超限会推送 `error` 帧（`{"error":"SSE connections limit (10) reached"}`）并关闭连接。注意：当前实现未做"SSE 失败 N 次降级为轮询"的兜底，仅依赖 3 秒重连。

### Q5：评估漏斗的「抢单成功率」和 KPI 的「抢单成功率」为什么数值不一样？⚠️ 已知问题
**A**：两者分子口径不一致。
- **KPI `order_success_rate`**（`business_kpi.py`）：分子 = `OrderRow.status == 'succeeded'`（仅已支付订单）
- **漏斗 `conversion_rate`**（`stats_eval_funnel.py`）：分子 = `OrderRow.status in ('paid','confirmed','succeeded')`（含 paid/confirmed/succeeded 三种状态）
- 原因：`business_kpi.py` 已修复为仅查 `succeeded`（注释明确说 `paid`/`confirmed` 在生产代码中从未被写入），但 `stats_eval_funnel.py` 未同步修复，仍保留三状态查询。
- 影响：同一时间窗下，漏斗的 `conversion_rate` 数值会 ≥ KPI 的 `order_success_rate`。
- 修复建议：将 `stats_eval_funnel.py` 的 `order_succeeded` 阶段也改为仅查 `status == 'succeeded'`。

### Q6：AlertRadar 上的告警项代表什么？
**A**：AlertRadar 已由旧版的雷达图改为折叠式 3 列列表卡片：① 抢单失败订单（`orders.status='failed'`）；② 待支付超时（`status in (pending,submitting,paying)` 且创建超过 5 分钟）；③ 评估异常 score<0.5（`events.type='eval.scored'` 且 `payload.score<0.5`）。每列展示前 5 条详情（后端查询 limit=20，前端 slice 5），标题处 Badge 显示总告警数（失败数 > 0 时红色，否则黄色）。点击失败/超时订单条目跳转 `/orders?ref=<id>`。标题点击可折叠/展开，展开时自动拉取最新数据。

### Q7：价格直方图可以筛选特定任务吗？
**A**：可以。`/api/prices/histogram` 接口接受可选的 `task_id` 参数，未传或传 `all` 则汇总所有任务。同时支持 `bins` 参数：`0`（默认）= 固定刻度分桶，`20` = 自动分桶（前端默认调用 `bins=20`）。选定任务时还会额外返回任务定价范围 `task_price_range`，前端据此在直方图上绘制绿色实线定价上下限标线。`bins=20` 自动分桶会融合任务定价范围 + P5/P95 裁剪极端值确定分桶边界，确保分桶覆盖定价区间且不受单个异常高价影响。

### Q8：页面切到后台还会刷新吗？
**A**：轮询 timer 不主动暂停（依赖浏览器对后台 tab 的自动节流）；SSE 连接在页面不可见时不建立新连接，已建立的连接保持但不再触发重连逻辑，恢复可见时自动重连。SSE 重连与可见性通过 `document.addEventListener('visibilitychange', ...)` 监听。

### Q9：TrendModal 支持哪些时间范围？
**A**：前端 TrendModal 仅暴露 7 天（168 小时）、30 天（720 小时）、90 天（2160 小时）三个按钮，但后端 `/api/stats/trend` 实际支持 5 个 `range_hours` 取值：24/72/168/720/2160，不在白名单内的值会回退到 24。`bucket_count` 映射 `{24:24, 72:24, 168:14, 720:30, 2160:90}`（即 24h 分 24 桶、72h 分 24 桶、7 天分 14 桶、30 天分 30 桶、90 天分 90 桶）。TrendModal 内显示最低/最高/均值/当前 4 个汇总值。eval_score 指标会显示中位数参考线，success_rate 指标会显示 50% 告警线。注意：当前 TrendModal 在主页面未绑定触发器（`setTrendOpen` 未被调用），属于预留组件。

### Q10：仪表盘上的统计卡片可以点击吗？
**A**：可以。4 张统计卡片分别为：运行中任务（点击跳转 `/tasks`）、待支付订单、成功抢单、抢单失败（后 3 张均跳转 `/orders`）。每张卡片下方内嵌 Sparkline 小图——任务卡显示 24 小时事件密度趋势（来自 `statsApi.trend({metric:'events',range_hours:24})`），3 张订单卡都显示 24 小时订单量趋势（来自 `statsApi.trend({metric:'orders',range_hours:24})`），通过颜色区分（primary/warning/success/error）。

### Q11：AI 价格分析按钮是如何工作的？
**A**：点击 PriceHistogramCard 中的"AI 智能分析"按钮，前端调用 `POST /api/prices/analyze?task_id=<id>`（60s 超时）。后端先校验 AI Key 与预算，再复用 histogram 接口获取统计快照（`bins=20`），组装 prompt 调用 LLM 生成 4 个维度的分析（价格分布特征/性价比区间/趋势判断/策略建议），并通过 `record_usage` 记录用量。返回的 `analysis` 文本以 Alert 形式展示在直方图下方，含"清除"按钮。`source` 字段标识结果来源：`ai`（成功）/`empty`（无数据）/`error`（失败）。前端根据 `analysis` 文案是否含"未配置"/"失败"/"错误"决定 Alert 类型（warning 或 success）。

### Q12：仪表盘顶部的引导 Banner 何时出现？
**A**：当 `overview.tasks.total === 0` 且 `overview.tasks.running === 0` 时显示"欢迎使用闲鱼猎人！"引导 Banner，提供"创建任务"（→`/tasks/new`）和"查看引导"（→`/onboarding`）两个按钮。此外当 `overview.scheduler_running === false` 时显示"调度器未运行"黄色警告 Banner，提示运营人员启动调度器。

### Q13：SSE 服务端有连接数限制吗？
**A**：有。服务端全局并发上限 10 个连接（`_MAX_SSE_CONNECTIONS = 10`），通过 `asyncio.Lock` 保护的计数器 `_sse_connection_count` 实现。超限时直接推送 `event: error` 帧（`{"error":"SSE connections limit (10) reached"}`）并关闭连接，防止多标签页或异常客户端耗尽服务端资源。连接关闭时（finally 块）计数器递减，且使用 `max(0, ...)` 防止异常情况下负数。

### Q14：仪表盘下方的"可视化配置入口"有哪些卡片？
**A**：共 11 个 `QuickEntryIcon` 卡片，每张卡片含图标 + 标题 + 副标题，点击跳转对应配置/管理页面：

### Q15：业务 KPI 4 项指标的具体含义和计算方式是什么？
**A**：4 项 KPI 来自 `/api/stats/business-kpi?range_days=30`，按时间窗与上一周期对比计算 `delta_pct`：
- **发现商品数**（`items_discovered`）：`task_links` 表 `link_type='item'` 去重 `link_key` 数，hint="采集到的去重商品总数（来自闲鱼搜索）"
- **评估通过率**（`eval_pass_rate`）：`risk_level='low'` 行数 / `EvaluationRow` 总行数，hint="低风险（可抢）评估 / 总评估"
- **抢单成功率**（`order_success_rate`）：`status='succeeded'` 行数 / `OrderRow` 总行数，hint="已支付订单 / 总订单"
- **推送失败率**（`notify_failure_rate`）：`stage like '%notify%'` 且 `level='err'` 行数 / `stage like '%notify%'` 总行数，hint="失败通知事件 / 总通知事件（越低越好）"，是反向指标
