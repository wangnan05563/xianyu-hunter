## 2. 功能概述

**一句话说明**：系统总览仪表盘，集中展示任务/订单运行状态、业务 KPI 米其林星级、评估漏斗与转化指标、今日异常列表、价格分布直方图与 AI 分析、SSE 实时事件流，以及系统状态与可视化配置入口。

**核心价值**：
- 让运营人员一屏掌握整体运行状况，无需切换多个页面；
- 通过米其林星级 KPI 直观反映系统健康度；
- 通过 SSE 实时事件流和今日异常列表，第一时间发现并定位问题；
- 通过评估漏斗与价格直方图，量化业务转化与市场价格分布；
- 通过 AI 价格分析，结合分位数与时间对比基线给出策略建议。

## 3. 用户场景

### 场景一：日常巡检
运营人员每日登录后第一眼查看仪表盘，关注 KPI 卡片的星级是否为绿色（≥3 星），并扫读 AlertRadar 折叠卡片标题处的告警徽标，确认今日失败订单/超时待支付/低分评估是否为零，再查看 EventStreamSection 的连接状态是否为"已连接"。

### 场景二：异常定位
当 AlertRadar 展开后看到"抢单失败"或"待支付超时"列表中有红色条目时，运营人员点击条目跳转 `/orders?ref=<id>` 进入订单详情；"评估异常 score<0.5" 列表则展示评估低分事件，便于人工复核评估策略。

### 场景三：业务复盘
运营人员通过 EvalFunnelCard 顶部的 Segmented 切换 7/30/90 天范围，查看漏斗各阶段数量、占采集/上一阶段比例，以及命中率、误报率、抢单成功率、端到端率 4 个关键指标，分析业务转化瓶颈。

### 场景四：价格策略
运营人员在 PriceHistogramCard 顶部选择特定任务，观察直方图柱状分布、P25/P50/P75 分位数标线、7 日/30 日/今日均价基线、任务定价范围标线，并点击"AI 智能分析"按钮让 LLM 基于这些统计数据生成价格策略建议。

### 场景五：新用户引导
无任务的新用户首次进入仪表盘时，顶部显示"欢迎使用闲鱼猎人！"引导 Banner，提供"创建任务"和"查看引导"两个快捷动作，避免新用户面对空仪表盘不知所措。

### 5.2 SSE 事件格式

SSE 端点共推送 5 类事件，全部使用 `text/event-stream` 媒体类型：

```
# 1. hello：连接建立后立即推送，含补拉统计
event: hello
data: {"ts":"2026-07-05T10:23:11+00:00","latest_id":12345,"replayed":3,"replay_requested":true}

# 2. app_event：业务事件（id 字段启用断线回放）
id: 12345
event: app_event
data: {"type":"buy.succeeded","task_id":"t_001","item_id":"i_998","level":"info","message":"抢单成功","created_at":"2026-07-05T10:23:11+00:00"}

# 3. ping：3 秒心跳
event: ping
data: {"ts":"2026-07-05T10:23:14+00:00"}

# 4. warn：回放失败告警
event: warn
data: {"msg":"replay_failed","error":"..."}

# 5. error：连接超限或生成器异常
event: error
data: {"error":"SSE connections limit (10) reached"}
```

**SSE 连接限制**：服务端全局并发上限 10 个连接（`_MAX_SSE_CONNECTIONS`），超限直接返回 error 帧并关闭连接。

## 6. 数据结构

### 6.1 events 表（EventRow）

仪表盘的实时事件流和异常统计均来自 `events` 表。

| 字段         | 类型     | 说明                                          |
| ------------ | -------- | --------------------------------------------- |
| id           | INTEGER  | 主键，自增；SSE 帧 `id:` 字段对应此列         |
| type         | TEXT     | 事件类型（点分格式，如 `buy.succeeded`，可为空） |
| task_id      | TEXT     | 关联任务 ID（可为空，有索引）                 |
| item_id      | TEXT     | 关联商品 ID（可为空，有索引）                 |
| stage        | TEXT     | 阶段（search/eval/buy/notify 等，NOT NULL）   |
| level        | TEXT     | 级别（info/warning/error，NOT NULL）          |
| message      | TEXT     | 事件描述（可为空）                            |
| payload      | TEXT     | 事件负载（JSON 字符串，可为空）               |
| created_at   | DATETIME | 创建时间（默认 `_utcnow()`，有索引）          |
| request_id   | TEXT     | 全局流水号（可为空，有索引）                  |

**索引**：
- 单列索引：`type`、`task_id`、`item_id`、`created_at`、`request_id`
- 联合索引：`ix_events_task_created` (task_id, created_at) —— Dashboard 按任务+时间范围查事件的核心索引

### 6.2 KPI 阈值配置

米其林星级采用 5 档阈值，覆盖 4 项核心 KPI（定义于 `frontend/src/pages/dashboard/utils.ts` 的 `STAR_THRESHOLDS`）：

| KPI 指标             | 单位  | 1 星     | 2 星     | 3 星     | 4 星     | 5 星     |
| -------------------- | ----- | -------- | -------- | -------- | -------- | -------- |
| eval_pass_rate       | %     | [0,50)   | [50,70)  | [70,85)  | [85,95)  | [95,+∞)  |
| order_success_rate   | %     | [0,40)   | [40,60)  | [60,75)  | [75,85)  | [85,+∞)  |
| items_discovered     | count | [0,200)  | [200,500)| [500,800)| [800,1500)| [1500,+∞)|
| notify_failure_rate  | %     | (20,100] | (10,20]  | (5,10]   | (2,5]    | [0,2]    |

> 注：`notify_failure_rate` 为负向指标，数值越小星级越高；阈值数组在源码中按 `[50,20,10,5,2]` 递减存储，逻辑使用 `v <= th[i]` 判定。

**星级计算逻辑**（`kpiStar` 函数）：
- 正向指标：从 5 个阈值由低到高遍历，`v >= th[i]` 则得 `5-i` 星；
- 反向指标：从 5 个阈值由高到低遍历，`v <= th[i]` 则得 `5-i` 星；
- 数值非有限或阈值缺失时返回 0 星。

### 6.3 评估漏斗 5 阶段

```
discovered → evaluated → eval_pass → order_triggered → order_succeeded
(采集商品)   (已评估)    (评估通过)  (抢单触发)        (抢单成功)
```

- **discovered**：`task_links` 表 `link_type='item'` 的去重 `link_key` 数（按时间窗过滤）
- **evaluated**：`evaluations` 表总行数
- **eval_pass**：`evaluations` 表 `risk_level='low'` 行数
- **order_triggered**：`orders` 表总行数
- **order_succeeded**：`orders` 表 `status in (paid, confirmed, succeeded)` 行数

每阶段 `pct_of_first` = 当前/首阶段；`pct_of_prev` = 当前/上一阶段。

### 6.4 4 个关键转化指标

| 指标                  | 计算公式                              | 业务含义                                 |
| --------------------- | ------------------------------------- | ---------------------------------------- |
| hit_rate              | eval_pass / evaluated                 | 评估通过率，反映评估策略宽松度           |
| false_positive_rate   | (order_triggered - order_succeeded) / order_triggered | 误报率，越低越好，反映评估+抢单策略准确性 |
| conversion_rate       | order_succeeded / order_triggered     | 抢单成功率，受库存/网络/风控影响         |
| overall_rate          | order_succeeded / discovered          | 端到端转化率，综合反映采集→评估→抢单能力 |

### 6.5 今日异常 3 维度

| 维度              | 数据来源                                           | 阈值/规则                                  |
| ----------------- | -------------------------------------------------- | ------------------------------------------ |
| failed_orders     | `orders` 表 `status='failed'` 且 `created_at` 今日 | 列表展示前 5 条，含 id/title/amount        |
| timeout_pending   | `orders` 表 `status in (pending,submitting,paying)` 且 `created_at` < now-5min | 列表展示前 5 条，含 age_sec（创建距今秒数）|
| low_evaluations   | `events` 表 `type='eval.scored'` 且 `payload.score` < 0.5 | 列表展示前 5 条，含 message/type/score     |

## 7. 业务逻辑

### 7.1 SSE 断线回放机制

```
[Client]                              [Server]
   │ ── 建立 SSE 连接（无 last_event_id）─→ │
   │                                       │ (should_replay=false)
   │ ←── 推送 hello 帧 ─────────────────── │ (latest_id=N, replayed=0)
   │ ←── 推送 app_event id=N ───────────── │
   │                                       │
   │ (localStorage["xh.sse.lastEventId"]=N) │
   │                                       │
   │ ── 连接断开 ────────────────────────→ │
   │                                       │
   │ ── 重连 + ?last_event_id=N ─────────→ │
   │                                       │ (should_replay=true)
   │                                       │ (从 events 表查 id > N 的行)
   │ ←── 推送 app_event id=N+1 ─────────── │
   │ ←── 推送 app_event id=N+2 ─────────── │
   │ ←── 推送 hello 帧 ─────────────────── │ (replayed=2)
   │ ←── 推送 ping（每 3s）─────────────── │
```

**关键实现**（`frontend/src/pages/dashboard/index.tsx`）：
1. 每收到一条 `app_event`，将 `event.lastEventId` 写入 `localStorage["xh.sse.lastEventId"]`；
2. `EventSource` `onerror` 触发时 `es.close()` 并 3 秒后重连（固定间隔，非指数退避）；
3. 重连 URL 附加 `?last_event_id=<N>`，服务端 `sse_stream.py` 同时支持 query 参数 `last_event_id` 与 header `Last-Event-ID`；
4. 服务端从 `events` 表查 `id > effective_last_id` 的行按升序回放，单次回放上限 1000 条；
5. 回放完成后推送 `hello` 帧告知客户端补拉数量 `replayed`；
6. 页面不可见（`document.visibilityState !== 'visible'`）时不建立 SSE 连接，恢复可见时自动重连。

### 7.2 轮询与 SSE 协同策略

- **KPI 轮询**：独立 5 分钟 timer，仅调用 `/api/stats/business-kpi?range_days=30`；
- **概览轮询**：60 秒 timer，并行调用 `statsApi.overview()` + `businessKpi(30)` + `recentEvents(15)` + `priceApi.histogram({bins:20, task_id})` + `taskApi.list({limit:100})` + `statsApi.trend({metric:'events',range_hours:24})` + `statsApi.trend({metric:'orders',range_hours:24})`；
- **SSE 实时性**：3 秒 ping 心跳保活，业务事件 `app_event` 实时推送，前端 prepend 到事件列表前 100 条；
- **可见性控制**：SSE 仅在页面可见时建立连接；轮询 timer 不受可见性影响（浏览器会自动节流后台 tab 的 setInterval）。

### 7.3 价格直方图分桶逻辑

后端 `price_histogram.py` 支持两种分桶模式：

**固定刻度模式**（`bins=0`，默认）：
- 使用预定义刻度 `[0, 50, 100, 200, 500, 1000, 2000, 5000, 10000, 20000]`，最后一桶为 `[20000, +∞)`；
- 优点：不同次请求桶边界一致，便于横向对比。

**自动分桶模式**（`bins=20`，前端默认调用）：
- 用 P5/P95 裁剪极端值确定 `[lo, hi]` 范围；
- 融合任务定价范围 `min_price/max_price`，确保分桶覆盖定价区间；
- 20 个等宽桶，首桶吸收所有低于 `b_lo` 的极端低价，尾桶吸收所有高于 `b_hi` 的极端高价，保证计数不丢失；
- `mode` 字段返回 `"auto"`，前端据此判断是否显示分位数标线。

### 7.4 AI 价格分析流程

`POST /api/prices/analyze?task_id=<id>` 的处理流程：
1. 校验 `settings.openai_api_key`，未配置则返回 `{analysis: "未配置 AI 服务密钥...", source: "error"}`；
2. 调用 `check_budget()` 校验 AI 调用预算，超限则返回 `{analysis: "AI 调用受限：...", source: "error"}`；
3. 复用 `prices_histogram(bins=20, task_id)` 获取统计快照；
4. 组装 prompt（含商品数/价格范围/均价/中位数/P25/P75/7日均价/今日均价/较7日变化/分档列表）；
5. 调用 LLM `chat/completions`（temperature=0.3, max_tokens=800, timeout=30s）；
6. 通过 `record_usage("price_analyze", model, resp)` 记录用量；
7. 返回 `{analysis: <LLM 内容>, source: "ai", scope_label: <scope.label>}`。

前端超时设为 60 秒（`priceApi.analyze` 的 axios timeout），覆盖 LLM 30 秒超时 + 网络余量。

### 7.5 KPI 米其林星级渲染规则

`KpiSection` 组件对每张 KPI 卡片：
1. 调用 `kpiStar(k)` 计算 1-5 星；
2. 满星（5 星）卡片左侧添加金色（`token.colorWarning`）3px 边框，数值也用金色；
3. 涨跌箭头使用 `ArrowUpOutlined`/`ArrowDownOutlined`/`MinusOutlined`；
4. 反向指标 `notify_failure_rate` 的涨跌方向取反：上涨=红，下降=绿；
5. 涨跌 Tag 文案为 `+x.x%` / `-x.x%` / `持平`；
6. 卡片底部展示 `k.hint` 业务说明文案。

## 9. 常见问题 FAQ

### Q1：仪表盘的数据多久刷新一次？
**A**：KPI 米其林卡片每 5 分钟轮询一次；StatCards、Sparkline、系统状态随概览每 60 秒轮询一次；EvalFunnel / AlertRadar / PriceHistogram 仅在初始加载或用户操作（切换范围/任务/展开）时拉取，不轮询；实时事件流通过 SSE 长连接实时推送，3 秒 ping 心跳保活。

### Q2：KPI 卡片上的星星是怎么计算的？
**A**：每项 KPI 有 5 档阈值，定义在 `frontend/src/pages/dashboard/utils.ts` 的 `STAR_THRESHOLDS`。例如 `eval_pass_rate`：[0,50) 为 1 星，[50,70) 为 2 星，[70,85) 为 3 星，[85,95) 为 4 星，[95,+∞) 为 5 星。`notify_failure_rate` 是负向指标，使用 `v <= th[i]` 判定，[0,2] 为 5 星，(2,5] 为 4 星，依此类推。计算函数为 `kpiStar(k)`。

### Q3：实时事件流断了会丢数据吗？
**A**：不会。客户端通过 `localStorage["xh.sse.lastEventId"]` 持久化最后收到的事件 id，重连时附加到 URL 参数 `?last_event_id=<N>`，服务端从 `events` 表查 `id > N` 的行按升序回放，单次回放上限 1000 条。回放完成后推送 `hello` 帧告知客户端补拉数量 `replayed`，前端据此显示"已连接（补拉 N 条）"。

### Q4：SSE 连接失败会怎样？
**A**：`EventSource` `onerror` 触发时 `es.close()`，3 秒后（固定间隔，非指数退避）自动重连。若页面不可见则不重连，待 `visibilitychange` 事件触发可见时再重连。服务端有 10 个连接的全局并发上限，超限会推送 `error` 帧并关闭连接。注意：与旧版文档描述不同，当前实现未做"SSE 失败 3 次降级为 30s 轮询"的兜底，仅依赖 3 秒重连。

### Q5：评估漏斗的 5 个阶段分别是什么？
**A**：discovered（采集商品，来自 task_links 表 link_type='item'）→ evaluated（已评估，evaluations 表总数）→ eval_pass（评估通过，risk_level='low'）→ order_triggered（抢单触发，orders 表总数）→ order_succeeded（抢单成功，status in paid/confirmed/succeeded）。每阶段的 `pct_of_first` = 当前/首阶段，`pct_of_prev` = 当前/上一阶段。下方还展示 4 个关键转化指标：命中率、误报率、抢单成功率、端到端率。

### Q6：AlertRadar 上的告警项代表什么？
**A**：AlertRadar 已由旧版的雷达图改为折叠式 3 列列表卡片：① 抢单失败订单（`orders.status='failed'`）；② 待支付超时（`status in (pending,submitting,paying)` 且创建超过 5 分钟）；③ 评估异常 score<0.5（`events.type='eval.scored'` 且 `payload.score<0.5`）。每列展示前 5 条详情，标题处 Badge 显示总告警数。点击失败/超时订单条目跳转 `/orders?ref=<id>`。

### Q7：价格直方图可以筛选特定任务吗？
**A**：可以。`/api/prices/histogram` 接口接受可选的 `task_id` 参数，未传或传 `all` 则汇总所有任务。同时支持 `bins` 参数：`0`（默认）= 固定刻度分桶，`20` = 自动分桶（前端默认调用 `bins=20`）。选定任务时还会额外返回任务定价范围 `task_price_range`，前端据此在直方图上绘制绿色实线定价上下限标线。

### Q8：页面切到后台还会刷新吗？
**A**：轮询 timer 不主动暂停（依赖浏览器对后台 tab 的自动节流）；SSE 连接在页面不可见时不建立新连接，已建立的连接保持但不再触发重连逻辑，恢复可见时自动重连。SSE 重连与可见性通过 `document.addEventListener('visibilitychange', ...)` 监听。

### Q9：TrendModal 支持哪些时间范围？
**A**：支持 7 天（168 小时）、30 天（720 小时）、90 天（2160 小时）三个时间范围，对应后端 `/api/stats/trend` 的 `range_hours` 参数。TrendModal 内显示最低/最高/均值/当前 4 个汇总值。eval_score 指标会显示中位数参考线，success_rate 指标会显示 50% 告警线。注意：当前 TrendModal 在主页面未绑定触发器（`setTrendOpen` 未被调用），属于预留组件。

### Q10：仪表盘上的统计卡片可以点击吗？
**A**：可以。4 张统计卡片分别为：运行中任务（点击跳转 `/tasks`）、待支付订单、成功抢单、抢单失败（后 3 张均跳转 `/orders`）。每张卡片下方内嵌 Sparkline 小图，分别展示 24 小时事件密度趋势（任务卡）和 24 小时订单量趋势（订单卡）。

### Q11：AI 价格分析按钮是如何工作的？
**A**：点击 PriceHistogramCard 中的"AI 智能分析"按钮，前端调用 `POST /api/prices/analyze?task_id=<id>`（60s 超时）。后端先校验 AI Key 与预算，再复用 histogram 接口获取统计快照，组装 prompt 调用 LLM 生成 4 个维度的分析（价格分布特征/性价比区间/趋势判断/策略建议），并通过 `record_usage` 记录用量。返回的 `analysis` 文本以 Alert 形式展示在直方图下方，含"清除"按钮。

### Q12：仪表盘顶部的引导 Banner 何时出现？
**A**：当 `overview.tasks.total === 0` 且 `overview.tasks.running === 0` 时显示"欢迎使用闲鱼猎人！"引导 Banner，提供"创建任务"（→`/tasks/new`）和"查看引导"（→`/onboarding`）两个按钮。此外当 `overview.scheduler_running === false` 时显示"调度器未运行"黄色警告 Banner，提示运营人员启动调度器。

### Q13：SSE 服务端有连接数限制吗？
**A**：有。服务端全局并发上限 10 个连接（`_MAX_SSE_CONNECTIONS`），通过 `asyncio.Lock` 保护的计数器实现。超限时直接推送 `event: error` 帧（`{"error":"SSE connections limit (10) reached"}`）并关闭连接，防止多标签页或异常客户端耗尽服务端资源。
