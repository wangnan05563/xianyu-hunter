# 整体结论（健康度评估 · Top 3 · 短期路线）

> 数据来源：`REPORT.md`（实测口径）、`OPTIMIZATIONS.md`（20 条建议）、`results/*`（原始样本聚合）。
> 本文不引入任何新数字，只做判断与排序。

## 1. 健康度评估

**一句话结论：作为「单人本地工具」健康；作为「多人共用的控制台服务」亚健康 —— 瓶颈不在正确性，而在容量形态。**

| 维度 | 评级 | 判据（实测） |
|---|---|---|
| 单用户响应体验 | **良好（局部差）** | 基线三组 P50 均为 10~11 ms，绝大多数接口 P95 < 200 ms；但有 **7 类接口在零并发下就已是几百毫秒到 1.1 s**（`anticrawl/strategy` 1 094.7 ms、`vector-admin/snapshots` 451/233.8 ms、`auth/me` 152.6 ms、`config/raw` 132.4 ms、`prices/category-comparison`、`maintenance/status` 单发 1.6 s），属固有成本，与并发无关 |
| 并发容量 | **偏弱** | 首屏/统计聚合读拐点 **4 并发**（TPS 封顶 81.2 后回落）、混合控制台读 **16 并发**、幂等写 **8 并发**。96 并发时轻组 P95 3 893.2 ms、P99 4 296.9 ms，已进入「界面不可用」区间 |
| 吞吐 | **偏低且与并发解耦** | 读侧上限约 **80 rps**（单进程 GIL + 同步 handler 挤同一线程池）；写侧上限约 **66 tps**，16 并发反而 −22% |
| 正确性 | **良好** | 全程 0 个 5xx（除环境性的 `links/live`）、**0 次 `database is locked`**、无高并发专属的竞态错误（未见 UNIQUE 冲突 / 锁边界缺陷）。写路径在容量范围内是正确的 |
| 长期稳定性 | **延迟/吞吐通过；内存未定论** | TPS 六窗恒为 59.6、末窗 P95 最优（398.6 ms，较首窗 −27%）—— **无退化**。句柄在长跑窗口内恒定（627~631），**无连接泄漏证据**。但存活样本口径下 RSS 在长跑 30 min 内 `347 → 378 MB`（拟合 +75.9 MB/h）、负载停止后不回落，30 min 尺度**无法与慢泄漏区分**（首版曾把关停后的 0 值采样计入，得出「末段回落到 350 MB」的假象，已改正，见 `REPORT.md` §6.8） |
| 资源水位 | **有裕量但结构受限** | CPU 均值 56.1%、峰值 269%（多核折算）—— 单进程模型下多核未被用满，属**软件形态限制而非机器饱和**；RSS 峰值 414.5 / 私有内存峰值 617.7 MB；WAL checkpoint 持续回收，库文件未见无界增长 |
| 可观测性 | **中** | 依赖不可用时用 503 表态（30 min 内 795 次全部来自同一接口，占本轮 5xx 的 100%），真实故障信号会被这类噪声淹没 |
| 数据增长抗性 | **偏弱（最大远期风险）** | 当前 items 774 / events·evaluations 数万，已经是百毫秒级；被过滤的 5 个列**无索引**，`/api/evaluations` 每请求全量拉 `eval.*`（limit=50000）+ Python 侧过滤分页。这类实现随采集累积**线性恶化**，且恶化不可通过加并发缓解 |

> 关于「亚健康」的限定：本结论的绝对吞吐受客户端能力压低（`python_replay` 96 并发已近上限、负载机与服务同机），因此 P95/P99 是**上界**、拐点绝对位置可能右移；但「拐点相对次序」「饱和形态（吞吐封顶 + 排队增长）」和「零并发固有慢接口」三项与机器无关，构成可信判断。详见 `REPORT.md` §6。

## 2. Top 3 优先处理问题

### ① 缓存击穿 + 同步线程池共享：高并发尾延迟爆炸与超时（影响面最大）

- **症状**：单用户 avg 50 ms 的接口，12 并发长跑变 200.5 ms；轻组 48→96 并发 P95 从 2 064.0 劣化到 3 893.2 ms，真实缺陷率单调升至 **3.17%**；`maintenance/status` 曾出现 P95 **60 033 ms**（客户端 60 s 超时），而它单发只要 1.6 s。
- **根因链**：测时版本的 `web/cache.py`（`_make_sync_wrapper` / `_make_async_wrapper`）冷/过期 miss **无 single-flight** → N 个并发各自重算同一聚合（同族 `stats` 接口齐处 165~200 ms 窄带，正是「大家都在等同一份重算」的指纹）；重算占住 anyio 默认 40 token 线程池 → 连 8.4 ms 的 `notifier/quiet-hours` 在 96 并发被拖到 **2 096.8 ms**（完成样本从 55 掉到 7）；`services/cache_scan.py:52,66` 的进程级 `RLock` 再把 `/cache-scan` 与 `/maintenance/status` 串行化。
- **对应措施**：B1（单飞，约 20 行）✅ **已于 2026-10-31 落地，本文数字全部是修复前基线** + B5（SWR 的「后台刷新」其实在请求线程里跑，见 REPORT 表 B9）+ B2（慢接口纳入 TTL）+ D1（慢同步接口独立线程池）+ D2（解锁）。B1 是**全场最大杠杆**。

### ② 请求路径上的重复文件/Socket 探测：与并发无关的固有成本（最易修、确定性最高）

- **症状**：7 类接口在**零并发**下就是几百毫秒到 1.1 s。
- **根因**：`modules/login_strategy.py:144` 每次请求对 CDP 端口做 `socket.create_connection(timeout=1.0)`（端口未开即吃满 1 s），随后 `:150-184` 打开 Chromium Cookie SQLite 做全表 `LIKE '%goofish%'`；`api_config.py:45-48` 每次 `_load_yaml()` 重读并 `safe_load` 整个配置（绕过了 `infra/yaml_config.py:784-789` 的单例缓存）；`api_vector_admin.py:103-104` 对同一目录调 `_dir_size` **两次**；`auth_query.py` 里 `_resolve_current_user_id` 被调用两次（`:336`、`:406`）+ 每次都重读 cookies 文件、写库、查库。鉴权本身（带 300 s 缓存的 `verify_session`）**不是**瓶颈 —— 这个区分很重要，否则会优化错方向。
- **对应措施**：C4 + C3 + C1 + C2 + A4。这几条**改动小、收益可预测**（按实测地板参照 7~9 ms 估算），属"第 1 周就该走完"的那一档。

### ③ 无索引 + 全量重载/全内存导出：随数据增长线性恶化（远期最贵）

- **症状**：`/api/evaluations` avg 195.9 ms / P99 858 ms，`prices/category-comparison` 长跑 avg 580.2 ms，导出类 P99 1 827.7 ms，私有内存峰值 617.7 MB。
- **根因**：`infra/repo_events.py:337` 每次 `limit=50000` 全量拉 `eval.*` 后在 Python 侧过滤分页，`:357-364` 另发一次 COUNT；`db_models.py` 核对后确认 `items.price`、`evaluations.risk_level`、`price_history.user_id`、`orders.type`、`task_links.updated_at` **无索引**；`repo_error_logs.py:63-65` 用 `%LIKE%` 前后通配（索引天然不可用）；`api_export.py:76-98` 虽已用 `StreamingResponse`，但先把整份 CSV 拼进 `io.StringIO` 再一次性 yield；`evaluations_list.py:69-80` 缓存 miss 时按 task_id 逐个跑 `_compute_sold_range`（N+1）。
- **对应措施**：A2（查询下推）+ A1（补索引）+ A5（前缀匹配/FTS5）+ D4（真流式）+ C5（批量化）。
- **为什么排第三而不是第一**：当前数据量下它不致命；但它是**唯一一类「不做就必然变坏」**的问题，且第 ① 项的收益会被它抵消 —— 缓存命中时快，每次击穿都要付全表代价。

### Top 3 之外的一条未定论风险（不是结论，是待验证项）

长跑窗口内 RSS 以 **+75.9 MB/h** 爬升、负载停止后不回落，而句柄同期恒定（627~631）。最可解释的来源是 `web/cache.py` 那份**无容量上限、无淘汰**的进程内缓存（`OPTIMIZATIONS` B4），但 30 min 尺度不足以把它与慢泄漏分开。判定路径很便宜：先落 B4（加 `max_entries` + LRU），再跑 4 h —— 斜率归零即确认为缓存，仍爬升则转 `tracemalloc`。这也是本次没有满足 ≥4 h 的直接代价。

## 3. 短期优化路线
| 阶段 | 动作 | 可验证的累计效果（复跑同一套 JMX 对比） |
|---|---|---|
| **第 1 周**（低风险高收益，不动架构） | ✅ B1 缓存单飞（已落地）→ B5 SWR 刷新真正放到后台 → B2 慢接口纳入 TTL → C1 `_dir_size` 合并 → C4 探测降本+缓存 → A4 计数降本 → E3 503 语义 | 混合场景 avg 200.5 → **≤90 ms**；长跑整体 P95 544.5 → **≤250 ms**；`maintenance/status` 过期后首次调用 1.6 s → **≈0**；消除 60 s 超时与 795 次 503 噪声（长跑缺陷率 0.74% → **0**） |
| **第 2–4 周**（结构性，仍单进程） | C2 `/auth/me` 去重 → A2 `eval.*` 下推 SQL → D1 慢接口独立线程池 → D2 打破 `cache_scan` RLock → C3 `_load_yaml` 走单例 → **B4 缓存容量上限 + ≥4 h 长跑复测** | 48/96 并发缺陷率 2.03%/3.17% → **<0.5%**；轻组 96 并发 P95 3 893.2 → **≤1 000 ms**；8.4 ms 级廉价接口在高并发不再被拖到 2 s；RSS `+75.9 MB/h` 的成因定论 |
| **季度内**（容量形态） | D3 写批量 UPSERT + `busy_timeout` 10 s→2 s → D4 真流式导出 → A1 补 5 索引 + A5 FTS → **E1 多 worker** | 读吞吐 80 → **≥150 rps**；写侧 16 并发不再从 66.4 回落到 51.9；内存峰值收敛；数据增长斜率变缓 |

**顺序上有两条硬约束，不可打乱：**

1. **E1（多 worker）必须排在 B1/B3 之后。** B1 已于 2026-10-31 落地，B3（预热扩展）还没有 —— 进程内 TTL 缓存会按 worker 分裂成 N 份，现在直接开多 worker 会把命中率打散、把「击穿」变成「N 倍击穿」，反而更慢。
2. **D3 里扩连接池不是解药。** 瓶颈是 SQLite WAL 单写者，`pool_size=20` 已满；继续扩池只会把「等待」变长而不是变短。正确做法是减少写次数（批量 UPSERT）并缩短 `busy_timeout` 让冲突早暴露。
